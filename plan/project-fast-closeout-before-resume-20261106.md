### 条件项怎么判定，避免又变成无限审阅

本轮源码核对显示：`AgentRunService` 的 `model_attempt_budget_factory` 依赖显式注入；正式 evaluation worker 构造该服务时未传入该工厂；Memory 提取 gateway 也没有注入预算；硬金额和自动摘要发布门仍关闭。所以上述预算故障**不天然是本次全部必修项**。

但“默认没有注入”不是完整可达性证明。接手进程只做一次有限检查：核对选定 API/worker 启动命令、创建服务的 composition、演示 AgentVersion/runtime 配置、研究 permit 和测试开关；确认没有测试/研究 adapter、budget factory 或 summary permit 被启用。记录结论即可，不另造大规模静态分析平台。

如果发现已启用，选择修复相应的已知错误路径，或从本次明确支持的产品范围移除尚未完成的实验装配；不能为隐藏一个正常产品路径中的漏洞而临时改开关、伪造正常结果。最终范围和边界应在文档中可见。

## 6. 工序 B：核心链路与启动复现

### B1. 主演示：治理执行与同 Run 恢复

优先复用现有 Incident Hero Demo，不新造应用：

1. 登录，进入隔离 workspace；确认 Owner/操作者与审批者身份按既有权限合同配置。
2. 选一个冻结发布版本，使用已配置可用的模型或明确标记的确定性测试 provider。
3. 执行只读调查，出现需要审批的写入提议；副作用仅发生在受控模拟系统，不能连接真实生产回滚目标。
4. 展示 WAITING_APPROVAL；刷新/重新附着，确认没有开新 Run。若演示“进程重启后恢复”，这次必须实际完成重启验证，不能把页面刷新冒充重启。
5. 独立审批者批准，恢复原 Run，查看实际动作执行状态及最终答复；保留 run_id/AgentVersion/时间和安全证据。
6. 再检查一次拒绝分支：拒绝审批后没有写入，最终答复不把拒绝说成成功。
7. 既有 UNKNOWN/crash 测试可作为面试追问证据；本轮不强制再录制所有故障窗口，不重放未知外部动作。

若该 Demo 的初始化障碍较大，缩为现有 Support 的同类治理链路，保留“只读→写提议→审批→恢复→证据”这一个主线；不要为了录视频扩展 Ops 工具或同时维护两个主 Demo。

### B2. 评测界面：展示管道能力

在最终候选上检查现有统计、逐题证据、筛选分页、失败/未知展示；使用一个已完成实验或小规模确定性受控实验。Viewer 不能看到原始 observation/敏感内容，至少实际检查一次权限边界。

历史实验可作为历史结果展示，记录它的执行版本/数据和测量边界；不能说是最新候选重新跑出的模型收益。没有必要为了简历再跑一次 64 trial 或开 HOLDOUT。

### B3. 启动复现

复用已有 Docker Compose/本地运行路线，最终只选一条被实际走通的推荐方式，不承诺所有操作系统都支持。

- 在新隔离目录/数据库/namespace 验证必要配置、依赖启动、显式 migration 和 checkpoint bootstrap，再启动 Web/API/worker；需要周期对账时包含 beat。
- 不读旧私密 local-env 来“碰巧启动”，不覆盖用户业务库和已有服务；现有合法模型配置仍由本地秘密提供。
- 确认 `/api/v1/health`、`/api/v1/ready` 和前端能用；启动步骤中的地址、代理、端口和执行目录一致。
- 用文档本身完成一次启动复核，记录具体环境、冷启动/模型权重初始化前置条件、启动和停止方法。只验证 Compose 语法不算服务已跑通。

**退出条件：** 当前候选能够启动并走完选定主线，操作者按文档能重复关键步骤；未出现需靠改数据库或跳权限“救场”的隐藏操作。

## 8. 工序 D：最终检查、交付与停止

开发中只做与本轮实际改动相关的检查，复用 R1 已有局部验收。最终可合并候选执行仓库要求的 CI/build/migration 检查；不在本地先全库、再为同一变化反复手动触发远端全库。

现有 workflow 可能自动触发 push/PR 两轮；本计划不虚假承诺只产生一个 workflow，也不为解决这个效率问题先开启 C01 大改。对失败只补与原因相关的修复与复验，不能用重复重跑掩盖真实错误。

冻结产品候选后，把最终 CI 链接/合并 SHA 放到 PR 回执或外部交付记录，不为“补记绿灯”反复修改产品提交和触发新一轮验证。相应授权齐备后完成推送/审阅/合并；需要现场演示的环境更新到交付版本，确认运行源码/构建一致。

### 收口判定：全部为“是”后停止

- [ ] 交付版本明确，R1 已纳入，预算/研究 Draft 没有混入。

- [ ] 评测结果与权限边界在当前版本可展示，历史模型结果未冒充新实验。
- [ ] 推荐启动路线实际走通，迁移/checkpoint 明确，秘密与数据不泄露。
- [ ] 必要最终检查通过；失败/跳过/未执行状态有真实说明。
- [ ] README、展示材料、能力—证据表和回执齐备。
- [ ] 剩余事项已经写明延期，不能再以 backlog 非空拒绝收口。

达到以上标准后，**停止其他功能施工，转入简历整理与面试准备**。只有影响已交付核心流程的真实回归才重新开修复；没有新问题就不再开启一轮全项目审阅。

## 9. 排期与卡点处理

建议以 **2–3 个工作日**作为范围受控时的排期目标，不是完成承诺：前半天冻结版本/判定条件项，约一天走通启动和主流程，余下时间整理材料、最终检查和交付。若出现核心阻断，修复和相应验收优先，不能为了赶时间把未通过写成通过。

仅允许三类事项阻塞收口：核心流程确实不可用；已启用路径存在已知安全/状态语义缺陷；启动步骤无法复现。后台研究、全局金额保证、人工校准、容量优化和公网部署的未完成不阻塞本次既定范围。

若卡在付费模型配置/调用授权：先用确定性受控 provider 验证工程主线并明确标记；历史真实 provider 证据可单独引用。只有获得明确模型/费用范围授权才做最小的真实调用验收，不以“收口需要”为由扩大成新模型研究。
