# MuSiQue 双跳问题的同源合并与补位

在 24 个独立问题上，默认切块有 6 题满足合并条件。补位后，完整显示两个官方支持段的问题仍为 15/24。额外来源均进入首发消息，但在这 6 题中没有增加完整的金标段。官方标注粒度是整段，不能据此判断丢失的字符是否为回答所必需。

## 冻结与配对

使用本地 MuSiQue v1.0 answerable TRAIN，每题保留原版 20 个竞争段，按段拆为独立 TXT。规范化 NFC 并去掉首尾空白，文件正文不加标题。选题要求两个不同的金标来源，且至少两个自然段各长于 1,200 字符；长度条件对全部段落计算。原样保留两跳的官方段落索引，分别检查两段的来源和全文。由此取得的 24 题代表含自然长段的题型，不代表训练集总体。

冻结时从本地历史研究结果目录中的 JSON/JSONL 提取 2,579 个看似 MuSiQue 题号的字符串，2,577 个能对应原版 TRAIN 或 DEV，另外两个是旧工具消息截断的 ID 前缀。在 1,365 道满足结构条件的题中，按冻结种子与题号的 SHA-256 排序，排除历史题号、组成跳 ID、规范化问题及完整支持段正文重复，入选题之间也做同样去重。去重依据是留存的本地实验材料，原始语料存放本身不计为做过该题。历史比较与题内去重均未根据本次排名、答案或触发情况选题。[种子、原版摘要、历史文件与逐题金标区间](manifest.json)

## 初始候选与进入消息的依据

默认档经过本地真实 HTTP 查询入口、生产入库与检索链、Qdrant、BGE-M3 稠密编码、BGE 分词稀疏编码、RRF 和 BGE 交叉编码器。处理每题的两臂使用同一快照。逐题核对 dense、sparse、fused 和 selection 四阶段的有序块 ID，两臂全部一致；候选臂的 20 块与融合池集合一致。固定每条最多六段，正文预算 16,000 估算 token。下面的默认档数据取自付费前拦截到的真实请求序列化消息，未评判读者模型输出。

压力档单独使用 320/80 字符窗口和步间重叠（默认档为 1,200/200），调用生产切块、同权重 BGE reranker、合并和正文预算函数。在 CPU 上对每题原版段落产生的**所有块**直接复排，再固定前 20。压力档没有运行 dense、sparse、RRF、HTTP 或供应商调用，其证据可见性按本地渲染文本计。两档之间同时改变了切块与候选生成路径，不能将跨档差异归因于某个单一变量。每一档的两臂独立地只改变同源合并和补位。

默认档这 48 个入口请求全部正好呈现 6 段。6 个自然合并段各带两个原块 ID，长度为 1,292–1,870 字符。超过 2,000 字符的回源能力由受控长引文的 API 和浏览器回归验证，这组自然段本身未触及原截断边界。

## 事后金标上界

对默认档 6 道已触发题保留实际的同源合并和其它四段，枚举原排名 7–20 中全部合法新来源块，每次只替换最后一个补位。若使用金标选择，完整支持段上界为 10/12（实际 9/12），两段完整题最多 4/6（实际 3/6）。只要求出现支持来源时，上界为 12/12（实际 10/12），双来源题最多 6/6（实际 4/6）。此外还有 3 题的候选已包含两个完整金标段，前六未呈现完整双跳，且没有合法合并补位机会；另外 2 道可触发题即使用最佳合法补位也无法拼全。这里的上界分别优化各指标，使用金标挑选，不是可部署答案选择规则。[逐题金标上界](posthoc.json)

python -m benchmarks.public_rag.experiments.musique_source_refill.freeze
python -m benchmarks.public_rag.experiments.musique_source_refill.pressure

python -m benchmarks.public_rag.experiments.musique_source_refill.score .scratch/composite-qa-preflight/fresh.jsonl primary
python -m benchmarks.public_rag.experiments.musique_source_refill.oracle
