# 客服未结工单核查 · DEV 2026-11-14

这项实验检查一项具体能力。客户要求“如果没有同主题未结工单才创建”时，助手能否先取得足够的查询证据，再决定是否提交审批，并准确回复数据库里实际发生的结果。六项查询任务包括现有 PENDING 单、排在第 24 位的同主题单、已关闭历史单、允许创建、审批拒绝和大量工单中的只读查询。另有两项直接建单对照，分别批准和拒绝，用来检查基础审批路径。

每个任务在每个变体下重复两次，按冻结顺序交替运行，共 32 个独立客服账户。baseline 在当前运行时重新发布了 11 月 5 日的候选提示词与当时只可读客户档案的工单工具配置。candidate 通过产品控制面绑定新目录中的两个工具，并加载客服应用模板。两者使用相同的阿里云北京模型、执行预算和审批策略。这个比较测量整套客服配置对指定任务的影响，无法单独估计提示词的贡献。

评分读取发送给求解模型的真实工具观察、数据库审批决策与执行状态、新增工单及用户要求的精确回执行。两次重复均通过才计为一组通过。合成审批人只允许前提已核实且参数与要求一致的提议进入批准流程，违规提议会计入失败。这与生产部署中的人工审批策略不同。[预登记协议](protocol.json)

在干净的本地测试数据库 `agenthub_support_dev_20261114` 上显式运行 Alembic 和 checkpoint 初始化后，将 `AGENTHUB_DATABASE_URL` 与 `AGENTHUB_TEST_DATABASE_URL` 指向该库。模型读取项目现有 `aliyun-rag` 路由。以下两步分别冻结材料和执行一次收费验证。

```powershell
.\.venv\Scripts\python.exe -m benchmarks.evaluation.experiments.customer_quality_20261114.runner freeze
.\.venv\Scripts\python.exe -m benchmarks.evaluation.experiments.customer_quality_20261114.runner run
```

本地原始材料位于 ignored `.scratch/customer-quality-20261114/study`。冻结清单绑定协议、评分器、研究代码、产品变更和两份已发布快照。正式调用复用历史研究的持久化物理调用账本实现，使用本研究独立的 6 元估算上限。每次派发前按完整供应商 token 容量预留费用，有完整 usage 后按预登记峰价结算。重定向、模型回退和自动重试都没有启用。

## 实测结果

| 预登记指标 | 旧客服配置 | 新客服配置 |
| --- | ---: | ---: |
| 两次都通过的任务组 | 2/8 | 7/8 |
| 通过的单次任务 | 4/16 | 15/16 |
| 需要查询的六组，两次均通过 | 0/6 | 5/6 |
| 直接建单的两组对照，两次均通过 | 2/2 | 2/2 |
| 已批准、已执行并落库的新增工单 | 2 | 5 |
| 已拒绝、未执行的审批 | 2 | 4 |
| 物理模型调用 | 33 | 40 |
| 按冻结峰价估算费用（元） | 0.103140 | 0.215800 |

所有 32 次运行得到了已知数据库终态。两份配置的 73 次真实调用都有完整 usage，按协议峰价估算共 0.318940 元。进程退出码为 0，没有截断回复或未结算调用。隔离数据库的 HOLDOUT 曝光事件数为 0。公开 JSON 给出冻结时间、两份已发布版本的 resolved spec hash、每次任务的分项断言和复核后的费用。原始请求和回复只在本地保存。[逐次结果](result.json)

新配置在两次重复中均找到了排在前 20 项之外的同主题未结单，并返回了实际工单号。唯一一次失败发生在存在同主题已结案记录的场景。模型已从工具确认没有同主题未结单，随后在文字中称已提议建单并正在等待审批，实际没有调用建单工具，数据库也没有相应审批或新增工单。该条的查询断言通过，审批、工单和回执断言失败。它没有声称工单已创建，因此没有触发此次只覆盖结构化创建回执的停止条件。这个结果仍然暴露了自由文本中误述“已提交”的风险。

旧配置在需要查询的六组中均无法检索未结工单；两项直接建单对照均通过。两组变体在这组刻意考察查询能力的样例上相差 62.5 个百分点。这个样本无法给出真实客服流量上的提升估计，也没有独立人工盲标。11 月 5 日的正式 DEV 为 baseline 13/16、candidate 14/16；它使用不同的变体、任务和自由文本评分办法，实测增益低于当时 15 个百分点的门槛。此次没有运行原 HOLDOUT，没有据此推广候选。[原评测记录](../../../../docs/reviews/T04-customer-quality-20261105.md)

## 建单提议的独立复核

针对上述“文字提议”失败，客服模板现在要求在授权条件满足后实际调用绑定的写工具发起提议，只按运行时的实际记录描述已提交或正在等待审批。另行冻结的三组新 DEV 使用自然中文回复，分别覆盖已结历史单后获批新建、审批拒绝、只读查询。前后版本实际发布快照中除了提示词之外的所有字段逐项相等。六个新账户分配给每个版本，两次重复分别通过才计该组通过。[复核协议](proposal-protocol.json)

| 指标 | 上一轮冻结的客服候选 | 修订后的客服模板 |
| --- | ---: | ---: |
| 两次均通过的组 | 2/3 | 3/3 |
| 通过的单次任务 | 5/6 | 6/6 |
| 实际获批并创建 | 1 | 2 |
| 实际拒绝且未执行 | 2 | 2 |
| 检查器识别到的无记录提交或待审批表述 | 0 | 0 |

旧提示词一次正确查到没有同主题未结单后，要求客户再次确认，既没有发起审批，也没有建单。新版在两次重复中均发起了实际审批并返回了新工单号。12 次原生运行全部达到已知终态，31 次真实调用全部有 usage，估算 0.156400 元。两次 DEV 合计 44 次原生运行、104 次模型调用，费用合计估算 0.475340 元。费用按冻结峰价计算，没有供应商发票核对。首次复核准备程序把发布接口摘要当作数据库记录，导致零派发准备失败。修正后读取持久化记录，复用了已经发布的版本，完成了两份快照的同条件校验。[复核逐次结果](proposal-result.json)

自然语言检查器只比对预登记的审批/执行事实和有限的措辞。复核自由文本时还看到，新版一次把“当前没有这个主题的未结单”解释为上一次工单确已结案。工具只返回了本次未结单结果，无法确认历史单本身。另一条只读回答把精确主题查询的完整性说成了整个账户列表完整。两处是本轮评分范围外的证据归因问题，保留原评分，不作通用语义正确率或生产验收结论。

下列命令使用第一阶段已发布的候选作为基准。实际复核发布的是后续修订版，复现已记录的历史比较须使用公开清单中的代码和提示词身份。

## 查询范围的后续修正

在两次收费实验结束后，`query_customer` 的工单结果增加了 `open_ticket_scope`。它给出这次读取的是全部主题还是某个精确主题、实际筛选的状态，以及是否包含历史状态。只有工单查询带该字段，客户档案查询继续返回原有字段。完整性标记只适用于这次查询的筛选范围。客服模板同时明确，空的未结记录无法证明历史工单曾经存在或已经结案。

在独立 PostgreSQL 数据库中，4 个 ToolRuntime 集成测试通过，核对了仅有已结历史单时的精确主题空结果、账户全部主题的完整列表、超出 20 条的列表、筛选后的第 21 张单、工作区隔离及旧工具版本仍拒绝新参数。另有 36 个应用模板和管理 API 合同单测通过。此项修正使用程序和真库验证，前面的两次模型实测结果对应各自冻结的版本。
