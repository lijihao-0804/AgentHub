## 1. 为什么 agent 评测不等于 LLM 评测

把“模型答得对不对”直接搬过来评 agent，会在五个地方失真：

| 差异 | 含义 | 后果 |
| --- | --- | --- |
| **评的是过程 + 终态** | 同一答案可能来自正确路径，也可能来自越权读取、绕过审批、反复试错 | 只看终态会把“危险地答对”判成成功 |
| **非确定性来源更多** | 采样温度、环境状态、用户模拟器、工具返回、网络 | 单次分数不可复现，必须重复 + 区间 |
| **有副作用** | 写库、发消息、退款、删文件 | 错误不可撤销，安全必须与功能同环境评 |
| **成本高** | 多轮 × 工具 × 重复 × judge | 不报成本的对比会诱导选最贵配置 |
| **可被环境内作弊** | agent 能去搜答案、读测试文件、滥用凭证 | 分数背后的行为可能完全不是你要的 |

HAL 的日志审查抓到了两类典型：agent 去 HuggingFace **搜索基准答案**而不是解题；订票任务里**滥用信用卡**（✅ [arXiv:2510.11977](https://arxiv.org/abs/2510.11977)）。这两件事都不会体现在准确率上。

## 2. 分类学：评什么 × 怎么评

目前最可引用的坐标来自 KDD 2025 综述（✅ [arXiv:2507.21504](https://arxiv.org/abs/2507.21504)）：

- **评什么（objectives）**：agent 行为、能力、可靠性、安全；
- **怎么评（process）**：交互模式、数据集与基准、指标计算方法、工具链。

它单独点出企业场景四个被忽视的维度：**基于角色的数据访问、可靠性保证、动态长程交互、合规**。ACL Findings 的另一篇综述独立收敛到同一组空白：**成本效率、安全鲁棒性、细粒度可扩展评测**（✅ [arXiv:2503.16416](https://arxiv.org/abs/2503.16416)）。

> 这两篇合起来说明：企业级 agent 平台的评测重点，不是“再做一个榜单”，而是**在权限、长程、合规约束下把可靠性测出来**。这正好是 AgentHub 的形态。

## 4. 指标：定义、方向与陷阱

| 指标 | 定义 | 方向 | 陷阱 |
| --- | --- | --- | --- |
| **success rate** | 成功 trial / 全部 trial | 越高越好 | 分母是否含失败/超时/空回答 |
| **%resolved** | 通过全部 F2P 与 P2P 测试的实例占比 | 越高越好 | 测试不完整会让错误解通过 |
| **pass@k** | k 次里至少成功一次 | 越高越好 | **乐观**，适合“可采样取最优”的代码场景 |
| **pass^k** | k 次全部成功 | 越高越好 | **悲观**，贴近生产“每次都得对”；只报 pass@k 会高估可部署性 |
| **progress rate** | 任务推进比例 | 越高越好 | 需要定义“进度”，主观性高 |
| **judge agreement** | 与人类标签一致率 | 越高越好 | 85% 一致率 = 15% 噪声，足以颠倒榜单中段 |
| **cost / task** | 总成本 / 任务数 | 越低越好 | 必须含失败尝试与 judge 成本 |
| **safety violation rate** | 违规 trial / 攻击 trial | 越低越好 | 必须分族报告，不能与能力分混算 |

### 4.1 `pass@k` 与 `pass^k` 的方向相反

- `pass@k` = 至少一次成功；`pass^k` = 全部 k 次成功。
- 单次成功率 0.8 时：`pass^3 = 0.512`、`pass^5 = 0.328`。
- τ-bench 的 README 直接展示了断崖：Pass^1 0.460 → Pass^4 0.225（✅）。

**结论**：客服、退款、审批这类“连续 k 次都不能错”的场景，`pass^k` 才是可承诺的数字；只报 Pass^1 等于隐藏方差。

### 4.2 基准本身会坏

ABC 清单（✅ [arXiv:2507.02825](https://arxiv.org/abs/2507.02825)）指出：SWE-bench Verified 测试用例不足、TAU-bench 把空回答计为成功，可致性能高/低估达 100%（相对量级）。BetterBench（✅ [arXiv:2411.12990](https://arxiv.org/abs/2411.12990)）审计 24 个基准后结论是：多数不报统计显著性、结果不易复现。

**工程含义**：引入任何外部基准前，先做“evaluator 有效性抽检”——用一个**已知错误解**跑一遍，evaluator 必须判负；否则你测的是 evaluator 的漏洞。

## 5. 污染与 holdout：agent 的三条独有泄漏路径

| 路径 | 机制 | 证据 |
| --- | --- | --- |
| **环境内泄漏** | agent 主动检索答案，而不只是“记住” | HAL 抓到 agent 去 HuggingFace 搜基准答案 ✅ |
| **测试即规格** | 判分逻辑公开，agent 可读测试反推期望 | SWE-bench 类基准的结构性风险 ◇ |
| **时间性漂移** | 真实站点/live server 改版，历史分数不可比 | WebVoyager / MCP-Universe ✅ |

缓解手段的强度排序（◇ 综合判断）：

1. **私有 holdout + 程序化任务生成**（最强，但难以对外证明）；
2. **答案 holdout 分集**（GAIA 300 题，中等）；
3. **审日志**（能发现分数看不见的作弊，强）；
4. **训练数据去污染 / 发布时间切分**（中等）；
5. **公开基准分数**（最弱，只能做参考）。

AgentHub 的规则 28（holdout 暴露是可审计的持久化事件）已经做到了公开基准社区普遍没做的一层；这部分是现有资产，不应推翻。

## 6. 2025–2026 的六条趋势

1. **从“问答”到“长程 + 有状态”**：判分对象从答案字符串转为世界终态。
2. **Computer-use 是主战场，工程重心是并行 VM**：WindowsAgentArena 的 20 分钟、HAL 的数百 VM 并行说明**评测吞吐是一等约束**。
3. **MCP 生态催生新一代工具基准**：考点从“调用给定函数”移到“在陌生、庞大、会漂移的工具空间里找到并组合工具”。
4. **成本与方差进入指标本体**：ScienceAgentBench 三元指标、HAL 的 $/rollout、`pass^k`。
5. **元评测兴起**：HAL 表明大量已发表分数受 harness 实现 bug 影响；跨论文比分数本身可疑。
6. **可靠性优先于峰值能力**：HAL 的 reasoning effort 反直觉结论 + τ-bench 的 Pass^4 断崖。

## 7. 选型决策树（面向 AgentHub）

```text
要回答什么问题？
├─ Q1 工具 schema 能不能被正确调用？
│   └─ BFCL 式：AST + 可执行性；用自有工具集重写；必含“不该调”子集
├─ Q2 端到端任务能不能做成？
│   ├─ 有确定性终态（DB/工单/文件）→ 状态断言（WebArena/OSWorld 范式）
│   └─ 开放交付物 → rubric + judge + 人工校准（GDPval 范式）
├─ Q3 长程、跨系统、含审批？
│   └─ 组织仿真 + 多检查点 + 进度率（TheAgentCompany/AgentBoard 范式）
├─ Q4 稳定性够不够上生产？
│   └─ 同任务重复 k 次 → pass^k（τ-bench）
├─ Q5 工具空间大、陌生、会漂移？
│   └─ MCP-Universe/MCP-Bench 范式；工具检索与调用分开计分
├─ Q6 安全边界在哪？
│   └─ AgentDojo（功能+攻击同环境）+ AgentHarm（拒绝率+能力保持）
└─ Q7 评测本身可信吗？
    └─ 三查：已知错误解必须判负；抽样审日志；成本与方差入表
```

**一句话**：2026 年选基准的关键分歧不在“哪个榜单权威”，而在**判分是确定性的还是 judge 的**、**任务是否有真实世界终态**。两者都弱的基准（真实网站 + LLM judge，如 WebVoyager），只能做探索，不能做验收。

## 8. 对 AgentHub 的五条直接启示

1. **先把终态断言做扎实，再谈 judge**。AgentHub 已有 support postcondition 与确定性 evaluator，这是正确起点；缺的是“每任务一个断言脚本”的通用化。
2. **`pass^k` 必须进指标**。现有 100 例数据集 + 3 次重复足以算 `pass^3`，这是最低成本的可靠性升级。
3. **轨迹是必需品，不是加分项**。MCP-Universe 的“企业产品不如 ReAct”与 HAL 的“搜答案”都说明：不看轨迹就无法解释分数。
4. **不要追公开榜单**。外部基准的 scaffold、工具集、模型版本都不同；正确用法是“借任务构造手法”，不是“借分数”。
5. **成本与安全要和能力同表**。只报成功率的评测，会系统性地奖励“更贵、更冒险”的配置。
