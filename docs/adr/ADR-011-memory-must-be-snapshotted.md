# ADR-011: 长期记忆必须被快照，而不是在每次执行时重新检索

- 状态：Accepted
- 日期：2026-09-22
- 相关：[ADR-007 AgentVersion 解析快照](ADR-007-agentversion-resolved-snapshot.md)、[ADR-010 评测数据集可复现](ADR-010-evaluation-dataset-reproducibility.md)、`docs/report/附录B-长期记忆与上下文管理.md`

## 背景

第 0 阶段把"一轮问答是一个驱逐单位"落实到了上下文预算里，第 1 阶段给每个 agent
加了一个显式的 `memory.thread_history_search` 开关，让模型可以在**当前这条线程**
里回头翻找被窗口挤掉的历史。

但这两件事都只解决了"同一条线程内"的遗忘。用户提出的原始问题是：

> 「不能检索一下开一个新对话」

也就是说，跨线程的、属于这个 agent 的稳定事实（用户偏好、项目约束、已经做出的
决定）必须活得比一条线程更久。这就是长期记忆（`memory.long_term_memory`）。

一旦引入长期记忆，一个新的危险立刻出现：**同一次运行，在不同时刻执行会得到不同
的上下文**。记忆表是可写的、会被后台任务追加、会被人工作废；而运行是可以在崩溃后
durable resume 的、是可以被评测重放的。如果 PREPARE 阶段每次都重新查一遍记忆表，
那么：

- 一次审批中断后恢复的运行，可能看到一条它开始时还不存在的记忆；
- 评测里"同一个版本跑两次"不再可比，A/B 实验失去意义；
- 事后排查"它为什么这么答"时，记忆表已经变了，现场不可复原。

这与本项目对知识库快照的处理是同一类问题，答案也应该是同一个。

## 决策

**长期记忆在一次运行的第一次 PREPARE 时被解析成一份快照，写入
`agent_runs.effective_memory_snapshot`；此后这次运行的任何一次 PREPARE 都只读这份
快照，不再查询记忆表。**

具体地：

1. 新表 `workspace_memories`，按 `(workspace_id, agent_id)` 归属。一条记忆是一段
   短文本，带来源（`thread_id` / `source_run_id`）、类别、状态、`content_hash`、
   `salience` 和可选的 `expires_at`。
2. PREPARE 时：
   - 若 `run.effective_memory_snapshot` 非空 → 直接按其中的 id 读取内容，**不做
     任何新的挑选**；
   - 否则按当前问题挑选至多 `MAX_INJECTED_MEMORIES` 条，写回快照，再注入。
3. 注入的形式是**一条** `MEMORY` 类别的消息，位置在两条 system 消息之后、线程历史
   之前。它是可投影、可丢弃的，永远不会挤掉当前问题。
4. 记忆内容一律按 `trust: UNTRUSTED` 处理，与工具输出同级。
5. 写入（抽取）永远不在热路径上：运行成功落库之后才入队，由 worker 另起一个任务
   做抽取；抽取失败绝不影响已经成功的运行。
6. 记忆不硬删除。重复的事实提升 `salience`；矛盾的事实做 soft-supersede；人工作废
   写 `INVALIDATED`。

## 为什么不是别的做法

**为什么不每次都查表？**
因为那样运行就不是可重放的了。本项目已经为模型档案、工具修订、知识快照都付出了
"冻结"的代价，长期记忆没有理由成为唯一一个可以在运行途中改变自己输入的东西。

**为什么记忆不是强制类别（mandatory）？**
因为记忆是**证据**，不是**指令**。一条三个月前的偏好不应该有能力把用户此刻的问题
挤出上下文窗口。把它放进可投影层，意味着预算紧张时它先被截断、再被丢弃，而当前问
题和 system prompt 永远在。

**为什么与检索证据共用 `max_retrieval_tokens` 预算？**
因为它们是同一种东西——注入到提示里的外部证据。给记忆单开一个预算键会改变
`DEFAULT_CONTEXT_BUDGET`，从而改变**所有**已发布 agent 的 spec hash，为一个绝大
多数 agent 没有打开的功能。记忆在这个共享预算里先分配（它以"条"为单位、总量有硬
上限），剩下的归检索证据。

**为什么不用 embedding / 向量检索来挑记忆？**
一个 agent 的活跃记忆是几十条量级，不是几十万条。对几十条做一次带词项匹配的排序，
成本是零、行为可解释、跨中英文都正确；而向量检索会引入一个需要重建、需要迁移、需
要解释"为什么这条没被召回"的新子系统。等到记忆真的多到扫不动，再换，届时快照契约
不变，换的只是挑选函数。

**为什么抽取要用模型，而不是规则？**
规则抽不出"用户更喜欢简短回答"这种东西。但模型抽取意味着**不可信输入**，所以写入
端必须有闸门：长度上下限、每轮条数上限、按 `content_hash` 去重、类别白名单。抽取
出来的东西进了库也依然是 `UNTRUSTED`。

**为什么不硬删除？**
因为"为什么它突然不记得了"和"为什么它还记得"一样需要能被回答。soft-supersede 保留
了链条，`superseded_by_id` 让"这条被哪条替换了"是一次查询而不是一次猜测。

## 后果

接受：

- 一次运行的记忆输入是可复原的；评测 A/B（开/关记忆）因此是可比的。
- 记忆永远不会导致上下文溢出失败，最坏情况是它自己被丢掉。
- `agent_runs` 多一个 JSONB 列，默认 `'[]'`，对没开记忆的 agent 恒为空。

付出：

- 一次长运行不会看到运行中途新产生的记忆。这是有意的，也是"快照"这个词的含义。
- 快照里存的是 id 而不是内容，所以一条被人工作废的记忆在旧运行重放时仍会被读出来。
  这是刻意的取舍：重放的目的是复原当时的输入，而不是复原一个"如果当时就作废了会怎样"
  的假设世界。作废只影响**之后**的运行。
