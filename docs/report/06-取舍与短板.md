# 06 · 取舍与短板

面试里「这个项目有什么不足」几乎必问。
**答得好是加分题，答得差是减分题。**

差的答法：「时间不够，还有很多想做没做」「测试覆盖率可以再高一点」——
空洞、不显示判断力。

好的答法：**说出你主动决定不做的东西，以及不做的理由。**
一个能清楚说出边界的人，说明他知道自己在做什么。

---

## 1. 主动不做的（有理由的取舍）

### 1.1 不做微服务

> 一个人开发、边界还在演进。微服务的成本（分布式事务、部署复杂度、调试）
> 换不来收益。但我按微服务的纪律划边界——依赖方向单向、领域层不依赖框架——
> 所以真要拆的时候能拆。M2 里程碑刻意不含 Agent/RAG/Tool，
> 就是在验证模型网关这个边界能不能单独交付。

### 1.2 不做自动审批策略

「低风险的自动过」听起来很合理，但：
> 自动审批规则本身也要被审计、被版本化、被评估——
> 否则「谁定的这条规则、什么时候改的」又成了黑盒。
> 那是另一个完整子系统。半做出来会比不做**更危险**，
> 因为它会给人一种「有治理」的错觉。

### 1.3 不做 Agent 之间的通信 / 多 Agent 编排

当前一个 Run 就是一个 Agent。多 Agent 会带来：
谁的预算、谁的审批权限、失败传播、循环依赖。
在单 Agent 的治理还没有被真实验证之前做这个，是在不稳的地基上加层。

### 1.4 不做长期记忆（Memory）

扩展计划里明确写了「不新增任何形式的 Memory」。理由：
> Memory 是一个会污染可复现性的东西——
> 同一个输入在不同时间得到不同结果，而且原因藏在一张你看不见的表里。
> 在「可复现」还是这个项目的核心卖点的时候，加 Memory 是在拆自己的台。

### 1.5 不做全文 PDF RAG / Evidence Matrix / 自动综述

Research 应用刻意只做到「检索 + 结构化卡片 + 人工 shortlist」。
自动综述是一个**极容易产生看起来很专业的幻觉**的功能。
在防幻觉设计还只有三层 prompt/投影的阶段，不碰。

### 1.6 不做 Artifact DSL / 富文本编辑器

`content` 是 JSONB，7 种类型的 schema 在 Pydantic 里定义。
不做 DSL、不做 DOCX/PDF 导出、不做协同编辑。
这些是「产品打磨」，不是「架构验证」。

### 1.7 不做多数据源聚合（Research v1 只用 OpenAlex）

多源聚合要解决去重（同一篇论文在不同源的不同 ID）、
排序融合、字段对齐。这是一个独立的问题，不是「再接一个 API」。

### 1.8 Playground 保持单次调试模式

Playground 的 Run 是 `thread_id IS NULL`，
**行为必须与引入 Thread 之前逐字节一致**。
理由：它是调试入口，调试入口的语义一旦漂移，
就没法用它来排查「是不是 Thread 引入的问题」。

## 2. 已知的技术短板（诚实承认）

### 2.1 没有真实的生产流量验证

所有验证都是本地端到端走通，没有并发压力、没有真实用户行为分布。
**能说的是：治理路径全部跑通过，包括 READ → 审批 → WRITE 的完整闭环
和真实模型（DeepSeek）驱动。**

### 2.2 单体 + 单库，横向扩展未验证

Run 的执行是进程内的。要横向扩展需要解决：
checkpoint 的并发访问、SSE 连接的会话亲和性、审批 claim 的跨进程竞争
（这一条已经用数据库抢占解决了，是已经对的部分）。

### 2.3 JSONB 路径查询的性能代价

`tool_revisions.spec` 里的治理字段要走 JSONB 路径查询。
规模上去后需要表达式索引。
**这是我明知的代价**：提到列上就意味着每加一个治理维度是一次迁移。

### 2.4 exactly-once 做不到，且明说了

远端 WRITE 的不确定结果交给人。这不是"解决了"，是"诚实地不解决"。
真正的解法需要远端提供幂等键，那不在我的控制范围内。

### 2.5 评估数据集规模小

评估平台的机制是完整的（可复现性哈希、发布闸门、消融），
但数据集本身是小规模的。
**机制先于规模**是有意的顺序——但规模确实是短板。

**补一句：规模的入口已经开了，但入口不等于规模。**
`POST /workspaces/{ws}/evaluation/datasets/{id}/versions/from-run`
允许把一次真实发生过的 Run 导入成数据集的新草稿版本，
也就是用**线上观测**去喂**离线评估**——这是数据集长大的唯一可持续来源，
凭空编造的用例长不出分布。

这里有一条边界必须讲清楚，因为它是这个接口最容易被做错的地方：
**Run 只是证据，不是标注。**
服务端从持久化的 Run 里派生 `input` 和 `source_provenance`
（source_kind / source_id / agent_version_id / resolved_spec_hash /
observed_status / observed_failure_code），
但 `expected` 必须由调用方给出。
因为「模型当时输出了什么」是事实，「它当时应该输出什么」是判断——
**把观测值直接当成期望值，等于让评估集去拟合模型现有的错误**，
之后所有回归测试都会为这个错误背书。
去重靠 `source_provenance.source_id`，重复导入返回 409
`EVALUATION_DATASET_SOURCE_DUPLICATE`。

**但导入不是标注。** 入口解决的是「候选用例从哪来」，
没解决「谁来定 expected」。规模这条短板只被削掉了一半。

### 2.6 前端无自动化测试

110 个 ts/tsx 文件没有组件测试或 E2E，**回归保护是不对称的：后端 92 个测试文件，前端 0**。
这是最容易承认也最容易改的一条。

替代方案是**八轮注入式浏览器实测**（见 [12 章](12-前端实测与优化报告.md)）：
注入探针测布局溢出、grid 轨道越界、WCAG 对比度、焦点环裁剪，
在 375 / 768 / 桌面三档 × 中英双语下跑了 61 次布局探测、38 次对比度探测。
找到并修掉 8 个真缺陷。

**但要说清这个替代方案的边界**：它是一次性的审计，不是回归保护。
下次改 CSS 的时候，没有任何东西会自动告诉我审批页又爆了。
**发现问题 ≠ 防止问题复发**，这两件事我只做到了第一件。

### 2.7 可观测只到自研 sink

有供应商中立的脱敏结构化 trace sink，契约留好了，
但没有实际接 Langfuse / OTel collector。

### 2.8 文档生命周期完全没有进数据模型（检索层最硬的一条）

`documents` 表只有 `{id, workspace_id, knowledge_base_id, name, created_at}`。
`retired`、`superseded_by`、`effective_date` 这三个字段
**在 `packages/` 和 `apps/` 里 grep 不到任何一处**。

后果是：一份 2025 年已废止的 v1 和一份现行 v2，在系统眼里是
**两份地位完全平等的文档**，排序只能靠语义相似度——而这两份文档
讲同一件事、用词高度重合，语义上本来就难分。

这不是推测。在 60 文档企业语料上实测（[13 章](13-语料库对抗测试报告.md)）：
version_sensitive 14 例里 top-1 命中正确版本只有 6/14，
其中**已退役文档压过其现行后继**的真实倒挂 **4/14**。

有意思的是，模型自己能从**文档正文**里读出 RETIRED 横幅并提醒用户
（QA-045 实测做到了）——**恰好反证了这个信息本该由系统提供，
现在却只能靠模型从正文里碰运气捡。**

最小修法：`documents` / `document_revisions` 加生命周期字段，
检索时对已退役文档做分数惩罚，或至少在证据项里带上状态。

### 2.9 检索路径没有相关性下限

`grep min_score|score_threshold|threshold|cutoff packages/knowledge/retrieval.py`
**结果为空**。

后果是：面对一个语料根本答不了的问题，管道照样把 6 个
rerank 分约 −7.5 的块交给模型。

而实测数据说明这个信号有多干净：

| | min | 中位 | max |
|---|---|---|---|
| negative（语料答不了）top-1 分 | −7.5703 | −5.8262 | **+0.1038** |
| 正例 top-1 分 | **+1.8760** | +4.9258 | +6.0234 |

**两个分布完全不重叠，中间空档 1.77。阈值完全可行，只是没实现。**

目前防幻觉靠的全部是提示词纪律（实测 negative 10/10 拒答、0 编造，
效果确实好）——但那是**模型在兜底**，不是**系统在把关**。
少一层本可以极便宜就加上的确定性防线。

## 3. 验证过程中遇到的真实问题（要主动说）

这三条在最终报告里也会写。面试里主动说出来，显示你知道自己的验证边界在哪。

### 3.1 文献数据源在验证时用的是本地 fixture

OpenAlex 的免费共享额度在验证期间耗尽（`429 Insufficient budget`），
所以端到端验证时 `literature_mcp` 指向了一个**本地的 OpenAlex 形状的 fixture 服务**。

**要点**：MCP 协议链路、工具治理、Artifact 投影全部是真实的，
只有数据源是替身。支持配置 OpenAlex API key 走真实额度。

### 3.2 从仓库根目录跑单元测试有 3 个失败

根因：`pydantic-settings` 会从**当前工作目录**加载 `.env`，
而开发用的 `.env`（gitignored）里开了 `mcp_allow_private_targets`。
从干净 CWD 跑，**69 passed，全绿**。

🔥 **这一条可以反过来用**：那 3 个"失败"恰好证明了
SSRF 的显式 opt-in 开关**确实在起作用**——
如果开关是摆设，那些测试无论 `.env` 怎么写都会一样。

### 3.3 `ruff format` 有 diff

`ruff check` 通过。`ruff format --diff` 显示的 75 个文件
**全部是本阶段未触碰的存量文件**。
没有为了让数字好看去做一次全仓格式化——那会污染 diff，
让 review 无法分辨哪些是真实改动。

## 3bis. 真机跑通三个应用时挖出来的缺陷（这一节最值钱）

上面 3.1–3.3 是**验证环境**的边界。这一节不一样：
这是拿真实 DeepSeek key、真实 Postgres、真实 MCP server
把 Incident / Data Analyst / Support 三条链路从头到尾跑完之后，
**代码里真实存在的问题**。

面试时这一节的价值高于任何"我实现了 X"的陈述——
它证明你不是只把 happy path 跑通就收工的。

### 3bis.1 🔥 `PATCH /agents/{id}` 在写入成功的情况下返回 500

**现象**：改 agent 的 system_prompt，接口返回 `500 INTERNAL_ERROR`，
但去数据库里一看——**改动已经提交了**。

**根因**（API 日志里的真实 traceback）：

```
pydantic_core.ValidationError: 1 validation error for AgentResponse
updated_at
  Error extracting attribute: MissingGreenlet:
  greenlet_spawn has not been called
```

拆开看是三件事叠在一起：

1. `updated_at` 是**数据库在 UPDATE 时填的**（`onupdate` / DB 默认值），
   不是 Python 侧算好再写进去的。
2. SQLAlchemy 在 commit 时会 expire 这类"由数据库产生的值"的属性，
   **这跟 `expire_on_commit=False` 无关**——
   `expire_on_commit=False` 管的是 commit 后的全量 expire，
   管不了 flush 阶段因 DB 生成值而产生的单属性 expire。
3. 于是 FastAPI 的 response serializer 在 **async 上下文之外**
   去读这个 expired 属性，触发了一次隐式 lazy load，
   而那里没有 greenlet，直接炸。

**修复**（`packages/agent_runtime/publish.py`）：

```python
agent.runtime_config = proposed["runtime_config"]
await session.commit()
# `updated_at` is filled in by the database on UPDATE, so the flush
# expires it no matter what `expire_on_commit` says.  Reload it here,
# inside the async context, rather than letting the response serializer
# touch an expired attribute where no greenlet is available.
await session.refresh(agent)
return agent
```

**为什么这条值得讲**：
它是"**写成功了但报错**"这一类最难查的 bug——
调用方看到 500 会重试，重试会再写一次。
这类问题在同步 ORM 里根本不会出现，是 async ORM 特有的坑。
而且它教训很具体：**凡是由数据库产生的列，commit 之后要显式 refresh**。

### 3bis.2 🔥 上下文预算与"最新轮原子性"规则互相打架

**现象**：Incident agent 跑到第三轮，运行直接失败，
错误说上下文放不下。但看数字：

| 指标 | 值 |
|---|---|
| `estimated_before` | 8 906 |
| `context_limit` | 65 536 |
| 实际用掉 | **13.6%** |

**86% 的上下文窗口是空的，运行却因为"放不下"而死了。**

**根因**，两条规则叠在一起：

1. `max_tool_result_tokens` 是一个**类目级（category-wide）的总上限**，
   不是每条工具结果的上限（`context_budget.py:515`）。
   所有 TOOL_RESULT 共享这一个额度，按**从新到旧**分配。
2. 但准入还有一条**原子性规则**（`context_budget.py:599`）：
   最新一轮交换的**所有消息必须全部进得去**，
   不能只进一半——半个工具结果比没有更危险。

于是：最新一轮有 3 个工具结果，加起来超过 `max_tool_result_tokens`
（默认 4000），类目额度不够 → 原子性规则说"那这轮不能进" → 报错。
**而全局窗口还空着 86%。**

雪上加霜的是 `Utf8ByteTokenEstimator` 是**按 UTF-8 字节保守估算**的，
对中英混排的 JSON 实测比 DeepSeek 真实 token 数**高约 3.5 倍**。
所以那个 4000 的额度，实际只对应约 1100 个真 token。

**当时怎么绕过的**：靠版本化。
把 `max_tool_result_tokens` 从 4000 提到 24000，
PATCH → publish 出新版本，线程自动用上新版本
（因为 `agent_threads` 只存 `agent_id`，不 pin 版本），
下一轮就过了。**没有改代码，没有改数据，没有重建线程。**

**代码层面该怎么修**（这是面试官会追问的）：

- 类目额度应该是 `min(配置值, 全局剩余)`，而不是一个硬上限——
  窗口还空着的时候不该因为类目配额而拒绝。
- 或者：原子性规则触发失败时，应该**先尝试抬高类目额度到全局剩余**，
  抬不动再报错。
- 估算器应该可以按 provider 注入真实 tokenizer，
  保守估算作为 fallback 而不是唯一选项。

**为什么这条值得讲**：
两条规则**各自都是对的**（类目配额防止工具结果挤爆窗口；
原子性防止半截上下文），**组合起来产生了一个谁都没预料到的死角**。
这是分层设计里最典型的一类 bug，
而且只有真跑多轮长结果才会撞上——单元测试测不出来。

### 3bis.3 🔥🔥 提示词里的 "propose"，让审批闸门根本没被触发

**现象**：Incident agent 判断出该回滚，
输出了一段**写得非常好的回滚提案散文**——
目标部署、预期影响、风险都说清楚了。
然后运行 `SUCCEEDED` 结束。

**没有任何审批被创建。没有任何工具被调用。**
（连续两次：`f89b44e1`、`e34ada81`）

**根因在提示词，不在代码**。原文是：

```
- Reading is yours to do. Writing is not. When you believe an action such as a
  rollback is warranted, propose it and say plainly what it will do, which
  deployment it targets, and what you expect to happen -- then let the approval
  gate do its work.
```

模型把 "propose it and say plainly what it will do"
读成了"**写一份提案**"。它照做了，而且做得很好。
问题是——**散文不会创建审批**。
审批是在 `TOOL_PROPOSAL` 节点、由一次真实的工具调用触发的。
模型不调用工具，整条治理链路（Policy → Approval → Action）
就**一个节点都不会执行**。

**修复**——把"提案"这个词的歧义堵死：

```
- Reading is yours to do. Writing is not -- but proposing a write means
  calling the write tool, not describing it. When you believe an action such as
  a rollback is warranted, call the tool with the arguments you intend. The
  platform will not execute it: it stops the run at an approval gate and shows
  a human exactly what you asked for. Prose describing a rollback reaches
  nobody and changes nothing, so do not substitute it for the call.
```

关键的三句话：

1. **"proposing a write means calling the write tool, not describing it"**
   ——直接定义这个词。
2. **"The platform will not execute it"**
   ——解除模型的顾虑。模型不敢调用写工具，
   是因为它以为调用 = 执行。告诉它调用只是"提请"。
3. **"Prose describing a rollback reaches nobody and changes nothing"**
   ——说明后果。这句是最有效的。

**发到 v4 之后，紧接着的第一次运行就停在了 `WAITING_APPROVAL`。**
Support agent 有**一模一样**的措辞问题，同样修掉。

**为什么这条最值钱**：

它是一个**提示词与机制的耦合缺陷**。
后端代码 100% 正确：审批闸门、状态机、resume 全都能工作，
有单元测试覆盖，测试全绿。
**但整条治理链路在生产里从未被触发过**，
因为提示词里一个动词的歧义，让模型绕开了入口。

这引出一个很深的问题：
**"提示词"在这个系统里不是文案，它是控制流的一部分。**
它应该像代码一样被版本化、被回归测试。
这个项目里它确实是版本化的（`prompt_version` + 冻结快照），
但**没有对应的回归测试**——
没有任何断言检查"给定这个场景，模型应该产生一次工具调用"。

**如果再给时间，我会加的是**：
一组「机制触发测试」——
不断言模型说了什么，只断言**某类输入必须产生某个节点的执行**。
这正好可以复用已有的 Evaluation 平台。

### 3bis.4 审批响应里的 `execution_status` 是过期的

approve / deny 接口返回的 `ApprovalDecisionResponse` 里，
`execution_status` 报的是 `NOT_STARTED`——
但那个动作在响应返回时**已经 SUCCEEDED 了**。

原因：响应体里的 approval 对象是在 **resume 之前**序列化的，
而 resume 是同步跑完的。UI 如果拿这个字段直接渲染，
会显示一个和事实相反的状态。

**影响**：不是数据损坏，是**接口契约的时序缺陷**。
轮询的前端会闪一下错误状态。
修法很简单：resume 之后重新读一次 approval 再序列化。

### 3bis.5 恢复运行后，运行计数器被覆盖而不是累加

审批恢复之后同一个 `run_id` 上：

| 字段 | 恢复后的值 | 应该是 |
|---|---|---|
| `tool_call_count` | `0` | ≥ 1 |
| `total_cost_amount` | `0.00029237` | `0.00059139 + 0.00029237` |

也就是说，**恢复后的运行只记录了审批之后那一段**。
审批之前烧掉的 token 和调用次数，在账上消失了。

**影响**：成本核算和用量统计对**所有走过审批的运行**都偏低。
这在一个把"治理"当卖点的系统里是个讽刺——
恰恰是最重要的那些运行，账记得最不准。

**根因方向**：resume 时是 `=` 赋值而不是 `+=` 累加。
修的时候要小心幂等——
resume 可能因为 checkpoint 重放而执行多次，
所以正确做法不是简单改成 `+=`，
而是让计数器由 `agent_run_steps` 聚合出来，
或者在写入时带上"已计入的 step_sequence 水位线"。

### 3bis.6 MCP READ 的错误载荷被丢弃

`packages/mcp/runtime.py:100-103` 在 READ 失败时
把 `outcome.data` 整个扔掉，只保留错误码。
模型因此看不到远端到底说了什么。

**这条我故意没修。**

因为把远端返回的内容喂回给模型，
会绕开 `trust: "UNTRUSTED"` 的标记路径（见 08 §4.2）。
一个"更友好的错误信息"换一条提示注入通道，不划算。

真要修，正确做法是让错误载荷**也走一遍 UNTRUSTED 标记**，
而不是直接透传。这是一个**有意识的取舍**，不是遗漏。

### 3bis.8 `effective_knowledge_snapshots` 被 graph state schema 丢弃（最高级，已修）

**症状**：Thread 里调 `search_knowledge`，稳定返回
`TOOL_REVISION_INVALID — "The published knowledge binding is invalid."`，
而数据层一切正常：快照存在、绑定是 `PINNED`、
`agent_runs.effective_knowledge_snapshots` 里有值。

**根因**：`_initial_state()` 把快照塞进了 LangGraph 的 state，
但 `AgentRunState`（一个 `TypedDict`）**没有声明这个键**。
LangGraph 在节点返回后按 schema 过滤 state，未声明的键被静默丢弃。
到 `TOOL_EXECUTE` 时：

```python
effective_snapshot_refs=tuple(state.get("effective_knowledge_snapshots", []))
```

拿到的是 `()`。而 `()` **不是 `None`**——
`PublishedToolResolver.resolve()` 用 `is not None` 判断"调用方是否指定了快照"，
于是它认为调用方明确指定了「零个快照」，
把 `snapshot_refs` 置空，随后 `search_knowledge` 的 fail-closed 守卫触发。

**影响面**：**任何 Thread 运行里的知识检索都必然失败**，没有例外。
Playground 单次调试模式同理。

**为什么测试没发现**：handler 的单元测试直接构造 `ToolDefinition` 调用，
resolver 的单元测试直接调 `resolve()`，两层各自都对。
断掉的是把它们连起来的 state 传递——**编排层没有被任何单元测试覆盖**。

**修复**：`50e2c32`，在 `AgentRunState` 里补上声明。一行。

**教训**（这条最值得讲）：

1. `None` 和空容器承载了不同语义时，中间任何一层把 `None` 变成 `()`
   都是语义损坏。这里 `tuple(state.get(k, []))` 正是那个转换点——
   它把「没有指定」压成了「指定为空」。
2. 用 `TypedDict` 当 state schema 是**静默失败**的：
   漏声明一个键不会报错、不会警告，只会让值消失。
3. fail-closed 在这里救了场。如果 `search_knowledge` 在绑定解析不出来时
   退化成「查最新快照」，这个 bug 会变成**静默的错误答案**——
   检索确实返回内容，只是来自错误的版本，且永远不会有人发现。

## 4. 如果再给三个月，我会做什么
