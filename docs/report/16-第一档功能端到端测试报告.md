## 1. A1：Run 活得比 HTTP 连接长 —— ✅ 通过

### 1.1 测试方法

`.scratch/t_a1_reconnect.py`：

1. 登录，`POST /workspaces/{ws}/agent-versions/{ver}/runs/stream` 开始一次真实的多轮
   工具调用 Run；
2. **收到第 3 个非 delta 事件后，主动抛 `RuntimeError("__hangup__")` 强行掐断 SSE 连接**
   （模拟关标签页，不是优雅关闭）；
3. `asyncio.sleep(3)`，让宽限期计时器跑起来但不到期；
4. `GET /workspaces/{ws}/agent-runs/{run_id}/stream?after_sequence=3` 重连补播。

### 1.2 结果

| 观察点 | 结果 |
|---|---|
| 掐断时刻 | 6.9s，sequence = 3 |
| 掐断后 Run 是否继续 | **继续**，模型调用与工具调用都在断连期间完成 |
| 重连补播起点 | sequence 50（`after_sequence=3` 之后的第一条持久化事件） |
| 终态 | `run.completed SUCCEEDED` |
| 事件表落库 | run `ae506f6f` 共 11 行，sequence 范围 1..472，**`message.delta` 行数 = 0** |

sequence 从 3 跳到 50、11 行却跨越 472 个序号——这是**设计如此**：
`sequence` 是游标不是计数，`message.delta` 故意不落库（否则日志规模 O(tokens)，
只为买一个打字机动画）。补播时看到空洞是正确行为。

## 3. C：单次 Run 成本上限 —— ⚠️ 测试前完全失效，修复后 ✅ 双向通过

这是本次测试最重要的发现。C 的代码是完整的，单测是全绿的，
**而线上跑起来，成本上限一次都没有生效过**。三个独立的断点，任何一个都足以让它静默失效。

### 3.1 缺陷一：冻结边界把上限丢了（真正的根因）

`packages/agent_runtime/frozen.py` 的 `parse_frozen_agent_spec` 在重建执行期
`runtime` dict 时，**只遍历 `DEFAULT_RUNTIME_LIMITS` 的键**。
`max_cost_micro_usd` 不在其中——因为它是唯一一个「可以合法缺席」的运行时值，
没有默认值可填。于是：

- 发布期 `_validate_runtime_config` 认认真真校验了上限，写进 `resolved_spec`；✅ 单测通过
- 执行期守卫 `_cost_guard_failure` 认认真真读 `runtime["max_cost_micro_usd"]`；✅ 单测通过
- **中间这一步把 key 丢了**，守卫永远读到 `None`，于是永远放行。

两个半边各自的测试都通过，而功能完全不存在。修复是显式地跨边界搬运它，并在搬运时校验：

```python
cost_limit = runtime_value.get("max_cost_micro_usd")
if cost_limit is not None and (
    isinstance(cost_limit, bool)
    or not isinstance(cost_limit, int)
    or not 1 <= cost_limit <= MAX_RUN_COST_LIMIT_MICRO_USD
):
    raise _invalid_binding()
runtime["max_cost_micro_usd"] = cost_limit
```

### 3.2 缺陷二：流式请求从来没要过 usage

OpenAI 兼容协议里，**流式响应默认不带 usage**，除非请求里显式写
`stream_options: {"include_usage": True}`。适配器没写。
于是每一次流式 Run 的 `usage_records` 都是空列表，守卫「没东西可量」于是放行。

顺带的后果比上限本身更严重：**此前所有流式 Run 的 token 数和成本字段全是空的**，
`total_cost_amount` / `cost_currency` / `total_tokens` 一律为 NULL。

### 3.3 缺陷三：流式响应拿不到价格

拿到 usage 之后仍然不行：流式响应不携带 `response_cost`，价格表在客户端。
结果是每一次设了上限的流式 Run 都以 `AGENT_COST_UNMEASURABLE` 停住——
从「静默放行」变成「一律拦截」，同样不可用。

修复：用 `litellm.cost_per_token` 从 token 数客户端计价；
**算不出价格时返回 `None` 而不是猜一个数**——「无法计量」是一个合法结果，
调用方（成本守卫）已经把它当作「不可计量」而非「免费」来处理，在这里猜反而更糟。

### 3.4 修复后的双向验证

测试脚本 `.scratch/t_c_cost_ceiling.py` 只改 agent 的**草稿**并发布新版本，
已发布版本不可变，已知良好的 `9ff339bc` 全程未被触碰，结束时在 `finally` 里还原草稿。

**方向一：上限 = 1 micro-USD（必然击穿）**

```
NEEDS_ATTENTION / AGENT_COST_LIMIT_EXCEEDED
事件序列：1 run.started → 2 context.budget → 3 message.started → 19 usage
        → 20 message.completed → 21 tool.requested → 22 tool.started
        → 23 tool.completed → 24 run.failed
```

注意守卫的位置：它在**每次模型调用之前**检查，所以第一轮永远放行（第一轮之前确实无可计量），
第一次工具调用完成后、准备发起第二次模型调用时才拦截。
终态复用既有的 `NEEDS_ATTENTION`，**没有新造状态**。

**方向二：上限 = 50,000 micro-USD（不应击穿）**

```
SUCCEEDED

cost_currency     = 'USD'
cost_is_estimate  = True
total_tokens      = 2729
```

这三个字段此前对所有流式 Run 都是空的。

## 4. B：LLM-as-judge 且 judge 本身被冻结 —— ⚠️ 测试前无法触达，修复后 ✅ 通过

B 的情况和 C 同构：judge 能被冻结、能被 worker 重建、能打分，
**但没有任何一条数据集用例可以合法地「报名」被它打分**。

### 4.1 缺陷四：`open_ended` 这个开关根本写不进数据集

`packages/evaluation/runner.py` 的取舍是明确的、也是对的：

```python
if self.judge is None or item.expected.get("open_ended") is not True:
    return None
```

即 **judge 是逐用例 opt-in 的补充分**，确定性评估器对其余用例仍是唯一打分者。

但 `packages/evaluation/validation.py` 的 `_CATEGORY_SHAPES` 里，
`KNOWLEDGE_QA` 的 `expected` 必须**恰好**是 `{answer, citations}`，可选集为空；
`NO_ANSWER` 恰好是 `{answer}`，可选集也为空。
于是带 `open_ended` 的用例一律 422：

```
422 EVALUATION_DATASET_INVALID
"KNOWLEDGE_QA input/expected fields do not match the category schema."
```

结果就是：实验可以携带 judge 被冻结，worker 可以忠实地把它重建出来，
然后它一个用例都打不到。全链路可用，唯独入口不存在。

修复：给两个自由文本类目加上 `open_ended` 这一个可选布尔键，并单独做类型校验。
`RETRIEVAL` 等封闭类目仍然拒绝它（已补测试钉住）。

### 4.2 缺陷五：创建/读取实验运行一律 500

`EvaluationExperimentRunResponse.holdout_exposure_index` 是**必填**字段，
而 `EvaluationExperimentRun` 这张表**没有这一列**——
曝光序号住在 holdout 曝光台账里，由路由随后用 `model_copy` 补上。
于是 `model_validate(run, from_attributes=True)` 先一步抛错：

```
pydantic_core.ValidationError: 1 validation error for EvaluationExperimentRunResponse
holdout_exposure_index  Field required [type=missing, ...]
```

`POST /experiments/{id}/runs` 与 `GET /experiment-runs/{id}` **无条件 500**，
与 DEV / HOLDOUT 无关。（实验运行其实已经建好并入队了，500 纯发生在响应序列化那一步，
所以是「功能在跑、接口在报错」这种最难察觉的形态。）
修复是给它一个 `None` 默认值——它在实验响应那个同名兄弟字段上本来就有默认值。

## 6. 这次测试真正说明了什么

四项功能里，**两项在写完、单测全绿、并且已经写进实现报告之后，线上一次都没有生效过**。
五个缺陷的形态高度一致：

| 缺陷 | 上游 | 下游 | 断在哪 |
|---|---|---|---|
| C-1 | 发布期校验并写入上限 | 守卫读取上限 | 中间的冻结重建把 key 丢了 |
| C-2 | 守卫要求 usage | provider 能给 usage | 请求里没要 `stream_options` |
| C-3 | 守卫要求价格 | 价格表在客户端 | 流式响应不带 `response_cost` |
| B-1 | 数据集能表达用例 | driver 读 `open_ended` | 校验器不接受这个键 |
| B-2 | 服务层建好了运行 | 路由补 `model_copy` | 响应 schema 先一步抛错 |

**每一个断点两侧的单元测试都是通过的**，因为每个零件都满足自己的契约。
断的全是接缝，而接缝没有主人。

这也解释了为什么坚持用真实 DeepSeek、真实 Celery、真实 PostgreSQL 跑一遍是必要的：
这五个缺陷没有一个能被更多的单元测试发现——它们恰恰生活在单元测试的边界之间。
