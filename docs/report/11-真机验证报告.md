### 1.1 两个环境层面的坑（值得单独说）

**坑一：Windows + psycopg 的事件循环**

uvicorn 默认用 Proactor 事件循环，psycopg 的异步路径在上面直接不工作。
必须用 `loop="none"` 自己装一个 `SelectorEventLoop`：

```python
# .scratch/serve.py
asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())
uvicorn.run(app, loop="none")
```

同样的问题在离线驱动 ingestion 脚本时又撞了一次。

**坑二：系统代理吃掉 localhost 流量**

环境里有 `HTTP_PROXY=127.0.0.1:7897`。
httpx 默认 `trust_env=True`，于是**所有对 localhost 的请求都绕进了代理**，
表现为莫名其妙的超时和 `WinError 10054`。

解法：所有本地 HTTP 客户端一律 `trust_env=False`，
或者进程级 `NO_PROXY="*"`。

> 这两条都不是项目的问题，但都真实地消耗了时间。
> 面试时如果被问"部署踩过什么坑"，这是两个很具体的答案。

## 2. 性能：慢的到底是什么

一度怀疑运行很慢。实测之后结论是**运行栈本身很快**：

| 环节 | 实测耗时 |
|---|---|
| MCP 工具调用（单次） | **≈ 20 ms** |
| DeepSeek 单轮调用 | **≈ 0.6 s** |
| 一次完整多步运行 | 几秒量级 |

慢的是一个**完全无关的东西**：知识库 ingestion 在反复重新拉取
2.2 GB 的 `BAAI/bge-m3` 权重，而那个下载**卡住了**。

这里还有一个值得记下来的细节：

> 下载脚本用的 `allow_patterns` 里写了 `*.safetensors`，
> 但 **BAAI/bge-m3 根本没有 `model.safetensors`**，
> 它的权重文件是 `pytorch_model.bin`。
>
> 于是下载器匹配到的是 `onnx/model.onnx`（1.6 GB）和别的东西，
> **2.6 GB 全下在了用不上的文件上**，
> 真正需要的权重一个字节都没下。
>
> 排查的关键线索是 HF 缓存目录里的
> `.no_exist/<revision>/model.safetensors` ——
> huggingface_hub 把"这个文件不存在"这个事实也缓存了下来。

**教训**：诊断"为什么慢"的时候，
第一步永远是**把栈的每一层分别计时**，
而不是猜。计完时之后，瓶颈根本不在怀疑的地方。

## 5. Support 的 Knowledge 腿：从 fail-closed 挖出一个真 bug

这一腿最初跑不通，报 `TOOL_REVISION_INVALID`。
追下去挖出了本轮**最有价值的一个缺陷**，现在已经修掉并真机跑通了。

### 5.1 现象

`search_knowledge` 稳定返回：

```
TOOL_REVISION_INVALID — "The published knowledge binding is invalid."
```

### 5.2 第一层：先把数据补齐

一开始怀疑是「根本没有快照可以 pin」，于是补了完整的真实 ingestion：

1. 新建知识库 `Support Policy`（`1ebef991-…`）
2. 上传 `refund_policy.md`——6 节的真实退款政策，
   其中 §2 刻意写了「退款只能退回原支付方式」这条约束，
   正好对上 commerce fixture 里 `ORD-77455` 那张 2026-06-30 过期的卡
3. 直接驱动 `_process_knowledge_ingestion` ——
   **这就是 Celery worker 调的那个函数**，同样的生产组件
   （bge-m3 dense + sparse + Qdrant），只是绕开了 Celery/Redis
4. 期间撞上 §2 那个 `allow_patterns` 写错的下载问题，修好权重后重跑
5. 作业最终 `('SUCCEEDED', 'INDEXING', 2, None)` ——
   3 个 chunk 真实嵌入并写进 Qdrant

然后创建快照（`5471094d-…`，`content_hash 6ad09d50…`）、
以 `PINNED` 模式绑定到 Support agent、发布 v5。
确认 `resolved_spec.retrieval` 里 `knowledge_binding_mode = "PINNED"`、
`knowledge_snapshots` 有值、run 行的 `effective_knowledge_snapshots` 也有值。

**数据全对。但还是报同一个错。**

### 5.3 第二层：进程外能解析，进程内不能

写了个脚本在 API 进程之外直接调 `PublishedToolResolver.resolve(...)`，
传入和运行时一样的 `effective_snapshot_refs`：

```
binding_mode = 'PINNED'
refs = ({'snapshot_id': '5471094d-…', 'snapshot_hash': '6ad09d50…'},)
```

**完全正常。** 同样的数据、同样的代码，在 graph 里就失败。
差别只可能在一个地方：`effective_snapshot_refs` 是怎么传进去的。

`packages/agent_runtime/runtime.py:1962`：

```python
effective_snapshot_refs=tuple(
    state.get("effective_knowledge_snapshots", [])
),
```

它从 **graph state** 里取。而 state 的 schema 是：

```python
class AgentRunState(TypedDict, total=False):
    run_id: str
    ...
    usage_records: list[dict[str, Any]]
    # ← effective_knowledge_snapshots 不在这里
```

### 5.4 根因

`_initial_state()` 把 `effective_knowledge_snapshots` 塞进了初始 state，
但 `AgentRunState` **从来没有声明过这个键**。
LangGraph 用 TypedDict 作为 state schema 时，
**未声明的键在第一个节点返回后就被丢弃**。

于是链条是这样断的：

```
run 行里有快照  ✅
  → _initial_state 塞进 state  ✅
    → PREPARE 节点返回，schema 过滤掉这个键  ❌
      → TOOL_EXECUTE 读到 []
        → tuple([]) == ()  ——注意，这不是 None
          → resolve() 走进 "effective_snapshot_refs is not None" 分支
            → snapshot_refs = ()
              → search_knowledge 的 fail-closed 守卫触发
                → TOOL_REVISION_INVALID
```

**这意味着：任何 Thread 运行里的 `search_knowledge` 调用都必然失败。**
单元测试之所以是绿的，因为它们直接调 handler 和 resolver，
不经过 LangGraph 的 state 序列化。

### 5.5 修复

一行，就是把键补进 schema（`packages/agent_runtime/runtime.py`）：

```python
    run_status: str
    usage_records: list[dict[str, Any]]
    # Seeded by ``_initial_state`` from the run row and read again at
    # TOOL_EXECUTE.  It has to be declared here or the graph's schema drops it
    # between the two, and ``search_knowledge`` then resolves against an empty
    # binding and fails closed with TOOL_REVISION_INVALID.
    effective_knowledge_snapshots: list[dict[str, str]]
```

提交 `50e2c32`。

### 5.6 修完之后的真机结果

重启 API，新开线程，问
「退款政策里，如果客户的原支付方式已经失效，应该怎么处理？请引用政策原文。」

错误码从「绑定无效」变成了「超时」，说明检索真的跑起来了，

模型热起来之后再问一次（run `592f0c4f-4d26-4e58-85dc-4a70455b30c2`）：

> 根据知识库中的《Refund and Return Policy — Consumer Hardware》（生效日期 2026-01-01）……

### 5.7 这一节的价值

三件事值得在面试里讲：

1. **fail-closed 救了场。** 绑定解析不出来时，`search_knowledge`
   选择**拒绝检索**而不是退化成「那就查最新的吧」。
   如果它降级了，这个 bug 会变成静默的错误答案——
   用户拿到的是别的快照的内容，而且永远不会知道。
   正因为它硬报错，我才能顺着错误码一路挖到 state schema。
2. **单元测试的盲区是编排层。** handler 有测试、resolver 有测试，
   两个都绿。断的是把它们粘起来的那层 state 传递。
   这类缺陷只有端到端跑真数据才会暴露。
3. **一个"不在 schema 里"的键是静默失败的。** TypedDict 不会报错，
   LangGraph 也不会警告，它只是安静地把键丢掉。
   这是把结构化 state 当配置用时最容易踩的坑。

## 6. 发现的缺陷汇总

详细分析见 **06 章 §3bis** 和 **08 章 §4.7 / §4bis**。这里只列清单：

| # | 缺陷 | 严重度 | 状态 |
|---|---|---|---|
| 1 | `PATCH /agents/{id}` 写入成功却返回 500（`MissingGreenlet` on `updated_at`） | 高 | ✅ **已修** |
| 2 | 提示词里 "propose" 的歧义让审批闸门从未被触发 | **最高** | ✅ **已修**（两个 agent） |
| 3 | 类目配额 × 原子性规则冲突，86% 窗口空着却报"放不下" | 高 | ⚠️ 已用版本化绕过，代码层修法已写进 08 章 |
| 4 | 审批响应里的 `execution_status` 是 resume 之前序列化的，过期 | 中 | 📋 已记录 |
| 5 | 恢复后运行计数器被覆盖而非累加，成本统计偏低 | 中 | 📋 已记录 |
| 6 | MCP READ 的错误载荷被丢弃 | 低 | 🚫 **故意不修**（见 06 §3bis.6） |
| 7 | 两处 seeding 缺口（KB 无快照 / `query_customer` 命名空间不相交） | 低 | 📋 已记录 |
| 8 | `effective_knowledge_snapshots` 未声明在 `AgentRunState` 里，被 graph schema 丢弃，**所有 Thread 内的 `search_knowledge` 必然失败** | **最高** | ✅ **已修**（`50e2c32`，见 §5） |

### 其中第 2 条是最值得讲的

**所有治理相关的单元测试都是绿的。
但第一次拿真 key 端到端跑的时候，审批一次都没触发。**

不是代码错了——是提示词里 `propose` 这个词有歧义，
模型选择了写散文而不是调工具，
于是 `TOOL_PROPOSAL` 节点从来没有被进入过，
`POLICY` / `APPROVAL_WAIT` / `ACTION` 三个节点一个都没执行。

结论：

> **在这个架构里，提示词不是文案，它是控制流的一部分。**
> 我们把它版本化、冻结了（`prompt_version` + 快照），
> 却没有给它写回归测试。

补救方向：加一组**机制触发测试**——
不断言模型说了什么，只断言
"某类输入必须产生 `TOOL_PROPOSAL` 步骤和一个 PENDING 审批"。
这种断言对措辞不敏感，换模型也依然有效，
而且可以直接跑在已有的 Evaluation 平台上。

## 7. 一个意外的架构验证

修第 3 条（上下文预算）的时候，做法是：

```
PATCH  runtime_config.context_budget.max_tool_result_tokens  4000 → 24000
POST   /agents/{id}/publish
```

然后**什么都没做**，正在进行的对话下一轮就正常了。

原因：`agent_threads` 表**只有 `agent_id`，没有 `agent_version_id`**。
线程不 pin 版本，每一轮去解析「当前最新的已发布版本」。

所以：

- **没有改代码**
- **没有改数据**
- **没有重建线程**
- **没有重启服务**

只是发布了一个新的不可变版本。

> 这个设计当初是有争议的（不 pin 版本意味着对话中途行为会变）。
> 但在这次验证里它**救了场**：
> 三个 agent 的预算配置和两个 agent 的提示词，
> 全部是在对话进行中热修的。
>
> 面试时可以把这当成一个**有意识的取舍**来讲：
> 我们选择了「Run 完全可复现（靠冻结快照）」
> \+ 「Thread 跟随最新版本」这个组合——
> 每一次运行都是可复现的，但会话能拿到最新的修复。

---

## 8. 一句话总结

> 四个应用跑在**同一套运行时**上。
> 换掉的只有**提示词、工具绑定、Artifact 投影**三样东西，
> 运行时、策略引擎、审批状态机、上下文预算**一行没改**。
>
> 真机跑完之后挖出 7 个问题，修了 2 个，
> 其中最重要的那一个证明了：
> **提示词是控制流，需要被当作代码来测试。**
