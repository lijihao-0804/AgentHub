### 1.1 两个环境层面的坑（值得单独说）

**坑一：Windows + psycopg 的事件循环**

uvicorn 默认用 Proactor 事件循环，psycopg 的异步路径在上面直接不工作。
必须用 `loop="none"` 自己装一个 `SelectorEventLoop`：

```python
# .scratch/serve.py
asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())
uvicorn.run(app, loop="none")
```

同样的问题在离线驱动 ingestion 脚本时又撞了一次。

**坑二：系统代理吃掉 localhost 流量**

环境里有 `HTTP_PROXY=127.0.0.1:7897`。
httpx 默认 `trust_env=True`，于是**所有对 localhost 的请求都绕进了代理**，
表现为莫名其妙的超时和 `WinError 10054`。

解法：所有本地 HTTP 客户端一律 `trust_env=False`，
或者进程级 `NO_PROXY="*"`。

> 这两条都不是项目的问题，但都真实地消耗了时间。
> 面试时如果被问"部署踩过什么坑"，这是两个很具体的答案。

## 2. 性能：慢的到底是什么

一度怀疑运行很慢。实测之后结论是**运行栈本身很快**：

| 环节 | 实测耗时 |
|---|---|
| MCP 工具调用（单次） | **≈ 20 ms** |
| DeepSeek 单轮调用 | **≈ 0.6 s** |
| 一次完整多步运行 | 几秒量级 |

慢的是一个**完全无关的东西**：知识库 ingestion 在反复重新拉取
2.2 GB 的 `BAAI/bge-m3` 权重，而那个下载**卡住了**。

这里还有一个值得记下来的细节：

> 下载脚本用的 `allow_patterns` 里写了 `*.safetensors`，
> 但 **BAAI/bge-m3 根本没有 `model.safetensors`**，
> 它的权重文件是 `pytorch_model.bin`。
>
> 于是下载器匹配到的是 `onnx/model.onnx`（1.6 GB）和别的东西，
> **2.6 GB 全下在了用不上的文件上**，
> 真正需要的权重一个字节都没下。
>
> 排查的关键线索是 HF 缓存目录里的
> `.no_exist/<revision>/model.safetensors` ——
> huggingface_hub 把"这个文件不存在"这个事实也缓存了下来。

**教训**：诊断"为什么慢"的时候，
第一步永远是**把栈的每一层分别计时**，
而不是猜。计完时之后，瓶颈根本不在怀疑的地方。

### 3.1 Incident Investigator — 目标 60%，**达成并超出**

#### 运行一：纯读，完整因果链

`run_id = f89b44e1-cd52-4553-ab2f-a27c1b039c4d`
状态 `SUCCEEDED`，**13 步**，产出 **10 个 `incident.timeline` Artifact**。

模型自己查出来的真实数据：

| 指标 | 故障前 | 故障后 |
|---|---|---|
| `http_5xx_rate` | 1.9 % | **36.8 %** |
| `p95` 延迟 | 418 ms | **4 005 ms** |
| `psycopg.PoolTimeout` / 分钟 | 6 | 198 → 455 → **630** |

定位到的根因：部署 `dep-20260314-2101`（v5.4.2，commit `abc123de`）
把 `pool_max_size` 从 **50 改成了 5**，
`pool_timeout` 从 **30.0 改成了 2.0**。

这不是模型编的——每一个数字都能在 `agent_run_steps`
的 `TOOL_RESULT` 里找到对应的工具返回。

#### 运行二：完整的 Read → Approval → Write

`run_id = ddd13c38-1748-45b8-919a-9717555f4022`

```

  → MODEL
  → TOOL_PROPOSAL          (rollback_deployment)
  → APPROVAL_WAIT          policy_decision = REQUIRE_APPROVAL

        ↓ 人工 approve
  → APPROVAL_WAIT
  → POLICY                 policy_decision = ALLOW_AUTO
  → ACTION                 rollback_deployment
  → OBSERVATION
  → MODEL
  → FINISH                 SUCCEEDED
```

- `approval_id = 64909643-086c-4e5b-aebb-60c9f81dc36a`
- `logical_action_id = b4799956-2134-5ca0-ab6a-1b7414375e76`
- **恢复发生在同一个 `run_id` 里**——不是新开一次运行
- 数据库终态：`decision_status = APPROVED`，
  `execution_status = SUCCEEDED`，`executed_at` 已写入

🔥 **这一段是整个项目最该演示的 30 秒。**

## 5. 唯一没跑通的：Support 的 Knowledge 腿

### 现象

`search_knowledge` 返回 `TOOL_REVISION_INVALID`。

### 根因

**这不是 bug，是 fail-closed 在正确工作。**

`packages/tools/builtins/search_knowledge.py:50-60`：

```python
if definition.retrieval_config.get("knowledge_binding_mode") != "PINNED":
    raise ToolHandlerError("TOOL_REVISION_INVALID", "The published knowledge binding is invalid.")
if not definition.snapshot_refs or any(
    not item.get("snapshot_id") or not item.get("snapshot_hash")
    for item in definition.snapshot_refs
):
    raise ToolHandlerError("TOOL_REVISION_INVALID", "The published knowledge binding is invalid.")
```

绑定模式是 `PINNED`，**但根本没有快照可以 pin**——
早先的 ingestion 因为模型权重下载卡住，从来没有跑完。

工具的选择是**拒绝检索**，而不是退化成「那就查最新的吧」。
这是对的：`PINNED` 的语义是"查那个被冻结的版本"，
查不到那个版本就应该失败，而不是悄悄换一个。

### 处理

重新做了一次完整的真实 ingestion：

1. 新建知识库 `Support Policy`
2. 上传 `refund_policy.md`（6 节的真实退款政策，含"退回原支付方式"约束）
3. 直接驱动 `_process_knowledge_ingestion` ——
   **这就是 Celery worker 调的那个函数**，
   同样的生产组件（bge-m3 dense + sparse + Qdrant），
   只是绕开了 Celery/Redis
4. 解析 + 分块**成功**（3 个 chunk 已落库）
5. 嵌入阶段失败：`EMBEDDER_LOAD_FAILED` ——
   即 §2 里那个下载 pattern 写错的问题

**状态**：分块已完成并持久化在 `document_chunks` 里，
卡在 `EMBEDDING` 阶段等权重。
这一腿是**本轮唯一没有真机跑通的**，原因是环境，不是代码。

> 诚实地说清楚比含糊带过好。
> 而且这一腿"失败"的方式本身就说明了两件事：
> ingestion 是**可恢复的分阶段作业**（parse → chunk → embed → index，
> 每阶段独立推进、带租约、可重试），
> 以及 `search_knowledge` 在绑定无效时**拒绝而不是降级**。

## 6. 发现的缺陷汇总

详细分析见 **06 章 §3bis** 和 **08 章 §4.7 / §4bis**。这里只列清单：

| # | 缺陷 | 严重度 | 状态 |
|---|---|---|---|
| 1 | `PATCH /agents/{id}` 写入成功却返回 500（`MissingGreenlet` on `updated_at`） | 高 | ✅ **已修** |
| 2 | 提示词里 "propose" 的歧义让审批闸门从未被触发 | **最高** | ✅ **已修**（两个 agent） |
| 3 | 类目配额 × 原子性规则冲突，86% 窗口空着却报"放不下" | 高 | ⚠️ 已用版本化绕过，代码层修法已写进 08 章 |
| 4 | 审批响应里的 `execution_status` 是 resume 之前序列化的，过期 | 中 | 📋 已记录 |
| 5 | 恢复后运行计数器被覆盖而非累加，成本统计偏低 | 中 | 📋 已记录 |
| 6 | MCP READ 的错误载荷被丢弃 | 低 | 🚫 **故意不修**（见 06 §3bis.6） |
| 7 | 两处 seeding 缺口（KB 无快照 / `query_customer` 命名空间不相交） | 低 | 📋 已记录 |

### 其中第 2 条是最值得讲的

**所有治理相关的单元测试都是绿的。
但第一次拿真 key 端到端跑的时候，审批一次都没触发。**

不是代码错了——是提示词里 `propose` 这个词有歧义，
模型选择了写散文而不是调工具，
于是 `TOOL_PROPOSAL` 节点从来没有被进入过，
`POLICY` / `APPROVAL_WAIT` / `ACTION` 三个节点一个都没执行。

结论：

> **在这个架构里，提示词不是文案，它是控制流的一部分。**
> 我们把它版本化、冻结了（`prompt_version` + 快照），
> 却没有给它写回归测试。

补救方向：加一组**机制触发测试**——
不断言模型说了什么，只断言
"某类输入必须产生 `TOOL_PROPOSAL` 步骤和一个 PENDING 审批"。
这种断言对措辞不敏感，换模型也依然有效，
而且可以直接跑在已有的 Evaluation 平台上。

## 7. 一个意外的架构验证

修第 3 条（上下文预算）的时候，做法是：

```
PATCH  runtime_config.context_budget.max_tool_result_tokens  4000 → 24000
POST   /agents/{id}/publish
```

然后**什么都没做**，正在进行的对话下一轮就正常了。

原因：`agent_threads` 表**只有 `agent_id`，没有 `agent_version_id`**。
线程不 pin 版本，每一轮去解析「当前最新的已发布版本」。

所以：

- **没有改代码**
- **没有改数据**
- **没有重建线程**
- **没有重启服务**

只是发布了一个新的不可变版本。

> 这个设计当初是有争议的（不 pin 版本意味着对话中途行为会变）。
> 但在这次验证里它**救了场**：
> 三个 agent 的预算配置和两个 agent 的提示词，
> 全部是在对话进行中热修的。
>
> 面试时可以把这当成一个**有意识的取舍**来讲：
> 我们选择了「Run 完全可复现（靠冻结快照）」
> \+ 「Thread 跟随最新版本」这个组合——
> 每一次运行都是可复现的，但会话能拿到最新的修复。

## 8. 一句话总结

> 四个应用跑在**同一套运行时**上。
> 换掉的只有**提示词、工具绑定、Artifact 投影**三样东西，
> 运行时、策略引擎、审批状态机、上下文预算**一行没改**。
>
> 真机跑完之后挖出 7 个问题，修了 2 个，
> 其中最重要的那一个证明了：
> **提示词是控制流，需要被当作代码来测试。**
