## A. 开场与定位（5 题）

### A1 ⭐ 介绍一下你这个项目

见 [README.md](README.md) 的三档自我介绍。**关键是先说解决什么问题，不要先说技术栈。**

### A2 ⭐🔥 这和调 OpenAI API 写个 while 循环有什么区别

> 区别在跑完之后你能回答的问题。
> 循环跑完只有一段文本。AgentHub 跑完有：用的哪个冻结版本、
> 上下文里哪些证据装入了哪些被截断（按语义分类）、调了哪些工具、
> 哪些因为是 WRITE 被拦下等人批准、谁批准的、远端返回是确定成功还是不确定、
> 产出的每条事实来自哪次工具调用。
> **这些不是日志，是可查询的领域模型。**

### A3 为什么叫「控制平面」

借网络的说法：数据平面是 Agent 实际执行的那条路径；
控制平面是定义/发布/授权/审计/评估那条路径。这个项目的工作量主要在后者。

### A4 这是你一个人做的吗，做了多久

如实回答。可以补一句：46,383 行 Python、99 个测试文件 744 个用例、27 个迁移、
每个里程碑有独立的验收文档（`docs/milestones/`）。

### A5 为什么选这个题目

> 市面上 Agent Demo 很多，能上生产的少。差的不是模型能力，是治理。
> 我想把「差的那部分」做出来。

## B. 架构与设计原则（10 题）

### B1 ⭐ 你的分层是怎么分的，依赖方向

```
Transport/API → Application → Domain/Contract → Infrastructure Adapter
```

`packages/` 不依赖 FastAPI。LangGraph 的 checkpoint 原始载荷、Qdrant SDK 类型、
Provider SDK 类型**都不允许穿过应用契约**。

### B2 🔥 怎么证明依赖方向没被破坏

三个证据：
1. `packages/` 里 `grep fastapi` 只在极少数明确的边界出现；
2. 换向量库只需要换 `knowledge/` 里的适配器实现；
3. M2 里程碑交付时刻意**不含 Agent / RAG / Tool**——
   一个边界是不是真边界，看它能不能单独交付。

### B3 ⭐ 为什么用 LangGraph 而不是自己写循环

> 我要的不是「图」，是 **checkpoint + interrupt** 这两个能力。
> 审批必须能让一次执行持久挂起、进程重启后从原地恢复。
> 自己写这套状态持久化，是在重写一个已经存在的东西。

追问「那图的部分是不是用不上」：8 个节点确实是相对线性的，
但条件边（policy 分流到 read_execute / action_execute / finish）
让「READ 自动执行 / WRITE 转审批」这个分支是声明式的，不是散在 if 里。

### B4 8 个节点分别做什么

`prepare`（完整性校验 + 消息装配）、`model`、`tool_proposal`、`policy`（治理判定）、
`read_execute`、`action_execute`、`observation`、`finish`。
固定边只有四条，其余全是条件边。

### B5 为什么 apps 和 packages 分开

`apps/` 是进程边界（可独立部署的东西），`packages/` 是领域库（可被多个进程引用）。
四个 MCP Server 是 `apps/`，因为它们是独立进程。

### B6 模块化单体 vs 微服务，为什么选前者

> 一个人开发、边界还在演进的阶段，微服务的成本（分布式事务、部署复杂度、
> 调试困难）换不来收益。但我按微服务的纪律划了边界——
> 依赖方向单向、领域层不依赖框架——所以真要拆的时候能拆。

### B7 数据库设计有什么讲究

单一真相源是 PostgreSQL。JSONB 用在**契约快照**（`resolved_spec`）和
**内容载荷**（`artifacts.content`、`tool_revisions.spec`）上，
用在这些地方的理由是：它们的 schema 由应用版本管理，不由 DDL 管理。

🔥 追问「那怎么查」：`tool_revisions.spec` 里的 `effect/risk_level/approval_policy`
确实要 JSONB 路径查询。这是我接受的代价——
如果提到列上，那么每加一个治理维度就是一次迁移。

### B8 27 个迁移单一 head 是怎么保证的

硬约束：任何新迁移的 `down_revision` 必须指向当前唯一 head。
CI 会跑 `alembic heads` 检查。
**这条是我给自己立的第一条规矩**——multiple heads 一旦产生，
在多人协作里会变成长期痛点。

### B9 为什么前端不用 UI 框架

113 个 ts/tsx、1,726 行手写 CSS。理由：这个项目的界面模式很少（三栏 + 表单 + 列表），
引入组件库的收益低于它带来的样式覆盖成本。`globals.css` 只做 import，
真正的样式在 `app/styles/*.css` 按领域分文件——**而且 import 顺序就是级联顺序**，
tokens 在最前、断点在最后，所以媒体查询永远赢，不用靠 `!important` 提权。

**但要诚实地说出代价**：手写 CSS 意味着框架帮你兜的底，你得自己兜。
我做了八轮浏览器实测来找这些洞，找到 8 个真缺陷（见 12 章），其中两个是同一个根因：

> `min-width: auto` —— 在 grid 里，隐式 `auto` 轨道按 max-content 定宽且**不受容器约束**；
> 在 flex 里，item 拒绝收缩到内容宽以下。审批页展开 JSON 后文档宽度从 1014px 撑到 2099px，
> 就是这条。

如果用组件库，这类问题大概率不会出现；但样式覆盖的成本会天天出现。
**这是个取舍，不是「我懒得学框架」——区别在于我能说出代价具体是什么。**

### B9b 🔥 前端质量你怎么验证的（没有 E2E 测试的情况下）

这是个好问题，因为我确实**没有**前端自动化测试。我的替代方案是**注入式实测**：

```
注入探针 → 点真实 <a> 导航 → 强制展开所有 <details> → 四类测量
  ① document.scrollWidth vs viewport
  ② 每个 grid 容器的轨道宽度和 vs 它自己的 clientWidth
  ③ 每个文本节点的前景色 vs 逐层 alpha 合成后的真实背景
  ④ 每个可聚焦元素 vs 最近的 overflow 裁剪祖先
```

三个细节值得讲：

1. **必须点真实的 `<a>`**，不能 `history.pushState`——后者不驱动 Next App Router，
   会测出一堆假页面。
2. **必须强制展开 `<details>`**——8 个缺陷里 5 个只有在真实数据摊开后才出现。折叠状态下一个都看不到。
3. **对比度必须对着合成后的背景测**。徽章自己画一层半透明 `-soft` 底，
   这层底又常叠在已着色的块上。按「在白底上好看」选的颜色，落到真实色层栈就掉到 AA 线下了——
   实测最差 **4.11:1**，整族加深一档后到 **4.96:1**。

**最值得说的一条**：14 个初判里 6 个是误报，误报率 43%，
其中一个还是我审计脚本自身的 bug（alpha 合成器恒返回 `a:1`，导致祖先遍历提前终止，
报出「深色泄漏到浅色主题」这种吓人但不存在的问题）。
所以我的结论是：**任何自动化审计的第一个发现都要手工复核一次再动手改**——
工具的价值是把 20 个页面缩小到 14 个待查点，不是给答案。

### B10 🔥 i18n 怎么保证不漏 key

```ts
export type MessageSchema = typeof enUS;   // 英文文件本身就是 schema
export const zhCN: MessageSchema = { ... };
```
中文少一个 key 是**编译错误**。这比「运行时回退到 key 名」好，
因为后者会悄悄上线。

## C. 冻结快照（6 题）⭐⭐

### C1 ⭐ 什么是 Frozen Execution Snapshot

见 03 章机制 1。要点：发布时求值、快照、哈希；运行时三重校验；不通过就拒绝执行。

### C2 快照里到底存了什么

system prompt / 工具契约（identity、input_schema、effect、risk、approval_policy、timeout）/
模型执行档案 / 运行时上限（`max_tool_calls`、`max_identical_calls`）/ 上下文预算配置 /
知识库绑定（含快照选择器物化结果）。

### C3 🔥 为什么要 canonical JSON hash

`json.dumps` 的 key 顺序、空白、浮点表示都不稳定，同一对象能算出不同哈希。
`packages/core/canonical/json_hash.py` 做规范化。
**这是一个很小但很能说明"想过"的细节。**

### C4 ⭐🔥 凭据也冻结吗

**不。** 契约冻结，凭据不冻结。原话：
> *"The contract is immutable; the credential is not, and that asymmetry is deliberate."*

理由：密钥轮换是运维常规操作，不应该逼人重新发布一个 Agent 版本。
但工具的输入 schema 改了，那是**行为改变**，必须走新版本。
**分清「什么是身份，什么是配置」。**

### C5 spec_schema_version 是干什么的

`SUPPORTED_SPEC_SCHEMA_VERSIONS = frozenset({1, 2})`。
快照格式本身也会演进，所以快照里记自己的格式版本。
加载一个不支持的版本，拒绝执行而不是尽力解析。

### C6 冻结了还怎么迭代 prompt

发布新版本。旧 Run 指向旧版本。**版本不可变，指针可变。**

## D. 工具治理与审批（12 题）⭐⭐⭐

### D1 ⭐ 工具是怎么定义的

数据库记录（`tools` / `tool_revisions`），`spec` JSONB 里含
`effect / risk_level / approval_policy / execution_kind` + input schema。
不是代码里的 if-else。

### D2 ⭐ 审批的判定逻辑

```python
if effect is READ and approval_policy is NEVER: return ALLOW_AUTO
return REQUIRE_APPROVAL
```
**默认拒绝。** 不是「WRITE 才审批」（那是默认允许）。

### D3 🔥 为什么要写成默认拒绝

> 如果写成 `if effect is WRITE: 审批`，那么一个 effect 字段缺失、
> 拼错、或者新增的第三种 effect 值，都会静默变成「自动执行」。
> 默认拒绝的失败模式是「多一次审批」，默认允许的失败模式是「多一次事故」。

### D4 ⭐⭐ 审批是怎么实现的，会阻塞吗

不阻塞。`interrupt()` + LangGraph checkpoint 落库，Run 置 `WAITING_APPROVAL`。
**此时可以重启整个 API 进程。** 批准后 `resume(run_id)` 在**同一个 Run** 内恢复。

### D5 ⭐🔥 为什么必须在同一个 Run 内恢复，新开一个不行吗

三个理由：
1. 审计上 `run_id` 必须是一个完整故事，不能要求审计员跨 Run 拼；
2. `max_tool_calls` 这类预算绑在 Run 上，新开就被重置绕过了；
3. 上下文是 checkpoint 恢复的，新开要重放，重放不保证一致。

### D6 两个人同时点批准会怎样

`claim_execution()` 是数据库层面抢占，只有一个成功。

### D7 ⭐ 审批的状态怎么建模

**两个正交维度**：
- `ApprovalDecisionStatus`：PENDING / APPROVED / DENIED / EXPIRED / CANCELLED
- `ApprovalExecutionStatus`：NOT_STARTED / CLAIMED / SUCCEEDED / FAILED / UNKNOWN_OUTCOME

🔥 追问「为什么不合成一个」：因为「批准了但执行失败」和「被拒绝」
是完全不同的事实，合成一个枚举就表达不出来。
**决策是人的行为，执行是系统的行为，它们的生命周期不同。**

### D8 幂等怎么保证

`ApprovalService.create_or_get()`，幂等键含
`run_id + tool_revision_id + arguments + proposal_ordinal`，产出 `logical_action_id`。
同一逻辑动作被重复提议，拿到同一条审批。

### D9 审批过期了算什么

`EXPIRED`，独立于 `DENIED`。「没人来看」和「有人说不行」不是一回事。

### D10 批准之后 Run 被取消了

`cancel_pending_for_run()` 把待决审批置 `CANCELLED`。
🔥 但如果已经 dispatch 出去了，取消不能撤销远端动作——
这时候是 `UNKNOWN_OUTCOME` 语义，交给人。

### D11 审批人怎么知道要批什么

SSE `approval.required` 事件带工具身份、参数、risk_level。
前端渲染成审批卡片。**参数是原样展示的**——
让人批准一个他看不见内容的动作，等于没有审批。

### D12 有没有想过自动审批策略（低风险自动过）

想过，没做。理由见 06 章。简述：
自动审批规则本身也需要被审计和版本化，那是另一个完整子系统，
半做会比不做更危险。

## E. MCP 与远程工具（10 题）⭐⭐

### E1 ⭐ 为什么用 MCP

工具的提供方和消费方解耦。运维团队维护 `ops_mcp`，我这边只是导入它的契约。
且用**官方 Python SDK v2**（`mcp>=2,<3`），
**禁止手搓 JSON-RPC / initialize / 分页**——
自己实现协议等于给自己造一个永远追不上上游的兼容性债。

### E2 ⭐ 远程工具导入的流程

连接（Connection）→ 测试（Test）→ 发现（Discovery）→ 导入为 Tool → 修订 → 发布。
发现只**列出**远端工具，不自动导入。

### E3 ⭐🔥 远端说自己是只读，你信吗

**不信。** `effect / risk_level / approval_policy / execution_kind`
**一律由导入方显式指定**，远端 annotation 只作展示参考。

> 让被调用方声明自己危不危险，等于没有治理。

### E4 ⭐⭐ SSRF 怎么防的

见 03 章机制 5。三个关键点：
1. **必须解析 DNS 再判断**，不能只看 URL 字符串；
2. **多条记录里有任意一条私网就整体拒绝**（防 rebinding）；
3. **连接后再查 socket 实际对端**（`authorize_peer_address`），关掉 TOCTOU 窗口。

### E5 🔥 为什么多记录不一致要整体拒绝，不是拒绝私网那条

> 因为最终用哪条是连接栈决定的。如果我放行公网那条，
> 实际决策权就落到了「连接恰好挑了哪条记录」上，
> 而这正是 DNS rebinding 攻击依赖的性质。

### E6 本地开发要连 localhost 怎么办

`mcp_allow_private_targets` 显式 opt-in。
**明令禁止 `if environment == "local": automatically allow`。**
> 因为那等于把安全属性绑在一个环境变量的拼写上。
> 谁在生产把 ENV 设错一次，防护就整体消失了。

### E7 ⭐⭐ 远程 WRITE 调用超时了怎么办

见 03 章机制 4。`UNKNOWN_OUTCOME` → Run `NEEDS_ATTENTION` → 交给人。
**不重试。**

### E8 ⭐🔥 为什么不重试

> `issue_refund` 重试一次等于退两笔钱。
> 在没有远端幂等键保证的前提下，重试是把「不确定」变成「确定出错」。
> 代码注释里我明确写了：不声称 exactly-once，因为这边做不到。

### E9 NOT_DISPATCHED 是什么

请求根本没发出去（工具未发布 / 连接不存在 / 连接禁用 / 未配置认证 / 密钥解密失败）。
**这五种可以安全地直接判 FAILED**，因为远端没有任何副作用。
只有「发出去了但没收到回应」才是 UNKNOWN。

### E10 发现的 payload 怎么限制

两个独立的界：`mcp_discovery_max_schema_bytes`（单个 schema）和
`mcp_discovery_max_payload_bytes`（**整个规范化后的工具载荷**：
name + title + description + input_schema + output_schema + remote_annotations，
跨页累计）。
🔥 后者是一次冻结审计发现的缺口——原实现只计 schema，
一个 schema 很小但 description 超大的工具能绕过。修完加了回归测试。

## F. 密钥与安全（6 题）⭐

### F1 ⭐ 密钥怎么存

静态加密 / 只写不读 / 永不出现在响应与日志。
主密钥 `AGENTHUB_CREDENTIAL_MASTER_KEY`。

### F2 ⭐ 没配主密钥会怎样

**失败关闭**：非开发环境直接拒绝该能力启动。
local/test/development 用既有本地回退 key。
**没有任何环境会退化成明文。**

### F3 ⭐🔥 为什么不复用已有的 ProviderCredentialCipher

**这是我最想被问到的一题**（见 03 章机制 6）。

> 共享的是 master key（那部分本来就该共享），
> 独立的是 ciphertext version 前缀。
> 因为将来改其中一种密钥格式时，不能让它悄悄地按新规则去解释另一种的历史行数据。
> Provider 凭据那条路径是已冻结的，为了省三十行代码去碰它，
> 是拿一个已验证的保证换一点整洁感。
>
> **知道什么时候不要 DRY，和知道什么时候要，一样重要。**

### F4 响应里怎么保证不泄露

契约层面禁止这些字段名出现：
`secret` / `encrypted_secret` / `secret_ciphertext` / `authorization` / `headers`。
且所有请求 schema 都是 `extra = "forbid"`。

### F5 多租户隔离怎么做

workspace 级隔离，且**404 不泄露存在性**——
访问别的 workspace 的资源返回 404 `*_NOT_FOUND`，不是 403。
403 会告诉攻击者「这个 ID 是存在的」。

### F6 RBAC 设计

8 个权限常量 + `WORKSPACE_OPERATIONAL_PERMISSIONS` 集合。
三个角色：ORGANIZATION_ADMIN / DEVELOPER / VIEWER。
🔥 加分点：**本阶段做四个应用，新增权限数是 0**——
如果每个应用都要自己的权限，那权限模型就是按功能堆的，不是按能力设计的。

## G. 上下文与 RAG（8 题）⭐⭐

### G1 ⭐ 上下文超长怎么处理

见 03 章机制 7。七个语义类别，三档处理（强制 / 可投影 / 可驱逐）。

### G2 ⭐🔥 为什么不直接从头截断

三个后果：砍掉 system prompt（行为突变）、砍出孤儿 tool 消息（OpenAI 兼容 API 直接 400）、
砍掉用户刚问的问题（答非所问）。
**截断必须是有语义的取舍。**

### G3 🔥 孤儿 tool 消息是什么

assistant 消息里的 `tool_calls` 必须和对应的 `tool` 角色消息成对出现。
只驱逐一半，API 会报错。所以我把它们绑成同一个 group key
`("tool_exchange", index, *ids)`，**一起留或一起走**。

### G4 用户怎么知道哪些被截断了

`context.budget` SSE 事件按类别上报 estimated / retained / truncated。
所以「为什么这次没引用到那篇文档」有确定答案。

### G5 ⭐ RAG 怎么保证可复现

知识快照。绑定支持 `LATEST`，但发布时**物化成具体的 KnowledgeSnapshot**，
逐条记录文档修订 ID。
> 如果绑 LATEST，三个月后重跑评估，结果变了你无法归因——
> 是模型变了还是知识库多了两篇文档？

### G6 检索链路

解析 → 分块 → 嵌入（BGE-M3）→ Qdrant → 检索 → 重排（BGE reranker）→ 引用问答。
CI 里注入确定性假模型，不下载权重。

### G7 检索效果怎么评估

`benchmarks/` 有检索评估基线数据，M3 里程碑有独立的检索评估。
评估器本身带版本号（`retrieval-evaluator: v1`），记进可复现性 manifest。

### G8 RAG 证据为什么单独成一类

`RAG_EVIDENCE` 有独立的 `max_retrieval_tokens` 上限，
不和普通 `TOOL_RESULT` 抢配额。
否则一次 `query_logs` 返回大量文本，会把检索到的文档挤掉。

## H. 幻觉与产出物（6 题）⭐⭐🔥

### H1 ⭐⭐ 怎么防止模型编造

**三层**（见 03 章机制 9）：
1. prompt 契约（`GROUNDING_RULES`）
2. 上下文契约（`THREAD_CONTEXT_RULES`）
3. Artifact 投影（模型没有写事实的权限）

### H2 ⭐⭐🔥 举个具体例子

**这题一定要用那个真实观测：**

> 多轮对话里，我问「这三篇哪篇引用最多」。Agent 没有重新调工具，
> 而是从它自己上一轮的摘要里读——**它报了 412 和 7，
> 而 Artifact 记录的真实值是 512 和 47。**
>
> 根因是历史轮次回填时只带了「说过什么」，工具结果本身不在上下文里，
> 但模型把摘要当成了数据源。
>
> 修法不是调参，是写进 prompt 契约：
> 引用行告诉你「检索过某样东西、大概多少量」，它不是数据，
> 你不能从里面读出字段值——追问任何具体数值都必须本轮重新调用工具。

**这一段的杀伤力在于：有现象、有数字、有根因、有结构性修法。**

### H3 ⭐ Artifact 是模型生成的吗

**不是。** 事实类 Artifact 是从工具结果**投影**出来的，
带 `{run_id, tool_call_id, tool_identity, step_sequence}` 溯源戳。
综合类 Artifact（shortlist / report / finding / handoff）是**人在 UI 上按按钮**产生的。

### H4 🔥 为什么综合类也不让模型生成

> 因为它们是判断，不是事实。「我认为这 5 篇最相关」是人的结论。
> 让模型产出它，会让一个概率性的意见穿上正式产出物的外衣。
> 分清「事实」和「判断」，比给模型加更多 prompt 有效。

### H5 Artifact 的 API 设计

只有一个通用端点：
`POST /workspaces/{ws}/threads/{thread_id}/artifacts`，body `{type, title, content}`。
🔥 **没有 per-application 端点**——这是检验抽象真假的一个办法：
如果每个应用都要自己的端点，那抽象就是假的。

### H6 为什么 content 用 JSONB 不做 DSL

v1 刻意不做 Artifact DSL。7 种类型的 content schema 在 Pydantic 里定义、
在应用版本里演进。DSL 是下一阶段的问题，现在做是超前设计。

## I. 评估与可复现（6 题）⭐

### I1 ⭐ 怎么判断换个模型是变好还是变差

评估平台：数据集 → 实验 → 运行 → 指标 → 对比 → 消融 → 发布闸门。

### I2 ⭐🔥 两次评估结果不同，你怎么知道是模型的锅

**可复现性哈希**。每次评估记 manifest：
`evaluation_schema_version` + 每个 evaluator 的版本 + 定价快照（`PricingSnapshot`），
算规范化哈希。哈希相同 = 两次在同样的规则下跑的。
再加上**构建身份**（`AGENTHUB_BUILD_SHA`，正则 `^[0-9a-fA-F]{7,64}$` 校验），
评估结果和代码版本绑死。
**加上知识快照，三个变量（代码 / 规则 / 数据）全部被钉住。**

### I3 发布闸门是什么

`release_gate.py`（692 行）。策略**不可变且显式**：指标 + 方向（`MetricDirection`）+ 阈值。
决策落库成 `EvaluationReleaseGateDecision`。
> 不是「跑完看一眼觉得还行」，是「策略先定，结果自动判」。

### I4 消融实验做什么

比如：关掉重排之后指标掉多少？把 `max_tool_calls` 从 10 调到 5 影响多大？
让「这个组件值不值得留」有数据回答。

### I5 定价快照为什么要记

成本是评估指标之一。模型单价会变。
如果不快照，三个月后回看「这个实验花了多少钱」会算出一个不同的数。

### I6 ⭐🔥 评估数据集的用例从哪来

**这是评估平台最容易烂尾的地方**：机制做得再漂亮，数据集是手编的十几条，
就永远在评估一个你自己想象出来的分布。

所以有一条从线上回流的通道：
`POST /workspaces/{ws}/evaluation/datasets/{id}/versions/from-run`，
把一次**真实发生过的 Run** 导入成数据集的新草稿版本。
线上用户问出来的问题，才是真实分布。

但这个接口有一条边界，我认为是它最关键的设计：

> **Run 只是证据，不是标注。**

服务端只从持久化的 Run 里派生两样东西——`input`，
以及 `source_provenance`（source_kind / source_id / agent_version_id /
resolved_spec_hash / observed_status / observed_failure_code）。
`expected` **必须由调用方提供**，服务端一个字都不猜。

**追问「为什么不直接把模型当时的输出存成 expected，不是省事吗」：**
因为那是在让评估集去拟合模型现有的错误。
「模型当时输出了什么」是事实，「它当时应该输出什么」是判断。
如果把观测值直接当期望值，那么模型当时答错的那些用例会被固化成「正确答案」，
之后所有回归测试都会为这个错误背书——
**评估集从测量工具退化成了模型的复读机**，而且你还看不出来，因为它永远 100% 通过。
更糟的是，最值得进评估集的恰恰是**失败的 Run**，
而失败 Run 的观测值一定不是期望值。

所以导入的是 `observed_status` / `observed_failure_code` 作为**溯源**，
不是作为标签。

**追问「重复导入同一个 Run 怎么办」：**
按 `source_provenance.source_id` 去重，返回 409
`EVALUATION_DATASET_SOURCE_DUPLICATE`。
因为同一次 Run 进两遍数据集，等于给这个用例偷偷加了权重。

**这里也要承认边界**：这个接口解决的是「候选用例从哪来」，
没解决「谁来写 expected」。标注仍然是人工的，规模短板只削掉了一半。

**实现上值得一提的两点克制**：复用了已有的 `evaluation_manage` 权限，
没有为这个功能新增 RBAC permission；前端面板 546 行，
复用了 12 个已有 CSS 类，**没有新增任何样式文件**。
新功能倾向于顺手新建一套自己的东西，而每多一个权限、多一个样式作用域，
以后要推理的组合就多一倍。

## J. 工程实践（8 题）

### J1 测试怎么组织

99 个测试文件、744 个用例（pytest 收集 1,000），单元 / 集成分离。集成测试需要真实 PostgreSQL URL，
没配就跳过而不是失败。
🔥 **单元测试禁止依赖公网**——SSRF 那部分的测试用本地 fixture。

### J2 CI 怎么跑

GitHub Actions。每次冻结审计跑一次 **exact-head CI**——
精确到 SHA，不接受「差不多那个提交」。

### J3 ⭐🔥 有没有做过 code review / 审计

做过多轮**冻结审计**（freeze audit）：一个阶段交付后，
对照规格逐条核对，只修契约缺口，不动架构。
举例：3A 审计发现 discovery payload 只计了 schema 不计 description，
3B+C 审计发现三处（MCP READ 审批契约、重复逻辑工具身份、dispatch 后取消）。
**每次审计只修列出的项，然后跑精确 SHA 的 CI，然后 STOP。**

这一条展示的是**工程纪律**：不在审计里顺手重构。

### J4 怎么管理开发节奏

`plan/plan.md` + `plan/extend-plan.md` 分阶段。
每个里程碑有独立验收文档（`docs/milestones/`），有明确的 PASS / NOT PASS。
交付完立刻 STOP，不顺手做下一阶段。

### J5 遇到过什么难搞的 bug

可以讲那个幻觉问题（H2），也可以讲环境相关的：
pydantic-settings 会从当前工作目录加载 `.env`，
导致从仓库根目录跑测试时 3 个用例读到了开发用的 `.env` 而失败。

🔥 **这一条的价值在于它有两层**：

**第一层**，那个"失败"恰好证明了 SSRF 的 opt-in 开关**确实在起作用**——
如果开关是摆设，测试无论 `.env` 怎么写都会一样绿。

**第二层**（后来才想明白，更值得讲）：把它当环境问题绕过去（换个干净 CWD）
其实是把结论搞反了。这三条断言的是**默认值是什么**，
所以它们在干净检出上通过、在有配置的工作机上失败——
**一个在开发者机器上必然红的测试，等于没有测试**。

正确的修法是隔离测试，而不是改配置默认值、也不是换 CWD：
`tests/support/settings.py::declared_settings()` 构造 `Settings` 时
同时关掉两个来源——`_env_file=None` 屏蔽 dotenv，
并临时摘掉进程里所有 `AGENTHUB_*` 环境变量。
只关文件是不够的：pydantic-settings 的优先级是
`init > 环境变量 > dotenv`，一个 `export` 就能把同一个洞重新打开。

🔥 **可以主动补一句边界**：只有断言"默认值是什么"的测试才需要这种隔离；
断言"配置生效后的行为"的测试应当继续读环境，
否则就测不到配置这条路径了。所以没有做成全局 autouse fixture——
集成测试需要 `.env` 里真实的 `AGENTHUB_DATABASE_URL`。

### J6 lint / 格式化

Ruff（py312，line-length 100）。`ruff check` 是闸门。

### J7 Windows 上开发有什么坑

CRLF 换行规范化、路径分隔符、`postgresql+asyncpg://` 这个 SQLAlchemy URL
不能直接喂给 psycopg（要用裸 DSN）。小事，但会拖时间。

### J8 用了 AI 辅助开发吗

诚实回答。可以补：
**但每一个架构决策和每一条不变量是我定的**，
而且我能解释每一处「为什么这么写」——这份文档本身就是证明。

## M. 深挖题（面试官翻了代码之后问的）🔥

这一组对应 [08-代码级细节.md](08-代码级细节.md)，是第二轮技术面的深度。

### M1 ⭐🔥 提示注入你怎么防

> 三点。
> 第一，**工具结果的信任标记是运行时盖的，不是从数据里读的**。
> `context_budget.py:921` 对 TOOL_RESULT 类别无条件写 `trust: "UNTRUSTED"`，
> 注释原话是 *"Never allow a payload to promote itself."*
> 一个被攻陷的 MCP server 在返回值里写 `{"trust": "SYSTEM"}` 是无效的。
>
> 第二，**注入即使成功让模型提议了一个危险动作，也过不了治理闸门**——
> WRITE 类工具一律要人批准，而审批卡片展示的是**原始参数**。
>
> 第三，**模型无法伪造事实记录**，因为 Artifact 是投影出来的。
>
> 所以我的防线不是"让模型别被骗"，是"**就算它被骗了，后果也被挡住**"。

### M2 ⭐🔥 上下文超了你怎么截断，具体算法

不是切字符串，是**递归 JSON 投影**（`_project_json_value`）。
Mapping 按 key 排序逐个试塞，list 逐个试塞到放不下为止，标量包成
`{"value": ..., "truncated": true}`。
**产出永远是合法 JSON，且永远带 `truncated` 标记。**

追问「为什么标记重要」→ 见 03 章机制 13。

### M3 🔥 幂等键里为什么要有 proposal_ordinal

**这题能筛掉一大批人。**

> 同一个 Run 里模型**可能合法地两次提议完全相同的动作**——
> 第一次被拒，换个理由又提。没有序号的话第二次会被幂等吃掉，
> 直接复用"已拒绝"，人就再也看不到第二次提议。
>
> **幂等要防的是"同一次提议被重复提交"，不是"同一个动作被重复提议"。**

### M4 🔥 审批状态能不能撤回

不能。转移表里 `APPROVED/DENIED/EXPIRED/CANCELLED` 全是终态，
`allowed` 字典只有 `PENDING` 一个 key。

> 撤回不是状态，是新事件。允许 APPROVED → PENDING 的话，
> 审计上就分不清"还没人看"和"有人批了又反悔"。

### M5 🔥 为什么要禁止 tool arguments 里出现 workspace_id

递归拒绝 10 个保留 key（`_RESERVED_ARGUMENT_KEYS`）。

> 模型输出是不可信输入。如果它能塞一个 `workspace_id`，
> 而下游某处写了 `{**tool_args, **context}`，就是一次越权。
> 我没有去审查每个下游展开点——那防不住，将来还会有新的下游。
> **在边界上做一次约束，胜过在每个使用点做一次检查。**

### M6 token 怎么算的，用 tiktoken 吗

不用。`Utf8ByteTokenEstimator` 每个 UTF-8 字节算一个 token，
故意保守且离线。三个理由见 08 章 4.5：
准入语义不该依赖 provider 分词器 / 高估的方向是安全的 / 它是可注入的 Protocol。

### M7 🔥 SSE 流里为什么没有工具返回值

`_ALLOWED_FIELDS` 是**白名单**。`tool.completed` 只有
`tool_call_id / tool_identity / status / error_code / duration_ms`，**没有 result**。

> SSE 直接推到浏览器。一个返回身份证号的工具，
> 它的返回值不能进浏览器的网络日志。
> **白名单对"将来新加的字段"也生效，黑名单只能挡今天想到的。**

### M8 🔥 Run 说自己 WAITING_APPROVAL 但 checkpoint 没了怎么办

`ApprovalReconciliationService`：行锁 `with_for_update()` + `CheckpointProbe`
探测 checkpoint 真实存在性，把两边对齐。

> 追问"为什么不放一个事务里"：checkpoint 是 LangGraph 管的，
> 写入时机不在我的事务边界内。
> **与其假装它们原子，不如承认会不一致并提供对账入口。**
> 这和 UNKNOWN_OUTCOME 是同一个思路。

### M9 🔥 留出集暴露次数那张表是干什么的

`evaluation_experiment_holdout_exposures`。

> 反复用同一个留出集调参，等于把它变成训练集。
> 这是**沉默的**失败——没有任何报错会告诉你"你已经看过 40 次了"。
> 所以我把暴露次数落库。它不阻止你，但它让这件事可见。

### M10 可观测性为什么只有两个纯索引迁移

> 因为 M6 要回答的问题，数据已经在 `agent_runs` / `run_steps` 里了，
> 缺的是查询效率不是数据。
> **如果做可观测要新建一套表，说明原来的领域模型记得不够。**
> 我把这当成一次对前面设计的检验。

### M11 为什么投影函数返回 `BuiltArtifact | None`

> Artifact 是运行的副产物，不是目的。
> 投影遇到没见过的返回结构，正确行为是不产出，
> **不能抛异常把整个故障排查打断。**

### M12 `tool_tail()` 这个小函数为什么存在

工具身份是 `<workspace 前缀>.<工具名>`，投影要按**逻辑名**分派。
> 直接匹配全名的话，换个前缀导入同一个 MCP server，投影就失效了。
> **投影绑定的是"这是什么工具"，不是"它在这里叫什么"。**

## L. 必须提前准备好的三个"故事"

面试官喜欢故事胜过清单。准备这三个，每个 3 分钟：

**故事 1：412 和 7**
一次真实幻觉 → 根因是上下文契约缺失 → 结构性修法写进共享 prompt 常量。
（展示：调试能力、从现象到根因、不用调参糊弄）

**故事 2：那三十行代码**
本可以复用 ProviderCredentialCipher → 但那条路径已冻结 →
共享 master key、独立 ciphertext version。
（展示：知道什么时候不 DRY、风险意识、对"冻结"的尊重）

**故事 3：REPLACE 不在禁用词表里**
SQL 守卫双层设计 → 禁用词在任意位置都拒（因为 `WITH x AS (...) DELETE`）→
先剥注释再分句（因为 `SELECT 1 -- ;\nDROP`）→
但 `REPLACE` 和 `END` 故意不禁，因为它们也是表达式的一部分。
（展示：安全意识 + 对误报的敏感度 + 真读过 SQLite 文档）
