# 02 · 运行时、审批与故障拷打（14 问）

> **2026-10-05 更新口径**：以 [当前状态](../../current-state.md) 和 [收口报告](../../reviews/AgentHub-closure-memory-quality-20261005.md)解释已完成、未知与延期。原始调研/案例保留；功能开发已停止，建议不构成开工计划。

这一篇回答执行可靠性。先区分“模型建议”“业务许可”“动作实际结果”，再讨论恢复。框架背景参照 [LangGraph 官方中断说明](https://docs.langchain.com/oss/python/langgraph/interrupts)：恢复会重新进入中断所在节点，因此中断前代码可能再次运行。以下具体状态与处理属于 AgentHub。

## B01｜一次请求从进入系统到输出，经过哪些环节？

**可这样回答：** API 先解析身份和工作区上下文，再定位已发布版本，创建或准备 Run。运行时加载冻结规格与有效知识/记忆输入，构造经过预算准入的消息和工具定义。模型生成结果后，若提出工具调用，就校验参数、判定治理策略、执行或进入审批；工具观察结果再进入下一轮模型调用。最终保存 Run 状态、输出和用量，并把安全投影事件送给界面。

**继续追问：模型输出一个不存在的工具怎么办？** 调用必须解析到已发布的工具定义，不能让模型任意命名一个函数就执行。参数 schema、保留字段、权限和执行预算也是实际调用前的检查点。

**证据：** [runtime.py](../../../packages/agent_runtime/runtime.py)、[工具 runtime](../../../packages/tools/runtime.py)、[参数校验](../../../packages/tools/validation.py)。

## B02｜LangGraph 在这里到底解决什么？

**可这样回答：** 图让循环、分支和中断位置显式化，checkpoint 给恢复提供状态基础。项目把它封装在 adapter 后面，业务依赖稳定契约。审批记录、动作幂等和外部结果分类仍由业务模块实现。

**继续追问：它的 thread_id 就是用户会话 Thread 吗？** 不应仅凭名字认为相同。用户 Thread 是项目领域对象；框架 checkpoint 的配置身份服务于图状态恢复。解释时要打开 adapter 看具体映射，避免把多轮会话复用和同一次 Run 恢复混成一件事。

**证据：** [LangGraph adapter](../../../packages/agent_runtime/adapters/langgraph/checkpoint.py)、[ADR-006](../../adr/ADR-006-langgraph-checkpoint-persistence.md)、[真实 checkpoint 测试](../../../tests/integration/test_m5a_checkpoint_runtime.py)。

## B03｜工具怎样决定要不要审批？READ 就可以自动执行吗？

**可这样回答：** effect 表示是否产生业务副作用，risk 表示风险级别，approval_policy 表示审批要求，三者分开建模。当前 `ToolPolicy.decide` 的自动通过条件是 `READ + NEVER`；其他组合进入审批要求分支。不能只看 READ，远程只读接口也可能读取敏感信息。

**继续追问：risk 在 decide 里怎么没有单独 if？** 当前函数直接读取已构造的 definition 中的 effect 与审批策略。risk 与组合合法性需要结合工具创建、导入和验证路径查看，不能凭函数注释声称存在一段没写的风险判断。

**证据：** [policy.py](../../../packages/tools/policy.py)、[ToolDefinition 契约](../../../packages/tools/contracts.py)、[工具验证](../../../packages/tools/validation.py)。

## B04｜审批为什么拆决策状态和执行状态？

**可这样回答：** “人批准了”与“动作完成了”是两种事实。决策有 PENDING、APPROVED、DENIED、EXPIRED、CANCELLED；执行有 NOT_STARTED、CLAIMED、SUCCEEDED、FAILED、UNKNOWN_OUTCOME。两维分开才能表达“批准后执行失败”或“批准后结果不明”，不会把批准误显示为业务成功。

**继续追问：Run 和 Approval 是否共享枚举？** 不共享。Run 的 WAITING_APPROVAL 表示整次执行在等人；NEEDS_ATTENTION 表示需要处理。Approval 的 UNKNOWN_OUTCOME 表示具体动作结果不明。它们之间有映射，不能用同一个状态字段替代。

**证据：** [审批状态转换](../../../packages/approvals/contracts.py)、[审批模型](../../../packages/approvals/models.py)、[ADR-009](../../adr/ADR-009-approval-decision-run-status.md)。

## B05｜人工可能几个小时后才批准，线程一直阻塞吗？

**可这样回答：** 等待靠持久状态和 checkpoint 表达，而不是让原 HTTP 请求一直等人。进入审批后可以结束当前交互，界面从持久记录重建“等待中”。之后决策接口记录人类选择，运行服务恢复同一个 Run 的图执行。

**继续追问：为什么不创建一个新 Run 重做？** 重做可能产生不同提议、不同参数和新的动作身份，会模糊“这个人到底批准了哪个动作”。同 Run 恢复保留已经冻结的提议与历史。

**证据：** [审批路由](../../../apps/api/routes/approvals.py)、[runtime.resume](../../../packages/agent_runtime/runtime.py)、[审批集成测试](../../../tests/integration/test_m5a_approval_runtime.py)。

## B06｜两个人同时批准，或者批准和拒绝同时到达？

**可这样回答：** 前端按钮禁用只是体验。服务端决策对审批行加锁，在事务中读取状态、验证权限和有效期、只允许合法终态转换，再持久化决策和审计。后到的请求必须根据已持久化结果处理，不能再次把终态改掉。

**继续追问：行锁是否保证工具只调用一次？** 不保证。决策竞争与动作执行竞争是两个阶段。执行阶段还有 claim 和幂等边界。锁也不能跨越远端 HTTP 系统，外部写调用需要单独说明结果不确定问题。

**证据：** [ApprovalService.decide](../../../packages/approvals/service.py)、[状态域测试](../../../tests/unit/test_m5a_approval_domain.py)。

## B07｜批准和 checkpoint 不是同一事务，崩溃怎么办？

**可这样回答：** 不假设业务表与框架 checkpoint 原子提交。项目用审批对账读取持久状态和 checkpoint 探针，检查运行是否卡在不一致窗口，并按规则恢复、收口或保留需要关注的状态。对账本身也需要幂等、锁和明确的终态规则。

| 失败窗口 | 面试时应说明的处理原则 |
| --- | --- |
| 已写审批，Run/checkpoint 状态未协调完成 | 查业务记录和 checkpoint 的真实情况，避免再提议一个不同动作 |
| 已决定，恢复消息未执行 | 由恢复/对账再次协调；已决定不代表需要再让用户批准 |
| 已 claim，进程失去响应 | 不能仅凭超时认为外部动作没发生；按执行来源与证据判断 |
| Run 等审批，checkpoint 却缺失 | 不能伪造恢复成功；把异常显式暴露并按对账规则处理 |

**继续追问：你用了分布式事务吗？** 没有用一句“强一致”掩盖窗口。这里是持久状态、恢复规则与故障注入的组合；具体各窗口应对照测试，不承诺不存在代码之外的崩溃可能。

**证据：** [reconciliation.py](../../../packages/approvals/reconciliation.py)、[M5 集成测试](../../../tests/integration/test_m5a_approval_runtime.py)。

## B08｜外部写请求已经发出，超时了，为什么不重试？

**可这样回答：** 超时只能说明本端没收到确定结果，不能说明远端没执行。比如工单已创建但响应丢失，再发一次可能创建第二张。所以项目区分发送前失败与发送后结果不明，后者进入 UNKNOWN_OUTCOME，Run 映射 NEEDS_ATTENTION，保留原动作身份供人工或后续对账。

**继续追问：那系统是不是可用性很差？** 这是以避免重复副作用换取人工处理成本。如果远端确实提供可验证的幂等键和结果查询协议，可以设计更自动化的恢复；这是依赖远端契约的增强，不能默认所有 MCP 写工具都具备。

**证据：** [ActionExecutionResult](../../../packages/tools/actions.py)、[MCP runtime](../../../packages/mcp/runtime.py)、[ADR-008](../../adr/ADR-008-tool-side-effect-semantics.md)。

## B09｜你的幂等键是什么，为什么不用模型的 tool_call_id？

**可这样回答：** 逻辑动作身份由 workspace_id、run_id、tool_revision_id、规范参数哈希和 proposal_ordinal 构成，经 canonical hash 再得到确定性 UUID。Provider 的 tool_call_id 不应成为业务动作身份，因为重入或重生成时它可能变化。

**继续追问：同样参数为什么还要 ordinal？** 同一次提议的重复提交应复用身份；但同一 Run 内两次独立提议相同参数，不一定是同一个业务动作。ordinal 保留“是哪一次提议”的区别。不能简单把参数相同等同于永远只执行一次。

**证据：** [compute_logical_action_id](../../../packages/approvals/contracts.py)、[审批创建](../../../packages/approvals/service.py)。

## B10｜能宣称 exactly-once 吗？

**可这样回答：** 需要限定范围。内部创建工单动作在本地事务、唯一幂等键和冲突后回查下，可以实现该业务结果的 effectively-once。消息可能重复投递，执行函数也可能重入。远端副作用缺乏共同事务，项目选择暴露不确定性，不能说全系统端到端 exactly-once。

**继续追问：拿什么证明本地不会双写？** 看唯一约束是否存在、冲突是否 rollback 后回查同一个业务结果、并发集成测试是否验证重复调用。只有进程内 set 或按钮禁用不能作为跨进程保证。

**证据：** [CreateTicketActionExecutor](../../../packages/tools/actions.py)、[工具数据模型](../../../packages/tools/models.py)、[动作测试](../../../tests/unit/test_m5a_actions.py)。

## B11｜队列消息丢了或重复了，知识入库任务怎么办？

**可这样回答：** IngestionJob 的持久状态负责记录工作，队列负责唤醒执行。worker 用条件更新领取 job，生成 lease_token 和过期时间；后续推进验证租约，旧 worker 不能在接管后继续提交状态。对账扫描到期或未投递任务重新协调。失败人工重试还需要重置 attempt_count，否则满次数任务可能一重试就再次失败。

**继续追问：Celery 配上 acks_late 就够了？** 不够。确认策略不能替你定义业务重复执行的安全性，也不能堵住所有进程退出窗口。官方文档也要求任务自行具备幂等语义；项目的 lease 和持久 job 才是业务层依据。[Celery 官方 Tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html)。

**证据：** [claim_ingestion_job](../../../packages/knowledge/ingestion.py)、[知识重试服务](../../../packages/knowledge/services.py)、[重试单测](../../../tests/unit/test_knowledge_retry.py)。

## B12｜SSE 断了，运行就失败吗？为什么不用 WebSocket？

**可这样回答：** 当前客户端主要接收服务器执行事件，SSE 满足单向流式展示；客户端发消息、审批、取消仍走 HTTP。项目已有 Run 后台任务与持久事件机制，让执行可脱离某个浏览器连接。但要区分具体入口和生产组装配置，不能从一个 hub 测试推导所有路径都无限后台运行。

**继续追问：断线能把每个 token 一字不漏重放吗？** 不能。message.delta 不落事件表，持久事件写入也采用有界队列，可在压力下丢弃重放帧。因此重连恢复结构和最终结果，不是保证完整逐 token 动画；业务状态和结果要看 Run/Turn 持久记录。

**证据：** [event_store.py](../../../packages/agent_runtime/event_store.py)、[open_stream/attach_stream](../../../packages/agent_runtime/runtime.py)、[断线测试](../../../tests/unit/test_durable_run_stream.py)。

## B13｜流式输出到一半模型故障，可不可以偷偷切备用模型？

**可这样回答：** 透明 fallback 只允许在首个可见输出之前。已经显示一半再切，会把两个模型的不同回答拼在一起，用户无法分辨出处。网关维护可见输出标志，结合冻结的模型链、能力要求与重试策略决定能否重试或回退。

**继续追问：首字没出之前重试会不会重复工具副作用？** 模型调用的重试和已经执行过的工具动作是不同边界，不能混用一个“失败就重跑”的策略。工具重入必须继续受逻辑动作身份和执行状态保护。

**证据：** [gateway.py 的 `_stream`](../../../packages/model_gateway/gateway.py)、[模型能力解析](../../../packages/model_gateway/profile_resolution.py)。

## B14｜Agent 一直循环调用工具怎么办？取消是否立即生效？

**可这样回答：** runtime 配置对模型轮数、工具次数、重复调用等设置限额，上下文也经过预算准入。项目还有 Run 级成本闸门，但成本依赖可测的用量/价格，不能承诺第一轮就绝不超支。取消是持久请求与执行侧检查配合；关闭客户端流只是停止本地读取，不能替代服务端取消，更不能撤销已经发生的外部副作用。

**继续追问：为什么不直接杀线程？** 杀进程不提供明确业务结果，可能让已发出的外部调用变成不确定。应在可判断状态的位置收口，并把无法确认的结果留给人工。具体是否能中止底层请求还取决于 adapter。

**证据：** [runtime.cancel 与执行守卫](../../../packages/agent_runtime/runtime.py)、[成本边界测试](../../../tests/unit/test_durable_run_stream.py)、[前端取消处理](../../../apps/web/components/apps/app-conversation-pane.tsx)。
