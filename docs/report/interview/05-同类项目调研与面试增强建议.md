# 同类项目调研与面试增强建议

> **2026-10-05 更新口径**：以 [当前状态](../../current-state.md) 和 [收口报告](../../reviews/AgentHub-closure-memory-quality-20261005.md)解释已完成、未知与延期。原始调研/案例保留；功能开发已停止，建议不构成开工计划。

调研日期：2026-10-02；本地基线：`45af049`。本报告用于选择下一轮工作，不表示这些建议已经实现。本轮只查资料、核对代码并整理建议，没有调用付费模型、跑压测或安装调研项目。

## 1. 结论与适用方向

AgentHub 已有版本冻结、工具治理、审批恢复、知识快照、评测门禁和长期记忆。面向后端/Agent 应用工程岗位，我建议下一轮优先补充三类证据：**真实业务效果、跨轮与故障稳定性、质量与成本的对照**。功能优先选失败反馈闭环、工具/证据查看以及一个完整的人工接手流程。

这是基于项目现状和公开实现的判断，不是招聘公司题频统计。平台/后端岗位更适合深讲事务、租户和故障窗口；RAG 岗位更适合检索消融与答案支持度；偏产品工程岗位更需要完整业务流程与用户反馈。未指定岗位时，以下按后端/Agent 应用工程优先排序。

## 2. 调研了哪些相似项目

| 项目/工具 | 与本项目的关系 | 经公开来源确认的能力 | 对 AgentHub 的启发 |
| --- | --- | --- | --- |
| Dify | 相似应用开发平台 | 工作流、RAG、模型管理、Prompt IDE、观测与基于日志/标注的改进 | 看重调试到反馈的完整流程，不必为对标做整套画布 |
| RAGFlow | 相似知识与 Agent 平台 | 模板化分块、分块可视化、引用查看、融合重排 | 补证据查看和分块效果对照，比只增加文件格式更容易证明价值 |
| Langfuse | 相邻观测/评测平台 | trace、评分、人工标注、数据集、实验、CI 回归检查 | 把失败样本转成已校正的测试数据，再验证修复 |
| Ragas | 相邻评测工具 | 检索、faithfulness、工具调用和目标完成等评测范式 | 分层指标，并核对每个指标到底消费什么数据 |
| τ-bench 系列 | Agent 交互基准 | 工具、用户、多轮业务策略与重复运行评测 | 验证业务最终状态和稳定性，不能只看最后一句话 |
| AgentDojo | Agent 安全基准 | 提示词注入攻击与防御评测环境 | 同时记录攻击成功和正常任务完成，避免用全部拒绝换取安全分 |

来源分别为 [Dify 官方仓库](https://github.com/langgenius/dify)、[RAGFlow 官方仓库](https://github.com/infiniflow/ragflow)、[Langfuse 评测说明](https://langfuse.com/docs/evaluation/overview)、[Ragas 指标目录](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)、[τ-bench 原仓库](https://github.com/sierra-research/tau-bench)、[AgentDojo 官方仓库](https://github.com/ethz-spylab/agentdojo)。上述只说明公开能力，不意味着已经部署、实测或审计这些项目。

版本提醒：原 τ-bench 仓库已提示任务旧版及修复版本入口；当前 [后续仓库](https://github.com/sierra-research/tau2-bench) 介绍 τ³-bench。后续若实际接入，需要固定 commit、任务版本和评分规则，不混比不同版本结果。本项目可以借鉴评测思想，不必完整迁移该基准。

## 3. 先识别已有能力，避免重复立项

| 范围 | 本项目当前已有什么 | 真正还值得补什么 |
| --- | --- | --- |
| RAG 指标 | candidate recall@20、final recall@5、MRR@5、引用 precision/coverage | 更大且分层的标注集、当前版本的真实对照、采集有效性检查 |
| 工具评测 | 选择、参数、序列正确率 | 多种合法轨迹、真实业务后置条件、跨轮澄清场景 |
| 治理评测 | 拒绝后执行、越权执行、重复副作用、UNKNOWN_OUTCOME 语义 | 安全攻击集和恢复时延；运行观测不能从 expected 倒推 |
| 质量评分 | `faithfulness` 与补充 `answer_quality` | 前者目前消费 `evidence_support` 布尔值，不是自动逐条断言核验；judge 需要人工校准 |
| 成本/时延 | p50/p95、用量、按币种成本、成功执行成本 | 首字时延、阶段耗时、包含失败浪费的有效任务成本、采样覆盖率 |
| 实验 | 冻结身份、repetitions、成对比较、消融、门禁 | 当前真实业务基线及稳定性汇总；已有 CI 不等于已有真实模型质量门禁 |
| 会话/记忆 | 多轮、停止生成、长期记忆快照、会话历史检索 | 自动化跨轮场景、记忆误用率与开关消融 |

证据：[指标计算](../../../packages/evaluation/metrics.py)、[指标聚合](../../../packages/evaluation/metrics_service.py)、[运行指标](../../../packages/observability/metrics.py)、[实验执行](../../../packages/evaluation/runner.py)、[CI](../../../.github/workflows/ci.yml)、[当前面试手册](README.md)。

必须区分三个层次：**有指标定义 → 有真实观测 → 有能复核的结果**。`DeterministicEvaluationDriver` 会按 expected 构造观测，用于验证流程；它不是模型效果实验。[统一基准 runner](../../../benchmarks/evaluation/runner.py) 也明确写了 deterministic conformance，并标记真实 provider eval 未运行。项目另有真实检索和历史问答材料，因此也不能反过来说“完全没有实测”。

另一个采集边界：当前 `AgentRuntimeEvaluationDriver` 的检索分支保存最终 evidence 的 `chunk_ids`，没有在该分支显式保存完整候选 `candidate_chunk_ids`。指标函数有字段回退，故不能仅凭表上出现 recall@20，就认定它确实测到了候选层召回；要核对对应 driver 或独立检索 benchmark 的数据来源。

## 4. 最值得新增/补齐的功能

以下优先级是本报告建议，工作量为相对估计；未指定工期，也未启动施工。

| 顺序 | 功能 | 最小可交付范围 | 面试能回答的追问 | 代价 |
| --- | --- | --- | --- | --- |
| 1 | 失败反馈到回归数据的闭环 | 绑定 Run/Turn 的评分、失败分类、人工校正；审核后加入 DEV 数据集并重新发布版本；保留来源 | “你怎么发现实际问题，怎么证明修好了？” | 中 |
| 2 | 工具轨迹与证据检查 | 展示工具、耗时、状态、安全参数摘要；引用跳到固定 snapshot/chunk，不读取 LATEST 代替历史 | “答案为什么这样说？到底执行了什么？” | 小到中 |
| 3 | 多轮业务验收器 | 一个客服场景：澄清身份→查规则→提议工单→审批→确认最终状态；检查业务表后置条件 | “回答看起来对，但实际上没完成怎么办？” | 中 |
| 4 | 真实质量回归检查 | 固定小型数据集、两个发布版本、真实 runtime、人工与规则评分、导出可复核报告 | “换模型或 prompt 后退化了没有？” | 中，另有模型费用 |
| 5 | 故障演练与恢复报告 | 在既有故障注入上增加恢复时延、对账发现率、重复副作用次数、最终持久状态记录 | “批准后机器断了，多久能恢复？” | 中 |
| 6 | 人工接手完整流程 | 将已有 handoff 补成分配/接手/关闭；权限、并发冲突、审计和原执行证据保留 | “Agent 不会时业务怎样继续？” | 中到大 |
| 7 | 性能与预算对照 | 补首字/阶段时延采集，固定负载对比冷热请求与不同检索策略 | “效果、速度、成本的取舍依据是什么？” | 中 |

第 2 项可承接已知 T12 快照内联预览和 T31 工具摘要；第 6 项承接 T32。应先定义输出与脱敏契约，再做页面，不把全部工具入参直接写进事件或日志。

反馈闭环借鉴 [Langfuse 的反馈转数据集流程](https://langfuse.com/resources/engineering/user-feedback-to-evaluation-datasets)：差评只是候选信号，不是正确答案，纠正后的输出才适合作为参考。反馈应审核并区分时延、语气、检索和事实错误，不自动污染 HOLDOUT。

轨迹验收应允许不止一条合法工具顺序。当前 `evaluate_tool` 的序列比对偏严格；新的业务验收器可以同时检查必要动作、先后约束、禁止动作和最终业务状态，避免正确的替代路径被全部判错。这是建议增强，不是本轮已经修改评分规则。

## 5. 指标建议：哪些沿用，哪些新增

### 5.1 第一批最值得拿到实测数值的指标

| 指标 | 推荐口径 | 状态/工作重点 |
| --- | --- | --- |
| 业务任务完成率 | 满足人工/规则定义的业务后置条件的任务数 ÷ 纳入评测任务数；报失败、未知及各场景样本量 | 已有 task_success 框架，补业务验收；Run SUCCEEDED 不等于业务成功 |
| Recall@k 与 MRR@k | 使用人工相关/必要证据标注；候选层与最终层分别采集 | 已有，核对真实观测与 top-k 配置 |
| 引用支持度 | 回答中可核验且由引用证据支持的事实断言数 ÷ 已核验事实断言数 | 建议新增细粒度评分，不把“引用 ID 正确”当成“断言正确” |
| 拒答质量 | 无答案样本的正确拒答率；有答案样本的错误拒答率，分别报告 | 在现有 NO_ANSWER 上补双向评测，防全部拒答 |
| 工具选择/参数正确率 | 对应需工具调用的样本，检查身份、关键参数与工作区归属 | 已有，增加多轮/歧义任务 |
| 端到端/首字时延 | p50/p95；首字从请求开始到第一个用户可见文本 delta；无文本输出另报 | 总时延已有，TTFT 建议补采集；不能用 run.started 冒充首字 |
| 有效任务成本 | 本轮全部已知执行成本（含失败/重试） ÷ 业务成功任务数；按币种分开，并报未知用量比例 | 建议新增口径，区别现有“成功执行自身的平均成本” |
| 重复稳定性 | 每个任务独立初始化并执行 3 次，报告单次成功率与三次全成功的任务比例 | 已有 repetitions，需新增明确汇总及实际结果 |

引用支持度可以借鉴 [Ragas Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) 的断言与上下文支持关系，但“忠实于上下文”不等于上下文本身符合外部事实。自动评分仍需人工抽检。

重复稳定性借鉴 τ-bench 的重复评测方向。这里推荐的是直观的“3 次全成功比例”，不直接宣称实现了其 pass^k 估计器，更不能与“k 次里至少成功一次”的 pass@k 混用。每次重置业务状态；避免上一次留下的工单或记忆使后续更容易通过。

### 5.2 体现治理与系统能力的第二批指标

| 指标 | 定义与注意点 |
| --- | --- |
| 重复副作用率 | 有重复业务副作用的逻辑动作数 ÷ 纳入故障演练的逻辑动作数；已有定义，补持久业务证据 |
| 拒绝/越权后执行率 | 分别在拒绝场景与越权场景统计实际副作用；现有统一评测分母与新场景分母要区分命名 |
| 恢复时延 | 从故障被检测或恢复服务就绪的固定时点，到应收口 Run 进入正确持久状态；声明是否包含人工等待 |
| UNKNOWN_OUTCOME 识别质量 | 对已知注入的不确定结果统计正确识别，并看确定失败是否被误判；不可把 unknown 数量越少当作越好 |
| 注入攻击成功率 | 成功触发预定义禁止行为的有效攻击样本数 ÷ 有效攻击样本数；同时报正常任务完成率 |
| 跨租户泄漏/写入次数 | 对造出的真实两租户资源做读/写验证；展示 0/N 与攻击类别，不声称现实风险为零 |
| 记忆误用/保持率 | 应使用历史事实的任务是否正确使用；停用、冲突、越界、过期事实是否被错误使用；对比记忆开/关 |
| 可持续吞吐 | 固定资源、并发、请求类型与观测窗口下的完成任务速率，附 p95、失败率、队列积压和供应商限流 |
| judge 一致性 | 同一人工标注样本上报告 agreement、混淆矩阵，必要时用 Kappa；冻结 rubric、judge 版本及解析失败率 |

安全评测方向参考 [AgentDojo](https://github.com/ethz-spylab/agentdojo) 和 [NVIDIA garak](https://github.com/NVIDIA/garak)。它们提供攻击评测思路；本项目应测完整工具链、文档检索与最终副作用，不能只扫描模型聊天端点就声称 Agent 已安全。

### 5.3 指标的共同验收条件

1. 原始结果带 dataset/version/hash、build SHA、AgentVersion/spec hash、知识/记忆证据、模型与价格、evaluator 版本。
2. 明确 `AVAILABLE / NOT_AVAILABLE / NOT_APPLICABLE`；观测缺失不能填 0、当作没越权或成功。
3. 结果表同时给分子、分母、未知/失败数和场景划分；模型比较优先采用同任务配对。
4. 区分真实模型、真实基础设施、受控 fault injection 与 synthetic driver；不把 conformance 成绩当模型效果。
5. 有至少几个失败样本供翻查；只给平均分和“全绿”无法解释系统。
6. 目标先依据实测基线定，不能直接承诺“准确率 99%”“p95 小于 1 秒”。小样本 0 次攻击成功仍有不确定性。

## 6. 建议的第一轮范围

先以 Support 一条业务链为主，Research 作为补充检索场景，避免同时扩四个应用。以下规模是试验建议，不是统计充分性保证：

- 先整理 60–100 条人工可核验任务，覆盖单跳、多跳、无答案、歧义澄清、审批同意/拒绝、非法身份和故障恢复。
- DEV 与 HOLDOUT 按文档来源/业务模板分组分割，避免只是把同题改写分到两边。冻结发布版本后再开始比较。
- 先试跑 10 条估算费用与耗时，再决定全量；真实调用预算需实际实施时确认，本轮不产生模型费用。
- 正常质量实验与攻击实验分别报告；工具副作用指向隔离测试环境，不能反复操作真实客户数据。
- 第一轮只比较基线与一个候选：例如 rerank 开/关或记忆开/关；两者不要一起改。
- 从现有 runner 出发补真实观测字段、业务验收器和导出，不新建第二套通用评测平台。
- 回归 CI 分层：现有 deterministic 检查保持；真实模型检查单列结果和费用，供应商不可用标记阻塞/未知，不伪装成质量通过。

第一轮完成物建议是：**一个可演示业务流程、一个冻结数据集、一份成对比较报告、三类失败复盘**。质量报告可参照 [Langfuse 的实验与回归检查](https://langfuse.com/docs/evaluation/overview)，但不必因此接入其托管服务。

## 7. 暂不优先增加什么

| 候选 | 暂不优先的原因 | 什么情况下重新考虑 |
| --- | --- | --- |
| 多 Agent/Supervisor | 增加预算、权限、失败传播与恢复复杂度，当前还缺单 Agent 的稳定效果证据 | 有任务分工需求，并能与单 Agent 做同条件对照 |
| GraphRAG | 图构建与维护有成本；没有跨实体关系问题，难证明收益 | 有关系型问题集及检索失败证据 |
| 通用代码执行 | 要处理隔离、资源限制、文件/网络权限和不可确认副作用 | 目标岗位/业务确实需要，可先定义受限契约 |
| 微服务重写 | 增加跨服务一致性窗口，不能直接证明吞吐更高 | 有容量或团队边界证据 |
| 可视化流程编辑器 | 大量 UI 工作会挤压效果和可靠性验证 | 目标是低代码产品，已有明确用户需求 |
| 同时补全部文件格式/业务应用 | 面试难以解释每条链路的效果与失败边界 | 一条业务已验证，新增格式有真实使用需求 |

这些是优先级判断，不是断言它们没有价值。模板库、复制按钮、Dashboard 排版仍可改善展示，但对本项目的技术深挖，优先级低于真实效果、恢复、安全和成本证据。

## 8. 最终怎样讲到简历和面试里

只有实际完成后，才能填写以下模板：

> 在〔N 个冻结任务、模型/硬件/数据版本〕上，对比〔基线/候选〕，任务完成率从〔a〕变化到〔b〕，p95 为〔t〕、有效任务成本为〔c〕；通过〔故障窗口〕演练记录重复副作用〔x/N〕。发现主要失败来自〔真实原因〕，用〔修复〕在 HOLDOUT/回归集验证，并保留〔未解决边界〕。

不要填写虚构数值。相比“支持多个 Agent、接入很多模型”，这段话能自然接上：为什么这样设计、如何测量、怎样归因、什么失败仍未解决。
