## 0. 这四件事为什么放在一次做

它们表面上是四个独立功能，实际上是**同一类缺陷的四个切面**：

> 某个本应是「系统的性质」的东西，悄悄变成了「某一次 HTTP 请求的性质」。

| | 本应属于 | 实际属于（修复前） |
|---|---|---|
| A1 | Run 的生命周期 | 那条 SSE 连接的生命周期 |
| A2 | Run 的执行位置 | 恰好接到请求的那个 API 进程 |
| B | 实验的可比性 | 「跑的时候 judge 配的是哪个模型」这个没人记录的事实 |
| C | Agent 版本的预算约束 | 没人约束，靠事后看账单 |

所以四项共用一条叙述主线，面试里可以当一件事讲：
**把隐式绑定在请求/进程/时刻上的东西，显式地冻结或持久化到系统里。**

## 1. A1：断连不再中止 Run，并支持 `?after_sequence=N` 补播

### 1.1 修复前的缺陷

`POST /agent-versions/{id}/runs/stream` 是在 **SSE 响应生成器内部**驱动整个执行的。
客户端断连 → 生成器被取消 → `abort_if_active()` 被调用 → Run 直接终止。

也就是说：**一次 Run 就等于一次 HTTP 请求。** 关标签页 = 杀任务；网络抖一下 = 前功尽弃。
这跟 06 章里「Run 的生命周期由 checkpoint 定义」的说法是直接冲突的，面试里会被当场抓住。

### 1.2 落地方案

新增三块：

| 文件 | 职责 |
|---|---|
| `packages/agent_runtime/stream_hub.py` | `RunStreamHub` / `RunStreamRegistry`：**Run 由 hub 拥有，不由当前正在读它的人拥有** |
| `packages/agent_runtime/event_store.py` | 事件落库与回读（`should_persist` / `_event_from_row` / `RunEventReader`） |
| `migrations/versions/0027_agent_run_events.py` | `agent_run_events` 表，按 `(run_id, sequence)` 有序 |

对外新增一个端点：

```
GET /api/v1/workspaces/{workspace_id}/agent-runs/{run_id}/stream?after_sequence=N
```

`after_sequence` 是客户端**最后看到的那个 `sequence`**；服务端先从持久日志里把之后的补播完，
再无缝接回在线流。在线与重连走的是**同一条代码路径**，不是两套。

### 1.3 三个刻意的设计决定

**① 补播数据源用新表，不用现成的 `run_steps`。**
附录 A 原文写的是「补播数据源 ✅ `run_steps`」，实现时推翻了。
理由：`run_steps` 记的是「步骤」，不是「发给客户端的那条事件」。
拿它补播，重连客户端拿到的流的**形状**跟首次连接时不一样——补播出来的是步骤记录，
不是原始事件。代价是多一张表和一次迁移；买到的是「重连拿到的流与首次连接逐字节同构」。

**② 跨进程扇出不用 Redis pub/sub，而是 tail 这张有序日志。**
附录 A 原文写的是「API 退化成 Redis pub/sub 的订阅端」，实现时也推翻了。
理由：**有序持久日志本身已经保证了顺序和恰好一次**；再叠一条投递保证更弱的 pub/sub 通道，
等于给同一份数据造两条语义不同的路径——出问题时第一件事得先判断是哪条路径的错。
Redis 仍然是 Celery broker（投递「该干活了」这个信号），但**不承担数据扇出**。

**③ `message.delta` 故意不落库。**
落 delta 会让日志体积变成 O(tokens)，而买到的只是一个打字动画。
因此 `sequence` 是**游标不是计数**，补播时出现跳号是正常的。
这一点写进了 `events.py:190` 的注释和 `docs/api-contracts.md`，
否则后来的人一定会把跳号当 bug 修。

### 1.4 宽限期而不是「永不中止」

「没人看了」终究还是要结束 Run，只是不能**立刻**结束：

- `AGENTHUB_RUN_STREAM_GRACE_SECONDS`（默认 `60`）内没有任何订阅者 → 中止；
- 窗口内重连 → 中止被取消；
- **detached（worker 里跑的）Run 永不因为「没人看」被中止**——在 worker 里没人看是常态，不是被遗弃。

## 2. A2：执行移进 Celery worker，API 退化成跟读端

### 2.1 落地方案

| 文件 | 内容 |
|---|---|
| `apps/worker/tasks/agent_runs.py`（新） | `agenthub.execute_agent_run` 任务，`acks_late=True` + `reject_on_worker_lost=True` |
| `packages/agent_runtime/queue.py`（新） | `AgentRunQueue` Protocol + `CeleryAgentRunQueue` |
| `apps/worker/celery_app.py` | 注册新任务模块 |
| `apps/api/knowledge_dependencies.py` | `get_agent_run_queue` 依赖 |
| `apps/api/routes/agent_runs.py` | 开关打开时：入队 → 自己变成普通跟读者 |

路由里的分叉只有六行：

```python
if request.app.state.settings.run_execution_in_worker:
    await queue.enqueue(workspace_id=..., run_id=prepared_run.id, request_id=...)
    stream = service.attach_stream(context, run_id=prepared_run.id)
else:
    stream = service.stream(...)
```

注意 `attach_stream` 就是 A1 给重连用的那个方法——**发起请求的客户端和重连的客户端，
拿到的是同一种流，没有谁是特权连接。** 这是 A1 先做的直接红利。

### 2.2 两个安全/正确性决定

**① 队列消息不是授权。**
worker 收到的只有 `workspace_id / run_id / request_id` 三个字符串，
权限一律用 `TenantService().get_workspace_access(...)` **从数据库重新推导**。
否则任何能往 broker 里塞消息的人就等于能越权执行 Agent。

**② worker 里的服务组装必须和 API 完全一致。**
`_build_service` 逐项对齐了 `apps/api/agent_runtime_dependencies.py`，
包括 `thread_context_provider` 和 `artifact_recorder`。
代码里留了注释说明原因：
*「一个 Run 不能仅仅因为被哪个进程捡起来，就丢了它的会话历史、或者不再记录 artifact。」*

### 2.3 为什么默认关闭

`AGENTHUB_RUN_EXECUTION_IN_WORKER` 默认 `false`。
Playground 是**单次调试**场景，要的是最短时延和确定的进程内行为；
把它改成「入队 → 等 worker 捡起来 → 跟读」会平白多一跳。
约束里明确写了「`thread_id IS NULL` 的 Run 必须逐字节同于从前」，这个开关就是兑现它的方式。

### 2.4 踩到并修掉的坑

worker 里 `run` 对象是在 `async with factory() as session:` 里加载的，
但 `run.input_text` 在块外才被读 → SQLAlchemy detached 实例懒加载失败。
修法：在 session 内把需要的标量先取出来，并显式 `session.expunge(run)`，
注释写明「让它带着已加载的属性脱离 session：这个对象要活过这个 session」。

## 3. B：LLM-as-judge，且 judge 本身被冻结和版本化

> 这一项由子 agent 完成主体，我补完了最后一段 API/worker 接线，并追加了 manifest 回读的安全校验。

### 3.1 定位：judge 是补充，不是替代

确定性评测器（exact match / citation / tool / approval / failure / retrieval）仍然是**主**。
judge 只对**确定性评测器根本没法打分**的开放式输出产出一个补充指标 `answer_quality`
（调研综述、故障分析、数据解读这类）。
只有 `expected["open_ended"] is True` 的数据项才会被送给 judge。

### 3.2 核心设计：judge 像 AgentVersion 冻结模型那样被冻结

`FrozenJudgeProfile.projection()` 把「provider / model / temperature / max_tokens /
timeout / profile_id / credential_ref / rubric」这份**非机密投影**规范化后哈希，
取前 16 位得到 `evaluator_version = "jv1-<16hex>"`（20 字符，正好塞进现有的 `String(32)`）。

于是：

> **换了 judge 模型 → evaluator_version 变了 → 现有的
> `evaluator_version_mismatch / NOT_COMPARABLE` 守卫直接拒绝把两次实验放在一起比。**

这是复用既有守卫（`metrics_service.py:207`），不是新造一套。
不换 judge 就不会触发，历史实验的 manifest 没有这个 key，读作 `disabled`，照常验证通过。

### 3.3 我补完的部分

**① API 接线。**
`POST /evaluation/experiments` 新增可选 `judge_model_profile_id`
（`extra="forbid"` 保持不变）。路由里走**和 Agent 发布完全相同的解析路径**
（`SqlAlchemyModelGatewayRepository` → `ModelProfileResolver` → 取 provider credential），
再 `freeze_judge_profile()` 冻进实验。

权限上**没有新增任何 RBAC permission**：选 judge 是「定义实验」的一部分，
复用既有的 `evaluation_manage`。并且权限检查提前到解析之前——
否则一个没有 `evaluation_manage` 的调用方能通过错误码差异探测出某个 model profile 是否存在。

**② manifest 里补存投影，worker 按 manifest 重建 judge。**
原来 manifest 只存版本号字符串，worker 无从重建一个能真正调用的 judge。
现在有 judge 时额外存 `judge_profile`（非机密投影，`credential_ref` 是 id 不是密钥），
没有 judge 时**这个 key 根本不出现**——历史 manifest 和它们的哈希完全不动。

worker 侧 `_build_judge()` 从实验的 manifest 重建，而**不是**拿 `model_profile_id` 重新解析：
profile 从实验创建到现在可能已经被人改过，用改过的 profile 打分的实验，
就不是它自称的那个实验了。

**③ 重建后必须自证身份。**
`judge_profile_from_manifest()` 重建完会**重新投影、重新哈希**，
必须等于 manifest 里存的那个版本号，否则抛 `EVALUATION_JUDGE_MANIFEST_INVALID`。
一份「投影已经算不出自己那个版本号」的 manifest，说明它被改过或 rubric 漂移了；
照样打分就会把两个不同 judge 的裁决归到同一个版本号下——那正是冻结 judge 要防的事。
为这条加了 3 个参数化的篡改用例（删投影 / 改模型 / 改 rubric 权重），全部拒绝。

**④ 会话作用域的 judge transport。**
gateway 是 session 作用域的，而一次 Run 可能跑几分钟。
`_SessionScopedJudgeClient` 每次调用才开一个短 session，避免为了「最后打个分」
把一条连接空占整场。密钥全程不经手——gateway 自己解密 `provider_credentials`。

### 3.4 不落库的东西

只存 rationale 的**哈希**，不存文本；observation 里仍然只有分数、身份和哈希，
不含被评判的正文。与既有的 `safe_observation_hash` 纪律一致。

### 3.5 无需迁移

judge 身份全部落在既有 JSONB 字段里
（`evaluation_experiments.evaluator_manifest`、`evaluation_experiment_case_results.observation`）。
**没有新增迁移，Alembic 仍然单 head（`0027_agent_run_events`）。**

## 4. C：单次 Run 成本上限

### 4.1 表示法：整数 micro-USD

`runtime_config.max_cost_micro_usd`，整数，范围 `1 ~ 100_000_000`（上限 USD 100/次）。

**为什么不用浮点美元**：这个值会被冻进已发布的 AgentVersion 并参与哈希。
整数只有一种表示，浮点有好几种——`0.05` 和 `0.050000000000000003` 会算出两个 spec hash。
一个「同样的配置却哈希不同」的发布系统，它的可复现性承诺就是空的。

`None`（不填）= 不设上限 = 所有在这个字段存在之前发布的 Agent 的现状，行为完全不变。

### 4.2 检查时机：在模型调用之前

守卫放在 `_AgentRunGraph.model()` 里 `max_steps` 守卫的紧后面，**调用前**判断。
注释写的理由：

> *一个只能在超支之后才发现超支的上限，是一份报告，不是一个上限。*

### 4.3 终止状态：复用 `NEEDS_ATTENTION`，不新造状态

超限不是 `FAILED`——**什么都没坏**。
是预算耗尽，需要人来决定「加预算继续」还是「放弃这次」。
`NEEDS_ATTENTION` 正是既有的这个语义，通过 graph 终态里既有的 `run_status` 钩子设置
（和 `runtime.py:310`、`:838` 用的是同一个机制），没有新增 Run 状态、没有新增迁移。

两个失败码：

| 码 | 含义 |
|---|---|
| `AGENT_COST_LIMIT_EXCEEDED` | 已计量花费达到上限 |
| `AGENT_COST_UNMEASURABLE` | 花费无定价或非 USD，上限**无法**被执行 |

第二个是刻意的：如果某个 provider 没有定价、或者记的是别的币种，
「装作没事继续跑」等于这个上限在**悄悄失效**——
*一个静默失效的上限，读起来像一个保证，实际什么都不保证。*
所以宁可停下来。

### 4.4 发布期校验

`publish.py` 的 `_validate_runtime_config` 里显式把 `max_cost_micro_usd` 从标量循环里摘出来单独校验
（因为它允许 `None`，而其他限额不允许），拒绝 `0 / 负数 / bool / 浮点 / 字符串 / 超上限`。
`bool` 要单独拦是因为 Python 里 `isinstance(True, int)` 为真——
`max_cost_micro_usd: true` 会被当成 1 micro-USD 悄悄通过。

## 8. 一句话总结

四项都不是加功能，是**把四个「碰巧还能工作」的隐式绑定，改成显式的、可验证的系统性质**：
Run 的生命周期属于 Run（不属于连接），执行位置属于配置（不属于恰好接到请求的进程），
评测的可比性属于被冻结的 judge 身份（不属于跑的时候的配置），
预算属于被冻结的 Agent 版本（不属于事后的账单）。
