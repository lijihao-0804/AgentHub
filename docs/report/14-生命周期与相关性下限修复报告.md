## 0. 先更正 6 章里两处不准确的说法

写在最前面，因为这两条是**我自己先前写错的**，不更正会误导后面所有判断。

### 0.1 「文档生命周期完全没有进数据模型」——措辞不准确

`DocumentRevision.lifecycle_status`（`ACTIVE` / `RETIRED` / `DELETED`）**一直存在**，
在 `packages/knowledge/snapshots.py:180` 构建快照时被消费。

它管的是**同一份文档的某个修订版**退役。真正缺的是**另一件事**：
`password-policy-v1.md` 和 `password-policy-v2.md` 是 `documents` 表里
**两行完全独立的记录**，之间没有任何关联字段。

所以准确的说法是：**缺的是跨文档的 supersession 关系**，不是「生命周期完全没建模」。
这个区别很重要——它决定了修复应该加在 `documents` 上而不是 `document_revisions` 上。

### 0.2 「负例正例空档 1.77，阈值完全可行」——数算错了

原表格拿的是**正例 top-1 分**的最小值 +1.8760 当下界。
但相关性下限砍的不是 top-1，是**返回的每一条证据**。

按「一个问题真正需要的文档中，分数最低的那条」重算：

| | 分数 | 来源 |
|---|---|---|
| 最难的**可答**问题 | **+0.1483** | QA-060「员工应向哪里报告可疑安全事件」 |
| 最强的**不可答**问题 | **+0.1038** | QA-082 |
| **真实窗口** | **0.0445** | ——不是 1.77 |

差了 40 倍。按 1.77 的说法取一个「明显安全」的 1.0，实测**静默丢掉 3 个可答问题**
（见 §3.2）。这条更正已经写回 `settings.py` 的注释里，因为那里是别人真正会照着标定的地方。

## 1. 缺口一：跨文档 supersession

### 1.1 数据模型

`documents` 表新增两列 + 一个自引用外键 + 一条 CHECK：

```python
effective_date: Mapped[date | None] = mapped_column(Date, nullable=True)
superseded_by_document_id: Mapped[UUID | None] = mapped_column(SQLUuid(as_uuid=True))

ForeignKeyConstraint(
    ["superseded_by_document_id"], ["documents.id"],
    name="fk_documents_superseded_by", ondelete="SET NULL",
)
CheckConstraint(
    "superseded_by_document_id IS NULL OR superseded_by_document_id <> id",
    name="ck_documents_supersession_not_self",
)
```

几个刻意的选择：

**用单列外键，不用复合外键。** 复合外键（带 `workspace_id`）配 `ON DELETE SET NULL`
会把 `workspace_id` 一起置空，而它是 `NOT NULL`——删一份文档就会炸。
「后继必须在同一个知识库」这条规则因此移到 Service 层做，而不是靠数据库约束。

> **更正（2026-09-22）**：上面这段的**理由是错的**，虽然结论我保留了。
>
> PostgreSQL 15 起 `ON DELETE SET NULL` 可以**指定只置空哪一列**：
> `ON DELETE SET NULL (superseded_by_document_id)`。所以复合外键并非「配
> `SET NULL` 就必炸」，只是必须把列名写出来。我当时不知道有这个语法，
> 于是把一个「写法问题」当成了「不可行」。
>
> 更难堪的是：同一个误解在别处真的酿成了缺陷。`agent_runs.thread_id` 等
> **四个**复合外键当时就是按不带列名的 `SET NULL` 建的，结果「删掉任何一个
> 跑过的会话」必然 `NotNullViolation` 500——这个 bug 一直活到迁移
> `0029_set_null_columns` 才被修掉（见 19 章 §5.2）。
> 现在有 `tests/unit/test_set_null_scopes_to_column.py` 扫元数据兜底。
>
> 那为什么这里仍然保留单列外键？因为对**文档后继**这条关系，
> 「后继必须同库」本来就比「后继必须同工作区」更严，复合外键只能保证后者，
> Service 层那道检查无论如何都省不掉。所以这是一个**取舍**，
> 不是一条被数据库逼出来的唯一解——原文把取舍写成了必然，这是要改的地方。

**partial index。** 只有 11/60 文档有后继，全列索引是浪费：

```python
postgresql_where=sa.text("superseded_by_document_id IS NOT NULL")
```

迁移 `0026_document_lifecycle`（`down_revision = "0025_thread_kind"`），
升降级往返已验证。注意 `alembic_version.version_num` 是 `varchar(32)`，
revision id 不能超长——这是个踩过的坑。

### 1.2 写入路径

新增 `PATCH /workspaces/{ws}/knowledge-bases/{kb}/documents/{id}`，
落在既有的 `knowledge_edit` 权限上——**没有新增任何 RBAC permission**。

请求体 `extra = forbid`，且空对象 `{}` 返回 422。

`None` 有两种含义，必须区分开：

| 请求 | 含义 |
|---|---|
| `{"superseded_by_document_id": null}` | **清除**这个关系 |
| 请求体里根本没这个字段 | **不动**它 |

实现上靠 Service 层的 `set_effective_date` / `set_superseded_by` 两个布尔标志，
路由层用 `"effective_date" in payload.model_fields_set` 推导。

错误语义：

| 情况 | 响应 |
|---|---|
| 文档不存在 / 不在本 workspace | 404（不泄漏存在性） |
| 后继在另一个知识库 | 404 |
| 自己指向自己 | 422 `INVALID_DOCUMENT_SUPERSESSION` |
| 唯一约束冲突 | 409 `DOCUMENT_LIFECYCLE_UPDATE_FAILED` |

每次成功写入追加一条 `document_lifecycle_update` 审计。

### 1.3 读取路径

supersession 是从 `_load_chunks` 里 `documents` 的 join **实时读**的，
不是从冻结的快照里读。所以改完生命周期数据**不需要重建快照**——
这一点对运维很重要，否则每次标记一份文档退役都要重新切一次 embedding。

每条证据的 metadata 新增四个字段：

```
document_name, effective_date (ISO 字符串或 None),
superseded (bool), superseded_by_document_id (str 或 None)
```

`search_knowledge` 工具结果里带前三个，**故意不带 `superseded_by_document_id`**——
一个裸 UUID 对模型没有任何可操作价值，只会占 token。

## 2. 缺口二：相关性下限

### 2.1 实现

```python
floor = (query.min_rerank_score if query.min_rerank_score is not None
         else self.min_rerank_score)
if floor is not None:
    kept = [item for item in ranked if item[1] is None or item[1] >= floor]
    dropped_below_floor = len(ranked) - len(kept)
    ranked = kept
```

三个关键决定：

**只在有 rerank 分的时候生效。** `item[1] is None` 那一支是必须的：
纯 HYBRID 策略下分数是 RRF 融合分，是个**排名统计量**，量纲跟 rerank 分完全无关。
拿 rerank 标定的阈值去砍 RRF 分，会把每一次 HYBRID 查询清空。
这条单独写了一个单测锁住。

**trace 里保留被砍掉的块。** `rerank_trace_results` 是**下限生效前**的。
这是故意的——只有看得见「被砍的那条是多少分」，才可能从真实 query 标定出该取什么值。
同时 `RetrievalTrace.dropped_below_floor` 记下砍了几条，
这样「空证据」和「索引挂了」在排查时能区分开。

**默认关闭。** 理由见 §3.2，实测证明这个值的可用窗口窄到不适合给默认值。

## 3. 实测结果

环境：60 文档 / 233 chunk，snapshot `bffe88bc`，bge-m3 + bge-reranker-v2-m3，
34 个决定性用例（negative 10 / version_sensitive 14 / ambiguous 10）。

先把语料自带的生命周期数据灌进新字段——`metadata.jsonl` 里**本来就写着**
`effective_date` / `retired` / `superseded_by`，正好是新建模的那几个字段：

```
patched 60 documents, 11 of them superseded
```

### 3.1 五种配置的横向对比

| 配置 | 版本题 top-1 | 版本题 @6 | 歧义题≥2候选 | **负例空返回** | 歧义题误杀 |
|---|---|---|---|---|---|
| penalty=0 floor=off（基线） | 6/14 | 14/14 | 10/10 | 0/10 | 0/10 |
| penalty=2 floor=off | 5/14 | 14/14 | 10/10 | 0/10 | 0/10 |
| penalty=2 floor=0.5 | 5/14 | 11/14 | 7/10 | 10/10 | 1/10 |
| penalty=2 floor=1.0 | 5/14 | 11/14 | 4/10 | 10/10 | 1/10 |
| **penalty=0 floor=0.13** | **6/14** | **14/14** | 9/10 | **10/10** | **0/10** |

结论很干净：**penalty=0 + floor=0.13** 是唯一一个
「负例全拒 + 正例零损失 + 歧义题零误杀」的配置。
代价只有一处：一个歧义题从 2 个候选掉到 1 个。

### 3.2 相关性下限：窗口比预想窄 40 倍

floor=1.0 时负例确实 10/10 全拒，但同时：

| 被砍掉的期望文档 | 分数 |
|---|---|
| QA-041 `api-changelog-v2` | +0.480 |
| QA-059 `api-changelog-v2` | +0.467 |
| QA-060 `acceptable-use-policy-v1` | +0.148 |
| QA-034 `employee-handbook-v1` | −0.809 |
| QA-036 `refund-policy-v1` | −0.228 |

其中 **QA-060 整个查询被清空**——而「员工应向哪里报告可疑安全事件」
是一个语料**完全答得了**的正常问题。它最好的一条证据只有 +0.148，
离负例上界 +0.1038 只差 **0.0445**。

这就是 §0.2 那条更正的来源，也是**默认关闭**的直接理由：
可用窗口 0.04 宽的东西，不能当常量发布。

### 3.3 supersession 惩罚：常量做不了这件事

penalty=2.0 修好了 2 例，**打坏了 3 例**：

| 用例 | 问的是 | 结果 |
|---|---|---|
| QA-037「**current** SLA」 | 现行版 | ✅ 修好 |
| QA-039「effective **2025-12-01**」 | 现行版 | ✅ 修好 |
| QA-040「Under the **retired** policy」 | **退役版** | ❌ 打坏 |
| QA-079「**2025 版**中文客户 SLA」 | **退役版** | ❌ 打坏 |
| QA-080「部署指南 **v2**」 | **退役版** | ❌ 打坏 |

这不是调参能解决的。看分数差：

| 用例 | 想要 | 退役文档分 | 后继分 | 差值 |
|---|---|---|---|---|
| QA-037 | 现行 | 4.87 | 3.80 | **1.07** |
| QA-039 | 现行 | 5.64 | 5.54 | **0.10** |
| QA-040 | 退役 | 3.15 | 2.28 | **0.87** |
| QA-079 | 退役 | 5.46 | 5.31 | **0.15** |
| QA-080 | 退役 | 5.63 | 3.80 | **1.83** |

「想要现行」的差值是 1.07 和 0.10，「想要退役」的是 0.87、0.15、1.83——
**完全交错，任何阈值都切不开**。

原因很直白：**判断用户要哪个版本的信号在问题里，不在文档里。**
排序层只看得见文档，看不见问题。这是个结构性限制，不是参数没调好。

### 3.4 两个设置还会互相破坏

更糟的是它们不能同时开：

| 配置 | 最难可答题 | 最强负例 | 真实间隔 |
|---|---|---|---|
| penalty=0 | +0.1483 | +0.1038 | **+0.0445** |
| penalty=2 | **−0.8086** | +0.1038 | **−0.9124** |

惩罚把「正确但已退役」的证据**压到了负例底下**，
于是相关性下限赖以工作的那条分界线直接反号，
24 个可答用例里有 2 个变成**任何阈值都救不回来**。

所以 `eb6b8fb` 在 `settings.py` 里明确写了：这两个不要一起开。

### 3.5 真正管用的是：把生命周期交给模型

既然信号在问题里，那就交给唯一看得见问题的那一层。
`search_knowledge` 每行现在都带 `superseded` 和 `effective_date`。

拿排序层做不到的那 5 个用例直接问 Agent（DeepSeek，各自独立 thread）：

| 用例 | 要求 | 结果 |
|---|---|---|
| QA-037 | 现行 SLA 可用性 | ✅ 99.9% |
| QA-039 | 2025-12-01 生效的最小密码长度 | ✅ 14 |
| QA-040 | 退役策略的轮换周期 | ✅ 90 天 |
| QA-079 | 2025 版 P1 首响 | ✅ 4 个工作小时 |
| QA-080 | 部署指南 v2 的数据库连接 | ⚠️ 拒答（见下） |

**4/4 答对**，而且模型明确是**照着新字段推理**的：

> The current SLA policy is **sla-policy-v2** (effective 2025-10-01, status ACTIVE)...
> The older **sla-policy-v1** committed to 99.5% monthly uptime, but it was
> **retired on 2025-09-30** and superseded by v2.

注意它**主动对比了两个版本**并说明为什么不采用旧的——这恰恰是版本感知系统
应该给出的答案形态。排序层惩罚做不到这个，因为它只会把旧文档藏起来。

QA-080 那一例是**人设范围问题，不是检索问题**。Agent 原话：

> **What I did not do:** I did not search the knowledge base, because it's a
> published customer-support snapshot, not an engineering documentation store.

语料横跨 HR / 安全 / 工程，但绑的是客服人设的 Support Agent，
所以工程类问题被挡在检索之前。**行为本身是对的**（没有编造），
只是让这一例**结论不成立**，而不是「失败」。

| negative 拒答 | **10/10**，0 编造 |

## 4.5 复查时又发现的两个缺口（已修）

上面那轮改动做完之后，我拿真实的 60 篇企业语料库又走了一遍「人能看到什么」，
发现**写得进去、读不出来**：11 篇文档已经被 PATCH 标了 supersession，
但没有任何一个读取面能显示这件事。两个都是我上一轮漏掉的，和清理数据库无关。

**① 文档列表接口不返回新字段。**
`GET .../knowledge-bases/{id}/documents` 走的是
`KnowledgeDocumentManagementResponse`，这是一个**独立于 `DocumentResponse` 的
投影**，只带 `current_revision_*`（那是**某一版**的 lifecycle_status，
不是跨文档的 supersession）。实测 60 篇文档全部显示 `superseded=0`。
已在 schema 和 `_document_projection` 里补上 `effective_date` /
`superseded_by_document_id`。

**② 检索 playground 把 metadata 整个丢了。**
`RetrievalPlaygroundEvidence` 只取到 `snippet` 为止，
调用时直接 `KeyError: 'metadata'`。这一条比①更要紧：
playground 是**人工标定 `knowledge_min_rerank_score` 的唯一界面**，
而 3.2 已经证明这个阈值的可用窗口只有 0.04——
看不到哪篇是退役文档，就根本标不了。

有一处是刻意做的不一致：playground **保留了后继文档的原始 UUID**，
而 `search_knowledge` 工具结果里不给。因为读者不同——
裸 UUID 对模型是噪声，对人却正是「我要去打开哪一篇」的答案。

两个面都补了回归测试：

| 文件 | 用例 |
|---|---|
| `tests/integration/test_document_lifecycle.py` | `test_the_document_listing_shows_a_document_was_superseded`（顺带断言后继文档**不**被标成退役） |
| `tests/unit/test_knowledge_m3d_playground.py` | `..._evidence_carries_document_lifecycle` / `..._of_a_live_document_is_not_marked_superseded` |

集成 8 passed、playground 单测 7 passed、`ruff check .` 干净。

> 顺带一提：这轮复查还清掉了 16 个历史里程碑验收留下的 scratch PostgreSQL 库
> （释放 202.3 MB）。保留 `agenthub`（在用）、`agenthub_test`（CI 和 M1 文档引用）、
> `postgres`（系统库）。上面两个缺口是清库之后复查现网时发现的，**不是清库造成的**。

## 5. 测量过程中自己踩的三个坑

这三个都是**我的测量工具错了**，不是产品错了。写下来是因为它们各自都一度
给出了会误导决策的数字。

**① 倒挂指标本身是错的。** 原脚本把「退役文档排第一」记为倒挂，
但 QA-040 / QA-079 / QA-080 里退役文档**就是正确答案**。
换成「top-1 是否等于 golden 期望」之后，数字才有意义。

**② Agent 结果全空。** `POST /turns` 是异步返回的，
`output_text` 当场是 `null`，答案在 run 的 `final_output` 上。
第一轮测出来 0/5，实际上 4/5 是对的——改成轮询 run 状态才拿到真实结果。

**③ 拒答正则漏判。** negative 一度测出 8/10，
查下来 QA-052 / QA-082 是**完全合格的拒答**（"nothing found answers the question"、
"I won't guess at a date"），只是措辞不在正则里。补齐后确认 10/10。

## 6. 结论

| 缺口 | 状态 |
|---|---|
| 跨文档 supersession 未建模 | ✅ 已修（模型 + 迁移 + API + 审计 + 检索 + 列表/playground 读取面） |
| 检索无相关性下限 | ✅ 已修（默认关闭，窗口已实测标定） |

但更实在的结论是两条**负面结果**：

1. **排序层惩罚解决不了版本选择**——信号在问题里，不在文档里。
   已实测证伪，并写进配置注释防止后人再试。
2. **相关性下限的可用窗口是 0.04，不是 1.77**——我先前的算法错了，
   已更正。它可用，但必须按「最弱的那条需要的证据」标定，不能按 top-1 标。

真正把版本选对的是**把生命周期信息交给模型**（4/4），
而不是在排序层做文章（2 对 3 错）。
