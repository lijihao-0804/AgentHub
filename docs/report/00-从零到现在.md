# 00 · 从零到现在：做了什么，以及为什么是这个体量

> 其余 14 章都是**横切面**：架构怎么分层、机制怎么实现、应用怎么复用、证据怎么取得。
> 横切面有一个共同的盲区——读完之后仍然可能答不上最朴素的那个问题：
>
> **「你到底为什么需要这么多东西？」**
>
> 这一章是**纵切面**。它按因果顺序走一遍：每一块是被什么问题逼出来的，
> 做完之后又暴露了什么，从而不得不做下一块。
> 它是全书的主干，其余各章是主干上的展开。

---

## 1. 起点：一个判断，而不是一个功能清单

整个项目建立在一句判断上：

> **Agent 产品的难点不在模型，在治理。**

这句话不是口号，它是可以被证伪的，而且它决定了要建什么：

| 如果难点在**模型** | 如果难点在**治理**（本项目的判断） |
|---|---|
| 正确做法是等模型变强，自己少写点代码 | 正确做法是建运行时和控制平面，模型是可替换零件 |
| 核心资产是 prompt 和 few-shot | 核心资产是**可审计的领域模型** |
| 衡量标准是「答得准不准」 | 衡量标准是「三天后能不能解释当时为什么这么做」 |
| 体量应该很小 | 体量必然不小 |

**本项目全部的体量，都来自后一列。** 如果你认为第一列是对的，那这个项目就是过度工程；
这一章后半程会给出我自己认为溢出的部分，但主干是清醒选的。

四个被反复回到的真实痛点（01 章展开）：不可解释、不可控、不可复现、会编。
它们分别对应四个不变量：**发布即冻结、工具即数据、审批是持久中断、模型永不写产出物**。

## 3. 主干：七幕，每一幕是一个「不得不」

每一幕的写法固定为三段：**上一幕留下什么答不了的问题 → 因此必须建立什么不变量 →
做完又暴露了什么**。这条因果链就是「为什么这么多」的答案本身。

---

### 第一幕 · 地基（M0 → M2）

#### M0 语义基线 — 为什么第一个迁移一张业务表都不建

`0001_m0_semantic_baseline.py` 只建了一张表：`agenthub_schema_meta`，
记录语义版本与 API 契约版本。

**为什么值得单独一个里程碑**：因为一旦开始建业务表，「这套语义是第几版」就再也补不回来了。
后面 M7 的可复现性、3A 的契约冻结，全都要引用一个**在第一天就存在**的版本坐标。
这是典型的「不这么做，后面无法回头」的决定。

#### M1 认证与多租户 — 隔离必须先于第一张业务表

`0002` 一次建 7 张表：Organization / Workspace / User / 成员关系 / 角色 / 审计。

**为什么不能往后放**：workspace 隔离如果是后加的，它就只能是**查询条件**；
只有在第一张业务表之前建立，它才能成为**所有表的强制列**。
项目里的硬约束——「跨 workspace 一律返回 404 而不是 403，不泄漏存在性」——
依赖的正是这个顺序。

#### M2 模型网关 — 刻意不含 Agent / RAG / Tool

`0003` 只建 2 张表：`provider_credentials`、`model_profiles`。

**这一幕最能说明工程纪律**：这时候完全有能力顺手把 Agent 写了，但没有。
理由是要证明模型网关是一条**独立可用的边界**——凭据静态加密、只写不读、
永不出现在响应与日志（密钥三律），这些性质必须在没有 Agent 的情况下就成立，
否则它们会被写成 Agent 的实现细节。

> **这一幕暴露的问题**：能调模型了，但模型不知道任何企业内部事实。
> → 第二幕。

---

### 第二幕 · 能力（M3 → M4）

#### M3 知识中枢 — RAG 的可复现性来自快照，不来自「LATEST」

`0004` 建 7 张表（文档、修订、分块、快照、快照项……），
然后 `0005`、`0006` **两个不建任何表的迁移**专门加快照完整性约束。

**核心不变量**：一次检索必须绑定一个 `knowledge_snapshot_id`。
不允许「用最新的知识库」——那样同一个问题问两次，答案不同却无法归因到底是
模型变了还是知识库变了。可复现性的地基在这里。

#### M4 Agent 运行时 — 一次拆成五段（A/B/C/D/E）

| 段 | 迁移 | 建立的不变量 |
|---|---|---|
| M4-A 发布冻结 | `0007`（6 表） | AgentVersion 一经发布，prompt / 工具契约 / 模型档案 / 上下文预算全部快照化不可变 |
| M4-B 工具运行时 | `0008`（2 表） | **工具即数据**：带 `effect / risk / approval_policy` 的数据库记录，不是代码里的 if-else |
| M4-C 执行图 | `0009`（2 表） | LangGraph——要的不是「图」，是 **checkpoint + interrupt** |
| M4-D 上下文预算与 SSE | — | 截断必须是**有语义的取舍**，不是从头砍字符串 |
| M4-E 运行时评估 | — | 为 M7 留接口 |

中间还插了 `0010`/`0011` 两个纯语义闭环与回填迁移——同样不建表。

> **这一幕暴露的问题**：Agent 已经能调用会改动真实系统的工具了，
> 但**没有任何人能在它按下去之前拦一下**。
> → 第三幕。这是整个项目最核心的一跳。

---

### 第三幕 · 治理（M5 → M6）

#### M5-A 审批运行时 — 「审批是持久中断」是什么意思

`0012` 只建 1 张表，但这是全项目密度最高的一张。

命中 WRITE 工具时，Run 进入 `WAITING_APPROVAL`，LangGraph checkpoint **落库**，
进程可以重启；人批准之后**在同一个 run 内恢复**，不是新开一次执行。

**为什么不能用「阻塞等待」实现**：阻塞等待意味着进程要活着等人下班回来点按钮。
持久中断意味着人类进入了循环，但没有阻塞任何进程。
这一条决定了它是企业系统而不是 demo。

> **纪律注记**：M5-A 交付即**冻结审批状态机**，此后所有加固不允许改它。
> 这不是保守，是因为审批是安全边界——边界一旦可变，此前所有审计记录的含义都会漂移。

#### M6 可观测 — 两个迁移，零张新表

`0013`、`0014` 全是索引。Run 查询、详情、时间线、指标仪表盘、失败分析，
**全部复用既有领域模型投影出来**。

**这一点值得主动讲**：可观测没有建「日志表」。
因为 01 章末尾那句话是真的——这些不是日志，是**可查询的领域模型**。
如果需要新建表才能观测，说明领域模型一开始就没记住该记的东西。

> **这一幕暴露的问题**：能看见每一次运行了，
> 但「换个模型是不是更好」仍然只能靠感觉回答。
> → 第四幕。

---

### 第四幕 · 判据（M7）

七个迁移（`0015`→`0021`），建 15 张表：数据集、实验、执行、指标、对比、消融、发布闸门。

**这一幕回答的是一个此前无法回答的问题**：换模型 / 改 prompt / 调检索参数之后，
是变好了还是变差了，凭什么这么说。

其中一条边界值得单独记住，它是这一幕里最容易被问的：

> **Run 导入评估集时，Run 只是「证据」，不是「标注」。**
> `input` 和溯源由服务端派生，`expected` **必须人来给**。
> 否则评估集会去拟合模型现有的错误——跑分越来越高，系统越来越差。

> **这一幕暴露的问题**：所有工具都是内置的，
> 企业真实的系统在外面，接不进来。
> → 第五幕。

---

### 第五幕 · 开放（3A → 3B/3C）

`0022` 建 1 张表 `mcp_connections`。三条硬规矩：

1. **禁止手搓协议**——必须用官方 MCP Python SDK v2（`mcp>=2,<3`），
   不允许自己拼 JSON-RPC / initialize / 分页。
2. **SSRF 防护必须解析 DNS 再判断**，多条 A 记录不一致直接拒绝
   （防 DNS rebinding），`mcp_allow_private_targets` 是**显式 opt-in**，
   明令禁止「本地环境就自动放行」。
3. **不为了「代码复用漂亮」去碰已冻结的 Model Credential**——
   MCP 的密钥另起一套，遵守同样的三律。

**纪律注记**：3A 交付后明确 STOP，不顺手做 3B。
远程工具能连上、能发现、能测试，和远程工具**能被审批闸门治住**，是两件事；
中间需要一次独立的验收。

> **这一幕暴露的问题**：能力齐了，但它仍然是一个「运行时」，
> 不是一个「产品」——用户看到的是 run，不是会话，更没有可引用的产出物。
> → 第六幕。

---

### 第六幕 · 产品化（Thread / Artifact / 四个应用）

`0023` Thread（2 表）、`0024` Artifact（1 表）、`0025` ThreadKind（0 表，只加列）。

两条不变量：

- **Thread ≠ Run**。会话是耐久单位，Run 是一次执行。
- **Artifact 不是模型写的**。它从**工具结果**里投影出来，
  带 `{run_id, tool_call_id, tool_identity, step_sequence}` 溯源戳。
  这一条是整个防幻觉设计的地基——模型可以胡说，但它**没有写 Artifact 的权限**。

然后是四个应用：科研助理 / 故障排查 / 数据分析 / 客户支持。

**这一幕真正要证明的命题是**：加第四个应用需要改多少**运行时**代码。

答案是 **0 行**。运行时、执行图、`ToolPolicy.decide`、审批状态机、上下文预算、
SSE 协议、RBAC 权限、API 路由前缀——**一样都不用动**。
要加的全在「配置与展示」侧，一共五样：一个 `AgentTemplate` 常量（约 40 行 prompt）、
一个 MCP Server（若需新工具）、`ThreadKind` 枚举加一个值（一行）、
`ArtifactType` 白名单加条目 + 一个投影函数、前端一个三栏页面。

注意 `ThreadKind` 那一行：它只是**路由标签**，
**没有任何运行时行为分支挂在它上面**——加值不等于加分支（04 章逐条论证）。

> **这一幕暴露的问题**：全都写完了，但「写完」不等于「成立」。
> → 第七幕。这是最近、也是最该讲的一幕。

---

### 第七幕 · 自证（11 → 14 章）

前六幕是「建」，第七幕是「证」。四轮，每一轮都挖出了真东西。

| 轮次 | 章 | 怎么测的 | 挖出什么 |
|---|---|---|---|
| 1 | [11](11-真机验证报告.md) | 拿真 key 把三个应用跑完，审批同意/拒绝两条分支都走，前端真点 | **8 个缺陷**，含一个会让**所有**知识检索必然失败的最高级 bug |
| 2 | [12](12-前端实测与优化报告.md) | 八轮浏览器实测，注入探针测布局/对比度/焦点 | 8 个真缺陷 + **6 个误报**（误报率 43%） |
| 3 | [13](13-语料库对抗测试报告.md) | 60 文档 / 233 块真实企业语料，34 检索例 + 13 Agent 例 | negative **10/10 拒答、0 编造**；压出**两个架构缺口** |
| 4 | [14](14-生命周期与相关性下限修复报告.md) | 把两个缺口修掉并实测 | 修复完成；**并实测证伪了我自己的一个设计假设** |

这一幕最值钱的不是「修好了」，是**三条方法论结论**，它们都是被打脸打出来的：

**① 自动化审计的第一个发现必须手工复核。**
12 章实测误报率 **43%**，其中一个误报还是审计脚本自身的 bug。

**② 判「模型有没有做坏事」的正则最不可靠。**
模型*讨论*一件坏事和*做*一件坏事，文本高度相似——
实测把「Agent 主动驳回注入」误判成了「Agent 被注入攻陷」。
13 章把这个坑记为「第 5 次踩同一个坑」。

**③ 我自己算错过一次，是被自己的数据推翻的。**
这个数最早出在 13 章的语料实测里，6 章 §2.9 照抄了它：
「负例与正例的 rerank 空档是 1.77，全局阈值完全可行」。
14 章重算发现：那个 1.77 是拿正例的 **top-1** 分当下界算的，
但阈值砍的不是 top-1，是**每一条证据**。
按「真正需要的文档里分最低的那条」重算，真实窗口只有 **0.04**——窄了 40 倍。
按 1.77 的说法去取 1.0 这种「安全值」，实测**静默丢掉 3 个本来答得了的问题**。

还有一条**负面结果**同样重要：
「给退役文档的排序分加惩罚就能解决版本选择」——**实测证伪**。
5 个版本类问题里，想要现行版的分数差（1.07、0.10）和想要退役版的（0.87、0.15、1.83）
**完全交错**，没有任何常量能把它们分开，2.0 的惩罚修好 2 个、弄坏 3 个。
真正管用的是把 `superseded` / `effective_date` 交给**看得见问题的模型**去判断——
排序层做不到的 4 个例子，模型 **4/4** 做对了。

> 这条结论已经写进 `settings.py` 的注释里，防止后人再试一遍。

## 4. 正面回答：为什么这么多

逐项给出「不这么多会怎样」。**最后一列是我自己认为溢出的部分，不回避。**

| 规模项 | 值 | 不这么多会怎样 | 是否溢出 |
|---|---|---|---|
| ORM 表 | 57 | 治理四件事（冻结/审批/审计/评估）每一件都需要自己的事实表。砍掉任何一组，对应的问题就退化成「查日志」 | 否 |
| 迁移 | 26（单 head） | **其中 9 个不新建任何表**，只做约束、索引、回填、语义闭环。正是这 9 个说明表不是随手加的 | 否 |
| 产品代码 | 44,295 行 | 主要成本在 `packages/` 的 13 个领域包，而它们不依赖 FastAPI——这是「可替换」的代价 | 否 |
| 测试 | 96 文件 / 703 用例 / 24,703 行 | 测试是产品代码的 56%。审批状态机、SSRF、密钥三律、workspace 隔离这几类**错一次就是安全事故**，没有测试就不能声称成立 | 否 |
| MCP Server | 4 个自研 | 要证明「四个应用共用一套运行时」，至少需要两个**领域完全不同**的外部系统 | **部分溢出**：2 个就足以证明，第 3、4 个是为了让四应用对称 |
| 前端 | 113 文件 / 24,392 行 / 1,726 行手写 CSS | 零框架是刻意的——要证明级联顺序、主题 token、i18n schema 这些**结构性**决定，用组件库会把它们藏起来 | **部分溢出**：手写 CSS 拉长了工期，收益主要是可讲性 |
| 里程碑文档 | 27 份 | 每个里程碑一份验收，是「交付即 STOP」纪律的载体 | 否 |
| 本报告 | 15 章 / 5,903 行 | — | **明确溢出**：这是面试准备物，不是产品的一部分 |

**一句话版本**：体量不是功能堆出来的，是**不变量**堆出来的。
每一个不变量都要求一组表、一组约束、一组测试——少任何一层，它就从「不变量」退化成「约定」。

## 5. 如果重做，我会砍掉什么

诚实清单，比「我会做得更好」有说服力：

1. **MCP Server 砍到 2 个**。文献 + 商务就够证明跨领域复用，运维和数仓是对称性开销。
2. **前端引一套无样式组件库**（Radix 之类），只保留 token 层自己写。
   结构性论点一条不丢，省掉 1,700 行 CSS 的维护面。
3. **评估平台推后**。M7 有 7 个迁移 15 张表，但在没有真实流量的情况下，
   它的价值主要是「证明我想过这件事」。真实项目里它应该排在有流量之后。
4. **更早做第七幕**。11 章那个「会让所有知识检索必然失败」的 bug，
   如果在 M3 结束时就真机跑一次，能早四天发现。
   **写完不等于成立**——这是这个项目给我最贵的一课。

## 6. 三句话带走

> **一、** 这个项目回答的不是「怎么让模型答得准」，
> 而是「怎么让一个会改动真实系统的 Agent，在企业里可审计、可审批、可复现、可评估」。
>
> **二、** 它的体量来自七幕因果链：
> 地基 → 能力 → 治理 → 判据 → 开放 → 产品化 → 自证，
> 每一幕都是被上一幕答不了的问题逼出来的，不是功能清单。
>
> **三、** 最有价值的部分不是建成的东西，是第七幕：
