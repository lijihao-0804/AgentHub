# 18 · 截图演示：这个系统到底能做什么

> 前 17 章都在讲**代码里有什么**。这一章换一种证明方式：
> 把服务真的跑起来，用一个脚本驱动真实浏览器，**把每一页拍下来**，
> 然后按「一个人从注册到发布再到评估」的顺序，讲一遍这些页面各自解决什么问题。
>
> 这一章里的每一张图都是**实拍**，不是设计稿、不是 mock、不是示意图。
> 图里的每一个数字——76 次运行、90.8% 成功率、0.0483 USD、1198.2 ms——
> 都是数据库里真实存在的行渲染出来的。

## 0. 这些截图是怎么拍的

### 0.1 为什么不用 Playwright

第一反应当然是 Playwright。但 Playwright 需要额外下载约 150 MB 的浏览器内核，
而这台机器上已经装了 Chrome，Chrome 本身就说 CDP（Chrome DevTools Protocol），
并且 `websockets` 早就是后端的依赖之一。

所以最后的方案是：**不装任何新东西**，写一个约 150 行的 CDP 驱动
（`Page.navigate` / `Runtime.evaluate` / `Page.captureScreenshot` /
`Page.getLayoutMetrics` / `Emulation.setDeviceMetricsOverride`），
用 `--headless=new --remote-debugging-port=9333` 起一个无头 Chrome，
通过 websocket 指挥它。

这里踩到一个值得记的坑：**React 受控组件不能用 `el.value = x` 填值**。
直接赋值会被 React 的合成事件系统忽略，界面上看起来填了，state 里什么都没有。
正确做法是拿到原型上的 `value` setter 再 `call`，然后手动派发冒泡的
`input` / `change` 事件：

```js
const desc = Object.getOwnPropertyDescriptor(Object.getPrototypeOf(el), 'value');
desc.set.call(el, v);
el.dispatchEvent(new Event('input',  { bubbles: true }));
el.dispatchEvent(new Event('change', { bubbles: true }));
```

### 0.2 为什么必须真登录

前端的鉴权形态决定了没有捷径可走：**access token 只存在内存里**
（不进 localStorage、不进 cookie、不进 URL），refresh token 是后端下发的
HttpOnly cookie，每个请求都带 `credentials: "include"`。

也就是说，脚本**没有办法注入一个 token 就算登录**——
它必须像人一样打开 `/login`、填表、点「登录」、等待跳转。
这一点本身就是一条安全性证据：连拍截图的脚本都绕不过去。

### 0.3 数据来自哪里

截图里的工作区是 **`Verification Org / Research`**
（工作区 ID `d14d783d-fc2c-4bef-9a9f-dcccaec28667`），
也就是第 11、13、16 章做端到端验证时留下的那个真实工作区。
里面有 76 次真实运行、3 个知识库、60 个文档、17 个工作区工具、
5 个智能体、8 个已发布版本、3 条真实审批记录。

**没有一条是为了拍照造的。** 包括那几条失败——它们是当时真的失败了。

### 0.4 一个被抓出来的坑

第一次拍「调试台运行」时，脚本的点击助手是这么写的：

```js
document.querySelectorAll('button, a, [role="tab"], [role="button"], summary')
```

然后 `click("运行")` —— 结果它点中了**左侧导航栏里的 `<a>运行</a>`**，
直接跳到了运行列表页，而调试台里那个「运行」提交按钮根本没被点到。
截图拍下来了，但拍的是错的页面。

修法是把候选集收窄到 `button`（导航是 `a`，永远不会误命中），
并过滤掉 `disabled` 和不可见元素。**这一节留在这里，是因为它恰好说明了
自动化截图跟自动化测试是同一类活动：它一样会产生「看起来成功、实际上错了」的结果。**
（这和第 12 章「自动化审计的误报率 43%」是同一个教训的第二次出现。）

## 2. 仪表板：所有百分比都带分母

![工作区仪表板](assets/02-dashboard.png)

这是整套 UI 里我自己最满意的一页，原因是它**拒绝给出没有分母的数字**。

| 卡片 | 实拍数值 | 它旁边写了什么 |
|---|---|---|
| 成功率 | 90.8% | 已完成 **69 / 76** |
| p95 延迟 | 17 s | p50 4.26 s · **76 个样本** |
| 每次运行 Token | 5,127 | **70 已知 · 6 未知** |
| 每次成功运行成本 | 0.00072 USD | 基于 **65 次成功运行**的成本 |

注意第三行和第四行。「70 已知 · 6 未知」的意思是：
有 6 次运行的 token 用量系统**不知道**——可能是供应商没返回 usage，
也可能是运行在拿到 usage 之前就挂了。

一个偷懒的实现会把这 6 次当成 0 算进平均值，于是平均值被稀释、
看起来一切正常。这里的选择是：**把未知单独列出来，分母只用已知的那部分**。
成本那一行同理——76 次运行里只有 65 次进了成本分母。

同样的诚实出现在「各币种成本」卡片上：
`USD 0.0483`，下面标注**「估计 68 · 精确 0」**。
也就是说这 0.0483 美元**全部是估算值，一条精确账单都没有**。
系统知道自己在估算，并且说出来了。

再往下三块：

- **失败分布**：`RUNTIME 7 · 100%` —— 7 次失败全部是运行时类。
- **AgentVersion 分布**，页面自己写了一句免责：**「只列变化，不排优劣」**。
  它列出 v1→v8 每个版本的运行数、成功/失败/需处理、p95 和成本
  （比如 `v6 36 次运行 / 35 ✓ · 1 ✕ / p95 7.13 s / 0.0318 USD`），
  但**不会告诉你哪个版本更好**。判优劣是第 14 节评估平台的事，不是仪表板的事。
- **失败运行列表**，按分类可筛。实拍里能看到四种不同的失败码：
  `AGENT_COST_LIMIT_EXCEEDED`、`AGENT_COST_UNMEASURABLE`、
  `AGENT_CONTEXT_BUDGET_EXCEEDED`、`AGENT_RUN_FAILED`。
  前两条的状态是**「需要处理」**而不是「已失败」——区别见第 12 节。

页面顶部还有一句：**「原始提示词与工具负载数据不会出现在此视图中」**。
这是第 17 章那条权限越界 finding 整改后的结果：
VIEWER 该看得到状态与用量，不该看得到 prompt 原文。

## 3. 模型与供应商：密钥只写不读

![模型与供应商](assets/03-settings-models.png)

两张表。上面是**供应商凭据**，下面是**模型配置**。

凭据表里那一列「密钥」显示的是 **`凭据已配置`** 四个字——
不是掩码后的 `sk-****abcd`，而是干脆**不返回**。
表格上方写着：**「密钥只写不读，已保存的密钥不会返回浏览器」**。

这就是第 10 章「密钥三律」在界面上的样子：静态加密、只写不读、永不出现在响应与日志。
对应的操作列里因此有一个**「轮换密钥」**——因为你没法「查看再修改」，
只能整个替换掉。

模型配置那一行把**能力声明**平铺出来了：

```
streaming=true  tool_calling=true  structured_output=true  max_context_tokens=65536
```

这些不是从供应商 SDK 现场探测的，是**记录在数据库里的声明**，
因为 AgentVersion 发布时要把它快照进去（见第 8 节）。

还有一个「测试」按钮，旁边一行小字：
**「检查在服务端使用该配置的凭据执行，结果不会被保存」**。
两个意思：① 测试不在浏览器里发生，所以密钥不需要下发；
② 测试结果不入库，所以不会有人拿一个三天前的「测试通过」当今天的依据。

## 4. 知识库：文档 → 修订 → 快照

![知识库列表](assets/04-knowledge.png)

三个知识库。列表页有一行提示：
**「文档在知识库内部上传。打开某个知识库即可上传文件并发布快照。」**
这是一个刻意的层级约束——文档不能脱离知识库存在。

### 4.1 文档

![知识库详情 · 文档](assets/05-knowledge-detail.png)

`Enterprise Corpus v1` 里是第 13 章对抗测试用的那 60 份企业语料，
格式混杂（`.md` / `.pdf` / `.txt`），内容分七类：客服政策、HR、双语、
流程、API、安全、以及**三份故意植入提示词注入的文档**：

```
prompt-injection-faq-mixed.md
prompt-injection-it-notice-zh.md
prompt-injection-vendor-doc-en.md
```

这三份是**故意留在语料库里的**。第 13 节会看到智能体读到它们时的反应。

还有几组是**同名不同版本**的：`refund-policy-v1.md` / `refund-policy-v2.pdf`、
`sla-policy-v1/v2`、`employee-handbook-v1/v2`、`api-changelog-v1/v2/v3`、
`incident-response-runbook-v1/v2`、`data-retention-schedule-v1/v2`。
第 14 章整章都在处理它们带来的问题：**语义上几乎一样，但一份已经作废了**。

每一行右边是「查看修订版本」——文档本身是容器，**内容在修订（revision）上**。

### 4.2 快照

![知识库详情 · 快照](assets/05b-knowledge-snapshots.png)

```
ID        bffe88bc-9f83-404b-82cd-cba00fa15f76
内容哈希  00643ca5fbee4bca7209dd363e1d8366705aaf7cea0eb30f3c2966a47bbb5b84
条目数    60
Schema 版本 1
```

页面自己解释了快照的用途：**「快照用于固定检索内容，供 PINNED 绑定使用。」**

这是 RAG 可复现性的整个答案。一次运行绑定的不是「这个知识库」，
而是「这个知识库的这个快照」。哪怕之后又上传了 200 份文档，
那次运行重跑一遍看到的还是这 60 条。**内容哈希**让这件事可验证——
它不是自增 ID，它是内容本身的指纹。

## 5. 检索实验台：把四个阶段的证据全摊开

![检索实验台](assets/06-retrieval-playground.png)

标题下那句话就是这一页的全部意图：
**「查看单个知识快照在 Dense、Sparse、Fused、Rerank 各阶段的证据。」**

然后真跑一次。查询用中文：**「原支付方式失效时退款应该怎么处理」**。

![检索四阶段结果](assets/06b-retrieval-result.png)

```
快照      bffe88bc…
总延迟    1198.2 ms
最终证据  6

阶段 Dense   205.5 ms   30 条结果   #1 0.6581  #2 0.6275  … #30 0.5367
阶段 Sparse   58.7 ms   30 条结果   #1 28.3382 #2 28.2459 … #26 13.0054
阶段 Fused                （RRF 融合）
阶段 Rerank               （交叉编码器重排）
```

几件事值得指出来：

1. **分数量纲完全不同**。Dense 是 0.53–0.66 的余弦相似度，
   Sparse 是 13–28 的 BM25 分。**它们不可直接比较**，
   所以融合用的是 RRF（倒数排名融合）而不是加权求和——
   加权求和需要两边可比，而它们不可比。
2. **每条证据都带来源坐标**：`修订 a230e33a… · 第 15000–16200 字符`
   或者 `修订 072aed98… · 第 1 页`。PDF 给页码，文本给字符区间。
   这是「点回原文」的基础，也是第 15 节里 Artifact 溯源戳的上游。
3. **30 → 30 → 融合 → 6**。最终只有 6 条进上下文。
   这个收敛不是「取前 6」，而是重排之后过阈值的结果。
4. **总延迟 1198.2 ms 是热状态下的数字，冷启动远不止**——重排模型要先加载。
   脚本第一版给了 25 秒超时，拍到的是一张「检索中…」；
   第二版改成轮询字面量 `Rerank`、超时放到 300 秒，才拿到完整结果。
   这件事本身也是一条性能事实：**第一次请求承担了整个模型加载成本，
   而这个成本没有出现在「总延迟」里**——那 1198.2 ms 只计了检索本身。

## 6. 工具：副作用 / 风险 / 审批，三元组

![工具目录](assets/07-tools.png)

这一页是「**工具即数据**」这条不变量最直观的证明。
17 个工作区工具，每一个都有同样的五列：

| 名称 | 副作用 | 风险等级 | 审批要求 | 修订版本 |
|---|---|---|---|---|
| `search_papers` | READ | LOW | NEVER | #1 |
| `query_metrics` | READ | LOW | NEVER | #1 |
| `rollback_deployment` | **WRITE** | **HIGH** | **ALWAYS** | #1 |
| `query_sql` | READ | LOW | NEVER | #1 |
| `issue_refund` | **WRITE** | **HIGH** | **ALWAYS** | #1 |
| `create_ticket` | **WRITE** | **HIGH** | **ALWAYS** | #1 |

17 个里有 3 个是 WRITE，全部 `ALWAYS` 审批：
**回滚部署、发起退款、创建工单**——三个真的会改动外部系统的动作。
其余 14 个全是 READ / NEVER。

这不是代码里的 `if tool_name in [...]`，是**数据库里的列**。
换句话说，新增一个高危工具不需要改运行时代码，
而是在这张表里写一行 `effect=WRITE, approval_policy=ALWAYS`。

页面下半部分是**内置目录**，四个内置工具
（`calculator` / `query_customer` / `search_knowledge` / `create_ticket`），
每个右边一个「添加到工作区」按钮。目录上方写着：
**「副作用、风险与审批要求均由服务端声明。」**

最后一列「修订版本 #1」：工具契约本身是有版本的。
改了参数 schema 就是一个新修订，**已发布的 AgentVersion 仍然绑在旧修订上**。

## 7. 智能体：草稿 / 绑定 / 已发布版本

![智能体列表](assets/08-agents.png)

五个智能体，列表就四列：模型配置、**绑定模式**、提示词版本、更新时间。

绑定模式全部是 **`PINNED`**。这一列是整套设计的关键：
PINNED 意味着知识绑的是**快照 ID**而不是「最新」。
（第 14 章讨论过 LATEST 绑定的代价——它让「重跑一次」失去意义。）

![智能体详情](assets/09-agent-detail.png)

详情页六个 tab：**基础 / 模型 / 知识 / 工具 / 运行时 / 版本**，
右上角两个按钮：**打开调试台**、**发布**。

「基础」里是名称、描述、系统提示词、提示词版本（v1）。
注意提示词版本和 AgentVersion 是**两个不同的东西**——
草稿的 prompt 改了会涨 prompt 版本，但只有点「发布」才会产生 AgentVersion。

### 7.1 运行时预算

![运行时配置](assets/09c-agent-runtime.png)

七个可调项：最大步数、最大工具调用次数、最大重复工具调用次数、
最大并行读取数、预留输出 Token、最大检索 Token、最大工具结果 Token。

两行小字很重要：

> 留空的字段将回退到服务端默认值。
> **留空的字段不会出现在请求中，也不会以空值发送。**

第二句是在说：**留空 ≠ 发 `null`**。
如果留空发 `null`，后端就无法区分「用户想用默认值」和「用户想显式设成空」。
所以前端干脆不把这个 key 放进 JSON。这是一条被写在界面上的 API 契约。

### 7.2 版本与声明哈希

![智能体版本](assets/09b-agent-versions.png)

这张图是「**发布即冻结**」最硬的证据：

| 版本 | 解析后声明哈希 | 创建时间 |
|---|---|---|
| v1 | `d353ba11…3511` | 01:16:26 |
| v2 | `78a34b52…3d82` | 01:17:01 |
| v3 | **`78a34b52…3d82`** | 01:29:40 |
| v4 | `447ecf6d…4199` | 16:36:05 |
| v5 | **`447ecf6d…4199`** | 16:39:56 |
| v6 | **`447ecf6d…4199`** | 16:43:50 |
| v7 | **`447ecf6d…4199`** | 16:46:59 |
| v8 | `607a8e67…c71b` | 16:47:21 |

**v2 和 v3 的哈希一模一样。v4/v5/v6/v7 四个版本哈希也一模一样。**

这说明什么？说明这几次「发布」之间，**智能体的有效声明根本没变**
——改的东西没落到解析后的 spec 上。哈希把这件事暴露出来了：
你可以点八次发布，但系统知道其中只有三种实质不同的配置。

反过来，如果两次运行的声明哈希相同，那它们的可比性是**可以被证明的**，
而不是靠「我记得我没改过」。第 14 节的实验变体就是拿这个哈希去冻结的。

## 8. 调试台：一次提交 = 一次运行

![调试台](assets/11-playground.png)

页面顶部两行说明把边界划得很死：

> 运行已发布的智能体版本并实时查看执行过程。**一次提交即一次运行，这里不保留对话历史。**
> 正在运行 AgentVersion **v8** `607a8e67bc98ab992e436e1687137f2ac82d40e565a66d8ea390db280908c71b`
> **调试台运行的是已发布版本，而非当前草稿。**

三条信息，每条都在防一种误解：

1. **不保留对话历史** → 调试台是单次调试，不是聊天。多轮在应用页（第 13 节）。
2. **完整声明哈希直接印在界面上** → 你现在调的到底是什么，不用猜。
3. **运行的是已发布版本，不是草稿** → 防止「我改了 prompt 怎么没生效」。

左边还有 v1–v8 的版本选择器，可以指定跑哪个版本。

### 8.1 真的跑一次

输入：`Find recent work on retrieval-augmented generation published since 2023.`

![调试台 · 运行中](assets/11b-playground-streaming.png)

提交之后状态立刻变成**「运行中…」**，SSE 开始推。

![调试台 · 运行完成](assets/11c-playground-done.png)

跑完之后这一页给出的东西：

**状态**：已成功。右上角一个**「查看运行详情」**——
调试台的每一次提交都是一条正式的 Run，跟应用里跑出来的 Run 同级，
一样进运行列表、一样可对比、一样可加入评估集。

**用量**（实拍）：

```
输入 Token 2159    输出 Token 298    总 Token 2457    缓存 Token 1792
```

**执行动态**：

```
上下文已调整
已请求工具  search_papers
工具执行中  search_papers
工具已完成  SUCCESS  search_papers  耗时 217 ms
上下文已调整
```

这是 SSE 事件流的可视化。注意 `search_papers` 是一个**MCP 远程工具**
（跑在本机 8932 端口的文献服务上），217 ms 是真实往返耗时。

**模型输出**里有一句值得单独摘出来：

> A note on what came back: the result set is small, and one record has incomplete
> metadata — the 2025 paper by Maria Santos has **no abstract, no DOI, and no venue**
> listed in the tool output, so those fields are **unavailable rather than something
> I can fill in**.

模型明确说明了「这个字段我没有，而不是我可以补一个」。
这正是第 13 章对抗测试要压的那条线：**缺数据的时候说缺数据**。

## 9. 运行列表：工作区范围内的全部历史

![运行列表](assets/12-runs.png)

页面说明：**「工作区范围内的运行历史，展示脱敏后的状态、用量、成本与审批信息。」**
「脱敏后」三个字对应第 2 节讲的那条权限整改。

筛选器：状态（运行中 / 等待审批 / 已成功 / 已失败 / 需要处理 / 取消请求中 / 已取消）、
智能体版本 ID、应用。**七个状态**，值得逐个看一眼，因为它们不是随便设的：

- `需要处理` 和 `已失败` 分开 —— 见第 12 节。
- `取消请求中` 和 `已取消` 分开 —— 请求取消和真的停下来之间有个窗口，
  在那个窗口里工具可能已经发出去了。

1cc5c6db…  需要处理  v6   16.6 s   936    —            1  RUNTIME: AGENT_COST_UNMEASURABLE

## 10. 运行详情：时间线 + 用量 + 审批计数

### 10.1 一次普通运行

![运行详情](assets/13-run-detail.png)

头部：运行 ID、AgentVersion **v2**、状态「已成功」，
三个按钮：**对比 / 加入评估 / 重新运行**。

「重新运行」下面挂着一句警告：

> 这会使用同一个已发布的 AgentVersion 和同样的输入创建一次新的运行。
> **新运行可能会再次调用工具并再次发起审批。**

这句话是必要的：重跑一次退款工具不是无害操作。

指标条：持续时间 2.28 s / Token 1,035 / 成本 0.00033 USD /
模型步数 1 / 工具调用 0 / 失败 —。

**审批计数**单独一组，而且是五个数字：

```
待审批 0    已批准 0    已拒绝 0    执行失败 0    结果未知 0
```

后面三个是关键。「已批准」不等于「执行成功」——批准之后仍然可能执行失败，
甚至可能**结果未知**（`UNKNOWN_OUTCOME`）。
把决策和执行分成两组计数，是因为它们真的会不一致。

时间线下方每个节点都有「**技术元数据**」可展开，
并标注**「脱敏事件 · 供应商中立」**——
事件流里不会出现供应商特有的字段名，换个模型供应商，这条时间线结构不变。

### 10.2 一次用了工具的运行

![运行详情 · 含工具调用](assets/13a-run-detail-tools.png)

```
持续时间 6.93 s   Token 7,988   成本 0.0022 USD   模型步数 2   工具调用 2
```

时间线：

```
运行开始      运行中      AgentVersion 76e11797…
模型步骤      已成功
检索          已成功      search_knowledge
检索          已成功      search_knowledge
工具调用      已成功
模型步骤      已成功
运行完成      已成功
```

注意**「检索」和「工具调用」是两类不同的节点**。
`search_knowledge` 虽然是通过工具接口调的，但它产生的是检索事件——
因为检索需要记录的东西（快照、证据、分数）和一般工具调用不一样。

也注意 token 从 1,035 跳到 7,988：**工具结果进上下文是有代价的**。
这就是第 7.1 节那些「最大工具结果 Token」预算存在的理由。

### 10.3 一次撞上成本闸门的运行

![成本闸门运行](assets/13c-run-cost-limit.png)

```
AgentVersion v7   状态：需要处理
失败 AGENT_COST_LIMIT_EXCEEDED
持续时间 10 s   Token 903   成本 0.00027 USD   模型步数 1   工具调用 1
```

页面上有一行黄色提示：

> **需要处理**：该运行需要人工跟进（例如未确认的操作结果）。

时间线末尾很有意思，它有**两条**失败记录：

```
运行失败  已失败      失败代码：AGENT_COST_LIMIT_EXCEEDED
运行失败  需要处理    失败代码：AGENT_COST_LIMIT_EXCEEDED
```

先判定失败，再升格为「需要处理」。这两步是分开的事件，
因为「这次运行结束了」和「有人得来看一眼」是两个不同的结论。

这条运行就是第 15 章实现的 **Run 级成本闸门**在真实环境里的样子：
它在第 1 个模型步骤之后、第 1 次工具调用之后就把运行掐掉了，
**没有让它继续烧钱**。

## 11. 运行对比：只摆证据，不判对错

![运行对比](assets/13b-runs-compare.png)

页面说明把定位写得非常明确：

> 并排查看两次运行。**这是调试与检查，不是评估：系统不会判定哪一侧是正确的。**

输入两个 Run ID，得到四组并排：

**状态与失败**：`两次运行都使用 AgentVersion v6`。
——先告诉你可比不可比。如果版本不同，差异可能来自版本而不是输入。

**输入**：标注**「输入不同」**，然后并排给出两条中文问题。

**最终输出**：左右两段完整模型输出。

左边那段输出里有一句，是这次拍摄最值得展示的一段文字：

> (Note: one of the retrieved items, `prompt-injection-faq-mixed.md`, is a synthetic

这就是第 4.1 节埋的那三份注入文档之一被检索到了，

## 12. 审批：决策与执行分开跟踪

![审批收件箱](assets/14-approvals.png)

页面说明就是整个设计：

> 对工具操作进行人工审批，审批决定持久保存、不会丢失。
> **决定与执行状态分开跟踪——已批准的操作仍可能执行失败，
> 结果未知时需要人工处理，而不是盲目重试。**

计数条：`待审批 0 · 已批准 2 · 已拒绝 1 · 需要处理 0`
（下面小字：「计数基于当前已加载的列表。」——连计数的口径都说清楚了）。

三条真实记录：

### ① `rollback_deployment` —— 已批准，已成功

```
决定  已批准    2026/9/21 03:13:23（决策人 fb0630bc…）
申请  2026/9/21 03:12:59
执行  已成功    2026/9/21 03:13:23    尝试次数 1
```

参数里带着完整理由：

> Roll back 5.4.2 (dep-20260314-2101, commit abc123de) which reduced DB
> pool_max_size 50→5 and pool_timeout 30s→2s, causing psycopg.PoolTimeout and
> checkout 5xx rising from ~2% to ~37% at 21:03. Target is 5.4.1 (dep-20260313-1422),
> the last good deployment.

**审批请求里带的不是「要不要回滚？」，而是完整的证据链**：
哪个版本、哪个 commit、改了哪两个参数、导致什么指标怎么变、回滚到哪。
人能在 24 秒内做决定（03:12:59 → 03:13:23），靠的就是这个。

### ② `issue_refund` —— 已批准，已成功

```
amount 415   currency USD   order_ref ORD-77412
reason: Approved refund REF-5512 for returned order ORD-77412 … was never issued;
        issuing the outstanding USD 415.00 to the original card.
```

### ③ `create_ticket` —— **已拒绝**

```
决定  已拒绝    2026/9/21 03:16:55
执行  未开始    执行时间 —
```

被拒之后执行状态是「**未开始**」，不是「失败」。这两件事在数据上是分开的。

三条记录合起来覆盖了：**批准→成功、批准→成功、拒绝→未执行**。
这套 UI 还能表达第四种——批准→执行结果未知（`UNKNOWN_OUTCOME`），
那种情况下「需要处理」计数会 +1。当前工作区里恰好没有这样的记录，
但第 10.1 节的五个计数格子就是给它留的位置。

## 13. 四个应用：同一套运行时，四种产品形态

差别只在 ThreadKind 这个路由标签和各自的制品投影。

### 13.1 研究工作台

![研究工作台](assets/15-research.png)

> 研究会话把提问、回答提问的运行、以及运行产出的论文集中在同一个位置。

七个会话，每个标着「**3 篇论文 · 2 轮对话**」这样的计数。

![研究会话](assets/15b-research-thread.png)

左边会话列表，中间对话，右边**制品面板**。

对话是两轮：先问「2023 年以来 RAG 的新工作」，再追问「引用数最高的是哪篇，给准确数字」。
第二轮答：**893，Self-RAG（Asai & Wu，ICLR 2024）**，
并且顺带给出另外两篇的 512 / 47 做对照。

每条回答下面挂着 **`运行 #1887b263` / `运行 #f4a2a7ed`** 和一个「**查看运行**」。
**对话里的每一句话都能点回它的 Run。**

右边制品面板是这一页的重点：

```
Search: retrieval-augmented generation
论文检索   3 篇论文   2026/9/21 01:29:45   【只读】
产出自 运行 #f4a2a7ed

查询 retrieval-augmented generation   来源 openalex   总数 3

Precise Zero-Shot Dense Retrieval without Relevance Labels
  Luyu Gao, Xueguang Ma | 2023 | ACL | 被引 512 | DOI 10.18653/v1/2023.acl-long.99
  来源追溯：工具 search_papers · 步骤 5 · 运行
```

三个标记连起来看：**「只读」+「产出自 运行 #f4a2a7ed」+「来源追溯：工具/步骤/运行」**。

这就是「**Artifact 不是模型写的**」这条不变量的界面形态。
这 3 篇论文不是从模型输出里解析出来的，是从 `search_papers` 的**工具返回值**里
投影出来的，每一条都带 `{run_id, tool_call_id, tool_identity, step_sequence}`。
模型可以在正文里说错引用数，但**改不了制品**。

制品面板上方还有筛选（标题包含 / 起始年份 / 截止年份）和「收藏到候选清单」。

### 13.2 故障排查

![故障排查](assets/16-incidents.png)

> 一个排查会话把证据、收集证据的运行，以及最终收尾的那次写操作放在同一个地方。

一个进行中的故障：`Checkout 500s after the 21:01 deploy`，**14 个事件 · 5 轮对话**。

![故障排查会话](assets/16b-incident-thread.png)

这一张是**整套截图里我最想让人看的一张**，因为它拍到的是**失败**。

提问是中文的：「Checkout 接口在 21:01 那次发布之后开始大量 500。
请先查指标和日志确认影响范围，再看那次发布改了什么，然后给出你的判断和建议。」

而这一轮，**所有工具调用都失败了**（当时 MCP 服务确实挂了）。模型的回答：

> I have to stop here and report a gap rather than a finding.
>
> **What happened:** Every tool call I made this turn failed. … All returned
> `{"error_code":"MCP_TOOL_CALL_FAILED", …}`
> **This is a tool/transport failure, not an empty result. It is not evidence that
> the checkout service is healthy, and it is not evidence that it is broken.**
>
> **What I therefore cannot tell you (and will not guess):** …
> I cannot confirm a deployment even occurred at 21:01; **that timestamp is your
> report, not something I retrieved.**
>
> **Hypothesis status:** … *not yet supported* — not refuted, just unevidenced.
> **Stating a cause now would be fabrication, and a wrong commit SHA or timestamp is
> exactly the kind of thing an engineer would act on.**
>
> **Recommendation:** 1. Treat the observability tooling as the incident. …
> 3. **Do not roll back on my say-so.**

四层区分，每一层都不是废话：

1. **工具失败 ≠ 空结果**（前者什么都不能推断，后者可以推断"没有"）
2. **你说的 ≠ 我查到的**（21:01 这个时间点是用户给的，不是证据）
3. **未被支持 ≠ 被否证**（假设还在，只是没证据）
4. **别照我说的做**（因为我这次什么都没看到）

这是同一个智能体在**上游全挂**情况下的行为。
如果它编一个 commit SHA 出来，界面上会显示得同样漂亮——
而一个工程师可能真的照着去回滚了。

### 13.3 数据分析

![数据分析](assets/17-analytics.png)

> 问的是业务问题，不是表结构问题。智能体会先把指标口径弄清楚，再动手写 SQL。

![数据分析会话](assets/17b-analytics-thread.png)

问题：「先看看数据仓库里有哪些表和字段，然后告诉我最近的订单里，
按销售额排名前五的产品分别是什么，各自贡献多少。」

这是一个**前提就是错的**问题。模型的回答开头：

> I have to stop here and tell you the question can't be answered as asked.
> **The warehouse has 4 tables, and none of them contains products.**

然后它给了一张实际存在的表结构（`signup_page_views` 2785 行、`signups` 766 行、
`orders` 537 行、`payments` 545 行，含每张表的真实列名），并指出：

> There is no product table, no product ID column, and no product name column anywhere
> in the warehouse. An order is just an amount in minor units (`amount_cents`) tied to
> a user and a timestamp … **I won't invent product names or attribute order amounts to
> products that aren't recorded.**

它还额外标了两件事：

> 1. **The `sales` metric definition lookup failed.** … So even the definition of
>    "sales" is unavailable to me this turn — I can't tell you whether it means gross
>    order value, paid-only, net of refunds, etc. **I'm not going to guess at it.**
> 2. **"Recent orders" is also undefined.**

最后给了四个**这个 schema 真能回答**的替代问题（按金额排序的最大订单、
按日/周/月的销售额、按国家/平台/版本分组、已付/已退/已取消的金额拆分）。

这一页的价值是：**它没有跑出一条会误导人的 SQL。**
「Top 5 products」这种查询很容易写出一条语法正确、结果也是五行、但含义完全错误的 SQL。

### 13.4 客户支持

![客户支持](assets/18-support.png)

> 一个工单会话会查询客户信息、核对政策，然后要么给出解释，要么把已经做完的调查交接给人工。

![客户支持会话](assets/18b-support-thread.png)

问题：「退款政策里，如果客户的原支付方式已经失效，应该怎么处理？请引用政策原文。」

回答是中文的，并且**逐段引用了知识库原文**（Section 2 退款方式、
Section 6 升级、Section 5 已取消订单），每段都是块引用的英文原文，
下面跟中文归纳。其中一条：

> "When the original payment method is no longer valid — an expired card, a closed
> account, a revoked mandate — the automated refund will fail with
> `PAYMENT_METHOD_INVALID`. … **Support agents must not promise a customer that a
> refund to an alternative card is possible. It is not.**"

这一页右侧有两块独有的东西：

**客户信息**，下面一行提示非常诚实：

> 记下客户号与工单号，交接单才会带上它们。**这里的内容不会去后台取——它就是你填的。**

界面主动声明「这块是人填的，不是系统查的」，防止有人把它当成权威数据源。

**升级转人工**，提示：

> **升级是一种结果，不是一次失败。** 交接单的意义在于，接手的人不必从头再来一遍。

交接单字段：客户 / 工单 / 问题 / 已核查 / 发现 / 建议动作 / 升级原因，
并且强制校验：**「交接单需要一个问题和一条建议动作。」**

把「转人工」做成一等公民、还给它设计了结构化交接单，
比让智能体硬着头皮答完要有用得多。

## 14. 评估平台：让「哪个版本更好」这句话可复现

![评估平台](assets/19-evaluations.png)

> 数据集、实验、指标快照与发布门禁，让智能体的评估可复现。

四个计数（实拍）：**数据集 3 · 实验 1 · 定价快照 1 · 发布门禁策略 0**。
下面标注「计数来自工作区的实时列表」。

### 14.1 数据集

![数据集](assets/20-datasets.png)

> 带版本的评估用例集合。**已发布版本不可变，可被实验绑定。**

三个 `judge-smoke-*` 数据集，描述都是
`B verification: the open-ended slice scored by a frozen judge.`
——这是第 15/16 章验证 judge 冻结时留下的真实数据。

### 14.2 定价快照

![定价快照](assets/23-pricing.png)

> 绑定到实验变体的**不可变**模型价格记录。**金额保留记录时的币种，不进行换算。**

```
deepseek-chat-dafe2be1 | deepseek | deepseek-chat | USD
输入/1M 0.28000000   输出/1M 0.42000000   缓存输入/1M 0.02800000
来源说明 DeepSeek published list price, recorded for B verification.
哈希 358157cc…
```

两个细节：

- **八位小数**。单价乘以百万 token 再四舍五入，精度损失是会累积的。
- **不换算币种**。汇率是有时间的，今天把 USD 折成 CNY 存进去，
  明天这条记录就说不清它是哪天的汇率了。所以只存原币种。

价格是**快照**，因为三个月后供应商调价，你还得能算清当时那次实验花了多少。

### 14.3 实验

![实验列表](assets/21-experiments.png)

列：名称、状态、**切分**、用途、重复次数、构建、**HOLDOUT 曝光**、创建时间。

![实验详情](assets/21b-experiment-detail.png)

```
judge-experiment-dafe2be1     【就绪】【不可变】
状态 就绪        切分 DEV      用途 开发      重复次数 1
Schema 版本 1    Holdout 曝光次数 0
构建 SHA fc2efba81f76
数据集哈希 ec8a4eff…        声明哈希 cc55c989…
```

页面上一句加粗的话：**「READY——规格已冻结，不可再修改。」**

变体表：

```

定价快照 deepseek-chat-dafe2be1 (358157cc…) | 知识快照数 0 | 变体哈希 b200b9c7…
```

这一行里有**五个哈希**：数据集哈希、实验声明哈希、AgentVersion 声明哈希、
定价快照哈希、变体哈希。它们合起来回答一个问题：
**三个月后有人问「这个结论是怎么来的」，你能不能完整复现。**

还有两个字段值得单独说：

- **构建 SHA `fc2efba81f76`**：连跑这次实验的**代码版本**都记下来了。
  因为评分逻辑改了，同样的数据集也会给出不同的分。
- **HOLDOUT 曝光次数 0**：holdout 切分每被看一次，这个数就 +1。
  holdout 的意义在于没被拿来调过参，而「看了几次」是这件事唯一可审计的度量。
  这个实验是 DEV 切分，所以曝光 0。

### 14.4 发布门禁

![发布门禁](assets/22-release-gates.png)

> 不可变的规则集合，把对比证据转换为 PASS、FAIL 或 **INCONCLUSIVE** 的门禁决定。
> **策略不可变——如需调整请新建策略，而不是编辑现有策略。**

**这一页是空的**：「还没有发布门禁策略。」

我把这张空页也放进来，因为它诚实：**门禁的数据模型和 API 做完了，
但一条真实策略都还没建。** 这是当前最明确的一个未完成项，
第 17 节会再提一次。

注意三值而不是二值：`PASS / FAIL / **INCONCLUSIVE**`。
样本不够、或者两侧差异落在噪声里，正确答案是「判不了」，而不是随便给个 PASS。

## 16. 顺手能看到的几件小事

**双语**。右上角 `EN / 中文` 切换，整套界面都有中文。
第 13 节里有一条更有意思的证据：问题用中文问、政策原文是英文，

**明暗主题**。`☾ / ☀`，在每一张截图的左上角。

**无障碍**。每一页最上面都有一个「**跳到主要内容**」的跳转链接
（只在键盘聚焦时可见，截图里因为拍的是 DOM 文本所以能看到它）。
第 12 章那八轮前端实测就是在测这类东西。

**导航结构本身是一种表达**。侧边栏分五组：
`总览`（仪表板/运行/运行对比/审批）、

`构建`（智能体/知识库/检索实验台/工具）、
`评估`、`工作区`。
「应用」和「构建」分开，正好对应「同一套运行时 + 四种产品形态」这个架构。

## 17. 截图里看不到的东西

这一节是这章最重要的一节。**一组漂亮的截图最大的危险，
是让人以为没拍到的部分也一样完整。**

### 17.1 MCP 连接完全没有前端界面

这是最大的一条。

```bash
grep -rln "mcp-connections\|mcpConnections\|McpConnection" apps/web
```

**没有任何匹配。**

也就是说：第 6 节那 17 个工具里，绝大多数（`search_papers`、`query_metrics`、
`query_sql`、`issue_refund`…）都来自 MCP 远程服务器，
后端有完整的 MCP 连接管理、凭据加密、SSRF 防护、工具发现与同步，
**但这些全部只有 API，没有一个页面**。

所以本章拍不到「怎么添加一个 MCP 服务器」这一步。
要复现这些工具，得直接调 API。这是一个真实的产品缺口，不是"暂未截图"。

### 17.2 断线重连没有被拍到

第 15 章加的 `agent_run_events` 表和迁移 `0027` 让 Run 的生命周期脱离了 HTTP 连接：
断线之后重连可以重放事件。但**重放这件事在截图里是不可见的**——
它成功的表现恰恰是「看起来什么都没发生」。

要拍它，得在 SSE 中途杀掉连接再重连，然后证明事件没重复也没丢。
那是第 16 章用代码做的事，不是截图能做的事。

### 17.3 发布门禁一条策略都没有

见 §14.4。数据模型、API、三值判定逻辑都在，**策略是 0**。

### 17.4 前端 0 测试

第 6 章的状态表里这条还挂着：**后端 99 个测试文件 744 个用例，前端 0**。
这一章拍到的所有前端行为，验证方式都是「人看了一眼」或「脚本跑了一遍」，
不是回归测试。**截图证明它今天能跑，不证明它明天还能跑。**

### 17.5 这些截图是一个时间点

所有数字都是 2026-09-21 那个工作区的状态。
`76 次运行 / 90.8% / 0.0483 USD` 会随着每次跑动而变。
它们在这里是**样例**，不是**规格**。

### 18.3 截图脚本

脚本本身放在 `.scratch/`（这个目录在 `.gitignore:37` 里），

## 19. 三句话总结

1. **这一章的每个数字都是从真实数据库渲染出来的**，包括那些不好看的：
   6 次 token 未知、7 次失败、1 次撞成本闸门、1 条审批被拒、1 页门禁是空的。
2. **界面上反复出现的一件事是「承认不知道」**——未知 token 单独计、
   成本不可测就留 `—`、工具全挂时模型说「这是传输失败不是健康证明」、
   门禁有 `INCONCLUSIVE`、客户信息块主动声明"这是你填的不是查的"。
   这不是十个巧合，是同一条设计原则在十个地方的实现。
3. **最大的缺口现在是 MCP 连接没有 UI**——后端完整、前端为零。
   本章拍不出「怎么接一个 MCP 服务器」，这一条比任何一张截图都更值得记住。
