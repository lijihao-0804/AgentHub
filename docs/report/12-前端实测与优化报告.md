## 一、为什么要这样测

看源码能发现"写错了"，发现不了"在真实数据下垮掉了"。这一轮暴露的 8 个问题里，
有 **5 个只有展开真实数据后才会出现**——JSON 载荷、真实工作区名、真实徽章文案。
静态审查一个都抓不到。

### 测试方法

```
注入探针 window.__probe()
  ↓
点击真实 <a> 元素导航   ← 关键：保住内存里的会话 + 注入的全局变量
  ↓
强制展开所有 <details>   ← 关键：把折叠起来的真实载荷摊开
  ↓
四类测量：
  ① document.scrollWidth  vs  viewport 宽度
  ② 每个 grid 容器的轨道宽度和  vs  它自己的 clientWidth
  ③ 每个文本节点的前景色  vs  逐层 alpha 合成后的真实背景色
  ④ 每个可聚焦元素  vs  最近的 overflow 裁剪祖先
```

### 踩过的坑（方法论本身的教训）

| 坑 | 现象 | 原因 | 对策 |
|---|---|---|---|
| `history.pushState` 导航 | 评估子页面全报 h1「数据集」 | 不驱动 Next App Router | 只点真实 `<a>` |
| 编辑源码触发 Fast Refresh | 扫描卡死在 `n: 0` | 整页重载冲掉 `window.__probe` | 扫描期间不改源码 |
| 自写的 alpha 合成器 | 浅色主题里测出深色背景 | `over()` 恒返回 `a:1`，提前终止祖先遍历 | 用标准 source-over：`aOut = af + ab*(1-af)` |
| 可访问名检测 | 大批 `input` 报"无名" | 没检查 `<label>` 包裹 | 补 `closest('label')` / `label[for]` |

**第三条最值得记**：工具本身有 bug 时，会报出看着很严重的假问题（"深色泄漏到浅色主题"）。
修正合成器后重测，真实数字是 4.11——问题真实存在，但性质完全不同。**任何自动化审计的第一个
发现，都要手工复核一次再动手改。**

## 二、发现并修复的 8 个真问题

### 核心洞察：其中两个是**同一个 bug 穿了两件衣服**

`min-width: auto` ——
- **grid**：隐式 `auto` 轨道按 max-content 定宽，**不受容器约束**
- **flex**：flex item 默认不肯收缩到内容宽度以下

---

### #1 审批页布局爆破（Round 1 · 严重）

**现象**：`/approvals` 展开「技术参数」后，文档宽度 1014px → **2099px**，
整站出现横向滚动条，右侧「执行」列被挤出屏幕。

**测量**：
```
.approval-list  clientWidth = 681px
.approval-list  实际 grid 轨道 = 1814.4px   ← 隐式 auto 轨道撑到了 <pre> 的 max-content
.approval-card  = 1814px
```

**根因**：未换行的 `<pre>` 的 max-content 宽度 = 最长那一行的宽度。
外层 `.approval-list` 没声明列宽，隐式 `auto` 轨道乐意长到那么宽，然后依次撑爆卡片 → 列表 → 页面。

**两层修复**：

```css
/* 组件层：让载荷换行 */
.technical-details pre {
  overflow-wrap: anywhere;
  white-space: pre-wrap;
}
```
这一条同时是**产品决策**：审批人不该为了看清自己正在批准的东西而去拖横向滚动条。

```css
/* 结构层：让卡片成为自己宽度的权威 */
.approval-list  { grid-template-columns: minmax(0, 1fr); }
.approval-card  { grid-template-columns: minmax(0, 1fr); }
```

**影响面**：`TechnicalDetails` 组件全站用在 **16 处**，一处修复覆盖全部。

**验证**：`doc 1014 == vw 1014`，卡片回到 681px。

### #2 手机端顶栏压垮（Round 3 · 严重）

**现象**：375px 下，语言和主题两个药丸开关被压到 **2px 宽**，文字溢出到药丸外面；每页横向溢出 9px。

**根因**：`.ws-selector` 是 `min-width: auto`，**拒绝收缩**。
于是浏览器把全部压力转嫁给了看起来"能压"的两个固定尺寸开关——而它们其实毫无余量可让。

**修复**：明确谁让步、谁不让步。

```css
.lang-switch { flex-shrink: 0; }   /* 固定尺寸控件，没有可让的 */
.user-menu   { flex-shrink: 0; }
.ws-selector { min-width: 0; }     /* 工作区名是唯一能缩短而不丢控件的内容 */
.ws-selector-trigger { min-width: 0; max-width: min(20rem, 100%); }
```

**验证**：`doc 375 == vw 375`，开关恢复 53px / 76px。

### #3 截断截错了一半（Round 3 · 中等）

**现象**：修完 #2 后，顶栏显示 `V...`——被保留下来的是**组织名**，而不是工作区名。

**这是个语义问题不是排版问题**：
`Verification Org / Research` 截断成 `Verification O…`，读者不知道自己站在哪。
组织是上下文，工作区才是位置。

**修复**：拆成两个 span，让上下文先走。

```tsx
{orgPrefix && <span className="ws-org-prefix">{orgPrefix} /</span>}
<span className="ws-path">{workspaceLabel}</span>
```
```css
@media (max-width: 720px) { .ws-org-prefix { display: none; } }
@media (max-width: 480px) { .theme-switch  { display: none; } }
```

**为什么藏主题开关是划算的交易**：主题默认跟随系统 `prefers-color-scheme`
（`theme-provider.tsx:59`），手机本来就显示对的那个，不问也没错。
而"我在哪个工作区"没有这种默认值——在一个审批会写生产的控制面里，这是**唯一不能被压成一个字母的上下文**。

**验证**：顶栏读作 `☰ | EN 中文 | ● Research ▾ | 账户`。

### #4 中文界面里的英文枚举（Round 2 · 中等）

三个 `<select>` 在全中文界面里裸露 `LATEST` / `PINNED`。

修复时顺手解决了一个**更基础的问题**——新标签说的是"这个模式是什么意思"，
而不是要求读者已经认识这个枚举：

| 线上值 | en-US | zh-CN |
|---|---|---|
| `LATEST` | Follow the latest snapshot | 跟随最新快照 |
| `PINNED` | Pin to one snapshot | 固定到指定快照 |

线上值完全不变。`tsc --noEmit` 通过，同时也证明了两个语言包的 key 集合仍然严格镜像
（`zh-CN.ts` 的类型由 `en-US.ts` 推导）。

### #5 浅色主题状态色系统性压线（Round 6 · 中等）

**这是这一轮最有价值的发现**，因为它是**系统性**的，不是单点。

实测数字（修复前）：

| 元素 | 字号 | 对比度 | AA 要求 | 结论 |
|---|---|---|---|---|
| `tone-success` 徽章 | 11.5px | **4.11** | 4.5 | ✗ |
| `tone-danger` 徽章 | 11.5px | **4.46** | 4.5 | ✗ |
| `tone-attention` | 12.8px | **4.47** | 4.5 | ✗ |
| `tone-success` | 12.8px | **4.49** | 4.5 | ✗ |
| `lang-option` 激活态 | 12.5px | **4.32** | 4.5 | ✗ |
| `tone-warning` | 12.8px | 4.57 | 4.5 | 勉强 |

**根因不是"选色随手"，而是一个隐蔽的假设失效**：
这些颜色**几乎从不显示在白底上**。徽章自己用 `-soft` token 画一层淡底，
而这层淡底往往又叠在一个已经有色的块（`.approval-state-block`）上。
真实对比度要对着**这个色层栈**测，而不是对着页面背景测。
按"在白底上好看"选出来的颜色，落到真实位置就掉到线下了。

**修复**：整族加深一档。

```css
--accent:    #46772a → #3d6824;
--success:   #2b7a3a → #256b33;
--warning:   #8a6200 → #7c5800;
--danger:    #bc3126 → #ab2b21;
--attention: #a65413 → #954a10;
```

**结果**：最差从 **4.11 → 4.96**，全族过 AA，且留了一层色层的余量。
深色主题完全不受影响（这是 light 覆盖块）。

### #6 用边框 token 画文字（Round 6 · 轻微，但是个语义错配）

`.breadcrumb-separator { color: var(--border-strong); }`

浅色 **1.86:1**，深色 **3.3:1**——在 DOM 里存在，在屏幕上看不见。

它是 `aria-hidden="true"` 的装饰字符，WCAG 1.4.3 **不适用**，所以这不是合规问题。
真正的问题是：`--border-strong` 是为"贴着表面画一根发丝线"调的，拿来当文字色必然过淡。
换成表示"弱化文字"的 `--text-placeholder`。

### #7 键盘用户在两个开关上完全看不到焦点（Round 7 · 中等 · a11y）

**测量**：
```
.lang-option  相对 .lang-switch（overflow: hidden）的余量：
  左 0.8px  右 0.8px  上 0.8px  下 0.8px
全局焦点环：outline 2px + offset 2px = 4px 光晕  →  全被药丸裁掉
```

**修复**：把环画到内部。
```css
.lang-option:focus-visible { outline-offset: -2px; }
```
特异性 (0,2,0) > 全局 `:focus-visible` (0,1,0)，稳定覆盖。

**同时排除的误报**：全站扫描还标出了 `.research-pane-body` 里的一批按钮。
分轴复测后确认是**误报**——那是 `overflow: auto` 的滚动容器，
焦点会被自动滚入视野；而横轴上左右各有 16px 内边距，4px 光晕放得下，无裁剪。

### #8 flex 容器里的 Box Alignment 关键字（Round 8 · 轻微）

`applications.css:91` —— `align-items: end` 在 flex 容器里浏览器支持不一致，
构建时 autoprefixer 持续告警。改为 `flex-end`。

全量核对了其余 4 处 `align-items: end`，都是 **grid** 容器——`end` 在 grid 里是正确关键字，不动。

| 项目 | 初判 | 复核结论 |
|---|---|---|
| 评估子页面 h1 全相同 | 疑似 bug | **误报**：`pushState` 不驱动 App Router，源码 key 各不相同 |

| 大量重复请求 | 疑似缺陷 | **非缺陷**：41 个唯一请求里 32 个正好 2 次 = React StrictMode 的 dev 双调用，生产构建不发生 |

> **误报率 6/14 ≈ 43%。** 这不是工具差，这是自动化审计的常态。
> 价值不在于工具直接给答案，而在于它把 20 个页面缩小到 14 个待查点，
> 剩下的判断仍然必须人做。

关于那 **66 个隐式 `auto` grid 容器**（静态扫描发现的同类潜在风险）：
决定**不做无差别加固**，而是让探针在真实数据下判定哪些真的会垮。
768 / 375 / 桌面三档 × 双语系共 61 次探测中，轨道越界数 = **0**。结论：剩下 65 个当前无实际风险，
不为假想问题增加 65 条 CSS。

## 五、可复用的结论

1. **`min-width: auto` 是 CSS 布局爆破的头号元凶**，在 flex 和 grid 里表现完全不同，
   但根是同一个。凡是容器里可能出现宽内容（JSON、长 id、URL），
   就该显式写 `minmax(0, 1fr)` 或 `min-width: 0`。

2. **对比度必须对着合成后的真实背景测**，不能对着设计稿里的白底测。
   半透明 `-soft` token 叠加是这类问题的高发区。

3. **`overflow: hidden` 的圆角容器会吃掉内部元素的焦点环。**
   凡是把按钮包进药丸/胶囊的地方，都要给 `:focus-visible` 配 `outline-offset: -2px`。

4. **响应式收缩要明确指定"谁让步"。** 不指定的话，浏览器会选错——
   它会压最"软"的那个，而那个往往是最不该被压的。

5. **自动化审计的第一个发现必须手工复核。** 本轮 43% 的初判是误报，
   其中一个还是工具自身 bug 造成的。
