### 阶段 0 — 让上下文裁剪不再是黑盒

问题：原来裁剪按「消息」为单位，一轮问答的 user 和 assistant 可能被拆开，
模型会读到一个没有问题的回答。并且裁剪发生了什么，外面完全看不见。

做法：
- 把「一问一答」作为一个不可分割的驱逐单位（`exchange_group`）。
- 裁剪结果写进 step metadata，前端可以看到「丢了几轮、为什么丢」。

### 阶段 1 — 会话内检索

问题：窗口只回放最近几轮，更早的内容一旦被丢掉，agent 就只能回答「我不记得了」。

做法：给 agent 一个工具，可以回查被窗口丢掉的本会话轮次。
三个条件缺一不可才会挂上这个工具：发布版本打开了开关、本次运行属于某个会话、
组合层确实注入了 searcher。**少任何一个就干脆不给这个工具**——
模型能看见却用不了的工具比没有更糟，它会白白浪费一轮去发现这件事。

Playground 单次调试（`thread_id IS NULL`）完全不受影响。

### 阶段 2 — 长期记忆

这是最大的一块，三个独立的难点：

**(1) 写入门禁不能交给提示词。** 让 LLM 回答「什么值得记住」，它永远能找出点什么。
所以真正决定写不写的是代码不是提示词：模型产出的每一条都要过
`normalize_candidate`（长度、类型、空白归一）和 `content_hash`（去重），并提供一段
来自当前用户输入的可验证 `evidence`；抽取只读取用户输入，不读取 assistant final output。
才可能落库。

**(2) 注入的类别不能按 role 判断。** 注入的记忆用 `system` role 写，
这样供应商会把它当上下文而不是用户发言。但 `SYSTEM_PROMPT` 在预算里是**必留**的，
而记忆是证据。如果按 role 分类，记忆就变成不可驱逐的，
足够多的记忆会把「用户当前问的问题」挤出去。

解法：按**位置**判断。`_categorize_messages` 多收一个 `memory_message_count`，
在 role 判断**之前**先按位置判定 `is_memory`。同时把 history 的判定从开区间
（`index < history_end`）收紧成闭区间（`history_start <= index < history_end`），
否则记忆那条会被 history 吞掉。

**(3) 记忆不能自称可信。** 记忆是「更早的模型写的、关于更早对话的文本」，
它和工具输出一样是 `UNTRUSTED`。

> **这里抓到了一个真 bug。** 写测试
> `test_a_memory_cannot_claim_to_be_trusted` 时发现 `_project_json_value`
> 用的是 `candidate.setdefault(key, trust)`，于是一条自带
> `"trust": "SYSTEM"` 的记忆会**保留**这个标签——正好打穿了这个机制存在的唯一理由。
> 同样的洞也影响 `TOOL_RESULT`。改成 `candidate[key] = trust`（赋值，不是兜底）。
> 这是一个由测试驱动发现的、在注入攻击面上的真实缺陷。

**快照。** 记忆是可变的，运行是可重放的，这两件事打架。
所以第一次 PREPARE 把选中的 id 冻结进 `agent_runs.effective_memory_snapshot`，
之后每一次 PREPARE（审批恢复、重放、评测 A/B）都**按 id 装载**，
包括那些后来已被取代或被人停用的。重放要回答的问题是
「这次运行当时拿到了什么」，不是「它现在会拿到什么」。

快照是**对象**不是裸数组：`{"selected_at": ..., "memory_ids": [...], "memory_content_hashes": {id: sha256}}`。
因为「选了但一条都没选中」和「还没选过」作为数组都是 falsy，
而分清这两者正是整个确定性主张的全部内容。

**抽取永远不在热路径上。** 唯一的入队点是 `_complete_run`——
`ThreadService.submit_turn`（进程内）、`/runs/stream`（可能走 Celery）、
审批恢复（第三条路）三条路径都在状态提交后汇合于此。
入队时**不读 spec**（那要在热路径上加载 `AgentVersion`），
由 worker 重新校验 `long_term_memory` 开关——
所以伪造或重放一条队列消息，不能让一个没开开关的 agent 偷偷学东西。

### 阶段 3 — 记忆管理界面

三个接口挂在 agent 下面（不是 workspace 级，否则等于邀请调用方传一个不被校验的 agent_id）：

```
GET  /api/v1/workspaces/{ws}/agents/{id}/memories
POST /api/v1/workspaces/{ws}/agents/{id}/memories/{mid}/invalidate
POST /api/v1/workspaces/{ws}/agents/{id}/memories/{mid}/reactivate
```

前端新增「记忆」页签：列出内容 / 类型 / 状态 / 权重 / 最近使用 / 来源运行，
可按状态筛选、分页，并提供「停止使用」「重新启用」两个按钮。
`en-US` 与 `zh-CN` 同步新增同一套 key（`MessageKey` 是编译期强约束，两边必须完全一致）。

## 2. 做出的取舍（按用户授权「自行判断」记录在此）

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 权限 | 读取复用既有 `agent_run` / `agent_edit`，修改仍为 `agent_edit`，**不新增 RBAC 权限** | `workspace_read` 只读工作区元数据，不足以读取记忆正文；跨工作区仍按资源 scope 隔离 |
| 删除 | **没有删除接口**，只有 INVALIDATED | 删掉就等于删掉了「为什么那次运行会那么说」的答案 |
| 跨工作区 | 一律 404，不是 403 | 可区分的错误就是存在性探针 |
| 重新启用冲突 | 唯一索引拒绝 → 翻译成 409 `MEMORY_ALREADY_ACTIVE` | 停用期间可能又学到了同一条；不能让两条一样的 ACTIVE 记忆同时摆在模型面前，也不能让它变成 500 |
| 去重范围 | 唯一索引是**部分索引**，只管 `status = 'ACTIVE'` | 去重管的是「它现在相信什么」。一个月前被取代的事实完全可能被重新学到，那次插入必须允许成功 |
| 抽取用哪个模型 | 用 agent 自己发布的 model plan | 单独加一个模型配置 = 多一处要配、多一份凭据要解析、多一条「agent 的记忆被它主人从没批准过的模型写入」的路 |
| 默认值 | 两个开关都默认关 | 两个都不开，发布出来的 spec 哈希与记忆功能存在之前**完全一致**（`memory` 在全 false 时从 `resolved_spec` 里整体省略），`SPEC_SCHEMA_VERSION` 保持 2 不变 |
| 注入形式 | **一条**消息装全部记忆，不是一条一个 | 八条独立条目可能被裁掉一半，留给模型一个它无从察觉的残缺信念集 |
| 长记忆处理 | 超长候选**丢弃**，不截断 | 截断会得到一个半句话，读起来是另一个主张。丢掉没有损失：长到这个程度的「记忆」本来就是对那轮对话的摘要，不是记忆 |

## 3. 数据模型

新表 `workspace_memories`，单头迁移 `0028_workspace_memories`（down_revision `0027_agent_run_events`，**未制造 multiple heads**）。

关键字段：

- `status`：`ACTIVE` / `SUPERSEDED` / `INVALIDATED` — 这就是全部词汇表。
  `SUPERSEDED` 当前仅为未来语义替换预留，自动抽取不会创建；`INVALIDATED` 表示人工停用。
- `kind`：`FACT` / `PREFERENCE` / `DECISION` / `CONSTRAINT`。
- `content_hash` + 部分唯一索引 `uq_workspace_memories_active_hash`（`WHERE status = 'ACTIVE'`）。
- `provenance` / `thread_id` / `source_run_id`：回答「它为什么会这么认为」。
- `salience` / `last_used_at` / `expires_at`：为后续的衰减与 TTL 预留，**本次没有实现衰减逻辑**（见第 7 节）。

同时给 `agent_runs` 加了 `effective_memory_snapshot JSONB NOT NULL DEFAULT '{}'::jsonb`。

## 5. 真机验证（已完成）

### 5.1 抽取这一环单独验证

用**真实 DeepSeek**（`deepseek-chat`）跑了抽取链路中最不确定的一环：
真实模型面对真实的抽取提示词，到底会不会吐出可解析的记忆。
调用的是仓库里的真对象：`extraction_request` → 真实 API → `parse_candidates` → `normalize_candidate` 写入门禁。

| 用例 | 模型原始返回 | 解析 | 过门禁 |
| --- | --- | --- | --- |
| 中文·值得记 | `{"memories":[{"content":"用户团队每周五下午发版，周五下午不安排任何需要改动生产的任务。","kind":"CONSTRAINT"}]}` | 1 | **1** |
| 英文·值得记 | 两条：`AgentHub is built on Postgres.`(FACT) + 不要新增 RBAC 权限(CONSTRAINT) | 2 | **2** |

### 5.3 实测改掉的三个缺陷

都不是测试脚本的问题，是代码的问题。

1. **`record()` 返回一串 `None`**（`packages/memory/store.py`）。
   `WorkspaceMemory.id` 用 `default=uuid4`，这是 **flush 时**才生效的列默认值，
   所以 `session.add(row)` 之后立刻读 `row.id` 拿到的是 `None`。
   仓库里唯一的调用方只用了 `len(created)`，所以线上没炸，
   但"返回创建了什么"这个约定对任何别的调用方都是假的。

2. **worker 容器没有主密钥**（`docker-compose.yml`）。
   `docker` 不在 `DEVELOPMENT_ENVIRONMENTS` 里，所以容器内没有兜底密钥；
   而 worker 自己要解密 provider credential——agent 运行、评测、记忆抽取全都要。
   少这一项，worker 里**每一次模型调用**都会以
   "Credential encryption is not configured" 失败。
   影响面远超长期记忆。`beat` 只调度、不解密，没给。

3. **删会话必 500**（新增迁移 `0029`）。四个复合外键都是 `(workspace_id, 外键列)`，
   用意是子行永远不可能指向别的租户的父行；但 `ON DELETE SET NULL` 会把外键的
   **所有**列置空，`workspace_id` 也在其中，而这一列在四张表上都是 `NOT NULL`。
   于是删除父行不是「忘掉出处」，而是直接抛 `NotNullViolation`。
   对外的症状是 `DELETE /threads/{id}` 只要该会话跑过一次就返回 500。
   **其中两个约束是 0028 刚带进来的，另外两个（`agent_runs`、`artifacts`）
   从更早就一直是坏的，与长期记忆无关。** 四个一起修：只修记忆那两个的话，
   会话仍然删不掉，长期记忆连自己的清理路径都没有。
   PostgreSQL 15 起支持 `ON DELETE SET NULL (列名)`，只置空点名的那一列。
   修完复验：删掉教它的那个会话后，记忆还在，只是 `thread_id` 变成 `NULL`、
   `workspace_id` 完好——正是当初写在模型注释里的语义。

   顺带修了 `test_provider_credential_cipher_requires_key_in_production`：
   它断言的是「没配密钥」，但 `Settings` 会读环境变量**和 `.env`**，
   而任何能起 `docker compose` 的人都必须配了这个密钥，
   所以这条测试此前只在恰好没配的机器上通过。

### 5.4 为什么 API 跑在本机而不是容器里

Windows 上 uvicorn 的 `asyncio_loop_factory` 在 `sys.platform == "win32"` 时
**硬返回 `ProactorEventLoop`**，不看事件循环 policy；
而 LangGraph 的 Postgres checkpointer 用的 psycopg 明确拒绝在 Proactor 上跑。
所以本机起 API 时每一次 agent 运行都在
`packages/agent_runtime/adapters/langgraph/checkpoint.py` 抛
`Psycopg cannot use the 'ProactorEventLoop' to run in async mode`。

处置：自己建 `SelectorEventLoop` 再把 `server.serve()` 交给它跑
（`.scratch/run_api.py`，不入库）。
**这是 Windows 本地开发独有的问题，容器是 Linux，不会遇到**，
因此没有为它改任何产品代码。

验证数据全部清理完毕：`workspace_memories` 回到 0 行，
`agent_runs` / `workspaces` 回到实测前的基线。

### 5.6 顺带验了 RAG 整条链路，并抓到一个生产级缺陷

「知识库 / RAG 在容器里到底有没有真的跑起来」此前也是**没验过的断言**。
这次单独造了一份含虚构事实的结算规则文档（批次号 `BLUEWHALE-7731`、
每月 17 日 03:40 执行、96 小时作废、留存 1825 天），走完整条链路：

上传 → worker 解析/切块/向量化 → Qdrant 建索引 → 生成快照 →
检索 playground → 绑定 `search_knowledge` 工具与 PINNED 快照 → 发布 →
提问「BLUEWHALE-7731 这个结算批次是每月几号、几点执行的？」

**第一次跑是失败的**，而且失败得很有价值。容器日志：

```
Loading SentenceTransformer model from BAAI/bge-m3 ...
{"tool_identity": "search_knowledge", "decision": "ALLOW_AUTO",
 "status": "error", "error_code": "TOOL_TIMEOUT", "duration_ms": 30722.674}
```

agent 于是诚实地回答「知识库检索超时，我无法确认……所以不知道。」

**根因**：检索组件是懒加载的，冷进程的第一次 `search_knowledge`
要在**工具自己的 30 秒预算之内**把 BGE-M3 和 cross-encoder 两个模型加载完，
实测约 35 秒。也就是说——**每次部署之后的第一次知识库检索必然失败**，
而且失败的样子是「知识库里没有」，不是「系统还没准备好」，
这比直接报错更糟：它会让人以为是知识库的问题。

**修法**：把加载挪出请求路径。

- 三个适配器各加一个 `warm()`（`embeddings.py` / `sparse.py` / `reranker.py`）；
- `packages/knowledge/composition.py` 加 `warm_retrieval_components()`，
  逐个预热，**单个模型加载失败只记 warning 不中断进程**——
  不需要检索的路由不该被拖垮，需要的那条会在使用点带着 request id 失败；
- API 在 lifespan 里用 `asyncio.to_thread` 起一个**不 await** 的后台任务
  （别的请求不必排在半分钟的加载后面），关闭时取消；
- worker 挂 `worker_process_init`，**每个子进程各付一次**——
  组件缓存是进程内的，Celery 在导入之后才 fork，父进程预热不保证被继承；
- 开关 `knowledge_warm_models_on_start` **默认关**：打开意味着首次要下 ~3.3GB，
  本地只想看看设置页的人不该付这个钱。`docker-compose.yml` 的 api 与 worker 都显式打开。

**修完复跑，同一个问题**：

| 指标 | 修之前 | 修之后 |
| --- | --- | --- |
| 首次 `search_knowledge` | TOOL_TIMEOUT（30.7s 超时） | 正常返回 |
| 入库耗时 | 33s（冷） | **2.0s**（热） |
| 检索 playground | 7.1–11.7s（冷） | **0.7s**（热） |
| 回答 | 「检索超时，所以不知道」 | **「每月 17 日 03:40（UTC+8）。」** |

并且断言了它是**查出来的不是猜出来的**：运行步骤里确实出现
`search_knowledge`，且没有任何一步 FAILED。

结论：**RAG 在容器里是通的**，此前没通的是「刚部署完的那一次」。

### 5.7 界面这一轮改了什么

记忆管理页原来只有一个状态下拉和一张表。这一轮补齐的是「记忆多起来之后
还能不能用」——因为真实场景里这张表很快就是几十上百行：

- **内容搜索框**，300ms 防抖，最长 200 字符，与后端 `q` 参数对齐；
- **类别筛选**（FACT / PREFERENCE / DECISION / CONSTRAINT）；
- **「清除筛选」按钮**，只在确实有筛选时出现，且看的是输入框的即时值而不是
  防抖后的值——否则按钮会晚 300ms 才出现；
- **状态用色块徽章**而不是纯文字，三个状态三种色调；
- **分页范围读数**（第 x–y 条 / 共 z 条），此前只有上一页下一页两个按钮，
  翻到哪了是看不出来的；
- **「没有匹配」与「还没学到任何东西」分成两个空状态**——
  前者要放宽筛选，后者要去跑一次对话，给同一句话是帮倒忙；
- 内容列单独给了 `.memory-content` 样式，长句子折行而不是把表格撑破。

诚实地记一笔：**这一页没有截图验证**。本机没有可用的浏览器自动化
（这台环境的 in-app 预览未启用，装 Playwright 属于为了截图新引入一整套依赖），
所以它的保证只到「`tsc --noEmit` 通过 + 两个语言包的 key 由类型系统强制齐全
（`MessageKey` 由 en-US 推导，`DICTIONARIES` 要求 zh-CN 结构一致）+
它依赖的接口行为已被容器内端到端验过」。
造数脚本已经写好（10 条不同类别/状态、含一条超长中文句），
下次有浏览器环境时按 `.scratch/ui_seed.py` 打印的地址登录即可看。

## 9. 语义收口与安全硬化补充（2026-09-22）

- Memory 的唯一业务 scope 是 `(workspace_id, agent_id)`，表示团队、项目和工作流的共享上下文，
  不建立 user-level 个人画像。读取复用既有 `agent_run` 或 `agent_edit`；仅有 `workspace_read`
  时返回 403，写入状态仍要求 `agent_edit`。
- 后台抽取只把当前 `user_input` 交给模型；每个候选必须携带不超过 300 字符、且逐字出现在
  当前用户输入中的 `evidence`。assistant final output 不进入抽取请求。证据会写入 provenance，
  但不会保存整段用户输入。抽取是 best-effort 异步过程，运行成功不保证产生记忆。
- 新快照保存 `memory_ids` 与 `memory_content_hashes`。回放时缺行或 hash 不一致会以
  `AGENT_MEMORY_SNAPSHOT_INTEGRITY_ERROR` fail closed；历史 ID-only 快照保持兼容。
  只有最终 ContextAdmissionResult 中仍含具体 memory id 的条目才更新 `last_used_at`；选择、
  reinforcement 或被预算淘汰不会更新它。
- 新启用长期记忆的发布版本冻结独立 `max_memory_tokens=1500`；旧的 memory-off 版本继续使用
  原有共享预算与 hash 语义。`MEMORY` 始终是 `UNTRUSTED` evidence。
- 自动抽取只做去重与 salience reinforcement，不创建 `SUPERSEDED`；该状态和
  `superseded_by_id` 仅为未来明确的语义替换流程保留。批量写入以候选级 savepoint 隔离并发唯一键冲突，
  一个候选冲突不会回滚同批其他候选。
