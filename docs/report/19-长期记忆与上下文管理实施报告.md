### 阶段 0 — 让上下文裁剪不再是黑盒

问题：原来裁剪按「消息」为单位，一轮问答的 user 和 assistant 可能被拆开，
模型会读到一个没有问题的回答。并且裁剪发生了什么，外面完全看不见。

做法：
- 把「一问一答」作为一个不可分割的驱逐单位（`exchange_group`）。
- 裁剪结果写进 step metadata，前端可以看到「丢了几轮、为什么丢」。

### 阶段 1 — 会话内检索

问题：窗口只回放最近几轮，更早的内容一旦被丢掉，agent 就只能回答「我不记得了」。

做法：给 agent 一个工具，可以回查被窗口丢掉的本会话轮次。
三个条件缺一不可才会挂上这个工具：发布版本打开了开关、本次运行属于某个会话、
组合层确实注入了 searcher。**少任何一个就干脆不给这个工具**——
模型能看见却用不了的工具比没有更糟，它会白白浪费一轮去发现这件事。

Playground 单次调试（`thread_id IS NULL`）完全不受影响。

### 阶段 2 — 长期记忆

这是最大的一块，三个独立的难点：

**(1) 写入门禁不能交给提示词。** 让 LLM 回答「什么值得记住」，它永远能找出点什么。
所以真正决定写不写的是代码不是提示词：模型产出的每一条都要过
`normalize_candidate`（长度、类型、空白归一）和 `content_hash`（去重）
才可能落库。

**(2) 注入的类别不能按 role 判断。** 注入的记忆用 `system` role 写，
这样供应商会把它当上下文而不是用户发言。但 `SYSTEM_PROMPT` 在预算里是**必留**的，
而记忆是证据。如果按 role 分类，记忆就变成不可驱逐的，
足够多的记忆会把「用户当前问的问题」挤出去。

解法：按**位置**判断。`_categorize_messages` 多收一个 `memory_message_count`，
在 role 判断**之前**先按位置判定 `is_memory`。同时把 history 的判定从开区间
（`index < history_end`）收紧成闭区间（`history_start <= index < history_end`），
否则记忆那条会被 history 吞掉。

**(3) 记忆不能自称可信。** 记忆是「更早的模型写的、关于更早对话的文本」，
它和工具输出一样是 `UNTRUSTED`。

> **这里抓到了一个真 bug。** 写测试
> `test_a_memory_cannot_claim_to_be_trusted` 时发现 `_project_json_value`
> 用的是 `candidate.setdefault(key, trust)`，于是一条自带
> `"trust": "SYSTEM"` 的记忆会**保留**这个标签——正好打穿了这个机制存在的唯一理由。
> 同样的洞也影响 `TOOL_RESULT`。改成 `candidate[key] = trust`（赋值，不是兜底）。
> 这是一个由测试驱动发现的、在注入攻击面上的真实缺陷。

**快照。** 记忆是可变的，运行是可重放的，这两件事打架。
所以第一次 PREPARE 把选中的 id 冻结进 `agent_runs.effective_memory_snapshot`，
之后每一次 PREPARE（审批恢复、重放、评测 A/B）都**按 id 装载**，
包括那些后来已被取代或被人停用的。重放要回答的问题是
「这次运行当时拿到了什么」，不是「它现在会拿到什么」。

快照是**对象**不是裸数组：`{"selected_at": ..., "memory_ids": [...]}`。
因为「选了但一条都没选中」和「还没选过」作为数组都是 falsy，
而分清这两者正是整个确定性主张的全部内容。

**抽取永远不在热路径上。** 唯一的入队点是 `_complete_run`——
`ThreadService.submit_turn`（进程内）、`/runs/stream`（可能走 Celery）、
审批恢复（第三条路）三条路径都在状态提交后汇合于此。
入队时**不读 spec**（那要在热路径上加载 `AgentVersion`），
由 worker 重新校验 `long_term_memory` 开关——
所以伪造或重放一条队列消息，不能让一个没开开关的 agent 偷偷学东西。

### 阶段 3 — 记忆管理界面

三个接口挂在 agent 下面（不是 workspace 级，否则等于邀请调用方传一个不被校验的 agent_id）：

```
GET  /api/v1/workspaces/{ws}/agents/{id}/memories
POST /api/v1/workspaces/{ws}/agents/{id}/memories/{mid}/invalidate
POST /api/v1/workspaces/{ws}/agents/{id}/memories/{mid}/reactivate
```

前端新增「记忆」页签：列出内容 / 类型 / 状态 / 权重 / 最近使用 / 来源运行，
可按状态筛选、分页，并提供「停止使用」「重新启用」两个按钮。
`en-US` 与 `zh-CN` 同步新增同一套 key（`MessageKey` 是编译期强约束，两边必须完全一致）。

## 2. 做出的取舍（按用户授权「自行判断」记录在此）

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 权限 | 复用 `workspace_read` / `agent_edit`，**不新增 RBAC 权限** | 能改一个 agent 记得什么，和能改它的提示词是同一种权限。单开一个权限只会多一样忘记授予、或者授予过宽的东西 |
| 删除 | **没有删除接口**，只有 INVALIDATED | 删掉就等于删掉了「为什么那次运行会那么说」的答案 |
| 跨工作区 | 一律 404，不是 403 | 可区分的错误就是存在性探针 |
| 重新启用冲突 | 唯一索引拒绝 → 翻译成 409 `MEMORY_ALREADY_ACTIVE` | 停用期间可能又学到了同一条；不能让两条一样的 ACTIVE 记忆同时摆在模型面前，也不能让它变成 500 |
| 去重范围 | 唯一索引是**部分索引**，只管 `status = 'ACTIVE'` | 去重管的是「它现在相信什么」。一个月前被取代的事实完全可能被重新学到，那次插入必须允许成功 |
| 抽取用哪个模型 | 用 agent 自己发布的 model plan | 单独加一个模型配置 = 多一处要配、多一份凭据要解析、多一条「agent 的记忆被它主人从没批准过的模型写入」的路 |
| 默认值 | 两个开关都默认关 | 两个都不开，发布出来的 spec 哈希与记忆功能存在之前**完全一致**（`memory` 在全 false 时从 `resolved_spec` 里整体省略），`SPEC_SCHEMA_VERSION` 保持 2 不变 |
| 注入形式 | **一条**消息装全部记忆，不是一条一个 | 八条独立条目可能被裁掉一半，留给模型一个它无从察觉的残缺信念集 |
| 长记忆处理 | 超长候选**丢弃**，不截断 | 截断会得到一个半句话，读起来是另一个主张。丢掉没有损失：长到这个程度的「记忆」本来就是对那轮对话的摘要，不是记忆 |

## 3. 数据模型

新表 `workspace_memories`，单头迁移 `0028_workspace_memories`（down_revision `0027_agent_run_events`，**未制造 multiple heads**）。

关键字段：

- `status`：`ACTIVE` / `SUPERSEDED` / `INVALIDATED` — 这就是全部词汇表。
  现在相信的 / 被后来学到的取代的 / 被人关掉的。
- `kind`：`FACT` / `PREFERENCE` / `DECISION` / `CONSTRAINT`。
- `content_hash` + 部分唯一索引 `uq_workspace_memories_active_hash`（`WHERE status = 'ACTIVE'`）。
- `provenance` / `thread_id` / `source_run_id`：回答「它为什么会这么认为」。
- `salience` / `last_used_at` / `expires_at`：为后续的衰减与 TTL 预留，**本次没有实现衰减逻辑**（见第 7 节）。

同时给 `agent_runs` 加了 `effective_memory_snapshot JSONB NOT NULL DEFAULT '{}'::jsonb`。

## 5. 真实模型验证（已完成）

用**真实 DeepSeek**（`deepseek-chat`）跑了抽取链路中最不确定的一环：
真实模型面对真实的抽取提示词，到底会不会吐出可解析的记忆。
调用的是仓库里的真对象：`extraction_request` → 真实 API → `parse_candidates` → `normalize_candidate` 写入门禁。

| 用例 | 模型原始返回 | 解析 | 过门禁 |
| --- | --- | --- | --- |
| 中文·值得记 | `{"memories":[{"content":"用户团队每周五下午发版，周五下午不安排任何需要改动生产的任务。","kind":"CONSTRAINT"}]}` | 1 | **1** |
| 英文·值得记 | 两条：`AgentHub is built on Postgres.`(FACT) + 不要新增 RBAC 权限(CONSTRAINT) | 2 | **2** |
| 无可记 (`1+1 等于几？`) | `{"memories": []}` | 0 | **0** |

三件事因此被真机证实：

1. 提示词确实能让真实模型产出**严格 JSON**，无代码围栏、无前言。
2. **「大多数轮次没什么值得记」这条约束真的生效了**——琐碎问答返回空数组，
   而不是硬编出一条。这是整个功能最容易失败的地方。
3. 记忆**用用户自己的语言**写下，`ensure_ascii=False` 的选择被证明是必要的。

API key 全程通过环境变量传入、脚本不打印、脚本跑完即删，**未进入仓库、未进入日志**。

## 6. 未完成项与原因（不加修饰）

**没有跑通的是：起真实 API + worker + Postgres + Redis，发布一个打开长期记忆的 agent，
对话一轮，等后台抽取落库，再开一轮看记忆是否被注入，以及 memory-on / memory-off 的 A/B。**

原因链条：

1. 本机 PostgreSQL 与 Redis 都不是系统服务，而是跑在 `docker-compose.yml` 里的容器。
2. Docker Desktop 当时没在运行。启动后，引擎起不来，backend 直接崩溃，日志：

   ```
   starting services: initializing Inference manager:
   listening on unix://.../Docker/run/dockerInference:
   remove .../Docker/run/dockerInference: The file cannot be accessed by the system.
   ```

3. 该目录下 `dockerInference` / `dockerEthernetVfkit` / `userAnalyticsOtlpHttp.sock`
   三个残留的命名管道桩已经 stat 不出来也删不掉（`rm` 返回 0 但文件仍在）。
   Docker Desktop 弹出的对话框只给两个选项：**Quit** 或 **Reset to factory defaults**。

**处置决定：停在这里。**

- 「Reset to factory defaults」会清掉用户所有的镜像、容器和卷。不做。
- 继续去动 OS 层的孤儿管道句柄，大概率需要重启机器，
  并且有把用户这套 Docker 装得更坏的实际风险。
  用户在睡觉，这类不可逆、面向环境的操作不属于「自行判断继续」的合理范围。

这是**用户环境的问题，不是本次代码的问题**。恢复办法通常是重启机器后
Docker Desktop 即可正常启动。醒来后要跑通端到端，需要：

```bash
docker compose up -d postgres redis
```

## 7. 明确没做的（不是遗漏，是刻意留白）

- **记忆衰减 / TTL**：`expires_at`、`last_used_at`、`salience` 三个字段都已在表里，
  但**没有实现衰减或过期清理逻辑**。在没有真实数据、不知道记忆实际累积速度之前，
  定一条衰减曲线只是凭空猜测。
- **记忆的人工新增 / 编辑**：只提供「停用 / 重新启用」。
  让人手写记忆等于开了一条绕过写入门禁的路，且立刻要回答
  「人写的和模型写的冲突时谁赢」，这个问题现在没有答案。
- **语义检索**：当前 `select` 用的是词项加权匹配（`_TERM_WEIGHT`），不是向量检索。
  在记忆条数还是两位数的时候，向量检索带来的是一条额外的嵌入依赖，不是效果。
- **跨 agent 共享记忆**：记忆严格 scope 到 `(workspace_id, agent_id)`。
