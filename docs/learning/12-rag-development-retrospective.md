## 一、先统一数据口径

### 1.1 我们实际测过好几种不同的 RAG 与 Wiki 路径

| 数据/阶段 | 实际任务和范围 | 主要数字代表什么 | 最容易误读的地方 |
| --- | --- | --- | --- |
| M3 / M7-E 内部数据 | `m3-retrieval-v1`，小型项目检索集 | Candidate Recall、Final Recall、MRR、检索时延 | 小集合满分不能说明公开任务也接近满分 |
| 10 月初短政策对照 | 8 个短政策，24 个 DEV 问题，每策略重复 3 次，共 144 次 | 真实检索生成、目标政策命中及有限语义抽检 | 72 次调用不是 72 个独立问题；48 份抽检不覆盖全部 144 份答案 |
| SciFact | 全部 5,183 篇文档、9,189 个生产切块；809 train / 300 test | 文档级 nDCG、Recall、MRR | 0.7974 是排序分，不是 79.74% 回答正确率；train DEV 与 test 不同 |
| FiQA | 全部 57,638 篇文档、71,576 块；648 test 问题 | 跨语料检索排序确认 | 没有在这一轮生成最终答案；test 暴露后不能继续当新盲测 |
| QASPER 离线场景 | 给定论文，在论文内部找证据 | 段落召回、完整证据集、正文覆盖代理 | 段落 ID 命中不等于必要文字完整，更不等于答案正确 |
| MuSiQue-Ans | 每题给定含干扰的候选段落，多跳短答 | 支持段落召回、完整支持链、答案 EM/F1 | 是题内候选任务，不能叫开放全库多跳检索；Ans 轨不评价天然不可回答能力 |
| QASPER 真实 Run | 论文转 Markdown 后真实上传、入库、发布并执行服务层 AgentRun | 实际证据可见性、答案、Run 时延 | 没有覆盖原 PDF/OCR、HTTP/UI、Celery broker、所有恢复场景 |
| P-A1 语境前缀 | SciFact / FiQA 各 20% 种子抽样语料 | 抽样索引上的检索对照 | 64 / 252 个可评查询不能直接和全语料成绩横比 |
| Wiki 独立 v1 | 五份来源编译，六个固定问题 × WIKI/RAG/HYBRID；另做一次新增来源的增量编译 | 页面组织、输出门禁、可答性标志、查询/编译用量 | raw 基线是 MiniLM＋DENSE，不是最终生产 BGE；有效输出不是语义正确率 |
| Wiki 冲突维护 v2 | 增量后六份来源；两次 MODEL 复核失败，另验编辑者声明与邻接冲突交付 | 自动复核的失败边界、缓存复用、双方证据与拒绝裁决 | 不是 v1 同来源对照；人工声明成功不能记成自动冲突召回成功 |
| Wiki 原生 W5 | A Wiki 型 20 题、B 双层证据 20 题、C 撤销 10 题；111 次模型请求 | 原生工具链、引用范围、origin、撤销与运行完成率 | 双层送达 11/11 是成功子集，全题为 12/20；不是 Wiki-vs-RAG 质量 A/B |

同名“200 题”也有不同身份：消费者预算确认使用排除旧问题 ID 的一批；互补集合确认又排除了历史问题和相同支持来源；后来的交付修复回归重新使用了已曝光问题。下面会分别标明，不能合并成“统一的 200 题测试集”。

### 1.2 这份报告怎样使用指标

**检索质量**至少分三层：候选里是否有相关来源，相关来源是否排在前面，最后输出是否保留完整支持集合。Recall、nDCG、MRR各回答其中一部分。多跳任务还必须看“全链齐备”，只找对一半支持材料通常不能完成问题。

**答案质量**以各轮原有 EM/token F1 为准，保留失败计零和原分母。它们测的是与参考答案的词面匹配；不能直接改名为语义准确率。引用 ID 合法、原文引句存在、引句支持所问关系，依次是不同强度的保证。

**成本**分开记录实际输入、输出、额外选择调用、模型流水线时延和完整 Run 时延。历史多数公开实验没有冻结价格快照，因此有 token 账本也不能据此编人民币或美元总费用。缓存筛查只能提供质量证据，不能提供真实时延证据。

Wiki 还要分开初次编译、增量更新、冲突维护与查询。独立 v1 的 23 次模型请求已包含编译和查询；加两次复核后累计才是 25 次，不是 23+25。原生 W5 是另一套语料和执行链，111 次不能与独立 v1 拼成同一轮质量或成本比较。这里不编造两条线合并后的总体准确率。

下文 `pp` 表示百分点。例如 F1 从 27.92% 到 39.39% 是增加 11.47pp。nDCG 从 0.7533 到 0.7974，则优先写差值 `+0.0441`。置信区间跨零，只说明没有证实稳定正向或负向，不能写成“等价”“确定无效”或“显著下降”。

## 二、开发线：按问题出现的顺序还原

### 2.1 9 月 18—19 日：先把可运行、可追溯的检索底座做出来

最初的开发不是先做高级检索策略，而是依次建立上传与修订、可靠入库 worker、索引、Hybrid 检索、Playground、Citation QA 和知识快照。提交大致按下面的顺序展开：

`b316bc0` 上传与修订 → `5398aaa` 可靠 worker → `9a60c67` 索引 → `ccee315` Hybrid 检索 → `6ee29f2` Playground → `0261823` Citation QA → `f4bd4ab` / `09ef846` 快照与完整性修复。

这条链路形成了后续实验最重要的基础：Document 是逻辑文档，Revision 是内容版本，Chunk 是原始片段，Snapshot 冻结本次可用的修订成员。Qdrant 返回候选后，还要回数据库装载真实 Chunk，核对工作区、知识库和快照成员；不能把向量库的命中直接当成最终授权与来源证明。

第一份 [M3 基线](../benchmark/m3-retrieval-baseline.md) 使用 BGE-M3 与 BGE-reranker-v2-m3，本机 RTX 3060 Laptop GPU。总体 Candidate Recall@20 和 Final Recall@5 都是 1.0000，MRR@5 为 0.9833。当时证明的是这套工程链能在内部数据上正确检索，不涉及答案质量。

随后 [M7-E 策略消融](../benchmark/m7e-retrieval-ablation.md) 的真实数据让“Hybrid 必然比 Dense 好”这个直觉先受了一次检验：

| 策略 | DEV Final Recall@5 | HOLDOUT Final Recall@5 | 全集 MRR@5 | 全集 P95，ms |
| --- | ---: | ---: | ---: | ---: |
| DENSE | 1.0000 | 1.0000 | 0.9333 | 61.845 |
| HYBRID | 0.9500 | 0.9000 | 0.8083 | 93.118 |
| HYBRID_RERANK | 1.0000 | 1.0000 | 0.9833 | 525.339 |

**当时的收获：**框架跑通、检索满分、重排有效，是三个不同结论。Hybrid 自身可能引入噪声，重排可以修复部分排序，但延迟明显上升。小数据下的满召回尤其容易掩盖后续研究空间。

### 2.2 9 月 21—22 日：先撞上的坑是知识生命周期和冷启动

`7c7ab82` 的提交说明记录了一个非常具体的业务问题：两份独立文件分别代表旧版和新版政策，但系统只能表达同一文档内部 Revision 的退役，不能表达“这份文件被另一份替代”。14 道版本敏感问题中，4 道选中了过时文件。两份文件都与问题相似，单纯调相关性无法表达权威性。

修复引入 `effective_date` 和 `superseded_by_document_id`，检索对被替代文档施加可配置惩罚，同时把文档名和是否被替代告知模型。这里选择惩罚而非直接过滤，是因为用户也可能明确询问旧政策。该提交还增加可选 rerank-score 下限：当时语料上不可回答问题最高约 +0.10，可回答问题最低约 +1.88，但明确没有把这个阈值写成通用常数。

**心得：**“语义相似”不等于“当前适用”。生效时间、版本、替代关系属于知识语义，不能完全交给 embedding 猜。相关性下限也需要按语料校准，不能从一组分数间隔推广到所有知识库。

`bfc275d` 则记录了部署后的第一次检索超时：模型冷加载约 35 秒，超过工具自身 30 秒预算，最终表现成“没有知识可答”。修复把加载挪出请求路径，加入进程内预热和权重缓存。提交说明中的现场观察为入库 33s→2.0s、检索 7–11s→0.7s。

这些是当时的部署观察，不能冒充随机配对性能实验，但故障性质很清楚：**系统未就绪不能被解释成知识不存在**。API 与 worker 的模型缓存各在自己的进程里，预热也不能只做一处。[现有课程](06-knowledge-rag.md)保留了这一条写入、读取与预热主线。

### 2.3 10 月初：从检索测试走到真实检索生成，但小政策集仍然太容易

[M-I3 / M-I4 验收](../reviews/AgentHub-面试增强M-I3-M-I4验收报告-20261003.md) 对 8 个短政策、24 个 DEV 问题做了 Dense 与 Hybrid-Rerank 各 3 次真实调用，总计 144 次。

| 指标 | Dense，72 次 | Hybrid-Rerank，72 次 |
| --- | ---: | ---: |
| 最终相关政策召回 | 1.000 | 1.000 |
| MRR | 0.9722 | 0.9931 |
| 全部答案含目标政策引用 | 72/72 | 72/72 |
| 总时延 P50 / P95，ms | 2810.5 / 3398.3 | 2957.5 / 3770.4 |

这次用到了真实生产 BGE、Qdrant、`search_knowledge` 和生成模型，比纯检索基线更接近用户路径。但两组目标召回都满，实际能看到的主要是排序与时延差异。语义抽检仅覆盖每题每策略第一轮，共 48/144，不能把它扩写成全批无幻觉；跨文档推理也没有在这批证明。

**这一步暴露了评测本身的瓶颈：**系统需要更有难度、任务类型更清楚的公开数据，而不是继续在八篇短政策上追求微小分数变化。

### 2.4 10 月 21—22 日：公开数据第一轮，最确定的收益来自 SQL

`38af57d` 引入公开 RAG 数据与固定的 RAGChecker 源码材料。SciFact 随后成为第一条完整公开检索基线：5,183 文档、9,189 块、809 train DEV 和 300 test，切块 1200 字符、重叠 200。模型仍为 BGE-M3 dense、词法 sparse、BGE reranker。

DEV 分阶段计时发现 rerank 之外还有明显数据库开销。原 `_load_chunks` 每题把快照全部 5,183 个 revision ID 展开进 SQL；改为通过 `KnowledgeSnapshotItem` JOIN 候选块，并保持租户、知识库、文档、修订与快照约束。没有改排序、模型或阈值，Qdrant 的原范围过滤也保留。

[SciFact 首轮验收](../reviews/AgentHub-RAG-SciFact首轮优化验收-20261021.md)在同进程共享预热模型、逐题随机交错顺序的条件下得到：

| test 300 题 | 旧 SQL | 快照成员 JOIN |
| --- | ---: | ---: |
| nDCG@10 | 0.748634 | 0.748634 |
| Recall@5 | 0.801556 | 0.801556 |
| Recall@20 | 0.875111 | 0.875111 |
| 热检索均值，ms | 488.223 | 439.650 |
| 热 P95，ms | 658.609 | 600.312 |
| 候选块加载均值，ms | 51.754 | 7.329 |

配对热检索均值差为 **−48.573ms，95% CI [−60.356,−37.384]ms**，均值下降 9.95%。四阶段全部块排名和分数一致。

**心得：**先做阶段归因，比先调 RRF 更划算。原计划曾预留 `rrf_k=10` 的尝试，看到 DEV 时延构成后没有执行，改做可验证的 SQL 优化。这是一次有依据地放弃调参。这里的“端到端”仅指检索服务调用，不包含回答生成、HTTP 或整个 Agent Run。

### 2.5 10 月 22 日：扩池与来源配额——找回更多尾部证据，前排却没更好

下一步将 `candidate_top_k`、`rerank_top_k`、`final_top_k` 分开，并增加每篇文档的软配额。借鉴了 RAGFlow 的阶段预算和 Haystack 的多样性思路，但实现是来源配额，不是 embedding MMR。

固定 SciFact DEV 809 题，四个候选与同一 baseline 对照：[预算与多样性消融](../reviews/AgentHub-RAG预算与多样性消融-20261022.md)。

| DEV 方案 | nDCG@10 | Recall@5 | Recall@20 |
| --- | ---: | ---: | ---: |
| baseline，重排 20 | 0.753314 | 0.811578 | 0.876102 |
| 来源配额，重排 20 | 0.753686 | 0.810960 | 0.876720 |
| 重排 40 | 0.748953 | 0.808797 | 0.891553 |
| 来源配额＋重排 40 | 0.748641 | 0.810033 | 0.892789 |
| 重排 60 | 0.745428 | 0.806943 | 0.890008 |

各候选主差的多比较校正区间都跨零，没有方案同时达到冻结门槛。随后已暴露 test 300 题的真实五臂回归中，重排 40 / 60 的均值约从 476ms 升至 791 / 994ms，成本增幅约 66% / 109%；没有因为回归某列好看就推翻 DEV 选择。

事后诊断很有启发：

- 来源配额把重复来源块均值从 2.988 降到 2.734，却只补回 1 个相关问题—文档对。
- 重排 40 块在输入中补回 36 个相关对，但首个相关文档在 23 题前移、78 题后移。
- 重排 60 块补回 45 个相关对，仍有 91 题首个相关文档后移。

**心得：**多样性改善、候选覆盖改善、最终前排改善不是同一件事。更大的池子也引入难负例，重排器未必会利用新增材料。能力保留为可选配置，扩大预算和来源配额没有成为默认。

### 2.6 同一天：把“BGE sparse”真正做成 learned sparse，数值对齐了但组合收益没过门

原生产 sparse 使用 BGE tokenizer，计算 `1+log(TF)`，再由 Qdrant 加 IDF；它既不是 BGE-M3 原生 learned sparse，也不能直接叫标准 BM25。

这轮真正实现 hidden state → sparse linear → ReLU，重复 token 取 max、排除特殊 token，无额外 IDF；在独立 collection 建索引。为避免 ANN 重建干扰，两个实验臂的 dense 查询仍共享旧索引，只切 sparse。

[learned sparse 消融](../reviews/AgentHub-RAG学习稀疏召回消融-20261022.md)先验证实际 CUDA/FP16 数值：hidden state 最大误差 0、sparse 权重最大误差 0、dense 最小余弦 1.0，再跑全量 809 题。

| nDCG@10 的阶段 | 原词法 sparse 组合 | learned sparse 组合 |
| --- | ---: | ---: |
| sparse 单路 | 0.633084 | 0.658648 |
| RRF 融合后 | 0.713480 | 0.713832 |
| BGE 重排后最终结果 | 0.753314 | 0.744123 |

最终差 **−0.009191，95% CI [−0.019878,+0.001117]**，跨零；平均耗时增加约 27.65ms。没有通过选型门，未进入生产 factory，也未继续消费新数据集标签。

**心得：**“官方路径实现正确”和“在当前系统里有净收益”必须各验一次。单路显著更好的点估计到了融合只剩微小变化，最终还可能回落。这里被否决的是这个 learned sparse、RRF、BGE rerank 的固定组合，而不是整个 learned sparse 方法族。

准备阶段也踩过一个普通实现坑：把 tokenizer 返回的字符串路由元数据当成 tensor 调 `.to()`，首轮失败；修正元数据处理后重建成功。失败日志保留，数值门没有放宽。

### 2.7 父文档前置重排与 DBSF：两个“局部合理、整体不值得”的分支

**父文档前置重排。**把命中子块映射到同一合法 revision 的完整标题与摘要，同父只计算一次，再把分数广播回子块。它借鉴了 RAGFlow / LangChain 的父子身份，但实验操作发生在 BGE 重排前，不能写成完整复现 ParentDocumentRetriever，更不能泛指所有 Small-to-Big。

[809 题实测](../reviews/AgentHub-RAG父文档重排消融-20261022.md)：nDCG@10 **0.753314→0.754578**，差 +0.001264，95% CI [−0.009147,+0.011725]，未过门；平均时延 **475.90→658.75ms**，增加 182.85ms。

模型文本对减少了约 15%，但 padded token slots 从 5,806,308 增至 8,920,496，约多 54%。这解释了“调用对数减少，为什么反而更慢”：神经模型成本取决于输入长度和批次 padding，不只取决于候选数。父文本截断为零，不能用“也许被模型截断了”替这个结果找未经测量的解释。

**Qdrant DBSF。**固定每路均值±3σ归一化与相加，用已计算的候选 BGE 分数做质量缓存筛查。[结果](../reviews/AgentHub-RAG项目分数融合筛查-20261022.md)为 fusion nDCG **0.713480→0.725329**，但最终只有 **0.753314→0.753391**，差 +0.0000769，95% CI [−0.002152,+0.002317]。

809 题融合顺序都变了，460 题 top20 集合也变了，仍没有转化成最终有效收益。于是停止，未追加 GPU/真实时延实验，也没有继续扫权重和 σ。

**共同心得：**成熟项目提供机制假设，不提供本仓收益保证。最后一环的主指标不通过，就不应拿上游局部分数或者节省的调用次数宣布成功。

### 2.8 Onyx 风格来源选择：首次出现可跨语料确认的排序改进

这轮改变思路：保留 BGE 的 20 个子块先验，把同一来源最多 3 个已命中块组成模型视图，一次让 LLM 选择最多 10 个相关来源；被选来源整组前移，其余按原顺序补齐。没有引入新来源，也没有检索邻块。

首个请求就遇到 **HTTP 200、模型名正确、正文却为空**：256 个 completion token 全部被推理消耗。运行立即停止，保留 4,975 个已观测 token。核对实际适配代码后补上原生 thinking disabled 映射，另开执行记录，没有把首个失败覆盖成成功。[Onyx 原实验](../reviews/AgentHub-RAG-Onyx相关性选择-20261022.md)随后得到：

| SciFact DEV，809 题 | BGE 原排序 | Onyx 风格来源选择 |
| --- | ---: | ---: |
| nDCG@10 | 0.753314 | 0.797435 |
| Recall@5 | 0.811578 | 0.855089 |
| Recall@20 | 0.876102 | 0.876102 |

主差 **+0.044121，95% CI [+0.031808,+0.057236]**。六项 DEV 门通过。新增请求均值约 727ms，809 次成功执行观测 3,945,944 tokens。它提高了排序，没有增加候选集合；多轮使用的 SciFact DEV 仍属于探索。

随后冻结方法，不按新数据追调，在完整 FiQA 语料的 648 test 问题上做[独立确认](../reviews/AgentHub-RAG-FiQA独立确认-20261022.md)：

| FiQA，648 题 | BGE 原排序 | 冻结来源选择 |
| --- | ---: | ---: |
| nDCG@10 | 0.413369 | 0.453196 |
| Recall@5 | 0.408063 | 0.446980 |
| Recall@20 | 0.486300 | 0.486300 |

主差 **+0.039827，95% CI [+0.028954,+0.051075]**，六门通过。646 VALID、2 INVALID_OUTPUT，失败保留并回退 baseline；新增 API 均值约 744ms，观测 2,982,846 tokens。空标题适配错误发生于执行中，原失败和修复均保留，没有重试首题或删题。

**心得：**如果主要缺口在候选内的优先级，联合观察多个来源比继续换一个融合公式更可能对症。但这是付费排序改进，不能说更快、更便宜，也不能把 nDCG 增益当作答案增益。

### 2.9 FiQA 阶段损失复盘：后面再聪明，也救不回前面丢掉的候选

[瓶颈复盘](../reviews/AgentHub-RAG优化瓶颈复盘-20261022.md)读取同一批真实 trace，分开统计：

| FiQA 阶段 | 标注相关来源宏平均覆盖率 | 文档 nDCG@10 |
| --- | ---: | ---: |
| dense 原始 30 块 | 0.574303 | 0.397266 |
| sparse 原始 30 块 | 0.265861 | 0.150762 |
| 两路并集，最多 60 块 | 0.598908 | 不给无定义的融合顺序打分 |
| RRF 截断 20 块 | 0.486300 | 0.318534 |
| 同 20 块 BGE 重排 | 0.486300 | 0.413369 |
| 同 20 块 Onyx 选择 | 0.486300 | 0.453196 |

共 1,706 个标注正例问题—文档对，753 对在并集外；并集到 RRF20 又丢 203 对，其中 176 对只有 dense 找到。前一个问题关乎初始召回，后一个关乎候选保留，最后一个才关乎同池排序。

当前参数下的 RRF 还存在可手算的偏好：双路都在第 30 名的块得分为 `2/(60+30)=0.022222`，高于只在一路第 1 名出现的块 `1/(60+1)=0.016393`。这是当前排名融合的性质，不证明共同命中就不相关，但能解释为什么要检查通道共识是否挤掉有用的单路材料。

固定 20 块按已有 qrels 理想排序，FiQA nDCG@10 oracle 约 0.536175；两路并集的相应 oracle 约 0.645430。**这是固定候选与标注内的条件上限，不能当作全任务上限，也不是可部署的实测成绩。**

### 2.10 10 月 23 日：换场景才发现，输出填充比邻段扩展更有用

SciFact / FiQA 的文档排序无法回答“论文里的证据是否齐了”“多跳链是否完整”。于是开始 QASPER 与 MuSiQue 场景实验。

QASPER DEV 固定 train 80 篇、235 题，其中 202 题证据能完整对齐。比较原文前 5 锚块、加标题路径、预算内继续填充、同章节邻段扩展：

| QASPER 开发方法 | 证据召回 | 完整证据集 |
| --- | ---: | ---: |
| plain_small | 54.38% | 45.54% |
| heading_small | 57.84% | 50.50% |
| heading_fill | 77.04% | 69.31% |
| heading_neighbor | 63.84% | 56.44% |

固定预算内继续填充最强，邻段扩展有收益但不及填充。标题路径单独的增益区间跨零，不能把联合方案全部归功于标题。

[冻结确认](../reviews/AgentHub-RAG场景优化验收-20261023.md)结果如下：

| 任务与分母 | 证据召回 | 完整支持集 |
| --- | ---: | ---: |
| QASPER 官方 dev，854 可评 / 全采集 1005 题 | 62.24%→84.39% | 55.27%→78.69% |
| MuSiQue-Ans 官方 dev 抽样 300 题 | 73.97%→91.11% | 45.00%→76.33% |

QASPER 召回增益 95% CI [+19.79,+24.64]pp；MuSiQue 完整集增益区间 [+25.44,+37.72]pp。QASPER 的 60 道不可回答、91 道未完整对齐仍保留，只是不混入可评证据分母。

本轮最大的解释性证据是输出损失：MuSiQue 候选池不齐备始终 21 题，池内齐备却在输出后缺失从 **144 题降至 50 题**。QASPER 对应数量从 **233 降至 47**。这轮主要修的是“已经找到了却没交付”，不是换了更强 embedding。

代价也很实际：QASPER 输入均值 3509→7874 bytes，MuSiQue 3396→7854 bytes；标注 precision 分别 18.57%→12.40%、40.03%→21.75%。同为 8000 bytes 上限，并非实际输入等成本。MuSiQue 四跳完整集仅 **8%→30%**，远未解决长链。

额外试过 QASPER 的 LLM 来源选择：235 次调用、645,420 tokens，相对填充只 +2.47pp，99% CI [−1.51,+6.70]pp，未采用。之前在 SciFact / FiQA 有效的选择思想，也不是换个场景就自动值得额外成本。

### 2.11 真正接上消费者：检索预算设大了，模型却仍只收到一段 JSON preview

离线场景能装约 12 段，不代表真实 Agent 也能看到这些内容。`search_knowledge` 之后，runtime 还使用通用工具上限 4000；超限会转成截断 JSON preview。检索专用预算即使配到 8000，也救不回已经被前一层切掉的内容。

[消费者闭环实验](../reviews/AgentHub-RAG消费者闭环与答案评测-20261023.md)固定最多 5 个原子证据，增加 RAG 专用预算与完整 record/reference 配对准入，并做了关键的“只对齐预算”对照。新 200 题来自 MuSiQue 官方 dev，排除旧 300 题 ID，139 个共享支持原文组：

| 方案 | 答案 F1 | EM | 完整支持集 | 最终证据 bytes 均值 |
| --- | ---: | ---: | ---: | ---: |
| 旧路径，通用 4000 上限 | 27.92% | 20.00% | 25.50% | 4000 |
| 旧路径，仅通用预算对齐 8000 | 38.63% | 30.00% | 54.00% | 6241 |
| RAG 专用预算＋完整记录配对 | 39.39% | 31.50% | 54.00% | 6294 |
| 无检索诊断 | 1.00% | 0.00% | — | — |
| 标准支持段落诊断 | 62.83% | 48.00% | 100.00% | 3027 |

主比较 F1 **+11.47pp，95% CI [+5.76,+17.69]pp**。但新结构相对“仅预算对齐”只有描述性的 +0.76pp，开发集甚至 −0.54pp。因此不能把这次整体收益写成证据结构算法的独立突破。专用路径的工程价值是：不用给所有工具一起放大预算，还能在紧预算下整条取舍、保住匹配引用。

**这里学到最关键的一件事：评测必须捕获实际发给 provider 的消息。**拿 retriever 返回值证明“模型看见了”，中间少看了工具、observation 和最终准入好几层。

这轮还踩了数据泄漏坑：早期 MuSiQue chunk/locator ID 带跳数任务标签，进入了生成消息。发现后更换为不含任务标签的 UUID，污染版不用于选型或确认；干净来源型开发请求重新执行，原费用保留。这说明 gold 不进正文还不够，ID、locator、文件名、分组字段也可能泄漏。

### 2.12 证据包装压缩：输入少一半，质量非劣却没有成立

接着做共享 `EvidencePlan`，把模型阅读视图和完整来源注册表分开。模型看短引用、原文、标题及必要位置；完整知识库、快照、Revision、Chunk 身份留在运行状态侧。实验在固定 MuSiQue train160 上比较，继续保持最多 5 个原子证据和相同选择。

[结果](../reviews/AgentHub-RAG共享证据组装实施与评测-20261023.md)：

| 指标 | 原 `rag_records_v1` | 新紧凑视图 |
| --- | ---: | ---: |
| F1 | 47.86% | 45.69% |
| EM | 39.38% | 38.13% |
| 支持召回 / 完整集 | 81.15% / 61.88% | 81.15% / 61.88% |
| 平均输入 tokens | 2270.45 | 1160.64 |

输入减少 **48.88%**，但 F1 差 **−2.17pp，95% CI [−6.10,+1.68]pp**，不能满足预设 −3pp 非劣下界。于是没有推广默认，保留显式 `compact_v1` 实验选项。

相同原文、相同 5 个成员，意味着压缩包装没有补上缺失的关系链。还有一次可避免的成本：同证据的紧凑诊断与候选实际消息完全相同，执行前没合并，额外花了 160 次同输入请求。这些结果只能反映生成波动，不能当成另一算法或更多独立样本。

**心得：**效率改进要有自己的验收目标；省 token 并不自动意味着质量非劣。同题完全相同消息的诊断，应在派发前去重，并保留逻辑结果和物理请求的对应关系。

### 2.13 互补证据集合：不再只问每段多相关，而是问这几段能否一起回答

前面多跳场景已经说明：独立相关性最高的 5 段，未必覆盖问题的不同关系。新 `EvidenceSetSelector` 一次看最多 20 个候选，选最多 5 个互补原子证据；选择器的理由和答案不传给回答模型，只交付原文。

为了隔离“选了什么”和“如何排列”，主方案 `set_rank5` 改集合后仍按 BGE 排序；`set_read5` 只改变同一批原文的阅读顺序，作为诊断。[完整实验](../reviews/AgentHub-RAG互补证据选择与阅读组织-20261023.md)先在 train160 通过，再冻结到来源隔离的新 dev200：

| 来源隔离确认，200 题 / 134 组 | 基线 | 互补集合＋原 BGE 顺序 |
| --- | ---: | ---: |
| F1 | 36.34% | 52.49% |
| EM | 29.00% | 45.00% |
| 支持召回 | 82.58% | 90.67% |
| 完整支持集 | 63.50% | 80.00% |
| 最终证据 bytes 均值 | 6185 | 3034 |

F1 **+16.15pp，95% CI [+10.16,+22.82]pp**；完整集 +16.50pp。198 题候选池完整，基线保留 127 个完整集，新方法 160 个：恢复 47 题、损失 14 题，净增 33。

但“最终正文少了”不等于总成本下降：选择＋回答平均输入约基线 **1.979 倍**，增量流水线 P95 约 **1.619 倍**。选择器仍要先读候选池。新方案平均最终只选 2.45 段，也提示模型有提前停止的可能。

开发集阅读顺序诊断 F1 **61.22% 对 61.13%**，没有可靠额外收益，所以保留原相关性顺序。长链表现也不稳定：开发四跳完整集 3/13→0/13；确认四跳只有 7 题，完整集虽上升，答案 F1 仍低。不能用总体收益宣布长链已解决。

本轮还有整批请求失败的教训：最初 160 次选择请求全为 HTTP400，提示未含 JSON 模式需要的显式字样是修复时发现的适配问题，但因未存错误正文，不能把它断言为服务端已核实根因。后来首题先验有效再放量。全轮实际 1293 次请求，168 次已知 HTTP400，失败费用与未知用量保留。

最终留下显式组合服务 `EvidenceSetKnowledgeRetriever`，没有推广成全局默认。**这一机制是多跳的“交付层集合组织”，和后面“多查询结果聚合”不是同一个实验角色。**

### 2.14 尝试改回答过程：任务指导提示、先定位后回答，都没有稳定过门

证据集合改善后，仍存在问错关系、属性、时间和行政层级的错误，于是尝试两条回答侧机制。

**单次任务指导提示。**增加所问对象、关系、限定条件、最终属性和中间事实的区分，不改模型与材料。[固定 train160 实验](../reviews/AgentHub-RAG单次回答提示实验-20261023.md) F1 **61.15%→61.75%**，+0.60pp，95% CI [−1.95,+3.49]pp，EM 均 50%。11 对删除证据对照中，删除后正确拒答 **100%→81.82%**，未采用。

**先定位原文片段再回答。**第一阶段只能给出精确来源引句，本地验证逐字子串与范围；第二阶段保留原材料并附高亮。总最大输出配额控制为直接回答 768，对照定位 512＋回答 256。[结果](../reviews/AgentHub-RAG原文定位与答案生成评测-20261023.md)为 **60.78%→63.06% F1**，+2.28pp，95% CI [−1.11,+6.00]pp，没达到 +3pp 且区间为正的门槛；输入约 **2.216 倍**，模型流程 P95 约 **2.983 倍**。

这些局部确实帮助了个别连接题，但“海生普查执行时期”仍答成结果发布年份 2010，目标行政层级仍可能停在上一级。定位到一句真实原文，不能自动判断它是不是所问关系。两条方向都收口，没有为了微小点估计继续改同批提示追分；两阶段 reader 留在 benchmark 实验区。

### 2.15 真实论文 Run：离线证据覆盖的漂亮数字，到了实际路径不再成立

[12 篇论文场景](../reviews/AgentHub-RAG真实论文问答场景实验-20261023.md)把 QASPER 论文转 Markdown 真实上传，12 个成功任务、291 块，每篇一个知识库/快照，两配置共 24 个发布版本，执行 84 个服务层 AgentRun、168 个模型请求。

42 题全部保留，其中 1 题标注分歧，主比较 41 题。通用配置与论文配置的结果为：

| 指标 | 通用配置 | 论文配置 |
| --- | ---: | ---: |
| F1 | 21.16% | 24.02% |
| EM | 4.88% | 4.88% |
| 人工证据完整文本可见 | 5.26% | 10.53% |

F1 +2.87pp，95% CI [−0.35,+7.18]pp，未达推广门。38 道共识可答题的融合候选完整串可见为 18/38，两臂相同；最终模型实际可见只有 **2/38 对 4/38**。论文臂配置“最多 10 块”，实际每题只装入 4 块。设定上限不能当作实际处理量。

原测量还有一处偏差：通用臂全部落在 preview 字符串，评分器只识别 `data.results`，把已有可读片段漏计了。后来从保存的实际消息解析可恢复记录和 snippet 前缀，原数据与原报告保留，没重新请求来修分。说明**观测工具也可能错，不能把观测不到直接等同于真实没有。**

真实服务层 Run 比受控 I/O 更接近产品，但这批仍不覆盖 PDF/OCR、HTTP/UI、Celery broker 和完整恢复流程。后续分析也指出两配置同时改变了交付路径，因此 +2.87pp 不能解释成某个论文算法的独立因果效果。

### 2.16 自然段切块：可见性上升，答案基本没变，索引却增至 2.45 倍

下一轮试“段落优先，超长按句子/词/字符退化，最大 1000 字符，无重叠”，对照原 1200/200 固定窗口。24 篇论文、原计划 70 题，真实入库并发布两臂 48 个版本。

[结构化阅读单元报告](../reviews/AgentHub-RAG结构化阅读单元真实评测-20261024.md)：

| 原 70 题分母 | 固定窗口 | 自然段独立 |
| --- | ---: | ---: |
| F1 | 17.0136% | 16.9497% |
| EM | 2/70 | 3/70 |
| 人工证据完整可见 | 12/64，18.75% | 21/64，32.81% |
| 索引块数 | 635 | 1558 |

新组 31.2% 的块不足 200 字符。段落边界保住了，语义单元也可能被碎片化；元数据和块数的开销又重新影响交付。不能单凭可见性提高宣称“结构化切块成功”。

执行完整性也有限制：首题出现初始化、备用及未确认请求，另作补充登记仅运行剩余 69 题，保留原 70 题分母，首题双方补零，`inference_valid=false`。因此 F1 差 −0.0639pp 及跨零区间只作开发描述，不能当原计划完整确认。后来还查出 3 对问题的实际检索字符串不相同，提示约束没有被服务端强制，不能叫严格切块单变量实验。

**心得：**“自然段通常更合理”不是充分采用依据。边界、最大长度、是否合并、重叠、最终阅读视图是不同变量。这里测的是一整套段落独立策略，既不能泛化否定所有结构化切块，也不能因为它可见性更好就忽略答案门失败。该方案没有成为默认。

### 2.17 三材料诊断、实体交付与原文坐标：开始把“读错”和“没看见”分开

当召回与可见率无法解释答案，项目转向小规模可复核诊断。

**actual / sufficient / removed。**同一问题分别给实际片段、来源复核后的充分材料、删除必要来源后的材料。8 对＋5 道自然不可答，共 29 次请求。[结果](../reviews/AgentHub-RAG答案路径三条件诊断-20261024.md)：实际 F1 47.15%，充分 40.74%，EM 都为 12.50%；删除后拒答 4/8，自然标签不可答题拒答 2/5。

充分材料分数更低不能直接解释成“材料越多越差”：例如 SQuAD 两次都识别对名字，充分材料下多写了规模，F1 反降。另一方面，MAML 比较题实际/删除条件回答 Yes，充分列表条件却拒答，是真实关系与有界否定问题，不能全部归咎词面评分。诊断揭示了混合损失，没有给出总错误百分比。

**实体短值＋引文＋状态。**8 题、完整/删除两条件、两方案，共 32 次调用。新方案允许 ANSWERED / PARTIAL / 缺据 / 需澄清，并逐实体引文。[结果](../reviews/AgentHub-RAG实体答案交付契约开发评测-20261024.md)完整实体集合 **7/8→6/8**，格式/名称锚定有效 14/16，未过门。部分状态确实保住两题的缺口说明，但也把词向量训练语料 ukWaC 当成分类器评估数据的部分答案。名字能逐字引用，角色却错了。

**原文坐标覆盖。**历史指标按排名把片段串接后寻找完整段落，会被乱序和重叠干扰。[坐标复盘](../reviews/AgentHub-RAG全链路性能归因与决策-20261024.md)改为同来源区间并集。MAML 题的 1108 字符标注段落，在全索引和完整候选中实际覆盖 100%，旧串接指标却为 0；最终选 4 块后只剩 55.14%，模型的四个 1000 字符摘录只剩 37.27%。

这个例子把三个问题分开了：前段的 0 是测量误差；后段互补块排第 15 被舍弃是集合选择损失；进入 snippet 后再次减少是真实交付损失。引用合法但回答 Yes，不代表关系有来源支持。

**心得：**段落 ID、正文覆盖、关系支持要分别测。机器辅助语义审核也会引错条件或引用不精确；发现这种问题时，应保留 UNKNOWN，不能把它直接升级成人类金标。

### 2.21 查询分解 P-C1：子查询找到了，RRF 共享 top5 又把它们挤掉

`d8f0e02` 记录一次负结果。固定 200 题 MuSiQue，每题约 20 段，用确定性 BM25 作为零检索模型成本代理；两臂唯一策略差异为原问题对照“LLM 分解＋多查询 RRF＋共享 top5”。

| 跳数 | 题数 | Δ Recall@5 | 95% CI，pp |
| --- | ---: | ---: | --- |
| 2 | 114 | −6.58pp | [−12.50,−0.43] |
| 3 | 59 | −13.56pp | [−19.88,−7.27] |
| 4 | 27 | −18.52pp | [−26.92,−11.29] |

200 次分解、32,506 tokens；门失败即停，**答案生成 0 次**。[原负结果](../reviews/AgentHub-P-C1查询分解负结果报告-0e7ffb3.md)。

[后续法证复核](../reviews/AgentHub-RAG负结果法证复核-0730a94.md)补了有用的三臂比较：原问题 top5 召回约 **0.530**，多查询 RRF top5 **0.427**，任一子查询 top5 的并集覆盖 **0.730**。说明子查询确实带回了额外候选，而聚合没能在共享名额内保住它们。

需要再收紧一个容易夸大的说法：**union@5 是“每个子查询各取 5 个再并集”，不是总共只取 5 个。**它使用更大的候选集合，只证明有额外可用覆盖空间，不证明分解在同一最终预算下已经提高 20pp，更不证明后续一定能收回这 20pp。

当前 RRF 会奖励跨子查询都还算相关的干扰段落，而专门支持某个关系的来源只从一路获得贡献。这与早先 FiQA 的通道共识偏好呼应，但 BM25 题内代理不能代替生产 dense 检索实验。关闭的是当前固定组合，不是所有查询分解。

48 题双臂拒答干预中，删证据 28 题两臂均正确拒答；充分证据拒答却从 5/20 升至 8/20，F1 0.543→0.4733，负结果关闭。报告总账约 290 次调用，含实现缺陷导致的废跑，超出原路径 200 次上限；不能只算 96 次正式考卷隐藏成本。

**格式压词也没有跨过全部门。** [自闭环收尾](../reviews/AgentHub-自闭环收尾执行报告-a88bf74.md)记录最终 100 题 F 桶合并臂：格式失分回收 90.3%，F1 0.6374→0.6801，+4.28pp；但配对 CI 下界 −1.65pp、拒答 20→21，因此 FAIL 并终局关闭。词面护栏 0/100 激活，说明该机制没有真正受试，不能写成“已证明护栏无效”或“剩下的都只能靠模型能力”。该结论仅关闭已测试方案。

**表格试点也停在便宜的门。** TAT-DQA 单页财报 30 文档/61 题，生产 pypdf 的答案字符串送达率 68.9%，pdfplumber 表格平铺 77.0%，+8.1pp，未达到 +15pp 且 CI>0 的门；0 模型调用，DeepDoc 按规则未触发。没有把新解析器加入生产默认，也不代表 OCR、跨页表格或计算题已验证。

这条 RAG 研究线收口的同时，Wiki 在独立分支完成了编译与维护，再与最新 RAG 并轨。下面回到同期并行线，说明为什么增加 Wiki、哪些预期没有成立，以及接入消费者后又暴露了什么；不是说以下每步都发生在上述收尾之后。

### 2.26 Wiki 起点：把重复的证据组织提前做

此前的 RAG 已经证明，找到相关材料、选出互补集合、把必要文字送到模型，是三项不同工作。但跨问题仍在反复做主题归组和来源组织：相同政策、概念和实体，每次回答都从原始片段重新拼。Wiki 方向尝试把这部分工作提前到资料编译时，保存主题页、精确引句、来源和导航关系，供后续问题复用。

这只是一个值得检验的设计假设，不能从“预先整理了”直接推出答案更准或总成本更低。`0771735` 的调研与 `3fe00ed` 的实现选择自有薄编译层，复用现有 PostgreSQL、Celery、模型网关、RBAC 和原始 RAG；没有另起图数据库、Wiki 向量库或引入外部项目完整运行时。对既有项目更关键的是沿用 workspace、revision、snapshot 和发布语义，而不是多接一个框架。[选型记录](../wiki/research-and-selection.md)、[阶段 ADR](../adr/ADR-012-versioned-derived-wiki.md)。

第一版刻意收窄了“模型写知识”：模型提出标题、归组、命题与关联候选，业务代码校验 chunk 归属和精确 quote，再生成阅读页；原始修订继续作为事实来源。Markdown 是投影，数据库管理编译、缓存、页面与发布状态。没有把自由摘要反复作为下一轮事实材料，也没有把 relations 字段直接称为知识图谱。

**这一步的心得：**RAG 解决的是本次问题的取证，Wiki 增加的是跨问题的组织与维护。二者可以共享来源，却不能共享一个模糊的“知识已更新”状态；后面遇到的缓存、冲突、过期和撤销问题，都是这项持久化选择的直接代价。

### 2.27 独立六题对照：页数和导航边增加了，Hybrid 优势没有得到证明

`9beb449` 阶段固定三份 PostgreSQL 官方文档片段和两份受控冲突资料，六个问题分别走 WIKI、RAG、HYBRID，覆盖概念、精确事实、跨文档、冲突和不可回答问题。使用真实 DeepSeek；raw 为未改的 DENSE 路径＋本地 MiniLM 384 维＋内存 Qdrant，不能称为最终 BGE-M3＋Sparse＋Rerank 的对照。[独立验收](../wiki/acceptance.md)、[机器汇总](../wiki/live-summary-20261025.json)。

初次编译用 **5 次请求、12,565 tokens、68.779 秒**，生成 **23 页、31 条 claim、126 条导航边**。但只有 Records 页归并了两份来源，许多边是来源共现导航，不能把 126 当成经验证的语义关系数。这个观察提醒我们：结构产物数量容易增长，跨来源组织质量却需要另测。

| 查询模式 | 有效输出/尝试 | 可答性标志一致/尝试 | 查询模型请求 | 查询 tokens | 平均端到端时延 |
| --- | --- | --- | --- | --- | --- |
| Wiki-only | 3/6 | 3/6 | 5 | 4,849 | 2.215 秒 |
| RAG-only | 5/6 | 5/6 | 6 | 8,215 | 2.779 秒 |
| Hybrid | 5/6 | 4/6 | 6 | 10,509 | 3.471 秒 |

有效输出只表示 schema、引用范围和逐句引用门通过，可答性标志一致也不是语义判卷。五个失败保留为 WIKI_ANSWER_INVALID_OUTPUT；当时没有保存细分失败原因和失败响应原文，不能事后认定每个失败都由同一种格式或截断问题造成。

关键反例是冲突题：Hybrid 返回了“保存 7 年”和“保存 5 年”的双方证据，并明确无法裁定，但 insufficient 标志却是 false；Wiki 自身的编译 lint 也没识别出该冲突。文字看上去保守，不代表结构状态正确，更不代表自动维护已成功。

当轮结论是 **NO_DEMONSTRATED_HYBRID_BENEFIT**：Hybrid 有效输出没有超过 RAG，查询用量和时延更高，还没有摊入编译成本。Wiki-only tokens 较少，同时交付有效性也较低，不能直接当节省收益。保留多模式和原始路径，比按“混合一定更好”的直觉修改默认更有依据。

### 2.28 增量与生命周期：真正省下的是重复提取，新增的是状态管理责任

原计划增加一份来源后，增量编译只发 **1 次请求、1,036 tokens**，复用原有 **5 份 revision 提取缓存**。这是“未变化来源不用重新提取”的真实证据，不是所有页面更新都已做到最小图差分，也不是总时延、总费用按相同比例下降。初次/增量编译共六次请求，加查询十七次，共 **23 次、37,174 tokens**；usage 均已知，货币成本仍 UNKNOWN。[原始汇总](../wiki/live-summary-20261025.json)。

缓存边界因此拆开：单 revision 的提取规格没变，可以复用；全局冲突规则、编辑者声明、来源排除集改变时，仍要形成新的组织和发布身份。来源 snapshot 相同，不代表 Wiki 内容相同；只冻结原文 hash 无法解释“当时读的哪一版页面”。

工程上也踩了几类很具体的坑：

| 问题 | 修法与原因 | 学到的边界 |
| --- | --- | --- |
| 编译器把 locator 当字符串，真实字段却是 JSON 对象 | 对齐原有 DocumentChunk 数据合同 | 新模块应读真实模型，不能另造一份相似数据结构 |
| Decimal 费用直接写 JSONB 失败 | 保留精度为字符串，缺费用单列 UNKNOWN | 统计与持久化类型本身就是交付合同 |
| ORM 先转 READY 再插页，触发不可变保护 | 先 flush 完整页集，再于同一事务转 READY | 不可变规则要和写入顺序共同设计，不能靠关闭保护通过 |
| 初稿把 Wiki 撤销直接写成 raw DELETED，遇旧 ingestion 生命周期重算 | 改为 Wiki 范围撤销，编译冻结排除集，raw fallback 再过滤 | 新模块撤销权不能未经设计扩成全局资料删除权 |

这些问题与修复记在 [独立验收过程](../wiki/acceptance.md)。来源更新、新编译、显式发布、current 过期检查、历史读取和安全撤销逐渐分开；保留历史身份也不代表撤销后仍可交付正文。缓存与幂等不是只减少调用次数，还必须在崩溃、重投和权限变化后维持同一语义。

### 2.29 冲突识别：自动复核两次失败，人工声明仍要走真实交付验证

v1 的精确引句检查通过了，却漏掉 7 年/5 年冲突：不同来源给出的主题标签、谓词或条件并不天然一致。于是 `535e5bc`、`3081582` 增加独立的跨来源复核，把已验证 claims 交给模型，只允许返回有限的 claim ID 组，不允许它新增或改写事实。

这条看起来合理的自动路线，真实结果并未通过：

| 复核配置 | 实际用量 | 结果与证据边界 |
| --- | --- | --- |
| 4096 输出上限 | 输入 4,880，输出 4,096，合计 8,976 tokens | 结构无效；未记录 finish_reason，不能把截断当作唯一已证原因 |
| 显式改用独立 8192 复核 profile | 输入 4,880，输出 8,192，合计 13,072 tokens | 仍失败，finish_reason=length；停止继续扩大预算 |

原对照加这两次共 **25 次模型请求、59,222 tokens**，货币费用 UNKNOWN。没有发布无效复核结果，也没有因业务想要冲突功能就把失败记成完成。[4096 失败](../wiki/conflict-diagnostic-failed-4096-20261025.json)、[8192 失败](../wiki/conflict-diagnostic-failed-8192-20261025.json)。MODEL 模式保留为显式实验路径，默认 BASIC，没有把“更大输出预算”升级成默认解法。

最后落地的是 `e633111` 的编辑者声明：编辑者选取既有 chunk_id＋精确 quote，系统验证快照成员、原文和编译引文后，把声明冻结到新版本。复用全部 **6 份提取缓存，新增模型调用 0**，交付双方证据并拒绝自动裁决。它证明的是有证据约束的人工维护链，不是自动识别召回率。

这里还有第二个坑：第一次声明诊断命中了 Records 页，却没把邻接冲突页的内容送出来；**存了冲突关系，不等于问题入口能读到冲突**。`fa2fcc0` 补有界邻接检查和对方证据扩展，同一问题、同一已发布内容复验通过，零新增模型调用。首次失败也保留。[声明诊断](../wiki/declared-conflict-diagnostic-20261025.json)、[路由失败记录](../wiki/declared-conflict-diagnostic-failed-route-20261025.json)。

**这一步的心得：**把自动发现、人工确认、双方证据交付和真伪裁决拆成四件事，才能知道失败时由谁接手。人工路径有价值，但不该被包装为模型能力；导航边可用，也不该被包装为深层图推理。

### 2.30 从独立 API 到原生工具：接通结构门，不代表总体双层交付已经过门

Wiki 独立阶段先验收持久生命周期与 API，保留真实模型负结果；`11b74f8` 再把它并入最新 RAG，继续调用原有检索器。并轨定向验收 **288 项通过**是组合和兼容性证据，使用隔离数据库与确定性模型组件，没有重跑付费质量对照。旧报告写“原生绑定未实现”反映的是这个阶段，不是当前状态。[并轨记录](../wiki/integration-acceptance.md)。

`0523d06`～`318f604` 随后补全三条链：RAW/WIKI_DERIVED 统一证据 envelope；WikiBinding 发布时解析具体 publication ID/hash 并进入 resolved spec；Run/Experiment 冻结 effective_wiki_publications，由受治理的 query_wiki 消费。原文 RAG 的 LATEST 可在 Run/实验变体解析，Wiki 的 LATEST 则在 AgentVersion 发布时解析，两者不能按名字相同就照搬。

模型阅读视图只带必要正文、origin、页标识和短引用，完整 publication 身份留私有注册。这延续了前面 RAG 的经验：来源元数据不能挤掉正文，但压缩正文也不能丢掉来源合同。[原生实施](../reviews/AgentHub-Wiki原生绑定实施报告-318f604.md)、[当前架构](13-rag-wiki-architecture-and-rationale.md)。

`3cbc34e` 的原生 W5 使用固定 **50 题、111 次请求**，逐条核对 **320/320 条证据 origin 正确**。结果要按分母拆开看：

| 组别/门 | 结果 | 可以得出的判断 |
| --- | --- | --- |
| A：Wiki 型 20 题 | 18 完成，2 次工具调用上限失败 | 接入能工作，完整回答不是 20/20 |
| B：需双层证据 20 题 | 11 完成，9 次工具调用上限失败 | 存在真实执行可用性损失 |
| B：RAW＋Wiki 双层送达 | 成功项 11/11；计入后来失败 Run 时总体 12/20 | 全题仅 60%，没有达到 ≥80% 期望 |
| C：撤销 10 题 | 9 个新 Run 创建被拒；1 个预先冻结 Run 到工具后被阻断并最终拒答 | 历史冻结没有绕过消费层撤销，不是十个都在创建阶段拒绝 |
| 引用/来源/撤销硬门 | 分析记 PASS，引用范围与 origin 核对通过 | 结构与安全合同通过，不是语义正确率 100% |

工具上限耗尽说明运行失败发生在哪里，但不能未经新比较就断言“只要放宽次数便解决”。B 组模式还由系统提示要求，不是模型自主学会路由。A 组描述性 F1 **0.0877**受多句答案对短金标的形状影响；原分析的包含率观察也不是独立专家判卷。[机器分析与原始说明](../../benchmarks/wiki/results/wiki-native-e2e-20261025/analysis.json)。

### 2.31 10 月 26 日修复：组织结果必须带着风险状态到达最终消费者

**最后修的是不容易在离线排名里看见的故障。** `9ad8b9d` 修复预算类别漂移、消息信封、Citation QA 重试准入、HYBRID 双来源被挤掉、Wiki 风险状态丢失、选择器成本/截止时间等；`1673515` 修复编辑后重试身份，`c8bdeea` 归档验收。报告为 2078 项单测按用例身份覆盖通过（首跑夹具失败后定向补验，不是一次全绿）、144 项去重数据库回归、1 项旧数据迁移轮转、5 项前端 Node 回归及 TypeScript 通过；这些有各自范围与重叠，不能相加当本次新增测试或答案提升。模型付费调用为 0，业务环境未升级。[验收与机器汇总](../reviews/AgentHub-隐藏缺陷修复验收-20261026.md)。

对 Wiki 最直接的三个修复尤其说明问题：服务端标了不足/冲突，证据再投影却可能只留下正常引句；先排十条 Wiki 会把后面的 RAW 全部挤掉；LATEST 只看前十个 publication 会错过第十一个有效版本。修法分别是保留 server-owned 风险状态、在数量和预算层检查真实双来源并显式降级、分页扫描可用发布，而不是继续改回答提示词。

修后也没有宣称 HYBRID 永远双层送达：预算小到放不下两侧时仍需降级；publication 缺失/漂移不静默换新，撤销继续在消费层生效。`a2d47e4` 补齐本地构建与迁移一致性验收，仍未部署业务环境。这批数据证明的是 bug 修复和故障边界，没有新测答案 F1。

这段后续把 RAG 与 Wiki 的共同经验补完整：原始来源、派生组织、风险状态、工具返回、模型准入、恢复身份和账单都需要穿过真实消费者。只在服务层成功的一项能力，还不能算整个系统已经交付。

## 四、总结线：RAG 与 Wiki 研发真正学到了什么

### 4.1 RAG 要沿“信息在哪里消失”排障

这次最有效的调查顺序逐渐从“换哪个组件”变成下面这条链：

```text
原文是否有必要事实
  → 解析/切块是否保留
  → Dense / Sparse 并集是否包含
  → 融合后是否还在候选
  → 重排与集合选择是否保住整条支持链
  → 工具记录与引用是否完整
  → runtime 准入后实际消息是否仍有必要文字
  → reader 是否选对关系、范围、属性
  → 最终答案是否按任务契约交付
  → 评分是否反映用户要的结果
```

FiQA 的 203 个融合丢失正例对、MAML 排第 15 的互补尾块、通用工具 4000 的 preview 截断，分别发生在不同位置。只看最后 F1 无法区分；只看 Candidate Recall 又会把后半段全部漏掉。

Wiki 把这条链再向前延伸：原始引句有没有进入提取缓存，是否归到可命中的页，冲突关系是否随邻接证据交付，服务端不足/降级状态是否经过再投影保留下来。Records 页旁边明明存着冲突却没被读取，和 RAG 已召回正文却被 preview 裁掉，发生在不同层，但都属于“内部存在不等于用户得到”。

后来修复后的 MuSiQue 回归，候选池完整 195/200，而最终完整集只有 108/200，最该研究的是候选到最终集合；FiQA 并集覆盖只有约 0.599，初始召回也仍有空间。**瓶颈是场景与配置的属性，不是整个系统永久只剩某一层。**

### 4.2 独立相关性排序和互补性选择有不同目标

一个模型可以把五段都打成“很相关”，却五段都在解释同一个桥接实体，没有一段给出最终属性。扩池、去重、来源配额只能间接缓解，无法保证关系覆盖。

互补集合确认的 47 题恢复、14 题损失，是比“平均更相关”更具体的证据。它说明联合选择在那批任务有价值，也说明集合策略会伤到原本完整的题；不能只报恢复数。

RRF 在两路通道和多子查询场景都出现共识偏好。要检验的不是“RRF 好不好”这种大命题，而是当前通道质量、重复模式和共享预算下，分数累加是否服务于任务需要的证据组合。以后每一轮应先写清：想补哪类缺失、改变哪个集合、会不会增加干扰。

### 4.3 检索粒度和阅读粒度应该分开，但分开本身不保证效果

自然段独立带来更多短块，父文档前置重排带来 padding 成本，有界父段恢复又受预算约束。三者不是同一种失败。

合理的通用原则是保留原 Chunk 身份与坐标；扩展阅读视图另给范围和身份，不把后来拼接的文本写回旧引用。实际是否扩、扩多少、什么时候合并，仍要用新协议测覆盖与答案。不能从“Small-to-Big 架构合理”直接跳到“本仓已验证有效”。

### 4.4 预算不是一个数，而是一组会先后绑定的约束

至少有候选数、重排数、最终原子数、检索序列化 bytes、runtime 近似 tokens、模型总窗口与输出预留。再加元数据、工具消息名、调用 ID、历史和记忆，名义 8000 和实际可读信息经常不是一回事。

这次连续遇到三种情况：

1. 检索预算大，通用工具预算小：上游扩容被下游 preview 抹掉。
2. 包装节省了，条数先卡住：compact 省 28.6% bytes，却仍只能送 5 条。
3. 相同数值在不同单位计费：UTF-8 bytes 对中英文不对称，近似 token 又不等于供应商 tokenizer 的真实数量。

后续配置和 trace 应明确写单位、实际使用量、哪个限制触发；不能靠字段名猜，也不能把“已发布 JSON 没改”当成执行语义绝对冻结。

### 4.5 去重的正确目标是减少冗余成本，不是消灭所有重叠

固定窗口有重叠是为了保住边界。把任意重叠当重复，会正好破坏设计目的。完全包含与部分重叠要分开；没有可比坐标的 PDF 页来源不能贸然去重。

记录级召回 −0.67pp、全文级 +2.22pp 的交换也提醒我们：代理指标可能奖励多篇离散段落，却看不到连续文本的独有尾部。必须同时检查真实正文与机制案例，不能只用一份数据的排名决定正确性修复。

### 4.6 引用和结构化输出各只能保证自己那一层

真实引用至少有四问：ID 是否存在，正文是否真正可见，引用是否逐字来自该正文，正文是否支持所问关系。最后一问最难。

MAML 的“提到算法”不等于“做了比较”，ukWaC 的“训练词向量”不等于“分类器评估数据”。新 PARTIAL 状态也不是把相关名字放进去的豁免。严格 JSON 能挡掉漏字段、越界 ID，但增加字段本身会带来新的交付失败。

所以应分别报告格式有效、来源合法、值正确、关系支持、答案完整、缺据时是否拒答。现有记录尚不能提供经过专家校准的综合 faithfulness 分数。

### 4.7 强调短答案可能提高词面分，但不能牺牲用户需要的信息

Yes/No 后多写解释、实体名后附规模，都可能拉低 EM/F1。GLM 两道极性题贡献 83% 的小批差值，就是这种敏感性的直观例子。但解释也可能有错，不能只截首词重新记正确；更不能为了榜单把所有生产回答压成短词。

事实型任务可以分开短值、解释、证据与状态，以便各自评价；解释型任务要另立标准。官方分数保留不改，语义争议和别名误差可以另做诊断。剩余案例不应默认全部扔进“真实阅读错误”桶，UNKNOWN 是必要结果。

### 4.8 成熟项目最值得借鉴的是职责划分与源码边界

| 参考方向 | 在本仓真正有用的启发 | 需要避免的偷换 |
| --- | --- | --- |
| RAGFlow | 候选、重排、输出预算分开；可见证据身份 | 本仓移植一段父文本逻辑不等于复现完整系统 |
| Onyx | 联合看候选、保留间接支持、选择后再交付 | 来源排序、互补集合、多查询聚合不是同一个机制 |
| LangChain / LlamaIndex | 检索叶块和父阅读视图分离；边界处理 | 段落独立不等于完整 splitter 合并或层级检索 |
| Haystack | 多样性与位置调整要分别测 | 来源配额不能叫 embedding MMR；排列不能替代补全 |
| Qdrant | 融合只组合已有召回；核对真实公式 | 归一化局部增益不等于最终答案增益 |
| RAGChecker | 分开检索、使用和生成支持方向 | 下载源码或装 evaluator 不等于有专家校准真值 |
| Contextual Retrieval | 为缺语境的块补定位信息 | 外部降错百分比不能直接移植到本仓强基线和不同语料 |
| Wiki 调研中的 Raw/Wiki 分层与 ingest/query/lint | 原始证据、派生产物、维护检查分别管理；模型提候选，业务逻辑发布 | 这里概括仓库既有调研，不是复刻完整外部 Wiki 或 GraphRAG；导航关系不等于可靠语义图 |

这里总结的是历史项目报告中的源码借鉴，不是在本次整理中重新验证这些外部项目当前版本。真正进入决策的，应是固定版本机制、本地实现、受控数据与成本。

### 4.9 实验可信度也是持续开发出来的

本项目的评测从小集满分，逐渐加上阶段 trace、同题交错、来源分组 bootstrap、错误计零、曝光收据、源码归档、实际消息捕获和精确模型身份。

这不是一次性流程模板，而是从坑里补出来的：分组字段漏识别导致来源曝光漏排，任务标签从 ID 泄漏，preview 解析漏算内容，payload 缺 `chunk_id` 导致全零，串接字符串漏算完整段落，近似单变量实验里模型自行改写查询。

比较可信的做法是每次只修正已经定位的测量问题，保留旧报告和失败窗口，说明哪些数字更新、哪些历史推断资格失效。`PASS` 还要说清是程序执行、结构检查、工程回归、质量门还是独立审阅通过；它们不能相互代替。

### 4.10 负结果的价值取决于能否说清“否决了什么”

本次保留下来的负结果至少有五类：

| 类型 | 例子 | 正确解释 |
| --- | --- | --- |
| 最终收益没传下来 | learned sparse、DBSF | 单组件有改善，当前组合无净收益 |
| 成本不值得 | 父文档前置重排、两阶段 reader | 不是不会运行，而是收益未证实、成本已增加 |
| 跨语料不一致 | Contextual 前缀 | 有子域正向证据，整体推广门未过 |
| 测量或控制不成立 | thinking 开关、未完整模型比较 | 不能给有效质量结论，而非算法质量失败 |
| 前置门失败，后续没做 | C1b 的互补聚合、P1 的答案调用 | 未执行不能被记成负质量结果 |
| 表示增加，任务收益未证实 | Wiki 六题三模式，Hybrid 有效输出未超 RAG | 该小样本未证明优势，不等于 Wiki 组织与增量维护没有价值 |
| 自动化失败，转入有证据的人工维护 | MODEL 复核两次失败，编辑者声明路径通过 | 自动识别结论仍为失败，人工能力单独验收 |

停止得早也有具体收益：DBSF 缓存筛查未过就不做真实时延；P1 覆盖门失败不发答案；C1 只花分解调用；C1b 复用分解、零新增 API。相比不断在同一批标签上微调到过门，这些记录更能帮助下一次决定该不该投入。

### 4.11 Wiki 的意义是复用组织工作，是否值得用仍要按任务判断

做完这条线以后，更合适的问题不是“Wiki 和 RAG 谁更先进”，而是哪些工作值得提前做、哪些必须等看到问题再做。稳定主题、反复访问的政策与概念，有复用编译组织的机会；精确事实、长尾细节和新近变化，仍需要原始检索和明确版本。前者是设计上的适用性判断，当前六题和五十题数据还不足以给出广泛业务收益。

Wiki-only 3/6、Hybrid 5/6、RAG 5/6 的结果，让“先同时保留两条可审计路径”比“所有问题自动混合”更有理由。第一版按标题/词项和显式意图路由，没有把 AUTO 写成训练好的路由器；也没有因为产生了页面和边，就直接新增图数据库。先知道表示能补哪类任务，再决定增加哪种索引，是比扩展组件清单更可靠的开发顺序。

### 4.12 持久知识让“版本”从一个 hash 变成一条身份链

RAG 已要求固定原始 snapshot；Wiki 再要求固定“用什么规则把原文组织成哪一版页面”。同一来源可以因提示、模型、复核规则或编辑者声明不同而产生不同发布。缓存复用的粒度和对外发布的粒度因此不相同，不能用“来源没有变”跳过派生产物校验。

| 要回答的问题 | 应保留的身份 | 这次开发暴露的错误 |
| --- | --- | --- |
| 原文是哪一版？ | revision、chunk、snapshot ID/hash | 今日来源新增不应悄悄进入旧绑定 |
| 用什么规则提取和组织？ | 提取规格、compiler_spec、模型计划 | 修改全局规则不应无故重做未变 revision 的提取 |
| 当时读了哪一组页？ | compilation/publication 与内容 hash | 只固定 snapshot 无法唯一标识 Wiki |
| 哪次执行消费了它？ | AgentVersion、Run/variant effective_wiki_publications | 工具参数或历史 LATEST 不能临时换 publication |

发布时固定版本，减少了隐式漂移，也增加了升级步骤：新 Wiki 不会自动改变已发布 AgentVersion。撤销则是另外一条权限轴；保留历史记录不意味着仍可交付撤销正文。这些约束让重放可能不再“总能重现答案”，却能解释为什么停止、哪个来源已失权，比静默换新后声称恢复成功更可信。

### 4.13 冲突能力要分别评价发现、维护、送达和裁决

精确 quote 只能证明原文出现过这句话；同样真实的两句话仍可能条件不同、术语不同或互相矛盾。把 JSON 再写严格一点，不能自动解决实体别名、条件对齐和语义冲突。4096→8192 的两次失败也说明，提高输出预算并不替代对任务和结构复杂度的诊断。

最后成功的人工声明保持了权责：人指定需要共同呈现的已验证引文，系统检查来源并形成新版本，查询交付双方材料，回答拒绝自动选赢家。后续仍要测自动发现召回率；当前没有这组独立标注，不能用声明通过补上它。首次声明后仍漏读邻接冲突，又提醒我们：维护界面或数据库里“已经处理”，必须经真实查询入口验证才算用户可见的能力。

### 4.14 混合是否成功，要沿服务返回、模型送达和回答完成分别记账

原生 W5 同时出现 320/320 origin 正确、B 成功子集 11/11 双层、全题只有 12/20 双层。这三句话能同时成立，因为它们分别回答“已经交付的身份对不对”“完成项是否两层齐备”“所有请求有多少拿到双层”。挑其中最漂亮的一列，就会把运行失败和预算截断从产品结果里抹掉。

H-10/H-11 的后续修复把这个教训落到合同：不仅传正文，还要传冲突/不足/降级；不仅检查服务原始集合，还要检查数量和预算裁剪后的实际 origin。来源合法、状态保守、最终完成、答案正确仍是不同指标。RAG 与 Wiki 到这里使用同一套排障原则，不能给 Wiki 单独绕开预算或恢复校验。

### 4.15 Wiki 的收益核算必须包含编译、维护和失败成本

成本判断应至少写成：`总成本 = 初次编译 + 各次增量/冲突维护 + 所有查询尝试 + 本地基础设施成本`。比较纯 RAG 时同样计入它的入库和查询。只有固定任务质量、有效交付与统计范围后，才有资格讨论重复查询能否摊薄预计算成本。

这次能确认的局部节省是新增来源时复用五份提取、声明冲突时复用六份提取；不能从中推出整体省钱。Wiki-only 查询 4,849 tokens 低于 RAG 的 8,215，同时有效输出少了两题；Hybrid 查询更贵，编译还要额外支出。两次失败复核的 22,048 tokens 也必须计入维护账本。缺价格、缺独立质量判卷和长期查询分布时，保留“货币成本未知、总体收益未证明”，就是数据允许的结论。

Wiki 让这次开发心得多了一层：不能只优化一次问答的检索分数，还要决定哪些组织值得长期保存、如何更新和撤销、谁负责处理模型未解决的矛盾。做到这些，并不自动提高质量分数；它让系统的行为和取舍更可解释，也给下一轮公平评测留下了稳定边界。

## 五、最值得保留的成绩与剩余边界

### 5.1 可以有证据地讲的成果

1. **检索工程性能：**在 SciFact 全量语料的固定质量、固定预算下，用快照成员 JOIN 替换大 revision 列表展开，热检索均值下降 9.95%，相关质量指标和逐块排名一致。
2. **候选内排序：**Onyx 风格来源选择在 SciFact DEV 有探索收益，冻结后 FiQA 648 题 nDCG@10 提高 0.039827，区间为正，候选 Recall@20 不变。后续实现了显式 opt-in 接线。
3. **消费者证据交付：**把工具结果、RAG 类别预算、完整记录与引用配对打通，在既定 MuSiQue 确认中 F1 +11.47pp；默认交付链继续修复后，单次派发、响应身份核对的阿里云回归 F1 +10.40pp。
4. **互补集合组织：**在来源隔离的 MuSiQue 200 题确认里，保持最多 5 个原子证据、原格式和预算，F1 +16.15pp，完整支持集 +16.50pp；成本增加并披露，能力保留为显式组合。
5. **研究与排障资产：**有阶段 trace、原文坐标覆盖、曝光审计、失败计零、未知派发不补发、同消息复用和负结果账本，可以用来定位下一次失败。
6. **Wiki 组织与增量机制：**有来源的精确引文页、可恢复编译、原子发布、历史版本和 Wiki 范围撤销已落地；新增一份来源时复用五份提取缓存，仅新增一次模型请求。这是工程和局部复用证据，不是总体质量或费用优势。
7. **冲突维护与原生消费：**两次自动复核失败如实保留，六份真实缓存支撑的编辑者声明及邻接冲突交付通过；原生 WikiBinding、Run/Experiment 冻结和 query_wiki 接通，W5 核对 320 条 origin。自动识别、人工维护、双层总体送达和语义判卷继续分开。

这些成果互有重叠、基线和样本不同，不能相加成总提升，也不能画成 27.92→39.39→52.49→更高的一条连续升级线。

### 5.2 目前还不能讲成已经解决的事

不能声称公开检索已经达到某当前 SOTA，不能把外部模型公开分数当作本地复现；不能用 MuSiQue 题内候选约 99% 覆盖，推导整个系统所有语料初始召回都只剩不到 1pp 空间。FiQA 的阶段统计已经直接说明这个推论不成立。

不能把标准支持段落 F1 62.83% 叫理论天花板，也不能把其与 41% 左右检索臂的差简单归为纯生成损失。给定材料的质量、干扰、组织与生成都参与这个差；真正可回收量仍需要分层干预。

不能说长链、中文业务、表格/OCR、图索引、自主补检索、跨知识库多快照、所有 Gateway 或完整生产 Run 都已经同样确认。工具循环可运行，不代表“识别知识缺口→有界补检索→判定完成”这项策略已验收。

Wiki 同样不能讲成“自动维护事实真伪”“知识图谱已建好”或“Hybrid 已优于生产 RAG”。独立六题没有确认 Hybrid 优势，自动 MODEL 复核两次失败，原生 B 组全题双层 60% 未达期望；后续 bug 修复没有新增质量 A/B。没有统一价格与长期查询分布，也不能给出摊销后的省钱百分比。修复已验收与业务已部署仍须分开。

### 5.3 下次遇到低分，优先做的七步

1. 固定问题、来源身份、配置、代码与评分口径，先核对原文是否真的有必要事实。
2. 捕获候选并集、融合、重排、最终集合、工具返回、准入后实际消息，定位第一次真实丢失。
3. 对跨块文字用原文坐标并集；无法唯一对齐保持 UNKNOWN，不拿不同分母直接相减。
4. 在开发集上做实际/充分/删除材料对照，分别看值、关系、完整性、拒答和格式，不只看一个总 F1。
5. 只对已定位的损失提一个有限机制，设主比较、最小有用收益、成本与停止门；先做便宜检查再花答案调用。
6. 确认前冻结选择，保留未暴露来源；失败、未尝试、无效输出和 UNKNOWN 不从账本消失。
7. 采用时明确是默认、版本 opt-in、组合接口还是实验原型，再验证真实消费者；效果不够就收口，留下可复算的失败原因。

涉及 Wiki 时，再沿第 2 步补查：编译引文、页面归组、冲突邻接、发布绑定、服务端风险状态、最终送达的 origin。若症状是来源更新或撤销，先确认身份和权限，再研究质量；不能用重新编译或重新检索掩盖旧绑定失效。

这份经历最值得形成的习惯，是持续追问：**哪条必要信息在什么边界消失了？当前数据能把哪一种解释排除？新方法改善的是哪一层，代价又由谁承担？**
