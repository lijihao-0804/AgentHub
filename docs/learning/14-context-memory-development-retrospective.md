## 二、真实开发过程：按踩坑和解决顺序还原

### 2.1 M1：原子记忆准入 —— 差点把否定词切掉的教训与延后打标记

#### 1. 踩到的坑
最初做长期记忆（Memory）塞进 Prompt 的逻辑时，写得很随手：算一下模型还剩多少 Token 空间，然后把选出来的记忆条目一条条拼进去；如果最后一条超了，直接 `text[:remaining_chars]` 按字符硬切。

结果在回归测试时发现了极度危险的个案。比如这样一条规则：
> “退款必须在下单后 30 天内提出；超过 30 天一律不得退款。”

如果切片刚好切在“一律不得退款”之前，或者把“不得”切掉了，喂给大模型的文本直接变成了“超过 30 天退款”。模型拿到这种半截事实，输出的答案直接和业务要求完全相反。

另外还有一个假归因问题：我们数据库里设计了 `touch_count`（被使用次数）和 `last_touched_at`。旧代码只要 MemorySelector 把某条记忆捞出来，就顺手往数据库发一个 touch。但其实在后面的组装阶段，由于系统 Prompt 太长，这条记忆根本没被塞进发给模型的真正请求里。结果数据库显示它被“频繁使用”，其实模型一次都没见过它。

#### 2. 怎么解决的 (`71a0b8b`, `06826c5`)
* **整条进，或者整条不进（All-or-Nothing）**：
  在 `ContextBudgetPolicy.admit` 里重构逻辑：单条事实是原子单位。预算要算上 JSON 包装的所有开销。哪怕可用空间只差 1 个 Token，这条事实也必须**整条扔掉**，并在日志里明确记下 `DROPPED_POOL_BUDGET`。宁可少给一条背景，也绝不给半句残片。
* **等真正进门了再打标记（Late-Binding Touch）**：
  把 `touch` 的动作从“初选阶段”挪到 LangGraph 真正调用模型前的最后一刻。只有最后真正在 `admission.messages` 里的记忆 ID，才会批量触发数据库更新。被挤掉的那些，`touch` 次数严格保持为 0。

### 2.2 M2：模型自适应预算 —— 别只看主模型窗口，降级模型会撑爆

#### 1. 踩到的坑
主模型配置的是 128K 甚至号称 100 万窗口的模型，很多人的直觉是“那我上下文直接按 100K 组装就行了”。但企业级应用都会配降级链（Fallback Chain），主模型如果报 500、超时或者被限流，要自动降级到备用模型。

我们的备选模型是一个 32K 窗口的本地或保底模型。结果主模型一挂，系统带着 80K 的历史上下文转头请求备用模型，备选模型当场报 `ContextWindowExceeded` 错误，整个请求直接炸穿。所谓的容灾降级，在上下文没做交集对齐时完全是一句空话。

此外，早期代码拿浮点数算水位，比如 `if current / total >= 0.70:`，在临界 Token 上因为浮点数精度问题，模型在连续几轮对话中一会儿报警触发摘要、一会儿又解除报警，状态反复横跳。

#### 2. 怎么解决的 (`dedb323`)
* **木桶原理：预算由链路里最弱的模型决定**：
  在 `packages/agent_runtime/context_policy.py` 里写死规则：链路里每个模型都有自己的总窗口、独立输入上限和预留输出。系统算出每个模型的可用输入后，**强制取所有主备模型的最小值**：
  $$B = \min_{M_i \in \text{chain}} B_i, \quad B_{\text{work}} = \min(B, L_{\text{preset}})$$
  主模型窗口再大，只要备用模型是 32K（扣除预留输出和安全垫后剩 29,184），有效工作预算 $B_{\text{work}}$ 就必须死死按 29,184 来算。这样主模型挂了，备用模型接手绝对不会超窗。
* **全部用整数除法，告别浮点抖动**：
  水位的计算全部改成整数天花板除法和地板除法：
  - 软触发（70%）：`(70 * B_work + 99) // 100`
  - 硬阻塞（85%）：`(85 * B_work + 99) // 100`
  - 压缩目标（55%）：`(55 * B_work) // 100`
  整数临界点前后差 1 个 Token，状态清清楚楚，绝不再来回抖。

### 2.3 M3：Token 驱动历史规划 —— 偷懒截取“最近10轮”其实是在自欺欺人

#### 1. 踩到的坑
业内做 Agent 最常见的偷懒写法就是：取历史消息时直接写 `history[-10:]`，只看最近 10 轮。

这在长任务里极其坑人。比如一个任务跑了 15 轮，每轮对话加上工具调用有 2,000 Token，总共已经积攒了 30,000 Token。如果系统先偷懒截取最近 10 轮（剩 20,000），然后再去算占用率，就会得出“才用了 60%，还没到 70% 警告线”的错误结论。真实的高水位被截断掩盖掉了，直到某一轮单轮自身突然变长，把系统直接撑爆。

另一个坑是把工具调用切碎了：滑窗恰好把 Assistant 发出的 `tool_calls` 留下了，但工具返回的响应给切掉了；或者 RAG 回答里引了 `[H1E1]`，但上面带这个编号的证据块被滑窗丢了。发给 LLM 之后，LLM 要么直接报 Schema 错，要么对着空气瞎编。

#### 2. 怎么解决的 (`dcaffaf`, `995dd46`)
* **先看全貌，再动剪刀（Pre-trim Measurement）**：
  在 `packages/agent_runtime/history_planner.py` 里立了规矩：在对历史做任何裁剪前，必须用单调递增的 Watermark 锁定当前线程所有历史，测出未经裁剪的真实总需求 $N$，再加上预估增长 $G$。
  在测试用例中，12 轮 × 2,000 = 24,000 Token，超过 32K 窗口的 70% 阈值（22,938）。哪怕后续要裁剪，计划器在裁剪前就已经明确报警 `PlanPressure.SOFT`，绝不假装风平浪静。
* **工具调用与结果必须成对，同生共死**：
  定义了“完整交换组（Exchange Group）”：一次工具调用和它的全部返回是一个整体，保留就一起保留，丢弃就整组丢弃；RAG 证据注册表核验也是一样，证据丢了引用还留着，直接返回 422 报错停机，绝不带着破损历史强行跑。

### 2.4 M4：摘要生命周期与真实阿里云联调踩坑（重点）

M4 是整个系统里最复杂、也是在线联调被现实毒打最狠的一个阶段。很多在本地写单元测试看着挺顺的代码，一连上阿里云真实的 `deepseek-v4.1-flash`，问题全冒出来了。

#### 坑 1：DeepSeek 默认思考模式把输出 Token 烧光了，正文一个字没出
* **现场情况**：2026-10-27 第一次拿真实阿里云测试摘要调用，连发了 4 次请求，全部等待很长时间，返回的内容全为空，并且返回状态都是 `finish_reason == "length"`。
* **排查根因**：我们拿一个极简的问题去测试，逐字段看阿里云返回的原始 JSON，发现它返回了 64 个输出 Token，而且全写在 `thinking_tokens` 里！原来阿里云兼容模式下的 DeepSeek 默认开启了深度思考。当给它一个长篇会议文本让它摘要，又设了一个保守的输出上限时，模型在“思考”阶段就把给它的 Token 额度给烧光了，正文一个字都还没开始吐就直接触发长度截断退出了。
* **怎么解决**：在适配层（`aliyun_delivery_fix.py`）针对摘要节点强制加上 `extra_body={"enable_thinking": False}`（关停思考模式）。摘要是一个确定性的工程任务，不需要模型在后台写几千字内心独白，关掉思考之后，模型老老实实直接输出结构化 JSON，问题立马解决。

#### 坑 2：输出上限设成 1024 被腰斩，调到 1536 拿到满分且保留了失败现场
* **现场情况**：在第一次真实的跨轮 Thread 测试 `run-c343607f45be` 中，同步摘要顺利生成并存盘了，第一轮主模型开始回答问题。问题问的是复杂的合规留置与 ACTIVE 规则，需要覆盖 F1 到 F4 四大要点。结果模型答完 F1 和 F2，突然停了，`finish_reason` 是 `length`，只拿到了 2/4 分。
* **排查根因**：当时代码里图保守，把主模型输出上限卡在 `1024`。合规类长回答包含大量前置条件，1024 个 Token 根本不够写。
* **怎么解决**：我们没有删掉 `run-c343607f45be` 的日志去假装全绿，而是完整保存在 `docs/reviews/evidence/` 里。随后将输出上限调到 `1536`，并且在代码里加了死规矩：必须断言 `finish_reason == "stop"`，只要因为长度截断就必须判定为失败。在随后的 `run-e55f809a647b` 测试中，模型完整输出 264 个 Token 顺利停机，**F1–F4 拿到 4/4 满分**；第二轮续答复用摘要，**N1–N5 拿到 5/5 满分**。

#### 坑 3：拿字符数除以 0.7 估 Token，服务商账单一查差了 20%
* **现场情况**：前期没有接本地真实分词器，用了常见的启发式字符估算（中文字符数除以系数）。结果在真实调用后核对账单，服务商返回的真实 `input_tokens` 居然比我们估算的**高出了整整 19%～20%**！
* **为什么危险**：如果在 32K 边界上，模型以为自己只用了 28K，其实真实情况已经到了 33K，请求发给网关会被服务商当场拒识。
* **怎么解决**：不再碰运气猜字数。引入 HuggingFace 官方的 `tokenizers` 库，把 DeepSeek 官方开源的真实词表文件下载到本地（按 SHA-256 固化版本），在本地封装出 `DeepseekV41TextCounter`。派发前严格用官方词表做真实离线分词。改完之后，我们在随后的真实测试中，**本地预估 Token 数与阿里云返回的 `input_tokens` 实现了 100% 精确吻合（0 误差）**。

#### 坑 4：QMSum 跑不通老老实实认账，转战开源 Spark 3.5.9 文档做 B/C 对照
* **现场情况**：M4 计划用 QMSum 12 道公开会议题做评测。结果实际执行时接连碰壁：4 道题因为上游会议录像的 CC BY 4.0 商业分发许可问题，在派发前被合规拦截；4 道题因为原文太长直接超过 32K 物理窗口，在派发前被预算策略拦截；最后 4 道题又撞上了前面说的默认思考耗尽输出。一通下来，QMSum 跑出来的有效 B/C 对照组是 0。
* **怎么解决**：有些项目这时候可能会改改提示词、手动删点文本把分数“跑出来”。AgentHub 坚决不这么干，在记录里写明 QMSum 失败就是失败。随后我们找了完全遵循 Apache-2.0 协议的公开技术文档（Apache Spark 3.5.9 结构化流式重启语义章节），设计了标准的 Task 2 B/C 对照：
  - 基线 B（不压缩全部塞进去）：输入 2,958 Token，命中 G03–G07 全部 5 个核心点；
  - 路径 C（先做摘要再回答）：摘要花掉 1,830 Token，后续回答的输入压到了 1,366 Token（**省了 53.8% 的上下文**），同样命中全部 5 个核心点。证明这套摘要机制在长文档场景下确实能省上下文且不掉点。

#### 坑 5：数据库行锁排队导致时钟漂移，Worker 拿着过期租约去发请求
* **现场情况**：在并发故障注入测试里，当两个 Worker 同时抢同一个摘要任务时，后一个 Worker 会在 PostgreSQL 行锁（`FOR UPDATE`）上排队。等前面的执行完把锁释放，后一个 Worker 拿到锁时，它内存里记录的“租约过期时间”其实已经过去了，但代码还在继续往下走，拿着过期租约向大模型发请求。
* **怎么解决**：
  在代码里明确：**只要等过行锁，拿到锁的第一件事就是重新拿当前系统时钟校准**。在发网络请求前的最后一刹那，再核验一次租约。过期了立即放弃并回滚，坚决不让僵尸 Worker 乱发请求。

#### 坑 6：恢复状态找错 Checkpoint，加迁移给摘要强绑定 Checkpoint ID
* **现场情况**：早期摘要表里只记录了这个摘要属于哪个 Run ID。当系统发生中断恢复（Resume）时，如果恢复流程读到了图里更新的 Checkpoint，就会拿着新状态去消费老状态生成的摘要产物，导致上下文版本错乱。
* **怎么解决**：
  增加数据库显式迁移 `0047_summary_checkpoint_binding.py`，在表结构里加上 `checkpoint_id` 和 `checkpoint_ns`。摘要任务不仅属于某个 Run，还精确绑定在它被触发时的那个特定 Checkpoint 上，恢复时对不上直接拒绝。

#### 坑 7：大模型摘要会把关键约束“概括”丢，核心原话必须由服务端原样留存
* **现场情况**：只要是让大模型做摘要，不管 Prompt 里强调多少遍“千万别丢关键事实”，大模型在压缩时总喜欢自作聪明地做“归纳”。比如用户在第 3 轮说了：“我这单必须退款，发票是开给北京某某公司的，千万别给我换货”，模型摘要出来往往就变成了“用户咨询了退换货与发票政策”，把“必须退款、不要换货”这种带业务约束的原话全给丢了。
* **怎么解决**：
  我们彻底放弃了“完全指望大模型不犯错”的不切实际想法。在服务端加了确定性逻辑：在把历史前缀送去给模型做摘要之前，**由代码扫描前缀，把用户说过的每一句原话原封不动抠出来**，存在服务端的不可变字段 `server_protected_facts` 里。后续主模型工作时，这部分事实不经过大模型摘要，由服务端逐字拼到 Prompt 里。摘要归摘要，用户的硬性诉求原话 100% 逐字保留（差异为 0 字符）。

#### 坑 8：虽然单题和 Thread 跑通了，但多题收益没过门，生产开关坚决不开
* **决策定力**：虽然 M4 在 Spark 单题和真实 Thread 跨轮实测里拿了满分，但因为在公开大规模多题任务上还没拿到具有统计显著性的省钱省 Token 成绩，我们坚决不在宣传上吹“功能已全面上线”。
* **怎么落地**：在发布代码（`AgentPublishService`）里，任何人只要想在生产配置里把 `summary_policy.enabled` 设成 `true`，接口直接返回 `422 SUMMARY_QUALITY_GATE_NOT_MET`，硬性拦截。只有本地持有测试沙箱凭证的隔离环境才能运行。没做好就是没做好，不打肿脸充胖子。

### 2.5 M5：稳定表示与隐式缓存 —— 字典键无序导致缓存击穿，以及千万别拿缓存扣减预算

#### 1. 踩到的坑
在探索大模型服务商的 Prompt Cache（前缀缓存）时，我们遇到了两个非常典型的问题：
1. **JSON 序列化伪随机，导致云端缓存命中率归零**：
   在 Python 里，字典虽然有顺序，但如果不同模块构造参数时的代码写法不一样（比如 A 模块写 `{"id": 1, "name": "a"}`，B 模块写 `{"name": "a", "id": 1}`），在语义上完全是一回事，但 `json.dumps()` 出来的字节流完全不一样。上游服务商（如阿里云、OpenAI）做 KV Cache 匹配是完全按**前缀字节流**来比对的，只要中间有一个空格或键的顺序乱了，后面的缓存全泡汤。
2. **以为缓存命中了就能随意扩大上下文**：
   有开发人员看到服务商返回了 `cached_tokens = 2048`，就误以为“这 2,048 个 Token 没花上下文空间，我们可以在这轮多塞 2,000 个 Token 的背景进去”。这种想法极其危险：**云端的缓存是随时可能被淘汰的（Cache Eviction）**。如果服务商机器负载一高把缓存清了，下一轮你的请求在云端就会变成硬生生的真实物理 Token，当场引发上下文超限报错崩溃。

#### 2. 怎么解决的 (`b4ba093`)
* **全部强制按字典序排序序列化（Canonical JSON）**：
  在 `packages/model_gateway/adapters/litellm/adapter.py` 里重构工具定义和历史工具参数序列化：
  ```python
  json.dumps(args, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
  ```
  工具定义列表也严格按发布时冻结的规范顺序排，确保发给模型的前缀在字节级别绝对一致。
* **铁律：缓存读 Token 只能用来算账，绝不能用来抵扣上下文预算**：
  在 `ContextBudgetPolicy` 里定下规矩：供应商返回的 `cached_tokens` 只进账本和监控，**可用工作预算 $B_{\text{work}}$ 和当前需求 $N$ 里绝对不减去这部分 Token**。规划永远按最坏情况（0 缓存命中）来做物理防御。
* **真实阿里云在线测试验证 (`m5-504c36f247a9`)**：
  构造了 2,288 Token 的稳定前缀，在阿里云真实接口上连续发了 4 次请求：
  - 请求 1（冷启动）：`cached_tokens = 0`，首字延迟（TTFT）**1,009ms**；
  - 请求 2（热请求，相同前缀）：命中 `cached_tokens = 2,048`（**命中率 89.5%**），首字延迟直接砍半到 **514ms（下降 49%）**；
  - 请求 3（热请求，相同前缀）：继续命中 2,048 Token，首字延迟进一步降到 **485ms（下降 52%）**；
  - 请求 4（对照组，前缀首字节改了）：缓存命中立马变成 0。
  证明只要前缀字节对齐，云端缓存确实能带来稳定的首字延迟减半收益。

## 三、技术选型与采用决策总账

整个长上下文工程的所有尝试，最后落地和砍掉的账目如下：

| 技术点 / 机制 | 最终决策 | 为什么这么定（真实依据） |
| :--- | :--- | :--- |
| **单条记忆原子准入 (All-or-Nothing)** | **采用 (落地)** | 彻底解决字符截断导致否定词、条件丢失的问题；差 1 个 Token 整条放弃。 |
| **延后送达归因 (`touch` 状态机)** | **采用 (落地)** | 只有真正进入模型请求窗口的事实才增加 touch 计数，杜绝虚假归因。 |
| **主备降级链取预算最小值** | **采用 (落地)** | 备用模型的 32K 决定全局上限，防止主模型故障降级时超窗崩溃。 |
| **整数天花板/地板滞后回线** | **采用 (落地)** | 抛弃浮点数计算，消除 70%/85% 水位线上的反复抖动。 |
| **剪裁前全量高水位测量** | **采用 (落地)** | 杜绝靠截取最近 10 轮历史来假装系统没超载的自欺欺人做法。 |
| **工具调用对与证据链同生共死** | **采用 (落地)** | 保证历史重放时 Schema 合法，不留孤立的悬挂调用，缺了一半直接 422 报错停机。 |
| **PostgreSQL 显式分页快照** | **采用 (落地)** | 保证大历史分页拉取时不会出现幻读，时序绝不错乱。 |
| **服务端受保护事实原貌锁死** | **采用 (落地)** | 解决大模型摘要会把用户硬性要求“概括丢”的通病，原话逐字保留。 |
| **LangGraph 同步 `summary` 节点** | **采用 (落地)** | 在主图内串行执行摘要生成、落库和校验，拿到合法摘要后再调用主模型。 |
| **跨 Run 不可变摘要复用** | **采用 (落地)** | 相同水位直接复用已发布的 `revision_hash`，第二轮 Run 摘要模型调用次数为 0。 |
| **工具参数字典序序列化 (`sort_keys=True`)** | **采用 (落地)** | 消除 JSON 伪随机，实测在阿里云上稳定拿下 89.5% 缓存命中，首字延迟减半。 |
| **缓存 Token 预算物理绝缘** | **采用 (落地)** | 严禁把命中的缓存从可用预算里扣减，防御服务商随时可能发生的缓存驱逐。 |
| **QMSum 初始会议长文本微调候选** | **放弃 (负结果)** | 4 题商业许可不合规、4 题超窗、4 题思考耗尽，有效配对为 0，老实认账。 |
| **字符估算 Token (`approx_language_v1`)** | **限制使用 (不作保证)** | 比真实 Tokenizer 低估 20%，只能作为离线粗估，不能用于临界判定。 |
| **生产发布直接启用自动摘要** | **保持关闭 (门禁阻断)** | 多题净收益未过门，发布接口一律返回 422 拦截，只留本地沙箱做实验。 |

## 四、做完长上下文总结出的八条大白话经验

1. **宁可整条扔掉，也绝不切半截**：给模型一个不完整的事实，比完全不给危害大十倍。切掉后半句的“除非领导特别批准”，就等于直接把违规操作合法化。
2. **能装多少东西，取决于降级备胎有多大，不是主驾有多大**：如果备用模型只有 32K，主模型就算宣称有 1000 万窗口，你的有效工作区也只能是 32K。否则降级的时候死得比谁都难看。
3. **先截断再算水位的系统，都是在掩耳盗铃**：截断最近 10 轮再来算占用率，就像为了不发烧而偷偷甩温度计。压力在切除之前就必须被感知到。
4. **别指望大模型在做长摘要时能对细节忠实**：模型做摘要天生喜欢大而化之。关键的用户诉求、审批状态、数字和否定词，必须靠服务端代码白纸黑字原样留存。
5. **做结构化工程摘要，坚决关掉模型的“深度思考”**：模型在思考链里自己跟自己聊得热火朝天，把输出额度全占满了，最后正文一个字没吐出来直接截断，在工程上就是纯粹的灾难。
6. **分词器必须用官方词表做离线实测，不要自己除以 0.7**：在接近物理窗口边缘时，20% 的字数估算误差足够让你当场被服务商 400 拒识。
7. **前缀缓存是物理字节级别的较量，差一个空格都不行**：字典键的顺序变了、中间多了一个时间戳、工具列表顺序乱了，都会让云端缓存直接击穿。规范化序列化是必须做的脏活累活。
8. **承认有些实验没跑通，比伪造一个 100% 成功有价值得多**：跑不通就记下原因、封死上线开关。敢于把负结果和真实截断日志留着，系统才能在生产里真正站得住脚。
