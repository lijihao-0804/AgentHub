# AgentHub 上下文工程：开源项目代码对照

日期：2026-10-28。以下观察来自项目代码及其公开问题；链接指向读取时的分支，后续可能变化。它们是架构和回归依据，并不是对这些项目当前版本进行过本地复现，也不能代表 AgentHub 的实测质量。

## 设计主线：权威记录与可替换视图分离

AgentHub 的 Thread、完整交换、工具结果和审批／动作状态是权威来源；发送给模型的历史是绑定来源水位、权限和版本的派生视图。保留当前任务、系统权限、近期完整交换与不可丢失的原文；摘要只是可校验、可失效的辅助索引。空间不足时先降低可恢复内容的展示量；不能证明安全压缩时给出明确不足，不能用空摘要替代来源。

- [OpenHands 的 Condenser 抽象](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/base.py) 将压缩建立在只读历史视图上，区分软需求和硬需求：软需求没有可用压缩结果时可继续保留未压缩视图。AgentHub M3 已有按组规划和阻断结果，M4 应让每次压缩关联实际模型派发边界、只发布已验证版本。OpenHands 支持的硬重置不等同 AgentHub 已获授权删除保护内容。
- [Deep Agents 的摘要中间件](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/summarization.py)将旧消息持久转存，并记录摘要切分点和转存位置；代码也考虑媒体引用和工具 schema 的计数。AgentHub 已有原始 Thread 与 artifact，不应复制一份不受租户权限约束的原文文件；后续应通过现有受权来源读取机制按需恢复，并检验撤权、版本固定及多模态能力。
- [LangChain 的摘要实现](https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/summarization.py)专门寻找不拆开助手工具调用和对应结果的切分点。AgentHub 的 M3 以完整交换为单位、历史工具 ID 进行命名空间隔离；生产摘要仍需在多个并行工具调用、部分返回、审批中断和恢复后验证整个组保持完整。
- [LlamaIndex Memory](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/memory/memory.py) 把活动消息、归档和不同优先级的 memory blocks 分开管理，并在淘汰时考虑完整对话边界。AgentHub 可以借鉴“不同来源有不同保留策略”，但不应直接采用别人的默认比例或将可推测事实当作系统权限。

## 借鉴同时核查失败路径

[LangChain 公开问题 #39261](https://github.com/langchain-ai/langchain/issues/39261)报告了一种未调用摘要模型却用占位文本替换历史的场景；这是提交者报告，不在此声称所有版本都有该缺陷。AgentHub 应回归验证：空输入、模型空输出、截断、解析失败、无可摘要来源及压缩后仍超预算时，原来源和已发生费用都保留，不得把占位文本发布成有效摘要。

[OpenHands 公开问题 #4544](https://github.com/OpenHands/software-agent-sdk/issues/4544)报告压缩后已激活的规则可能未再次进入上下文；[另一个问题 #1395](https://github.com/OpenHands/software-agent-sdk/issues/1395)展示过摘要插入位置与并行工具调用配对的边界风险。AgentHub 需验证系统权限、活动工具及审批状态在每次请求中重新进入正确位置，摘要不能扮演权威状态；工具请求与结果及并行组不得拆散。这些是 AgentHub 的待验收用例，不能据此宣称已复现上游问题。

[LlamaIndex 公开问题 #21950](https://github.com/run-llama/llama_index/issues/21950)报告工具内容漏计的风险。AgentHub 已观察到本次供应商长文本输入比近似估算高约 19%–20%；完整请求的 system、工具 schema、调用参数、工具结果、图片及协议额外开销都要进入对应模型的计数或保守上界。当前研究计数器只验证过限定纯文本请求，不能推广到其他模型、网关或多模态。

[LiteLLM 的预算预留代码](https://github.com/BerriAI/litellm/blob/main/litellm/proxy/spend_tracking/budget_reservation.py)提供了每次请求先预留、后对账的思路；对无法估价的路径，其当前代码存在仅依赖已记录费用的分支。AgentHub 要求共享预算时，主模型、每次重试、fallback 和摘要必须进入同一账户；未知价格、未知结果和已显示的流式输出分别处理，不能将估算说成实际账单或把本地持久 intent 说成远端 exactly-once。

## 按当前里程碑推进

1. M4 首先完成可信来源审阅、每个派发边界最多一个摘要 job、持久费用预留和故障恢复；来源资格、受保护事实完整性及当前权限要分别证明，不能用模型输出替代。
2. 评测以任务继续时的关键事实、否定／金额／条件、动作状态、来源权限和不支持断言为主要质量指标，同时报告完整链路 token、延迟与费用。固定候选的四次长摘要均未形成可用结果，有效 B/C 配对为 0；质量与净收益为 UNVERIFIED。
3. M5 再评估稳定前缀和缓存。只有完成冻结身份、权限隔离和压缩质量验收后才能推广摘要；不要为了缓存将动态权限、审计时间或模型不可见的元数据混进稳定前缀，也不要将缓存命中误当成答案正确率。

本次调研没有对上游项目跑同样的数据集，也没有新增供应商模型调用，因此不提供跨项目准确率排名或声称收益。

## 长期记忆与线程压缩分别评估

[Mem0 的开源提取流程](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)先按作用域检索相关已有记忆，再将其与新消息交给提取器；[提取提示](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py)采用新增与关联思路。AgentHub 的 WorkspaceMemory 已有来源 Run、贡献记录、有效期和明确的管理状态；应继续将工作区长期记忆与同一 Thread 的历史压缩分开，分别检查租户、撤权、来源和时间变化，不能把二者的质量分数混在一起。Mem0 仓库列出的指标明确包含其托管平台的专有优化；没有相同数据、模型、检索预算与评分程序时，不能拿这些数字与 AgentHub 作直接对比。
