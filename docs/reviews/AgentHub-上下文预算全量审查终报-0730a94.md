# AgentHub 上下文预算全量审查终报：揪出所有不合理的预算机制

- 问题（用户）："所有涉及上下文预算的设计都要审查——有的场景只有中文语料，交付容量按中文几条英文几条不一样，这本身就不合理。把所有不合理机制揪出来，出最终报告。"
- 方法：枚举仓库内全部预算/估算/截断/上限机制（7 大层 20 项，逐项 file:line 核对）；关键怀疑全部用真实代码实验定案（记账膨胀、**顶层单位错配**、入口不对称、通用工具残留切割）。基线 `0730a94`，只读未改代码。
- 一句话终论：**最严重的问题不是某个池子小，而是整个预算体系用"字节"当"token"记账、且与模型窗口的"真实 token"混算——由此派生出三类不合理：①容量随语言漂移（中文 5 倍/英文 4 倍记账膨胀，交付条数中文 1 条英文 5 条）；②窗口利用率只有 3~8%（实验证明 16k 窗口拒绝 12k 真实 token 的内容）；③同一件事在不同入口有三种不同的账（字节/字符/不设限）。**

---

## 一、三项定案实验（本轮新证据）

1. **记账膨胀**：`Utf8ByteTokenEstimator` 把 1 字节记 1 token——中文 **5.0 倍**、英文 **4.0 倍**高估。一条中文记录真实 ~744 token 被记 3320。
2. **顶层单位错配（最严重，此前未被发现）**：`ContextBudgetPolicy` 的窗口下限取自 `profile.max_context_tokens`（**真实 token**），而输入估计用**字节**，两者直接相减。实验：16k 真实 token 窗口，喂 12k 真实 token 英文（=60k 字节）→ **被拒绝**（"newest conversation exchange cannot fit"）——实际完全装得下。整条准入链系统性只用窗口的 20~25%；证据池全用满只占 32k 窗口的 **3%**。
3. **入口不对称**：Citation QA 的 `max_evidence_chars=16000` 单位是**字符**——中文≈9600 真实 token、英文≈4000 token，**同一配置下两个语言容量差 2.4 倍**；而它的 compact 分支 `budget=source_bytes+1024` 实际**不设限**（全送）；工具入口又是第三种账（字节、严格预算）。同一个知识库三个入口三种容量语义。

## 三、"不合理"的统一定义与判定

用户提出的核心判据——**容量不应随语言变化**——成立且应定理化为设计原则。当前违反该原则的机制共 5 处：A1（字节记账）、A2（混算放大）、B4（记忆池）、E1（字符单位）、D1（切割点落在哪与内容编码相关）。此外两类不合理与语言无关但同源：**窗口利用率 3-8%**（A2+B1）与**同物异账**（工具/选择器/QA 三入口，C1/C6/E1/E2）。

## 四、统一修复蓝图（三步一实验，待批准后执行）

1. **第一步：统一记账单位（治本）**——估计器从"1字节=1token"改为"真实 token 近似"（ASCII ≈4 字符/token、CJK ≈1.6 字符/token，或接 provider tokenizer）。效果：中文/英文容量一致（语言中性达成）；窗口利用率从 3% 回到设计比例；现有 5000 池自动可装 5-6 条中文记录（"检索到全送"基本达成，无需动池子）。
2. **第二步：池随窗口派生**——`max_retrieval_tokens`/`max_tool_result_tokens`/`DEFAULT_MEMORY_TOKENS` 默认改为 `min(链上窗口)×比例`（如证据 25%、工具结果 15%、记忆 8%），随模型自动伸缩，消灭写死的 5000/4000/1500。
3. **第三步：同物同账**——Citation QA 入口改用与工具入口相同的预算策略与单位（E1/E2/E3）；通用工具结果的句中切割改为"整条装不下整条弃"或结构化投影（D1）；limit 改为"预算富余时允许送到上限 10"（C4）；compact 默认化在新记账下重评（C1）。
4. **一次 A/B 背书**：三步合并为一次变更集，预注册非劣效（MuSiQue 200 题，~400 调用）+ 中文合成送达量断言（修复后中文应=英文条数）+ 窗口利用率 trace 上报。按版本 opt-in 纪律推进。
