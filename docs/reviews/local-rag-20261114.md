# 本机 RAG 优化与实测

从 `dca82a7` 开始，沿用 BGE-M3、BGE-reranker-v2-m3、PostgreSQL 和 Qdrant。用不同测量分别检查大文档是否可检索、外部模型等待时的数据库连接占用、GPU 重排时延，以及用户最后收到的答案和引文。开发过程没有读取正式 HOLDOUT。

## 历史卡点

旧退款政策 DEV 的 50 题中，前 20 个候选找回了 108/109 个指定证据，前 6 降至 98/109。在时间、版本和范围的 8 题里，前 6 段只有 3 题凑齐指定证据组。既有逐题复核也发现部分原文可以相互替代，不能把每个机械漏项都算成答错。之前的生成实验同样记录了引用与政策替代条件的失误。这促使本轮单独测量从候选到最终答案的环节。[历史退款报告](AgentHub-客服退款政策RAG执行报告-20261026.md) · [既有诊断](AgentHub-RAG全链路性能归因与决策-20261024.md)

## 入库与恢复

| 本地上传样本 | 原有结果 | 最终结果 |
| --- | --- | --- |
| QASPER TRAIN 正文 55 万字符，160 字符分块 | 单条参数过多，数据库写入 0 块，任务留在 CHUNKING | 3,438 个分块持久化，3,438 个索引点，首次处理后即可纳入快照 |
| QASPER TRAIN 正文 200 万字符，默认 1,200 字符分块、200 字符重叠，1,024 维 | 2,000 个向量挤入一次 48,848,883 字节的请求，Qdrant 返回 400，索引 0 点 | 32 次请求均返回 200，最大 1,570,856 字节。2,000 点入库，快照和搜索读回成功 |

数据库现在在同一事务中分批写分块。Worker 每批最多生成并写入 64 个向量，所有批次确认后才把修订标为 READY。故意让第二批失败时，首批 64 点已存在，未完成的修订仍处于 PROCESSING；重试后精确计数为 3,277 点，最后一个分块可检索。两份大样本使用确定性向量隔离了写库和传输故障。另用真实 CPU BGE-M3 和 tokenizer 完成了 4,000 字符样本的入库及稠密、稀疏读回。[配置、数值与复跑命令](evidence/local-rag-20261114/ingestion.json)

## API 并发与计时

在真实 PostgreSQL/Qdrant 上把 API 的 PostgreSQL 池设为 1 个连接，溢出设为 0。分别暂停检索试验台的重排器、引用问答的模型适配器，让另一个请求获取连接并执行 `SELECT 1`。原版两个入口均触发 1 秒的连接池超时。修改后两个探针都在释放暂停前完成，原请求返回 HTTP 200。此处使用可控延迟观察持有关系。这项结果不能换算为线上 QPS。

鉴权、快照读取、候选回表和凭据准备各自有短事务。公开试验台读取轨迹元数据时按候选块和快照成员直接关联，只取修订 ID 与定位器。引用问答解析配置时只读取目标地址和供应商，实际生成前再读取凭据、核对同一租户及地址；生成期间连接已归还。生产检索 trace 的总耗时也包含快照作用域读取，旧版在这一段结束后才开始计时。[并发回归](../../tests/integration/test_m3e_citation_qa.py) · [SQLAlchemy 对长事务与连接池的说明](https://docs.sqlalchemy.org/en/20/errors.html#queuepool-limit-of-size-x-overflow-y-reached-connection-timed-out-timeout-z)

## GPU 重排

参考 FlagEmbedding 在编码器重排中按 token 长度组批、之后还原原序的实现，在 RTX 3060 Laptop 6 GB 上用相同 BGE FP16 权重、同一候选顺序做交错配对。冻结的 SciFact TRAIN 样本含 128 题、2,560 对候选。平均热重排从 270.86 ms 降到 249.77 ms，P95 从 306.64 ms 降到 290.56 ms。两臂文档 nDCG@10 均为 0.768271，128 题的前十块顺序全部一致。7.79% 的平均降幅低于预登记 10% 门槛，因此候选保留为可复跑实验，生产沿用已验证的原批序。[配对报告与冻结协议](../../benchmarks/public_rag/results/published/reranker-batching-20261114/README.md) · [FlagEmbedding 实现](https://bge-model.com/_modules/FlagEmbedding/inference/reranker/encoder_only/base.html)

其中 13/128 题在 20 个候选里已找不到金标文档，另有 8 题在这 20 个中找到了金标，但前五块没有。前一组需要改善候选召回，后一组才可能直接受益于改排序。这批结果限定于已公开的 TRAIN 查询和本机热重排。

## 答案是否引用正确版本

本轮从空工作区通过公开 HTTP 上传 20 份中英文合成政策，用 Celery、真实 BGE 和 Qdrant 完成入库。每个主题有两个互相矛盾的数值，替代关系只记录在文档元数据中。10 道固定 DEV 题包含 6 道现行规则、2 道历史版本和 2 道缺据题。10 题均检索到两个对应版本。每题固定同一组证据、顺序、模型和提示，交替安排两臂。改动只在材料旁标明已有的替代状态及可用的生效日期。本例显式设置了替代关系，未设置日期。

| 首次模型答复，每题每臂一次 | 原投影 | 带生命周期投影 |
| --- | ---: | ---: |
| 冻结的机械标准（目标数值和来源，或正确拒答） | 3/10 | 9/10 |
| 实际明确作出目标版本判断或正确拒答，事后逐题核读 | 0/10 | 9/10 |
| 未通过本地输出协议 | 3/10 | 1/10 |

原投影的 3 个机械通过样例都同时列出两个值并表示无法确定现行版本；数值和引文出现不足以证明问题得到回答。新增投影下有一条英文问题得到中英混合答复，还有一条收费问题在单次回答时未通过输出校验。以上是 10 道人工构造的小样本，用于检验机制。20 次配对生成共 20,423 个 token。另从公开 QA 接口抽查现行、历史、缺据各一题，均返回 200，分别取得对应修订的引用或零引用及显式拒答标志。[固定数据与复跑](../../benchmarks/evaluation/experiments/citation_lifecycle_dev/README.md) · [逐题答复与复核](evidence/local-rag-20261114/citation-pairs.json)

所配置北京端点在本次调用中拒绝 DeepSeek 的原生 `response_format=json_schema`。同址两个 Qwen 模型名的探针也未取得可用的原生结构化回答。沿用项目 Wiki 的显式 `PROMPT_JSON` 方式，将同一份 JSON 契约放入受预算控制的提示；本地严格验证字段、拒答状态、引文编号及其与正文标记的一致性。原生模式仍是默认值，保留模型链的能力检查。提示模式可以对语法正确、引用关系不一致的回复发起一次有界修正。出现重复字段或结构错误会返回 502。可用性取决于实际端点和部署，实测与官方通用说明分别留证。[API 契约](../api-contracts.md#grounded-citation-qa) · [阿里云结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

最后运行仓库内的公开 B 复验命令，在另一个空工作区重新上传、等待真实 Worker、建快照并向 `POST /api/v1/knowledge/query` 提交全部 10 题。8 个可回答问题均给出目标版本数值并引用对应修订，2 个收费问题均显式拒答且无引文。此次独立运行复用了同一组开发问题。接口没有输出模型用量与实际生成次数，因此不将这 10 个 HTTP 请求折算成 10 次供应商计费调用。[独立公开接口回执](evidence/local-rag-20261114/public-qa-replay.json)
