# M4 准备：开源实现与 AgentHub 边界

日期：2026-10-27。以下核对的是项目公开源代码，不是性能对比，也不证明摘要正确。

- [LangMem summarization.py](https://github.com/langchain-ai/langmem/blob/main/src/langmem/short_term/summarization.py) 先给摘要和既有 system 消息计入预算，保存已摘要的消息 ID 和水位；其示例会将滚动摘要放入 system 消息，并使用旧摘要更新新摘要。AgentHub 可以借鉴预算与来源范围跟踪，但不沿用提升摘要信任级别或未经验证的摘要套摘要：材料标记为不可信，保留原始来源和受保护事实。
- [LangChain summarization middleware](https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/summarization.py) 把触发阈值与保留范围分开配置，并寻找不切断 AI/tool 配对的截断位置。AgentHub 进一步以完整 Turn/并行工具组和现有证据身份作为不可分割单元；无法验证完整性时明确不足。
- [QMSum 官方仓库](https://github.com/Yale-LILY/QMSum) 提供会议转写、查询、参考答案及部分相关片段；只把转写作为不可信资料，参考答案和相关片段只用于离线评分。数据上游来源、使用许可、样本选择、真实压力和调用费用须分别核实，不能由仓库代码许可推断数据使用条件。

这些来源支持架构设计的部分选择；不能据此推断 AgentHub 的压缩质量、准确率或净收益。AgentHub 的冻结来源、权限复核、派发未知结果、持久化与费用边界仍需由本项目代码和故障注入验收。

本项目现有 `capture_auxiliary_model_calls` 使用 task-local 内存记录，进程崩溃后无法单独证明派发或计费结果；M4 不能把它当作持久账本。正式实验已有冻结价格快照，应核对实际供应商及 fallback 对应的价格，而不只沿用主模型价格。

M4 只读设计复核还发现：M3 的 `revision_sha256` 包含当前水位，不能直接作为跨后续 Run 复用摘要的稳定内容身份；应保留它用于精确重放，另建立不含水位但包含来源内容、绑定和权限语义的摘要来源身份。M3 将来源资格设为 UNKNOWN，旧材料为 KEEP_EXACT；M4 若要真正使用摘要，必须有可信资格来源及完整前缀覆盖，不可仅增加存储表。硬压力时规划器当前直接抛不足，M4 若需要后台准备，必须先安全记录任务再拒绝当前派发。真实调用还须核对 gateway 的 execution plan 重试和 fallback，单独设置 request 不足以禁用这些行为。以上是下一阶段的设计核查项，并非已实现或已验收。

M5 前置核对：现有 LiteLLM adapter 会读取 `prompt_tokens_details.cached_tokens`，缺失时保留 `None`，而非当作零；目前 `ModelUsage` 只有这一缓存读数，没有单独的缓存写入字段。该代码只说明已有字段归一化，不证明 Magpie 或具体模型支持可控缓存、实际产生了命中，也不能据此计算完整缓存收益。

低信任标签本身不能阻止模型遵从注入文本。任何摘要注入消息的角色、包裹方式及提示词都应结合 fake provider 的实际请求断言、恶意来源案例和真实模型质量评测核查；它们不能替代服务器端权限检查和工具执行约束。

M5 只读复核：当前首条系统消息可能拼入随历史裁剪量变化的 `history_hint()`，因此不能直接假定整个系统前缀跨 Run 恒定。需保留该提示的语义，考虑将其精确纳入前缀身份或作为合法的独立动态块；任何变更都必须验证原角色、顺序及工具配对。已有多轮 usage 汇总遇到未知缓存读数时保留 `None`，与明确的零有别；线上事件、写入 token 和完整缓存成本仍须单独核对。这里只记录静态发现，未做供应商缓存支持或性能声明。

后续逐题对照应把评分分成独立字段：任务要求是否覆盖、每个关键断言是否由原文支持、说话人和时间是否归属正确、否定/条件/冲突是否保留、动作状态是否正确、引用能否回查、是否明确承认证据不足。记录 B、C 两边的输出和失败理由，再对照 reference；reference 不能替代原文作为事实依据。无独立人工盲审时明确标注代理审阅，小样本仅报告逐题与描述性统计。
