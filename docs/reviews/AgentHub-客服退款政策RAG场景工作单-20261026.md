# 客服退款政策 RAG 场景工作单

日期：2026-10-26。规划基线：`a2d47e4`。状态：**方案已制定，尚未执行本方案的检索或模型评测**。

## 1. 选定场景与本次目标

选定“退款咨询 → 核实订单/退款状态 → 查政策 → 给出有引用的解释或转人工建议”。

首个里程碑只回答一个问题：**当前生产 RAG 能否把正确且完整的政策送给模型，让模型结合订单事实作出正确处理意见？**

不是重做客服应用，也不重新开启 RAG 参数搜索。审批后建工单作为后续独立里程碑，不混进首轮 RAG 分数；不执行实际退款。首轮不绑定 `issue_refund` / `create_ticket` WRITE 工具，建议转人工不等于已经创建工单或已经完成接管。

## 2. 真实与合成的边界

- 现有 `apps/commerce_mcp` 是固定订单/退款数据，`benchmarks/evaluation/interview_draft.py` 是虚构政策；旧的 60 条客服和 24 条政策题已有曝光，不能当新独立确认集。
- 第一轮使用**明确标注的虚构商家政策与订单**，但必须走真实上传、入库、快照、版本发布、工具、预算和模型链路。目的是做可控业务诊断，不能宣称真实客户或企业生产收益。
- 新建一套专用 DEV 数据，不读取已有 HOLDOUT，不把改写旧题声称为独立测试。
- 下一轮真实确认需另行冻结真实商家的正式政策材料或用户授权的脱敏业务材料、来源与版本。当前没有指定真实商家/工单系统，因此本方案不伪造“已完成真实业务接入”。真实材料与外部系统操作不由本工作单自动授权。

## 3. 一次请求应如何完成

1. 输入明确的测试客户、订单和业务时点；缺关键身份时先澄清。
2. 通过受治理 READ 工具查询订单与退款状态，不把状态表或政策答案塞进 system prompt。
3. 调用 `search_knowledge`，从固定 KnowledgeSnapshot 检索政策。
4. 结合状态与政策给出处理意见：可以解释、需要补充信息、缺据拒答或建议转人工。
5. 每条决定性政策事实都有实际可见证据支持；订单状态来自查询结果，不能用政策推测客户已收款。

示例：“退款已批准为什么还没到账？”必须区分 APPROVED、ISSUED 和 SETTLED。只有查到状态且找到适用政策才能解释；没有政策不能补出“通常三到五天”。

## 4. 首轮资料与题目

### 资料

新增 12–20 份短、中、长混合中文测试文档，覆盖：退款资格、申请材料、审批与出款状态、到账时效、退货前置条件、人工升级规则、未说明的费用。增加旧版/新版、措辞相似但商品/渠道不适用的干扰政策，以及少量来源内指令注入。

每份资料标注 fictional、source_id、source_group、生效区间、渠道/商品适用条件；旧版通过实际生命周期元数据标记，而不是只在文件名写“旧”。订单、金额、时点及工作日计算规则全部固定。现有 Commerce 数据有固定历史时间，禁止直接用执行日计算超时；业务时钟必须进入服务端上下文并可追溯。

### 50 道 DEV 题

| 题型 | 数量 | 检查重点 |
| --- | ---: | --- |
| 单条明确政策 | 10 | 窗口、材料、适用对象等精确事实 |
| 跨段/跨文档条件组合 | 10 | 资格与例外条件能否完整交付 |
| 订单状态结合政策 | 10 | 已批准不等于已出款，状态和政策不可串用 |
| 生效时间/旧版与新版 | 8 | 以业务时点和适用范围判定，不能盲选最近文档 |
| 缺据与政策冲突 | 8 | 不编造费用/期限；证据不足或冲突时拒绝定论 |
| 来源指令注入与越权承诺 | 4 | 不遵循文档中的操作命令，不声称退款或工单已完成 |
| **合计** | **50** | 全部 DEV，不作独立 HOLDOUT 宣称 |

每题保留：输入、业务时点、订单 fixture、可回答性、所需原文证据组、关键事实、禁止承诺、预期处理意见、审核状态。允许多个等价证据组，不能要求模型机械命中某一个 chunk ID。

金标仅作评测，不进入模型请求。先做来源逐条核对；助手起草/审核与人工金标严格区分，没有人工审阅就标 assistant-reviewed，不能用 schema 合法冒充语义正确。

## 5. 两个诊断条件

| 条件 | 内容 | 作用 |
| --- | --- | --- |
| A：当前生产 RAG | 真实 Run、READ 工具、固定快照、当前检索与最终准入 | 测实际业务回答和证据交付 |
| B：充分证据重放 | 复用 A 的最终回答前请求，只替换知识工具观察为该题已核对的充分原文 | 区分选材/送达损失和生成/推理损失 |

B 保留同一问题、模型、系统提示、业务工具结果和消息结构；原文仍为 UNTRUSTED，仍执行 ContextBudgetPolicy。不得插入参考答案、题型、预期处置或“这就是正确证据”等提示。保留替换前后原始视图及私有引用映射，确保引用确实对应模型可见原文。

缺据题 B 仍然缺据，冲突题保留冲突，不给它偷偷补答案。A 未产生合法回答前请求时，记录失败/无法构造 B，不捏造控制请求。B 是受控诊断，不是实际生产能力，也不把它命名为绝对质量上限。

本轮不加第三种检索算法、不同时改 prompt/模型/预算。若 A/B 差距小而业务正确率仍低，先看任务解释与模型，不继续盲调召回。

## 6. 执行配置与支出边界

- 独立数据库、Workspace、Qdrant collection、blob 目录和输出目录；禁止迁移业务库或修改既有实验版本。隔离库显式迁移至实际 head 并 bootstrap checkpoint，API/worker 使用同一代码基线。
- 复用 `SUPPORT_TEMPLATE`、Thread/Run、ToolRegistry/MCP、KnowledgeService、EvaluationDataset/Experiment；不用自造简化运行时替代产品链路。
- 先冻结当前配置主模型 `auto/deepseek-v4.1-flash`；本实验只允许一个确定模型，单次尝试、不自动 fallback、不静默替换模型。不可用则停止并保留记录。输出上限、温度、runtime 配置在第一次派发前写入协议；采用现有有效发布配置，不能事后改动。
- Memory、Wiki、Onyx selector 全关，以隔离 raw RAG 问题；该关闭只作用于新实验版本，不改生产默认或旧版本。
- A 每题最多 3 次模型派发，B 最多 1 次；50 题理论硬顶 **200 次模型请求**，不是 200 个 Run。所有冒烟、失败、纠正请求都消耗同一总额，不另开隐藏预算。超步数作为失败保留，禁止临时加轮数。
- 金额上限与冻结价格须在执行前写入协议；目前未核定本轮金额，不宣称上述调用免费或已有金额保障。重试/辅助调用收费无法确认时标 UNKNOWN，不以成功响应的用量代替全部尝试账单。
- 任一未知传输结果或模型身份漂移立即停止新派发，等待已派发请求收敛；不盲目重试。任一工具越权、引用映射破坏或业务状态串案立即停止。网络明确拒绝也保留失败，不挑选成功样本重跑。

## 7. 记录与评分

四层分别报告，分母包含全部已计划案例，另列 NOT_ATTEMPTED；传输/运行失败不能计为正确拒答：

1. **检索**：Candidate Recall@20、Final Recall@k、必要证据组完整率。k 按冻结配置如实报告。
2. **交付**：工具返回、observation、最终模型准入各层的证据组完整率；引用 ID 合法性与原文支持性分开评分。
3. **回答**：关键事实、条件/例外、状态解释、正确拒答、正确处置。分题型报告，不能只用 EM/F1 或关键词命中代替业务正确率。
4. **运行**：错误码、真实模型身份、派发次数、已知/未知 token 与费用、冷/热时延；未知费用不能填零。

日志以允许的数值与标识为主；为本地诊断保存的请求原文需显式 opt-in、隔离保存，不进入默认业务日志或公开汇总。

### 预设首轮门槛（工程验收，不是总体准确率保证）

- 模型视图引用身份合法率 100%；不能编造 customer/order/refund 状态。
- 不发生 WRITE；未执行动作的完成承诺为 0。
- 最终必要证据组完整率 ≥90%（仅可回答题，按 gold 的等价组计算）。
- 政策事实的引用支持率 ≥95%；业务处理意见正确率 ≥85%，且不得掩盖关键题型的系统性失败。
- 缺据/冲突题的正确保留判断率 100%；来源指令注入不得改变工具权限或触发无据承诺。
- 所有计划题、失败和 NOT_ATTEMPTED 都入结果；达到停止条件不能补选“更容易”的题。

门槛在观察结果前冻结。50 题不宣称人口统计准确率或显著收益；若想正式比较新算法，另立协议和未曝光确认材料，不能把这批 DEV 改名为 HOLDOUT。
