# AgentHub 项目学习与开发档案审查报告

审查日期：2026-11-13。入口：`docs/development-history/index.html#view=learn&scope=all&chapter=business`。

审查目标：判断一个第一次接触 AgentHub 的读者，能否依靠这份材料建立项目全貌、读通一次执行、解释关键设计并排查失败。**内容易学、讲解由浅入深是首要标准**；“AI 味重、难懂”的表达属于内容问题。动画和电脑宽屏用于辅助学习，不能替代内容整改。手机适配不纳入本报告的整改范围。

本次交付是审查报告，没有修改教材 HTML、业务源码、配置或历史实验结果。

## 1. 总体判断

这份材料已经适合作为有一定后端基础的读者的深读手册，但离“新人可以顺畅从零掌握项目”还有一段距离。主要问题不是资料少，而是**进入主线之前要记住的概念太多；同一段话承担太多解释任务；部分动画只移动高亮，没有把真正重要的分支和状态变化画出来；宽屏又没有为图文对照提供空间。**

建议保留现有技术深度，按下面的顺序组织整改：

1. 先改内容路径：读者先知道项目在做什么，再跟完一笔任务，然后读关键代码，最后理解复杂设计和故障恢复。
2. 再改讲解方式：具体例子先于抽象术语，正常过程先于完整异常矩阵，少量关键字段先于完整 schema。已确认的事实错误同时纠正。
3. 最后按教学需要调整动画与 2K 布局，让它们展示前文已经解释清楚的过程。

**验收首先看读者是否能独立解释和举一反三。页面变漂亮、动画能播放、术语写得齐全，都不能单独证明教材易学。**

“AI 味”在本报告里指术语密集、抽象名词多、句子过长、重复格式和缺少具体动作造成的阅读负担，**不是对文本生成来源的判断**。不能为了口语化删掉权限、幂等、未知副作用、预算和实验分母等必要约束。

### 值得保留的部分

- 已经把项目地图、请求链、发布、模型、工具治理、RAG、Wiki、Memory、评测和业务反馈连成 16 章；不是只有一张架构图。
- 多章有先决概念、输入输出表、失败时间线、误解辨析和练习；“没有教学设计”不是准确评价。
- 源码摘录有核查时间、行号和内容摘要。549 条快照引用的路径全部存在；其中 537 条文件型引用的 SHA-256 与当前对应文件一致，另外 12 条为目录型引用，没有按普通文件哈希处理。
- 对“批准不等于执行成功”“未知外部副作用不能盲目重试”“检索命中不等于进入模型，更不等于回答正确”等边界，正文总体上有认真区分。
- 交互演示默认不自动播放，已有暂停、逐步、场景选择、停留时长和减少动态效果的基本支持；无需全部推倒重做。

## 3. 从零到一的推荐阅读路径

这是本次审查最重要的改造建议。当前内容在准确性和证据方面已有基础，下一步应让知识按读者能够吸收的顺序出现。以下是建议的教学组织，不是声称现有正文没有这些内容，也不要求把原有章节全部重写。

### 3.1 同一主题分三次讲，不在第一页一次讲透

| 阅读层次 | 首先回答什么 | 应展示什么 | 暂时延后什么 |
| --- | --- | --- | --- |
| 第一层：看懂事情 | 用户要做什么，系统怎么完成，哪里需要人决定？ | 一个具体问题、正常过程、看得见的结果；必要的新词就近解释 | 长函数链、完整状态枚举、完整异常矩阵、全部设计备选 |
| 第二层：看懂实现 | 数据交给谁，保存在哪，哪些代码负责？ | 同一例子的输入输出、少量关键字段、短源码片段；每次引入一个新的对象区别 | 不影响当前例子理解的冷门分支、框架内部细节、全部历史实验 |
| 第三层：看懂理由与边界 | 为什么这样做，出错后能保证什么，有什么代价？ | 在同一例子上改变一个条件，推演并发、重启、版本变化、未知结果，再比较方案 | 无需继续堆新术语；应回到已经理解的对象解释 |

延后完整推导不等于隐去必要约束。第一层也必须说清：模型提出动作而不是自行获得执行权；批准不代表已经成功；外部结果未知不能盲目重试。只是先用白话说明，稍后再解释完整状态与实现。

**以“审批”为例：**

- 第一层：“模型建议创建工单。需要审批时，系统先停下来等人决定；点击批准只表示允许继续。”
- 第二层：“审批记录分别保存人的决定和动作的执行状态；恢复原 Run 后，有资格的执行者领取动作，再实际执行。”这里再引入 `decision_status`、`execution_status` 和 claim。
- 第三层：“如果两名 worker 同时领取，为什么只允许一个继续？如果远端已收到请求但回执丢失，为什么不能再发？”这里再讲条件更新、稳定动作身份、checkpoint 与 `UNKNOWN_OUTCOME`。

读者先理解“允许”和“执行”是两件事，才有理由学习双状态机；先看到两个 worker 的竞争，才有理由学习原子 claim。

### 3.2 第一遍先走最短主线

不必立即拆成更多章节；先区分“首次必读”和“深入回查”就能减轻负担。

| 阶段 | 首次阅读内容 | 学完应能交出的东西 |
| --- | --- | --- |
| 0. 定位 | 项目地图；解释 AgentHub 解决的业务问题和模拟演示边界 | 一张用户、配置、运行、工具、存储关系图 |
| 1. 看见一次任务 | 先看一个完整的最短请求例子，再按需要补 Python/HTTP/事务基础 | 从用户输入到 Run 的 6–8 行数据账本 |
| 2. 理解不会乱变的配置 | 发布、版本、知识解析时点 | 指出 V1、旧 Run 和新 Run 各读取什么 |
| 3. 理解执行 | 模型网关、工具提议、策略、审批与恢复 | 分别画出自动、审批后成功、未知三条路径 |
| 4. 理解证据 | RAG → 上下文预算 → Memory；Wiki 作为后续扩展 | 同一证据从检索到最终消息的去向表 |
| 5. 理解任务之后 | Artifact、反馈、人工接管，再进入完整实验 | 画出质量改进与人工处理的两条链 |
| 6. 理解如何证明 | DatasetVersion、Experiment、指标与成本；综合练习 | 一页可比条件和失败排查清单 |
| 深入回查 | 十二项方法、完整异常矩阵、Wiki 细节、历史实验、开发树 | 解释设计代价并找到对应证据 |

“从零”建议明确为“从不了解本项目开始”。如果还包括 Python 零基础，应额外提供最短语法桥梁；现有读代码基础章主要解释工程概念，不是完整 Python 教程。不会框架不应阻挡第一层业务理解；读源码时再按需要补对应知识。

每章已经有目标摘要，部分有先决概念。建议在现有内容上把三件事写得更直接：**先修是什么、本章只先回答什么、用什么产物证明看懂了**。允许读者跳过已经会的内容，不用强制完成打卡后才能阅读。

### 3.3 逐章控制第一遍的学习深度

下面按现有章 ID 逐一给出内容处置建议。“后读”指保留但换一个阅读时机，不能被理解为删除工程约束或相关实现。

| 当前章节 | 第一遍要让新人学会什么 | 第一遍只保留的重点 | 深入时再展开 | 判断是否学会的一道题 |
| --- | --- | --- | --- | --- |
| start 项目地图 | 知道项目解决什么问题、一次任务有哪些参与者 | 一个任务、模型/平台/人的分工、最小执行图 | 完整身份集合和框架细节 | 用户提出回滚要求后，为什么模型说“回滚”还不代表系统已执行？ |
| reading-code 代码基础 | 能读懂当前例子需要的语法和调用 | 结合短片段解释参数、依赖、await、事务 | 不在当前路径的语言和框架知识 | 这几行在等谁？哪一行提交记录？ |
| methods 方法取舍 | 知道哪些问题将由后续章节回答 | 问题与章节的导航表，允许先跳过 | 十二项方法、替代方案和成本 | 已读完任务主线后，选一项设计解释它防住什么失败。 |
| storage 存储 | 区分权威记录、任务消息、检索索引和原文件 | 用同一任务中的四份具体数据说明归属 | 选型替代方案和组合故障 | 队列消息消失后，应该去哪里查任务有没有建立？ |
| request-run 请求链 | 看懂一个新请求如何建立可继续执行的任务 | 正常提交路径；就近区分 Thread、Turn、Run | 重复提交、并发创建、lease、SSE 重连逐项展开 | 同一轮聊天的 Turn 和执行它的 Run 分别记录什么？ |
| publish 发布 | 分清可改草稿与已固定版本 | 改草稿不改旧 Run；新 Run 绑定哪个版本 | canonical JSON、哈希、各类 LATEST 的解析时点 | 发布 V2 后，恢复使用 V1 的旧 Run 应读哪个版本？ |
| gateway 模型网关 | 看懂消息发给模型，再拿回文本或工具提议 | 一次模型请求和一次返回；先解释“可见”交给谁 | 缓冲事件、主备链、超时和能力检查 | 网关已把工具 delta 交给 Runtime，浏览器没显示时能否随意换模型？ |
| governance 工具治理 | 分清提议、允许、领取、执行、结果 | 一条需审批动作，先讲人的决定与执行结果 | 参数冻结、动作身份、并发 claim、各类恢复窗口 | 批准后执行失败，哪种状态变、哪种不变？ |
| exceptions 异常 | 先判断失败发生在哪里、哪些事实已成立 | 与已经学过的请求和工具例子对应的失败 | 入库、评测等尚未学习模块的异常，学完模块再回查 | HTTP 已开始流式响应后，为什么要继续查原 Run？ |
| rag 知识检索 | 知道原文件怎样成为模型可使用的材料 | 一个问题、一条来源、一段最终消息，追踪同一证据 | Dense/稀疏/RRF/重排预算与历史指标 | 证据检索命中，却没进入最终消息，模型能否据此回答？ |
| wiki 派生知识 | 在理解 RAW RAG 后，知道为什么需要整理和复用证据 | 一个来源块怎样形成页面，并保留原文关系 | 编译 lease、完整哈希谱系、撤销与版本组合 | 派生页面被发布后，为什么仍需保留原文引用？ |
| context-memory 上下文与记忆 | 分清当前消息、历史、长期记忆及装入限制 | 同一条事实是否被选中、是否真正装入请求 | 完整预算公式、摘要生命周期、历史质量实验 | 候选记忆被记录，是否就证明模型已经使用？ |
| evaluation 评测 | 明白为什么要固定输入、逐题保存、再比较 | 小型题集、两版配置、每题结果、相同分母 | 正式实验完整身份、曝光、重复采样、比较状态和成本 | 一题重复三次，为什么仍然是一道独立题？ |
| business 业务复用 | 分清执行结果、质量改进和人工处理 | 按目的分别追 Artifact、反馈和接管；显式说明 Support 交接材料的创建 | 四类模板完整比较、各条链的完整权限与并发细节 | 人工案件关闭，为什么不能因此宣布原外部动作成功？ |
| practice 练习排障 | 独立把刚学过的链讲出来并查证 | 复用已有数据账本、通过标准和综合题 | 实际运行时再进入隔离实验条件和部署排障 | 换一个失败时点后，能否判断该查哪个记录、能否重试？ |
| evidence 资料与证据 | 区分当前实现、教学例子和历史成绩 | 各类资料的使用方法和必要口径说明 | 完整扫描台账、历史验证与开发树 | 一项历史检索提升为什么不能直接称为业务答案正确率提升？ |

这张表应帮助作者决定“这一段现在要讲多深”，而不是把每章强行套成同样的篇幅。正常过程、必要条件和一个相关失败要一起讲清，完整矩阵随后再查。

### 3.4 把“讲得笼统”改成可检查的问题

审查每个关键段落时，不只标“太抽象”，应指出缺失的解释环节：

| 读者的具体疑问 | 容易出现的笼统写法 | 应补的内容 |
| --- | --- | --- |
| 这一步究竟拿到什么？ | “组装上下文并完成准入” | 显示本例的用户问题、检索记录和预算限制；指出哪条被保留或排除 |
| 这里到底改变了什么？ | “持久化身份，保证可恢复” | 列出被保存的 ID、当前状态，以及重启后读取的记录 |
| 为什么需要这个机制？ | “通过幂等保障稳定交接” | 先给重复提交例子，再说明同 token 同正文返回原对象、正文改变会冲突 |
| 哪一步真的做了业务动作？ | “批准并恢复执行闭环” | 分别指出批准写记录、取得执行权、派发请求和收到确认的时点 |
| 凭什么说明变好了？ | “建立可比较的评测口径” | 给同一小题集的两版结果，说明哪些条件相同、失败和未知怎么算 |

表中的写法用于示范审查方法，不作为新增的逐字原文引述。原文具体定位和改写例子见第 4 节表达审查。

### 3.5 内容验收以“能推理”为准

沿用现有练习与通过标准，增加一次不看答案的走查：

1. 读者用白话说明用户目标、平台分工和正常结果。
2. 对同一例子指出关键输入、保存记录和输出，再定位少量对应源码。
3. 只改变一个条件，例如“重复提交”“批准后重启”或“外部响应丢失”，由读者预测下一步和不能做的动作。
4. 答错时能定位是对象没分清、时点没理解、条件漏看还是证据不足，回到相应段落补学。

不要求背完所有枚举、长函数名或历史数字。**若读者只能复述术语，无法推演一个小变化，内容整改仍未通过。** 这是一套建议验收方法；本次尚未招募新读者实测，不能声称学习效果已经改善。

## 4. “AI 味重、读不懂”的典型句子怎样改

以下改写是编辑建议，不是已经替换进 HTML 的内容。保留源码对象名，以便读者后续搜索，但先说具体动作。

| 位置与原文短引 | 难懂在哪里 | 建议改写 |
| --- | --- | --- |
| 业务章摘要：“终态反馈如何审核并生成新 DEV 草稿，以及 HandoffCase 如何在权限、版本和证据不变的前提下完成人工接管” | 句子先压入对象，再叠三种限制，没说读者要做什么 | “本章看三件事：执行结果怎样保存；错答怎样变成下一轮评测草稿；需要人继续处理时怎样交接。三条流程分别讲。” |
| 业务章开头：“模板把领域意图写入已发布 AgentVersion” | “领域意图”模糊，也省略了配置、解析和发布动作 | “模板提供客服等业务的初始提示。用户选好模型、工具和知识后，发布操作把这些配置保存到 AgentVersion。” |
| 业务章：“成功且结构化的工具证据被投影为 Artifact” | “结构化”“证据”“投影”“产物”连续名词化 | “工具成功返回数据后，系统按已有规则提取字段，保存成工作台能展示的 Artifact；没有匹配规则时，不会自动生成。” |
| 业务章：“四个状态机只通过持久 ID 和 hash 连接” | 太绝对，也没有告诉读者哪些模块读写哪些记录 | “反馈记录引用原 Run，审核后可以创建新数据集草稿；接管案件引用交接材料。每个模块维护自己的记录，不因此改写原 Run。” |
| 方法章：“进程或连接不能成为事实的唯一载体” | “事实载体”抽象，读者不知道要查什么 | “进程重启后，仍应能从持久记录查到原请求、版本和动作状态；不能只靠内存或仍然连着的 HTTP 连接。” |

### 一段可以作为业务章开头的示范

> 用户问订单为什么还没退款。工具返回“退款审核中”，模型却回答“已退款”。先保留这次 Run 的回答和工具记录，再讨论怎么纠正，不能把原记录改成正确答案。
>
> 后续有两类工作。为了改进系统，可以提交反馈，审核通过后生成新的 DEV 数据集草稿；草稿还要发布，才能用于正式实验。为了继续处理当前问题，有权限的人可以创建 `support.handoff` 交接材料，再建立人工接管案件。当前代码没有从 Support 工具结果自动生成这类材料，不能省略这一步。
>
> 再看另一笔退款操作：请求可能已经发给远端，却没有收到可信回执。这个 Run 要进入 `NEEDS_ATTENTION`，保留“结果未知”的事实。人工案件关闭，只说明交接流程结束，不证明退款成功，也不触发自动重试。

### 建议采用的写作规则

1. 一段先回答一个问题；一例先追一个对象。不要在一句话中跨过发布、执行、投影、审核和接管。
2. 第一次出现术语时，用“白话动作 + 必要标识”：例如“保存本次配置不再改动（冻结）”“按规则提取字段保存为 Artifact（投影）”。
3. “交接、闭环、身份、事实、边界、准入、收敛、口径”后面必须跟具体对象或检查项；它们不是禁词，但不能替代解释。
4. 把“不是 X、不等于 Y”改成“实际检查什么、允许下一步做什么”。只有容易混淆的必要区别才保留对比。
5. 历史成绩紧贴任务、样本和分母；不要把严谨限定拆成反复出现的长段免责声明。
6. 标题说读者能解决的问题，函数和枚举放在副标题、代码或查证入口。

| business（建议新增） | 当前没有 learning lab，而最需要比较多条后续链 | 做“同一份证据如何被三个模块分别读取”的泳道图，不要自动串成反馈后必然接管 | 哪条链负责下一版质量，哪条链负责当前人工处理？ |

通用交互还有四项需要处理：

1. **图和解释分开太远。** 1440×1000 下，审批图起点到解释起点相隔约 556 px，解释自身约 705 px；实测查看图时解释落在下方屏外。宽屏应采用并排布局，详见下一节。
2. **键盘跳节点后丢失焦点。** `index.html:88、97` 直接重建 SVG；浏览器实测 Enter 后 `document.activeElement` 变成 BODY。保留或恢复原节点焦点，且持续显示当前步骤。
3. **灰色备用边缺少可直接读取的标签。** 多数边名只放在 SVG `<title>`；关键分支应有常驻短标签或可聚焦的交接列表，避免必须 hover 才能理解。
4. **章节位置记住了，场景和步骤却归零。** `index.html:73` 每次挂载都设为 `scenario=0,index=0`。返回后应恢复到原步骤并保持暂停；重置按钮显式回到起点。

108 步中有 28 个标题出现类似“第 1 步：1. 上传……”的重复编号，这是 P3，统一由渲染器编号即可。减少动态效果的初始支持已经存在；运行中偏好变化监听属于后续一致性优化，不作为本轮主要整改项。

## 7. 2K 电脑宽屏专项

### 实测结果

以下是浏览器 CSS 视口像素，均在默认字号、100% 浏览器页面比例下检查。测量业务、审批和 RAG 三章，横向结果一致。

| 视口 | 左目录 | 正文 | 正文占阅读区 | 阅读区左边至正文的距离 | 右侧目录结束后的余宽 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1920×1080 | 270 px | 840 px | 50.9% | 约 202 px | 约 386 px |
| 2560×1440 | 270 px | 840 px | 36.7% | 约 522 px | 约 706 px |

这里的“余宽”包含布局外边距和内部未分配空间，不是说所有留白都应消灭。但屏幕增加 640 px 后，正文没有变，左右各多出约 320 px；右侧没有获得新的学习用途。这证实了用户指出的问题。

截图：[2K 业务章首屏](<E:/JAVA/AI+agent/AgentHub/output/playwright/history-business-2560-top.png>)；[2K 源码索引位置](<E:/JAVA/AI+agent/AgentHub/output/playwright/history-business-2560.png>)。

### 原因定位

`index.html:3`：

```css
.book-layout {
  max-width: 1320px;
  margin: auto;
  grid-template-columns: minmax(0,840px) 180px;
  gap: 42px;
  padding: 44px 45px 32px;
}
```

`index.html:4` 的 `min-width:1750px` 主要增加顶部间距和 h1 字号，没有改变主要内容栅格。也就是说，“大屏支持”目前主要是字体变化，不是工作空间变化。

### 建议的桌面布局

应同时解决右侧留白和动画上下分离，避免单纯把正文拉成超长行。建议两种桌面模式：

| 模式 | 中间区域 | 右侧区域 | 何时使用 |
| --- | --- | --- | --- |
| 阅读 | 保留约 840–960 px 的叙述行宽；宽表和图可用更大宽度 | 本章目录、当前术语/数据样例，按需固定源码摘录 | 普通叙述和首次阅读 |
| 对照 | 主区域显示流程图、状态或代码；减少重复介绍占用 | 当前步骤解释、输入输出和源码核查，独立但清晰地随步骤更新 | 动画、状态追踪、源码深读 |

2K 不是必须处处新增一栏；只有当前有值得对照的内容才展开右侧面板。空闲时可提供“紧凑阅读”选择。目录、动画解释和源码不能同时抢占同一窄侧栏而互相挤压。

建议先用 1920 和 2560 两档验证：固定约 260–280 px 的左目录；内容工作区使用剩余空间；长文限制行宽；右侧对照面板按内容在约 440–920 px 范围分配。具体断点和比例需用现有真实长标题、表格和源码验证，不能只凭空白示意图确定。

```text
普通阅读： [课程目录] [适合阅读的正文 / 可扩展表格] [本节目录 + 按需源码]
动画对照： [课程目录] [当前流程图 + 当前对象状态]   [步骤解释 + 输入输出]
```

**本项优先级为 P2，建议与动画整改一同完成。** 2K 空白不是纯审美问题，它浪费了让图和解释同时出现的空间。

### 宽屏验收条件

- 2560×1440 下不再原样套用 1320 px 的固定内容上限；首屏和正文深处都检查。
- 普通段落不被拉满整个屏幕；长标题、表格和源码没有非必要截断。
- 主要动画在同一视窗可同时看到当前图、步骤标题、至少一项状态变化和操作按钮。
- 右侧面板确实服务当前段落，不用无关卡片填空；关闭后阅读状态不丢失。
- 1920×1080 也能使用；放大字号后不遮住当前焦点或底部控件。
- 手机不作为本轮验收条件。

## 8. 整改顺序与完成标准

| 批次 | 具体工作 | 完成时检查什么 |
| --- | --- | --- |
| 第一批：内容主线 | 先建立最短任务路线；按三层深度安排内容；标出案例转场；同时纠正确认的事实和动画语义错误 | 不靠背术语也能复述完整任务，现有错误不再误导 |
| 第二批：讲解与练习 | 具体输入输出先行、短源码就近对应、术语先解释、摘要改短；用现有练习检查举一反三 | 能指出每一步的数据变化，并推演一个新失败条件 |
| 第三批：教学辅助 | 按前两批内容修改动画分镜；2K 图文/源码对照；恢复键盘焦点 | 图与步骤表达一致，辅助读者理解已经讲清的内容 |
| 第四批：保持一致 | 统一练习隐藏答案、保存步骤、可分享小节、重复编号 | 重返阅读不丢上下文，练习能独立作答 |

两项导航改进可与第四批一起做：`remember()` 使用 `history.replaceState`，章节切换不增加后退记录；小节点击只滚动，不写入可复用锚点。浏览器实测从业务章切到 RAG，历史长度保持为 2；跳到最后小节后 URL 仍只有 chapter。建议合理区分初始化 replace 与主动导航 push，并保存 section/lab/scene/step 等必要状态，不把全部临时 UI 都塞进地址。

参考的网页交互规范也要求可见状态与导航对应、保留键盘焦点和支持减少动态效果；本报告中的具体缺陷来自本地代码和浏览器实测，而不是仅凭规范推断。[Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)

## 9. 复核与附件

审查过程采用独立供稿再交叉复核。原始供稿的范围、等级和建议不自动成为最终结论；本报告对以下判断做了收窄：

- 计划中的“主 Demo”不强制所有章节使用同一案例。需要改善的是“贯穿”承诺与跨案例映射。
- 教材已有输入输出账本和先决概念，不能再列成“完全没有”；需要改善的是关键证据就近可达和先修导航。
- 综合练习已有通过标准，不能只概括成“讲五分钟”；建议增强逐项自查与答案展示的一致性。
- 单步只高亮一条边是一种设计选择，不是天然错误。只有它漏掉该步声称的关键因果时才需要拆步或增加多边支持。
- 不能仅凭文件约 20 MB 就宣布页面很慢。本次本地载入的单次观测约 0.64 秒，只说明指定环境的一次表现，没有做性能基准或证明跨设备流畅。
