## 1. 结论与证据口径

教材并不缺信息。解析 `archive-payload` 后，16 章共有约 229,016 个去标签文本字符、731 个正文段落、361 个二、三级标题、395 条源码/资料引用和 77 个展开框。`business` 单独就有约 13,700 个文本字符、27 个标题、8 张表和 5 道练习。真正影响“从 0 到 1”的，是这些信息还没有形成一条稳定、可诊断的学习主线。

优先处理五项 P1：

1. 统一一条与 `plan/plan.md` 主 Demo 一致的贯穿案例。
2. 明确“零基础”究竟是项目零基础还是 Python/SQL 阅读零基础，并设置先修检查。
3. 把平铺章节改成有先修关系、章节目标和掌握门槛的路径。
4. 把前置于主线的十二项方法目录缩成导航页，细节移到相关流程之后。

- **已证实**：可直接从 HTML、内嵌 JSON、页面内联脚本或 `plan/plan.md` 当前文本复现。

## 3. 高价值问题

### P1-1｜“贯穿本手册”的案例与产品主 Demo 冲突，后续又反复更换身份

**定位**

- `chapter=start` → 小节「先用一个具体任务认识 AgentHub」。
- `chapter=request-run` 章节摘要。
- `chapter=rag` → 小节「4. 贯穿实例：一份三页的湖区运维手册」。
- `chapter=context-memory` → 小节「二、要解决的问题与一个贯穿实例」。
- `chapter=evaluation` → 小节「问题与贯穿实例：一条题如何扩成六个 trial」。
- `chapter=business` → 小节「贯穿实例与阅读边界」。
- 当前产品语义真源 `plan/plan.md:133`：`## 3.2 Demo B — Customer Support Agent（主 Demo）`。

**原文短引**

> “贯穿本手册的教学任务是：‘checkout-api 新版本发布后错误率升高……’”

**已证实**

开篇把 checkout-api 事故回滚称为“贯穿本手册”的案例；产品计划却把 Customer Support Agent 定为主 Demo。后续请求章转向“客服工单”，RAG 章转向“湖区运维手册”，上下文章使用客服 `Run R7`，评测章使用 `D-SUPPORT-60 / E-9`，业务章再使用订单 `ORD-2026-0108` 的 `Support Run R1`。

**问题与新人为什么卡住（推断）**

新人每章都要重新记一套业务对象、编号和失败路径，很难看出哪些是同一系统能力在不同数据上的应用。开篇先建立的 `W1/U1/R1` 还会被后来更多 `R1/R7` 语境覆盖，产生“R1 到底是什么案例”的歧义。

**建议**

- 采用计划中的 Support 主 Demo 作为全书唯一主案例：用户要求查询退款条件，必要时创建工单或发起退款。
- 第一页放一张“案例卡”：`Thread T1 → Turn A → Run R1 → AgentVersion V1 → Approval AP1 → Artifact A1 → DatasetVersion DV4 → Handoff H1`，并标出每个身份由谁创建。
- Incident 回滚保留为第二个演示或补充案例，用于展示同类 Runtime 的复用，不再承担“贯穿”角色。
- 同一套案例分别覆盖：RAG 查询政策、上下文保留退款规则、审批执行 WRITE、未知结果转人工、反馈形成 DEV 草稿。

### P1-2｜“从零”没有定义目标读者的先修基础

**定位**

- `chapter=start` 的章节摘要：“从零区分 Agent、运行时、控制平面、进程、存储和版本”。
- `chapter=reading-code` 全书，尤其「不用先学完所有框架，先抓四种数据」「async/await 到底在这里做什么」「依赖注入不是‘全局魔法’」。
- 可复现事实：该章去标签约 3,770 字符，正文 `<pre>` 数为 0；它直接从 `async def`、`Depends`、`PrincipalContext`、repository 和事务讲起。

**原文短引**

> “不用先学完所有框架，先抓四种数据”

**已证实**

这句话只说明“不必先学完框架”，没有说明读者是否能读 Python 函数、类、import、`async def`、类型标注、SQL 和 HTTP。标题承诺“看懂 Python”，正文却没有 Python 语法入口，主要用概念解释加结尾源码卡片。

**问题与新人为什么卡住（推断）**

对会 Python 的后端初学者，这一章可以作为导航；对只了解其他语言或完全不会 Python 的读者，`Depends`、异步函数和 repository 已经越过先修门槛。两类人看到同一个“从零”标题，会得到错误预期。

**建议**

- 明示目标：例如“读懂本教材需会 Python 函数、类、import、异常与基础 SQL；不要求会 FastAPI、SQLAlchemy、LangGraph”。
- 在章首放 6 题、5 分钟的进入测试：能否找到函数参数、识别 `async def`、解释 `await`、区分查询与提交、读懂简单类定义。
- 若目标真的包括 Python 零基础，补一个 20–30 分钟附录，并用 `get_current_principal` 的 8–12 行短摘录逐行注释；若不包含，就把“从零”改为“从项目零认知开始”。

### P1-3｜学习目录是平铺顺序，没有可见先修关系与掌握门

**定位**

- `book.chapters[*]` 仅含 `id/title/summary/html/sources/nav/search`，没有前置章节、学习目标或掌握条件字段。
- `index.html` 内联 `list()`：将 `B.chapters.map(...)` 直接渲染成一列按钮，章号只取数组位置。
- `chapter=start` → 小节「如何使用这份教材，避免再陷入重复入口」。

**原文短引**

> “左侧‘逐章学习’是唯一主线：先认识进程和对象，再跟请求……”

**已证实**

这里给出了一句路径提示，但页面没有表达“读业务章前必须掌握哪些对象”的可操作关系。目录也不区分先读、可跳过、需回查或综合章。

**问题与新人为什么卡住（推断）**

平铺顺序容易被理解为每一章都必须按原位完全读懂。新人很难知道能否先读请求链、是否必须先读全部方法章，也不会在进入 `business` 前得到“已具备发布、审批、评测三项前置能力”的确认。

**建议**

- 为每章增加三行元数据：`先修`、`本章能做什么`、`通过条件`。
- 目录可按“主线 / 横向回查 / 综合实战”分组，并允许跳转，但保留一个推荐默认路径。
- 在 `business` 开头设置前置自检：说明 AgentVersion、Approval 决策/执行双状态、DatasetVersion DRAFT 与 HandoffCase 各是什么；答不出时直接链接到对应章节。

### P1-4｜方法章在主请求链之前一次展开十二项方法，认知负担过高

**定位**

- `chapter=methods` → 小节「读法：方法服务于不变量，而不是技术名词」「十二条方法及其取舍」「方法选用决策表」。
- 量化：约 15,954 字符、17 个二级标题、13 张表、43 条源码/资料引用；章节正文另有 1 个约 4,644 字符的代码块。

**原文短引**

> “本章横向比较 AgentHub 当前工作副本中的十二项工程方法。”

**已证实**

该章位于全书第 3 章，在真正跟完一次 HTTP 请求到 Run 之前，就同时出现持久 Run、队列重投、lease、LangGraph checkpoint、canonical hash、审批双状态机、fallback、Hybrid/RRF/rerank、上下文准入和实验冻结。

**问题与新人为什么卡住（推断）**

新人还没有一个具体请求作为“挂钩”，十二项方法只能被当成需要记忆的名词表。到后续请求、发布、治理、RAG、评测章再次遇到同一概念时，又缺少“这次只是复习，上一章已经讲过”的提示，容易把横向比较误当主线正文。

**建议**

- 保留一章“方法地图”，每项只给一句问题、一句当前选择和一个真实失败例子，控制在首屏可比较的长度。
- 将完整取舍、替代方案和代价移到相应主线章节之后，或标为“读完整条链后再看”。
- 每项方法增加“首次出现章节 / 深入章节 / 可跳过条件”，避免同一概念被当成新内容反复读。

### P1-5｜理论到代码的桥主要是函数名箭头，不是可执行的数据追踪

**定位**

- `chapter=business` → 小节「真实函数调用顺序」。
- 同一函数链在 `book.chapters[13].html` 中以约 1,193 字符的 `<pre>` 呈现。
- `business` 的 `sources` 有 26 条；页面会在章末追加 “本章源码与核查位置”按钮，但正文箭头本身没有逐步骤源码锚点。
- `index.html` 内联 `openChapter()` 负责在 `c.html` 后追加 source-list；源码按钮不是与每个箭头绑定的数据账本。

**原文短引**

> “发布 list_templates / get_template -> AgentPublishService._resolve_draft_spec -> 写入不可变 AgentVersion……”

**已证实**

章末源码入口存在，这一点是优点；不足是长链把发布、Turn、Run、Artifact、Handoff、Feedback 等不同业务路径压进同一段箭头文本。读者能看到“先调谁”，却看不到每一步拿到什么、写了哪张表、成功后留下什么证据、哪一步失败会改变哪个状态。

**问题与新人为什么卡住（推断）**

文件名和函数名过长时，读者会转为抄写或记忆名称，而不是建立调用模型。遇到真实故障时，也无法判断应从哪一条持久记录开始查。

**建议**

- 把长箭头改成 8–10 行数据账本：`触发者 | 输入 | 校验/调用 | 持久写入 | 输出身份 | 失败状态 | 核查位置`。
- 给出一个最小完整片段，例如从 `open_turn` 到获得唯一 `Run` 的输入、唯一约束与输出，然后让读者预测重复提交时哪一步返回原对象。
- 每个函数名就近关联章末源码按钮；不要把 26 个入口集中成一个名称瀑布。

### P1-6｜`evaluation` 到 `business` 缺少同一对象上的闭环交接

**定位**

- `chapter=evaluation` → 小节「问题与贯穿实例：一条题如何扩成六个 trial」。
- `chapter=business` → 小节「贯穿实例与阅读边界」「Feedback：错误答案怎样成为新 DEV 草稿」「Handoff：人工接管不是审批的另一个名字」。

**原文短引**

> “之后用户提交纠正，审核通过，系统生成新的 DatasetVersion 草稿；另一个可能分支是远端退款写入响应丢失……”

**已证实**

评测章使用 `D-SUPPORT-60 / DV-3 / E-9 / V-BASE / V-CAND`；业务章使用 `Support Run R1 / ORD-2026-0108 / H1`。业务章确实提到新 DRAFT 以后应经过 publish 才能绑定 Experiment，但没有把上一章具体实验和本章具体反馈连成一条状态时间线。“之后”与“另一个可能分支”也同时出现在一句里。

**问题与新人为什么卡住（推断）**

新人难以判断反馈、DRAFT、发布、实验和人工接管究竟是同一案例的连续步骤，还是互斥分支；也不知道 R1 的纠正最终如何成为下一轮评测的输入。

**建议**

- 画两条并列泳道：质量闭环 `R1 终态 → Feedback APPROVED → DV4 DRAFT → PUBLISHED → Experiment E10`；运营闭环 `R1 NEEDS_ATTENTION → support.handoff Artifact → H1 → CLOSED`。
- 在 `business` 开头明确：这两条链共享 Run 证据，但目的不同，任何一条都不能改写原 Run 的答案、审批决定或外部执行结果。
- 用一个具体 `R1` 表贯穿两章，并在评测章末保留“下一章将把这条 Run 转成新草稿”的显式出口。

**定位**

**原文短引**

**已证实**

一个章节内部已经明确存在“前半 / 后半”。`wiki` 的「6.1 每阶段的字段、身份与状态」单节约 4,685 字符，`rag` 的「6.1 用七个字段观察一次交接」约 4,585 字符，都是适合拆分的认知块。

短章可能只够建立词汇，无法支持独立操作；长章则要求一次性维持十几个对象和状态表。新人容易在 `exceptions` 或 `wiki` 中失去本周期的目标，转而只做局部名词记忆。

### P2-2｜固定边界声明在 8 章逐字重复，形成模板化阅读障碍

**定位**

完全相同的一句出现在 `book.chapters[1]`、`[5]`、`[6]`、`[7]`、`[9]`、`[10]`、`[11]`、`[12]`，对应 `reading-code`、`publish`、`gateway`、`governance`、`rag`、`wiki`、`context-memory`、`evaluation`。

**原文短引**

> “图中步骤与示例值用于解释机制，不连接数据库、模型或外部工具；不是现场运行记录。”

**已证实**

该句在 8 个不同章节逐字重复。统计上，正文出现 `不等于` 77 次（14 章）、`边界` 116 次（15 章）；这些词本身有必要，但高频重复与逐字模板会削弱重点。

**问题与新人为什么卡住（推断）**

每章都用同一段限定语提醒“不是实跑”，读者很快会把它当作页眉跳过；而真正需要注意的差别，例如“教学 ID”与“历史实验结果”或“静态源码摘录”与“当前运行证据”，反而容易被埋没。

**建议**

- 在课程入口放一次全局说明：页面交互与示例值不调用真实服务，历史数字按报告日期解释。
- 各章只保留一句与本章证据真正相关的声明，例如 RAG 章写“本章排名是教学值，历史 59.04%–78.29% 来自报告而非本轮复跑”。
- 将“技术边界”放入统一样式的标签或证据卡，正文直接讲当前例子，避免模板句插在开场和操作之间。

### P2-3｜`business` 把四条业务链一次讲完，章内阅读目标过多

**定位**

- `chapter=business` 的主要二级标题：四类应用复用 Runtime、模板到 Run、Artifact、Feedback、Handoff、真实调用顺序、模块边界、最小源码路径、失败时间线、常见误解、只读练习。
- `book.chapters[13].html` 约 13.7k 文本字符、27 个标题、8 张表、26 条源码引用。

**原文短引**

> “四类业务应用看似是四个产品入口，底层却在同一条模块链上交接……”

**已证实**

该章同时承担四类模板比较、不可变版本回顾、Run/工具链回顾、Artifact projection、Feedback 审核与 DEV 导入、Handoff 权限/状态机、源码导航和五题练习。

**问题与新人为什么卡住（推断）**

“复用同一 Runtime”本可以是本章主结论，但 Artifact、Feedback 和 Handoff 各自又包含独立状态机。一次读完时，新人的注意力会在四个领域入口、四个业务结果和多个权限状态之间切换。

**建议**

- 将 `business` 设计为两轮 capstone：第一轮只追 `模板 → 发布 → Run → Artifact`；第二轮再比较 `Feedback → DEV` 与 `UNKNOWN → Handoff`。
- 每轮结束给一个状态表，第二轮再来回查第一轮的不变量，避免一次塞入全部边界。
- 四类模板只保留一页比较表；真正练习放在 Support 主案例，其他三类作为变体。

### P2-4｜练习与答案呈现不一致，部分章节实际上没有形成回忆测试

**定位**

- `chapter=business` → 「只读练习与手算」。HTML 中有 5 个练习，但 `details` 只有 1 个，即词汇折叠；5 个“参考答案”是紧随练习全部直接显示的 `h3`。
- `chapter=rag` 和 `chapter=context-memory` 将练习/答案放入 `<details>`，`practice` 也使用 5 个折叠框。
- `chapter=evaluation` 在「只读练习与手算」下列出练习后，直接显示 6 个“参考答案”标题；`details` 仅用于词汇表。

**原文短引**

> “练习 1：某模板声明了‘查询订单’和‘发起退款’两个 tool hint……”

**已证实**

同样是“只读练习”，有的章允许先作答再展开，有的章答案一屏可见；`business` 的 5 个答案与题目连续排列，没有尝试输入、提示或掌握标准。

**问题与新人为什么卡住（推断）**

直接阅读答案会产生“看懂了”的错觉，但无法证明能否在新场景中重建调用链。不同章节的交互也使用户不知道何时应该主动遮挡答案。

**建议**

- 所有练习统一为“预测 → 提示 1 → 提示 2 → 展开答案 → 自评”。
- 每题列一个可观察产物，例如填写 `R1` 的 Input/Store/Output/Unknown 四格；不要只问一段自然语言能否成立。
- 按三级递进：概念辨认（模板与运行规格）、单链追踪（Artifact 来源）、故障诊断（Feedback/Handoff/UNKNOWN），每级至少一题。

### P2-5｜最终验收只有“讲五分钟”，没有可判定的掌握门槛

**定位**

- `chapter=practice` → 小节「完成学习的验收：连续讲完一条链」「学习记录模板」「用交互图检验是否真正掌握」。
- `chapter=practice` → 「学习记录模板」中的短引。
- `index.html` 内联 `progress()` 按 `read.has(c.id)` 统计章节数；页面只记录“已读”，不记录练习结果或掌握条件。

**原文短引**

> “‘标记读完’是你自己的学习记录，不代表测试通过。”

**已证实**

页面承认阅读进度不是测试，却没有提供一个替代的测试记录。综合验收要求连续讲五分钟、讲到每个词都能指出数据位置和故障状态，但没有评分表、遗漏项或最低通过条件。

**问题与新人为什么卡住（推断）**

学习者不知道“讲完”到什么程度算通过，也无法定位是哪一层理解断了。对准备面试或交接的人来说，这种验收不容易复用。

**建议**

- 提供一个 8 行验收表：身份、权限、发布快照、模型调用、工具提议、审批/执行、证据产物、评测冻结。每行填写“对象 / 持久位置 / 正常结果 / 失败结果 / 证据”。
- 明确通过条件：例如 8 行均能指出至少一个函数或数据表，并能正确解释 `APPROVED ≠ SUCCEEDED`、`hit ≠ admitted ≠ used` 两组边界。
- 把 `business R1` 作为必答 capstone，另给一个故障变体让读者判断是否自动重试或交给人工。

### P3-1｜术语首次出现分散，缺少一份全书统一的术语与别名表

**定位**

- 10 章包含“第一次见这些词？先用白话理解”折叠框；`start`、`methods`、`storage`、`exceptions`、`practice`、`evidence` 没有同类入口。
- `chapter=business` 的折叠词表只含 `Artifact`、`Feedback → DEV`、`handoff`；随后同一章又用表定义 `AgentTemplate`、`AgentVersion`、`AgentRun`、`Artifact`、`RunFeedback`、`HandoffCase`、`DatasetVersion DRAFT`。

**原文短引**

> “Artifact 面向业务展示和后续操作的结构化产物……”

**已证实**

正文并非没有解释这些术语；问题是解释入口分散，英文对象名、中文概念名和状态名混用，没有统一记录“首次定义在何处、拥有什么状态、由谁创建、在后续章节还叫什么”。

**问题与新人为什么卡住（推断）**

新人读到 `RunFeedback`、`feedback`、`反馈`，或 `HandoffCase`、`handoff`、`接管` 时，需要自行判断是否为同一对象的不同写法；上下文章又以 `WRITE/SELECT/FREEZE/ADMIT/USE/REPLAY` 引入另一组过程词，查找成本持续增加。

**建议**

- 在课程首页提供一张唯一术语表，至少包含：`AgentTemplate`、`AgentVersion`、`Thread`、`Turn`、`AgentRun`、`Approval`、`Checkpoint`、`Artifact`、`RunFeedback`、`DatasetVersion`、`HandoffCase`。
- 每项固定写出：一句白话、所属层、创建者、关键状态、常见误称、首次讲解章节。
- 各章只列“本章新词”，并回链到统一术语表；同一对象首次出现后保持英文标识不变，中文只作解释。

## 4. 建议的重排学习路径

当前顺序把“方法总表”放在第一次完整执行之前，也让异常章同时承担 API、工具、模型、入库和评测五类恢复。建议保留现有内容，但重排成下面的主线，`methods` 与 `evidence` 作为回查资料，`exceptions` 按边界拆读。

| 阶段 | 推荐顺序 | 进入下一阶段前应能完成 |
| --- | --- | --- |
| 0. 统一故事 | `start`（改为 Support R1） | 在纸上写出 User/Turn/Run/AgentVersion/Approval 五个身份及其关系 |
| 1. 工程先修 | `reading-code` | 通过 Python/HTTP/SQL 先修检查；能从 HTTP 输入追到一个持久记录 |
| 2. 系统骨架 | `storage` 的核心职责表 | 说清业务事实、队列消息、索引投影、checkpoint 各由谁负责 |
| 3. 第一条执行链 | `request-run` | 从一次提交走到 Run，指出幂等、唯一 Run、租约和 SSE 的证据 |
| 4. 冻结与调用 | `publish` → `gateway` | 区分草稿、发布快照、Run 有效知识、模型主备和首个可见输出边界 |
| 5. 受控副作用 | `governance`；`exceptions` 的 API/SSE 与 Runtime/Tool 部分 | 用 R1 的退款工具解释提议、批准、执行、未知和人工核查 |
| 6. 证据进入模型 | `rag` → `wiki` → `context-memory` | 区分命中、冻结、准入、可见和模型真正使用 |
| 7. 可复现质量 | `evaluation` | 从 R1 的反馈得到 DEV DRAFT，再说明它如何进入新的实验身份 |
| 8. 业务闭环 | `business` 第一轮 Artifact；第二轮 Feedback/Handoff | 分别画出“以后如何改进”和“现在如何人工处理”两条泳道 |
| 9. 综合验收 | `practice` | 完成 R1 数据账本、一次故障诊断和本章掌握门槛 |
| 回查资料 | `methods`、`exceptions` 的 Ingestion/Evaluation 部分、`evidence` | 在需要比较替代方案、定位跨层故障或查历史依据时再读 |

如果页面暂时不拆章，可在现有章节顶部增加两组链接：

- “先读到这里”：只给完成当前学习门所需的小节。
- “系统跑通后再看”：给完整源码表、替代方案、历史证据和跨域失败时间线。

## 5. 200–400 字示例改写

把 AgentHub 想成一个客服工作台。用户询问订单 ORD-2026-0108 的退款状态时，系统先选 Support 模板，再读取已发布的 AgentVersion，确定这次可以使用哪些提示词、模型、工具和知识。执行过程记成 Run R1。工具返回“退款审核中”是事实；模型若改写成“已退款”，不能覆盖这条事实。成功后，系统可以把有明确结构的工具结果保存为 Artifact；需要人工处理时，再由 Artifact 建立 HandoffCase。R1 结束后，用户纠正答案；审核通过后，系统生成新的 DEV 数据集草稿，供后续评测。若退款写入可能已经发生但结果未知，R1 应停在 NEEDS_ATTENTION；人工接管也不能把它改成成功。读者应先抓住这条事实链，再逐层查看各模块怎样保存和核验证据。

这段改写共 353 个字符，其中 212 个汉字，其余为必要英文标识和数字；处于用户要求的 200–400 字范围。它保留了模板、发布快照、Run、事实来源、Artifact、Feedback→DEV 与 UNKNOWN 的核心关系，同时把因果顺序写成一条可复述的故事。

## 6. 原句 → 为什么难懂 → 白话改写

### 示例一

**定位**：`chapter=methods` → 小节「读法：方法服务于不变量，而不是技术名词」。

**原句**

> “请求、知识、模型和动作都必须有可持久、可核验的身份，进程或连接不能成为事实的唯一载体。”

**为什么难懂**：把四类对象压缩成“身份”，又用“载体”指代内存变量、连接和队列；读者看不到具体应该保存什么、查什么。

**白话改写**

> 每次执行都要把用户请求、正在使用的版本配置、检索材料和工具动作保存成可核验的记录。不要只看内存变量、HTTP 连接或队列消息，因为进程重启后，这些都不能证明事情发生过。

### 示例二

**定位**：`chapter=business` → 首个小节「一次客服 Run 如何留下可复用、可纠正的证据链」。

**原句**

> “模板把领域意图写入已发布 AgentVersion；Runtime 执行受治理的工具并产生 Run；成功且结构化的工具证据被投影为 Artifact……”

**为什么难懂**：一句话连续堆入模板、AgentVersion、Runtime、Run、工具证据和 Artifact，六个名词之间的发布、执行、投影关系没有先建立。

**白话改写**

> 四类应用共用一套执行链。模板只决定某个业务怎么起步；发布后，AgentVersion 固定这次可用的提示词、模型、工具和知识。Run 记录执行过程；工具成功返回且系统能套用明确结构时，再把结果保存成 Artifact。

### 示例三

**定位**：`chapter=business` → 小节「Artifact：为什么不是模型一句‘总结一下’」。

**原句**

> “recorder 对无法表示的工具结果丢弃并记录 warning，不能让一个成功 Run 因展示层无法投影而失败。”

**为什么难懂**：“无法表示”“recorder”“投影”连在一起，没有说明谁失败了、什么仍然成功、用户会看到什么。

**白话改写**

> 如果工具执行成功，但系统没有合适的 Artifact 格式保存它的返回值，就跳过这个 Artifact 并记录警告。工具本身已经成功，所以 Run 仍是成功的；只是这次结果不会出现在工作台制品区。

### 示例四

**定位**：`chapter=evaluation` → 小节约「一次正式实验如何建立可审计身份」。

**原句**

> “任何一处只保留名字而没有冻结具体内容，结果就无法重现。”

**为什么难懂**：“任何一处”过于抽象，读者无法知道到底要保存哪些身份；同时“重现”没有说明是重新执行还是历史读取。

**白话改写**

> 评测时必须保存数据集版本和内容哈希、AgentVersion 的 resolved spec hash、知识快照、价格和评分器版本。只写“某个数据集”或“某个模型”，不足以重新执行同一实验。

### 示例五

**定位**：8 个章节共用的“教学推演”段落，例如 `book.chapters[1].html` 的「交互推演：两个 worker 同时看到可执行，谁能继续？」。

**原句**

> “教学推演：图中步骤与示例值用于解释机制，不连接数据库、模型或外部工具；不是现场运行记录。先预测，再单步验证自己的理解。”

**为什么难懂**：一句话同时交代示例性质、调用边界、证据边界和操作要求；重复八次后，读者很可能直接跳过整段，连本章真正需要保留的限制也一起漏掉。

**白话改写**

> 页面里的 ID、状态和步骤都是纸面示例，不会调用真实服务。请先预测下一步，再点开看原因。

全课程再统一保留一条证据说明：“源码摘录是静态阅读；历史成绩按报告原时点解释；本章实际操作不等同于产品验收。”这样既保留边界，也避免每章复制同一长句。

## 8. 审查边界

- 本文只审查教学内容与新手可理解性，不判断动画是否正确，也不对源码实现作验收。
- “已证实”只覆盖文档结构和当前静态内容；“新人会卡住”属于基于这些证据的教学推断。
- 没有修改产品状态，没有把源码摘录当作当前运行结果，没有扩充任何未经证据支持的产品能力。
