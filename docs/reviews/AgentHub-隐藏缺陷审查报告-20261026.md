# AgentHub 隐藏缺陷审查报告

审查日期：2026-10-26。代码基线：`4d07c87`，审查开始时工作区干净。

## 结论与范围

本轮重点寻找“代码和局部测试均通过，但实际执行、证据送达或异常恢复失效”的问题。主审检查运行图、上下文准入、工具结果裁剪及 Citation QA API；三个独立子审分别检查 Wiki 发布与原生工具、运行队列与审批恢复、模型网关与知识检索。以 `AGENTS.md`、`plan/plan.md` 的语义不变量为判据；未重开功能里程碑。

本轮只新增审查报告与复现证据，不修改产品实现，不调用付费模型，不发布或上传文件。发现的问题尚未修复。本报告不构成“整个项目已无其他问题”的保证。

第一轮收录 **16 项主要发现（11 项 P1、5 项 P2）**，并另列 **8 项需要真库或故障注入闭环的风险**。第二轮旧模块审查使用独立 L 编号，见报告后半部分。P1 表示可阻断交付、破坏关键状态语义或证据安全边界，应优先修复；P2 表示条件触发的可靠性、契约或可观测性缺陷。没有已证实的 P0 或跨租户越权结论。

## 已复现的缺陷

### H-01 · P1：裁剪后沿用历史消息数量，下一轮可能把当前任务删除

**代码依据**：`packages/agent_runtime/runtime_graph.py:558` 把 `state["messages"]` 替换为准入后的短列表，但未同步 `history_message_count` / `memory_message_count`；`:713`、`:714` 下一轮仍向分类器传入旧计数。`packages/agent_runtime/runtime_projection.py:360` 起按列表位置确定 memory/history 区间。

**触发路径**：Thread 带历史消息 → 第一轮因窗口不足裁掉部分历史 → 模型调用工具 → 第二轮再次准入。当前用户问题的索引前移，仍落入旧 history 区间，被降为可驱逐的 `CONVERSATION`，进一步的窗口压力会把问题本身删除。

**实测**：离线探针构造四组历史问答，第一轮确实驱逐历史；第二轮分类时当前任务变成 `CONVERSATION`；加入合法工具调用与观察后，准入结果保留工具消息，却完全没有当前用户任务。不是只根据代码推测。

**影响**：长 Thread 的多步 Agent 可能在工具调用后失去用户任务，表现为答非所问、反复检索或无法完成。memory 的位置计数同样存在漂移风险；本轮实测结论限于 history 路径，不声称已复现所有 memory 组合。

**为何现有测试漏掉**：`test_a1_thread_context.py`、`test_b2_long_term_memory.py` 主要验证第一次分类与一次准入，没有覆盖“使用裁剪后消息与旧计数进行第二次准入”。

**修复建议**：为消息保留稳定的类别与交换组元数据，随裁剪一起持久化；如暂时继续用计数，必须按实际保留消息重算，并确保当前任务有独立且稳定的必保留身份。验收至少覆盖两轮工具调用、历史裁剪、memory 被移除以及 checkpoint 恢复后的再次准入。

### H-02 · P1：引用正文上限与 API schema 不一致，正常回答返回 HTTP 500

**代码依据**：`packages/knowledge/evidence_records.py:15` 将 `MAX_EVIDENCE_EXCERPT_CHARS` 定义为 2000；`packages/knowledge/citation_qa.py:446` 用此上限生成引用。`apps/api/schemas/citation_qa.py:29` 仍限定 `excerpt` 最长 1000 字符。`apps/api/routes/citation_qa.py:63` 起构造响应时发生 Pydantic 校验。

**触发路径**：命中且引用一条长度超过 1000 的证据即可。默认 chunk 长度本身就是 1200（`packages/core/config/settings.py:77`），所以不需要异常数据或超常配置。

**实测**：1200 字符证据 → CitationQaService 成功生成合法回答与引用 → `_response` 抛 `ValidationError`；通过真实 ASGI 路由调用 `/api/v1/knowledge/query`，返回 HTTP 500。

**影响**：检索成功、生成成功之后仍无法交付，且已经发生的模型费用无法挽回。直接测 service 的用例可能通过，HTTP 消费者却失败。

**修复建议**：明确引用 excerpt 的独立展示契约，并让生产投影与 API schema 共用同一上限；无论选择 1000 还是 2000，都应添加 1000/1001/1200/2000 边界的路由测试，不依赖服务单测替代响应验收。

### H-03 · P1：普通工具结果贴近池上限时，正文被整体替换成截断标记

**代码依据**：`packages/agent_runtime/context_budget.py:741` 起只对特定 RAG 格式预留 `name` / `tool_call_id` 开销，普通 `TOOL_RESULT` 没有此预留。`:769` 按完整消息重新估计，超限后在 `:774`–`:781` 退化为只有 `truncated` 和 `trust` 的 marker。

**触发路径**：`_bounded_tool_result` 先按 payload 限制大小；随后总准入给它相同的数值上限，却额外计算工具名及调用 ID。刚好贴近上限的合法正文因多出的消息元数据超限，不会再缩小正文，而是整条清空。

**实测**：100 单位池、330 字符正文可稳定复现；默认 4000 单位池、15930 字符正文也复现。前一层保留完整 `data.value`，下一层最终只剩 `{"truncated":true,"trust":"UNTRUSTED"}`。总体模型窗口为 20000，远未耗尽。

**影响**：普通 READ/MCP/REST 工具明明成功，模型却看不到任何业务结果。与此前“检索到了但送不到”的问题同属跨层预算不一致。

**修复建议**：所有可投影类别在投影前统一扣除消息元数据成本；最终超限时在剩余正文预算内重新投影，而不是直接整条替换。加入默认 4000 池的边界测试，并验证完整项、引用和错误码仍能保留。

### H-04 · P1：Citation QA 绕过总上下文准入，小窗口或备用模型可在提供方才失败

**代码依据**：`packages/knowledge/citation_qa.py:303` 只按固定证据池选材；`:359`–`:376` 直接构造请求并调用 `generate`，`:407` 的纠正重试同样没有总准入。模型网关 `generate` 路径不承担 `ContextBudgetPolicy`；与之相对，`packages/wiki/answer.py:202` 起已按冻结模型链执行准入。

**触发路径**：证据符合本地固定上限，但证据、问题、系统提示、输出预留与 schema 的总量超过实际模型窗口。若 fallback 窗口较小，固定上限也不能保证备用链可执行。

**实测**：六条各 2000 字符的合法证据，无需超过 ingestion 上限，构造出的实际请求估计输入为 3420 单位；4k 窗口、2k 输出预留时可用输入只有 2048。service 仍派发给假网关，没有模型计划/窗口准入步骤。未调用真实提供方，因此不报告任何真实模型的报错率。

**影响**：固定证据池单测可以通过，真实模型或 fallback 却报上下文超限，浪费延迟与请求次数。预算修复目前没有覆盖所有入口，违反项目规则 20。

**修复建议**：先解析本次完整模型链，再对最终请求进行统一准入，输出预留覆盖链上参数；纠正重试加入的新消息也需重新准入。加入大小窗口、较小 fallback、长问题与重试场景，不仅验证 `_select_evidence`。

### H-05 · P1：审批决定后崩溃、或领取动作后崩溃，自动对账都不能使 Run 收敛

**代码依据**：`packages/approvals/service.py:239`–`:293` 分别独立提交审批决定与 `CLAIMED`；`apps/api/routes/approvals.py:79`–`:84` 在决定提交后才调用 resume。`packages/approvals/reconciliation.py:222` 起的状态转换，只处理缺 checkpoint、部分 RUNNING 和 `CANCEL_REQUESTED + CLAIMED`，不处理“WAITING_APPROVAL + 已决定”或“WAITING_APPROVAL + 陈旧 CLAIMED”。

**触发路径**：决定提交后、resume 前退出；或者 claim 提交后、结果持久化前退出。审批可能已经批准、拒绝、过期或领取，Run 仍停留在 WAITING_APPROVAL。存在 checkpoint 时，周期对账既不排队恢复，也不把无法确认的陈旧 claim 转为待处理。

**实测**：对真实 `_apply_reconciliation_transition` 输入 APPROVED/NOT_STARTED、DENIED/NOT_STARTED、EXPIRED/NOT_STARTED、APPROVED/CLAIMED 四种状态，并设置 stale=True、checkpoint 存在，四者均保持 WAITING_APPROVAL。已核对 worker 的对账接线；未实际杀死 PostgreSQL/Celery 进程。用户手动重发恢复可能处理部分情况，不能据此称自动恢复可靠。

**影响与修复**：审批后任务可能长期卡住；陈旧 claim 还涉及副作用是否已经发生。决定与恢复作业应通过 durable outbox 一致提交；claim 需要 owner/lease，超时且无法确认的结果应收口 UNKNOWN_OUTCOME / NEEDS_ATTENTION，禁止盲目重试。必须补齐这两个 crash window 的故障注入。

### H-06 · P1：审批恢复期间取消，可把未知副作用覆盖成 CANCELLED

**代码依据**：`runtime_service.py:293`–`:302` 的行锁只覆盖最初状态读取；后续 action 执行时 Run 仍可保持 WAITING_APPROVAL。`:421` 的 cancel 将 WAITING_APPROVAL 直接终结为 CANCELLED；`:1332` 起 `_complete_run` 无条件优先保留既有 CANCELLED。`runtime_graph.py:1175` 起正确生成的 NEEDS_ATTENTION 因而会被覆盖。

**触发路径**：恢复已领取并派发动作 → cancel 看到 WAITING_APPROVAL 并写 CANCELLED → 动作返回 UNKNOWN_OUTCOME → 最终提交试图写 NEEDS_ATTENTION。

**实测**：调用真实 `_complete_run`，给定已取消 Run 和 `NEEDS_ATTENTION / ACTION_RECONCILIATION_REQUIRED` 的动作结果，返回仍为 CANCELLED，failure_code 也被清空。该探针验证终态优先级；完整并发时序依据上述代码链确认，未做真库竞态压测。

**影响与修复**：用户可能把“结果未知”误解为“操作未发生”。动作进入 CLAIMED 后取消只能请求停止，不能宣称安全取消；最终写入须让未知副作用的 NEEDS_ATTENTION 优先，并用条件更新覆盖竞态窗口。

### H-07 · P1：worker 领取前取消，Run 停在 CANCEL_REQUESTED

**代码依据**：`runtime_service.py:424` 将 RUNNING 改成 CANCEL_REQUESTED；`apps/worker/tasks/agent_runs.py:98` 只接受 RUNNING，否则直接返回。`reconciliation.py:243` 只收敛带 CLAIMED 审批的取消。

**实测**：通过实际 `_execute_agent_run`，用假数据库返回 CANCEL_REQUESTED Run，worker 不启动执行，也不终结取消。再用真实 reconciliation 转换函数处理无审批的同一状态，仍不变化。

**影响与修复**：尚未开始执行的任务也可能一直显示“正在取消”，客户端持续等待。需要在明确未领取的情况下原子终结 CANCELLED；执行中则由 owner/lease 协调停止。加入“先入队、立即取消、再投递 worker”的回归。

### H-08 · P2：SSE 从历史补播切到 live 订阅时可漏掉已持久化事件

**代码依据**：`runtime_service.py:637` 先完成 replay，`:641` 才订阅 hub；live 收到更大 sequence 后直接推进 cursor。虽然 `:649` 再补播，但已经跳过中间缺失项。

**实测**：调用真实 `attach_stream`，用可控 reader/hub 实现“补播 10 → 查询为空后持久化并广播 11 → 开始订阅后收到 12”。持久记录实际包含 10/11/12，消费者最终只收到 10/12，结束后的补播也无法补回 11。

**影响与修复**：丢失的结构事件可能是工具结果或状态更新。应先订阅并缓冲，再补播、按 sequence 合并去重，或把持久日志作为唯一有序交付源。单独测 recorder 与 hub 不能覆盖这个交界时序。

### H-09 · P2：本地工单已提交后超时，却被记为确定失败

**代码依据**：`packages/tools/actions.py:110` 起先 commit 工单，再 refresh 返回；`:189`–`:200` 将本地 executor 的 TimeoutError 一律映射为 FAILED / ACTION_TIMEOUT，注释错误地认为取消本地协程等于动作没有发生。

**实测**：执行真实 CreateTicketActionExecutor 和 ActionRuntime；假 session 的 commit 记录工单已提交，refresh 阻塞触发 timeout。实际结果为 FAILED / ACTION_TIMEOUT，而非确认成功或未知结果。没有创建真实业务工单。

**影响与修复**：数据库业务状态与审批执行状态不一致。超时后先按 idempotency key 查询；确认已提交则成功，无法确认则 UNKNOWN_OUTCOME，不能把协程取消当事务回滚证明。

### H-10 · P1：Wiki 冲突和证据不足标志在模型视图中消失

**代码依据**：`packages/tools/builtins/query_wiki.py:162` 起生成 route、insufficient_evidence、supplemental_required、conflict_count；`runtime_graph.py:1452` 起只把 results/evidence_refs 传给 `assemble_evidence_plan`。`packages/knowledge/evidence_plan.py:15` 的字段白名单不含 conflict，`:77` 起将视图 status 固定为 SUCCESS。

**实测**：输入 HYBRID、insufficient_evidence=True、supplemental_required=True，且包含冲突证据；经过真实 observation 后，模型消息只显示 SUCCESS，顶层不足/补检索/冲突计数与记录内 conflict 均不再存在。两个独立探针覆盖观察层和证据组装层。

**影响与修复**：“缺据时拒答、冲突时不强答”的服务判断没有送达模型，可能继续产生普通回答；这不等于本轮已观察到真实模型幻觉。应把这些状态作为 server-owned evidence-view 字段贯通 observation、reproject、admission 与校验器。契约见 `docs/wiki/integration-plan.md:38`。

### H-11 · P1：HYBRID 命中十条 Wiki claim 时，RAW 证据被静默挤掉

**代码依据**：`packages/wiki/query.py:654` 先 Wiki 后 RAW 拼接；`packages/tools/builtins/query_wiki.py:132` 达到 10 条就停止，不为 origin 分配配额，也不标记此次数量截断。

**实测**：10 条 WIKI_DERIVED + 1 条有效 RAW，投影输出仍声明 HYBRID、supplemental_required=False，但 10 个结果全部为 WIKI_DERIVED。

**影响与修复**：检索器找到 RAW 并不等于双层证据真正送达；现有一条 Wiki 加一条 RAW 的正常样本不足以覆盖容量竞争。应按 origin 保留必要配额或交错选择，预算不足时明确退化并打标，不能继续声称 HYBRID 双层可见。

### H-12 · P2：LATEST 只看十个候选，漏掉第十一个有效 publication

**代码依据**：`packages/agent_runtime/publish.py:54` 定义扫描上限 10，`:570` 限制候选后只在这十个中跳过撤销候选。

**实测**：最新十个均撤销、第十一个有效；假 session 检查到实际 SQL limit 为 10，最终抛 WIKI_BINDING_UNRESOLVED。不是“完全不存在有效 publication”。

**影响与修复**：反复编译后再批量撤销来源，可使仍有有效历史版本的 Agent 无法发布。应分批继续扫描或在查询中排除撤销来源。需要区分“扫描预算耗尽”和“没有有效版本”。

### H-13 · P1：primary 空响应被当成成功，可用 fallback 不会执行

**代码依据**：`packages/model_gateway/adapters/litellm/adapter.py:235` 起允许无正文、无 tool call 的响应；`gateway.py:252` 起收到响应直接返回。Runtime 在 `runtime_graph.py:663` 才判定 AGENT_MODEL_EMPTY_RESPONSE，此时已经离开网关 fallback 循环。

**实测**：真实 ModelGatewayService + 假 adapter，primary 返回空正文/stop，fallback 已准备有效回答；网关返回空串，adapter 调用记录仅有 primary。尚无可见 token，仍没有使用预设备用模型。

**修复建议**：在网关执行边界识别真正的空/坏响应，并在首次可见输出前按现有规则切换；明确提供方拒绝等有语义的响应要保留，不将其与传输或空响应混淆。同步和流式均需覆盖。

### H-14 · P2：合法亚秒 Qdrant 超时被截成零

**代码依据**：Settings 允许正 float；`packages/knowledge/adapters/qdrant.py:32` 在传入 SDK 前执行 `int(timeout_seconds)`。

**实测**：Settings 接受 0.5；通过实际 QdrantVectorIndex 构造路径，替换 SDK constructor 观测收到 timeout=0。子审另离线核对安装的 SDK 对 float 与零的处理；本轮未连接真实 Qdrant，不声称测得具体超时率。

**影响与修复**：配置本意为半秒，实际变成零值超时，可能导致检索和探测异常。原样传递受支持的 float 或向上取整，增加 Settings→composition→SDK 的参数边界测试。

### H-15 · P1：Onyx selector 的模型调用丢弃 usage，不进入 Run 费用闸门

**代码依据**：生产 `search_knowledge.py:139` 接入 selector；`packages/knowledge/adapters/onyx_selection.py:364` 起自行请求 chat/completions，`:403` 只返回 section IDs。`runtime_graph.py:649` 的 usage_records 只添加主模型响应，selector 没有费用回传接口。

**实测**：通过实际 OpenAICompatibleSectionSelector，使用 httpx 本地 MockTransport 返回 110 tokens 的 usage；结果仅为 ID tuple `(0,)`，用量没有返回。主审核对调用链确认没有另一条账本写入；未构造真实收费请求或实测超支金额。

**影响与修复**：开启 onyx_v1 后，界面 token/费用少计，max_cost_micro_usd 不能覆盖全部模型活动，多快照可能重复产生隐形调用。selector 应接入统一 attempt/usage/cost 账本与调用前检查；成本不可测时，设置费用上限的运行应明确阻断或声明不可提供该保证。

### H-16 · P2：selector 内外层期限冲突，异常回退来不及执行

**代码依据**：search_knowledge 默认工具期限为 30 秒（`product_control_plane.py:106`），`tools/runtime.py:480` 的外层 timeout 覆盖完整工具；`onyx_retriever.py:61` 先做基础检索才等待 selector。selector 自身默认也是 30 秒，Settings 还允许更长；wrapper 仅捕获 SectionSelectorError/ValueError，外层取消会直接穿过。

**实测**：基础检索已返回证据后，让 selector 阻塞，由外层期限取消；真实 OnyxSelectionKnowledgeRetriever 抛 TimeoutError，没有返回保留的基础排序。探针用 0.01 秒缩放时间；实际生产 30 秒冲突根据配置及调用先后确认，未实测真实 endpoint 延迟。

**影响与修复**：可选选择器超时会把已有检索结果一并丢掉，而非降级原始排序。应把 selector 限制在工具剩余预算内，并留出 fallback 与投影时间；不能只测 selector 主动抛错的回退。

### L-01 · P1：旧 Turn 的恢复可串绑同一会话后来问题的 Run

`packages/threads/service.py:451` 的 `_turn_run` 仅按 workspace、thread 和 `AgentRun.created_at >= turn.created_at` 查最早 Run，没有稳定 Turn/Run 关联或请求内容校验。`submit_turn` 随即把查询结果 attach 给孤立 Turn。

**触发**：A 问题记录 Turn 后、创建 Run 前退出；同 Thread 的 B 问题随后完成；超过 60 秒重试 A。恢复查询会找到 B 的 Run 并当成 A 的结果，不会再执行 A。

**实测**：调用真实 submit_turn 和 `_turn_run`；保留生产 WHERE/ORDER/LIMIT，将 ID 投影在内存 SQLite 上执行，A 的 Turn 被绑定到输入不同的 B Run。不是简单让 mock 无条件返回错误 Run。未使用 PostgreSQL，时间和 UUID 的核心谓词已实际执行。

**修复/施工约束**：Run 创建前持久化稳定 turn_id/submission identity，并原子建立关联；没有可靠关联时不得按时间猜测。后续会话、恢复、worker 化施工前先关闭该缺口。现有 `test_thread_submission_idempotency.py` 把 `_turn_run` 本身替换为受控返回，未覆盖真实查询误认。

### L-02 · P1：所谓“当前 Run 之前的历史”只排除自己，没有时间或序列上界

`packages/threads/context.py:85`、`:159` 的 conversation/search 只有 `agent_run_id != before_run_id`，没有小于当前 Turn sequence 的过滤。API 允许同一 Thread 多请求，且后台执行顺序不一定等于 Turn 序列。

**实测**：将当前 Run ID 作为 before_run_id 传入真实 conversation，生产过滤谓词在 SQLite 执行后仍返回后续 Turn 的问答。较新 Turn 先完成、较旧 Run 后 prepare，或旧 Run 后续调用历史搜索时，均存在看到“未来问答”的路径。

**修复/施工约束**：先解析当前 Run 对应 Turn 的稳定序号，再统一限定 `ThreadTurn.sequence < current_sequence`；历史搜索也使用同一上界。仅冻结 AgentVersion 不能保证会话上下文可复现，后续正式评测引用 Thread 时必须补上此边界。

### L-03 · P1：流式 Turn 在创建 Run 前退出后，只会永久返回“正在启动”

`apps/api/routes/threads.py:207` 起发现重复 token 且 agent_run_id 为空时，直接返回 THREAD_TURN_IN_PROGRESS；没有使用同步路径 `ThreadService.submit_turn` 中的 grace/孤立恢复机制。

**实测**：调用真实 stream_turn，已存在十分钟前创建且没有 Run 的 Turn，重试仍返回 409，既不检查超时，也不恢复或终结。前端保留同一 token 重试，因此会持续命中该分支。

**修复/施工约束**：同步/流式入口共用一套带稳定身份和原子 claim 的 Turn 准备/恢复逻辑。与 L-01 一起解决，不能把按时间猜 Run 的实现直接复制到流式路径。

### L-04 · P2：同一 Run 的记忆提取重复投递，会把一次事实当成多次强化

`apps/worker/tasks/memories.py:57` 起启用 late ack/worker-lost 重投，但没有提取作业 claim 或完成标记；`packages/memory/store.py:310`、`:356` 只按内容 hash 去重，并对已有记忆执行 salience += 1，不区分 source_run_id 是否已贡献过。

**实测**：同一 source_run_id、同一事实已记录一次，再重放两次真实 store.record，salience 从 1 变成 3。模型表注释把 salience 定义为“多少个不同 Turn 断言过”，本行为违反这个语义；重放还会再次请求模型，提取结果不同时甚至可新增记忆。

**修复/施工约束**：按来源 Run 保存提取 attempt/完成状态与事实贡献唯一键；同一来源的重投不重复强化，真正不同 Turn 的重复陈述仍允许强化。既有集成测试验证内容去重和独立写者，不等于来源级幂等性已覆盖。

`apps/worker/tasks/memories.py:111` 起重新解析 Run 创建者的当前 WorkspaceExecutionContext，但随后直接 prepare/generate 并写记忆，没有 `agent_run` 权限门。与 Run worker 的 open_stream 权限检查不一致。

**修复/施工约束**：在背景派发前明确检查所需执行权限；检查失败应留下无业务内容的作业终止原因。该路径还没有总上下文准入/usage 回传，应按第一轮 H-04/H-15 的同类问题一并核对，不能因 Run 已成功就宣称所有后续模型调用已计费或已授权。

**修复/施工约束**：前缀检测用增量解码器 `final=False`，允许末尾字符待后续字节补齐；仍拒绝真正非法编码。今后增加格式支持时，不应复用“任意字节前缀必须可独立完整解码”的假设。

### L-13 · P1：正式实验有 fallback，却只冻结并使用 primary 的价格

`packages/evaluation/experiments.py:941` 的定价校验只看 primary provider/model；AgentVersion 仍可携带完整 fallback_profiles。`packages/evaluation/runner.py:763` 读取单一 variant pricing snapshot，`:803` 按它给汇总 token 计价，观测 DTO 没有逐 attempt 实际模型身份。

**实测**：真实 frozen parser 接受带一个 fallback 的规格，真实 pricing validator 接受仅 primary 的定价；真实 complete_case 将一百万 input 加一百万 output 按 primary 单价 10/30 结算为 USD 40。探针使用假 session 检查实际 UPDATE 参数，没有真实模型调用；fallback 真正接管的能力已有既有测试，计价链却无法表达其不同价格。

**影响/修复**：fallback 与 primary 的单价/币种不同时，正式成本指标、每成功样本成本及成本门禁结论可能错误。应冻结全链定价并保留逐 attempt 的模型与用量；无法确认实际模型或价格时，成本必须不可用，而不是给出看似精确的 primary 成本。
