# 四个业务智能体的真实入口验证

同一模型、同一工具版本和同一题目下，四个智能体的首轮配对从 **1/4 个场景完全达标** 提高到 **3/4**，逐项从 **9/16** 提高到 **13/16**。其中有一个客服基线运行在 API 中显示成功，但泄露了另一笔合成订单的商品、金额和日期，业务评分判为失败。每个场景只有一对，这些数字描述本批案例。

## 首轮配对

| 场景 | 基线 | 首轮候选 | 可核对的变化 |
|---|---:|---:|---|
| 文献研究 | 3/3 | 3/3 | 按完整 OpenAlex ID 取回同一份记录。两侧给出的题名、年份、7 次引用和摘要状态都正确。 |
| 事件响应 | 2/4 | 4/4 | 基线停在模型错误。候选核对了生产环境的历史版本，为 checkout-api 回滚到 5.4.1 建立审批。决策为 PENDING，执行为 NOT_STARTED，执行次数为零。 |
| 数据分析 | 1/5 | 2/5 | 候选取得指标口径、两期总体和分组的 SQL 结果，但最终没有返回文字。只给已核实的工具和数据项计分。 |
| 客户服务 | 3/4 | 4/4 | 候选请用户核对订单，停止退款查询和建单，避免披露他人的商品、金额和状态；仍额外列了请求人自己的两笔订单。 |

基线的 15 次模型请求按冻结单价折算为 0.145836 元，候选的 15 次为 0.160070 元。两侧冻结版本逐个比对，只有系统提示词及提示词版本号不同。后续有工具实现和绑定变更，相关运行单列在明细中。

## 业务路径

- **客服**。查指定订单时，订单工具同时匹配客户号和订单号。归属不符和无此单都返回空列表；客户号单参仍支持查该客户订单。模板处理旧工具时还会核对实际返回的订单和客户。两个候选客户号需要先澄清。条件建单要求核实工单范围及列表完整性，退款和建单分别受绑定的动作权限约束。单独按订单号取数仍属于运营工具，组合过滤本身不代表已认证终端客户。
- **事件**。只读部署核查沿部署、SHA、提交、文件查证。若部署记录没有仓库，可凭 SHA 查提交。有故障处置请求时，先查指定环境、时间段的指标和日志，再核对回滚目标确在该环境成功部署。审批状态、执行结果和服务恢复分别回读。
- **研究**。已知 ID 直接查原文献记录，主题检索才比较候选。返回零引用和未提供引用量有不同含义。排名只涵盖实际返回页。精确查到的论文可以进入研究成果并收藏，来源随收藏保留；ID 错配或调用失败不会生成论文卡。
- **数分**。先核实指标口径，分子、分母使用相同窗口，分别聚合后计算比例。先给总体，再看所问分组。没有分母的行保留“不可比”，不参与变化排名。按平台持平不能推出该平台下各版本持平。

## 公开实现与本项目的取舍

- **文献**。PaperQA2 把候选搜索、收集证据和生成答案分开。AgentHub 的文献工具当前提供元数据和可选摘要，故精确 ID 查询可以直接交付书目信息；只有摘要支撑的内容才进入比较。收藏把证据和调用来源一起保存。[PaperQA2 算法](https://github.com/Future-House/paper-qa#paperqa2-algorithm)
- **客服**。LangChain 的客服示例先收集前置事实，再按任务状态选择处理或移交。AgentHub 把这一思路用在身份澄清、订单匹配、政策核对和建单审批，订单归属在工具内部取交集。[LangChain 客服工作流](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs-customer-support)
- **事件**。Google SRE 把影响评估、缓解和根因分析放在不同阶段。AgentHub 的只读查询可以停在证据足以答复的位置；涉及回滚时，审批、执行和事后恢复观测各有独立判据。[Google SRE 事件响应](https://sre.google/workbook/incident-response/)
- **数分**。LangChain 的 SQL 助手先读表结构、核对查询，再根据数据库结果回答。通用题保留这条路径；对于已有字典定义、窗口和维度都明确的注册转化率，一次参数化读取能交付可复核的结果表。这与 Anthropic 建议围绕常见任务设计工具、用真实任务衡量效果的做法一致。[LangChain SQL 助手](https://docs.langchain.com/oss/python/langchain/sql-agent) · [Anthropic 工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)

## 独立追问与诊断

| 新题 | 事实与行为 |
|---|---|
| 查未收录的文献能否取得题名 | 明确告知无法核实，没有替代或编造题名。同一失败查找重复了一次。之后为用户禁止替代的精确查询补上本轮终止条件。 |
| 用户给两个客户号查发票工单 | 回复先请用户选定客户号。账户读取、写入、审批均为零。 |
| 只读核查 3 月 13 日生产部署 | 两次工具读取即定位到 5.4.1 和 src/checkout/capture.py，正确告知没有可读的 diff，没有发起回滚。 |
| 查 3 月 15 日 UTC 的 iOS 注册转化率 | 给出 14 次注册、45 次原始页面浏览，约 31.11%。用独立只读 SQL 重算一致。 |

四个新题使用场景当时已发布的版本。四题的用户交付均满足预先写下的判据，增加“避免相同参数重复查询”的运行效率检查后，三题完全满足。后续针对同题修订的运行是回归，不再计作独立样本。

单独升级工具发现后，事件智能体取到了正确仓库和两条提交，但模型仍以 MODEL_BAD_RESPONSE 结束，未提审批。数分已经拿到所问的总体和细分数据，又追加国家、逐日等查询，最终生成被截断。缩小取数范围后的数分 v4 在相同的 1024 token 上限内答出了 406/1330 和 336/1358，并定位到第二期 Android 5.2.0 的 56/448。不过开头错误地把两个旧版本都概括成持平。iOS 5.1.1 实际从 112/378 变成 84/252，上升约 3.70 个百分点。v5 加入核对文字与表格的指导，旧题第三次模型请求返回 MODEL_BAD_RESPONSE，仍未交付。这两次运行均保留在记录里。

## 注册转化率的完整交付

新增可选的 Warehouse MCP 只读工具 `get_registration_conversion`。它接受一至两个首尾日期均包含的 UTC 窗口，可筛选平台和细分平台、版本。服务端用参数化查询分别聚合注册与原始浏览，再由未舍入的计数计算百分点差。实际计算得到 −5.784047748 个百分点，保留两位应为 **−5.78**。v4 报出的 −5.79 用了舍入后的比率。通用指标和额外维度继续通过只读 SQL 查询。

| 同一数分题 | 模型请求 | 用户等待 | 峰时费用上界 | 用户得到的结果 |
|---|---:|---:|---:|---|
| 新工具，输出上限 1024 | 2 | 7.047 秒 | 0.019854 元 | 工具准确返回全部分组，末轮用尽 1024 token，用户没有收到最终答案。 |
| 同工具及提示词，输出上限 2048 | 2 | 13.578 秒 | 0.025096 元 | 返回完整对比表。406/1330 → 336/1358，下降 5.78 个百分点。Android 5.2.0 第二期为 56/448，第一期无分母；iOS 总体持平、iOS 5.1.1 上升 3.70 个百分点。 |

两次发布的快照中，只有模型 profile ID 和输出上限不同。实际推理路径由模型选择，后一次还查询了指标字典。两次取数参数一致。2048 的结果是这道复杂题的一次有效交付。数分 QA 单独选用了该配置，其他工作区的模型参数仍归工作区管理。

最终回答的九行数据均与独立 SQL 一致。附注把末日浏览的观察时间过短说成“最后一天没有机会完成注册”，措辞过宽。已将指标字典改为“临近窗口结束的浏览有较短观察时间，当日仍可能注册”。这项文字修订之后没有再发付费请求。

## 验证环境与复核

使用独立的合成业务工作区，在同一个场景 Agent 上发布不可变的不同版本。每次创建新线程，再以独立的 client_token 发起一次用户回合。通过线程、运行、步骤、工具、审批、成果 API 与该运行的 checkpoint 交叉核实。阿里云提供真实模型。订单、事件和数仓使用项目的测试业务数据，文献 MCP 使用可控的 OpenAlex 格式响应。没有批准外部退款或生产回滚。原有 Research 工作区保留已发布版本和定制草稿。

1. 在工作区导入所需 MCP 工具，确认工具版本、读写风险与审批策略，再在智能体草稿中绑定并发布。已有智能体要通过草稿发布新版本才能采用更新。
2. 用 `POST /api/v1/workspaces/{workspace_id}/agents/{agent_id}/threads` 建立对应业务线程，用 `POST /api/v1/workspaces/{workspace_id}/threads/{thread_id}/turns` 发送问题并记录返回的 run_id 和 agent_version_id。
3. 在同一工作区查 `/runs/{run_id}`、`/agent-runs/{run_id}/steps`、`/agent-runs/{run_id}/approvals` 和 `/threads/{thread_id}/artifacts`。审批等待时同时核对 decision_status、execution_status 和执行次数。数值题核对 SQL 或指标返回的实际行。

已知论文和未知论文另用确定性本地模型走实际 API 与文献 MCP。前者生成一篇带运行及工具来源的成果，后者产生零篇。真实浏览器点击收藏返回 HTTP 201，独立回读证实来源一致。最终客服错单和事件回滚也用本地确定性模型走正式应用入口，分别核对零条匹配订单和零次回滚执行。这些本地运行用于核验工具、页面和审批链路。

数分页面在浏览器中展开了指标参数，将 iOS 单日 14/45 的原始证据附入分析结论，保存返回 HTTP 201；重新读取后的参数、行和工具来源与原成果一致。非法日期保存返回 HTTP 422。历史 SQL 结果继续显示原 SQL。超出页面成果容量时保留总体及完整分组，显示总行数和已保留行数，引用继续携带截断标记。

最终代码的九个相关 Python 测试文件共 334 项通过，无失败、错误或跳过。全仓 Ruff、前端八组回归和 TypeScript 类型检查通过。四个业务场景的产品提交截止于 `eaed8fe`。

模型为阿里云北京 deepseek-v4.1-flash-1017，temperature 为 0。计量器逐请求预留并核对请求 ID 和输入、输出 token。按每百万输入 2 元、输出 8 元计算峰时费用上界，实际账单可能因缓存或时段折扣更低。此前两笔未知请求保持锁定。本轮的每个模型回合数、用时、费用、错误及判据见[逐运行明细](business-agent-api-20261120.json)。[阿里云模型计费说明](https://help.aliyun.com/zh/model-studio/deepseek-v4-1-flash)
