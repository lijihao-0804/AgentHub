## 三、修完的收益有多大

按可信度分层：

**① 我独立复算/重跑证实的（机制层）**：中文默认路径从"0 条完整记录"到"整条成对送达"；多轮检索第 2 轮从 18 字节标记到完整保留；重叠冗余窗被去重；preview 前缀切割对 `search_knowledge` 不再可达（R-26 系统级测试锁定，防回归）。

**② 实施报告给出、原始工件在档且头部数字经我独立重算吻合的（效果层）**：
- 冻结重放 200 题（零模型调用）：运行时观察证据召回 **0.590→0.790（+20.0pp）**、完整证据集合率 **0.255→0.550（+29.5pp，翻倍以上）**、送达完整记录 2.16→5.00 条；gold 控制臂 1.000 无回归；三臂（legacy5/aligned/structured5）召回收敛为 0.790——配置不再决定交付质量。
- 真实 deepseek 网关 A/B（同 200 题、同模型同提示词）：**F1 0.2892→0.4135（+12.4pp，相对 +43%，配对 p=0.0010）、EM +10.5pp（p=0.000049）**、拒答率 −11.5pp（错误拒答减少）、跳数分层 4 跳 +23.3pp（0.062→0.295）——总汇报告"损失随跳数放大"的症状在仅修交付层后大幅缓解。交叉验证：before 0.2892 ≈ 已发布生产默认 27.92%，after 0.4135 略高于已确认"预算贯通"臂 39.39%（差额方向与叠加的瘦身/去重/预览上限一致）。
- 成成语料：28000 池中文 5/5 全量送达（修复前 0/5）。

**③ 收益边界（诚实声明）**：A/B 的 after 消息是修复后管道生成、评分仍为 SQuAD 词面口径；生成侧 ~63% 的 gold 天花板（R-09）不受本轮影响——交付层从最大损失点移除后，**下一个最大损失点就是生成侧**。剩余交付层空间见 G-02。

## 四、"改机制而非给阈值"专项判定（用户重点）

| 截断/损失点 | 修复方式 | 判定 |
| --- | --- | --- |

| citation_qa 末条证据句中硬切（R-16） | 整取整弃（whole-record admission），docstring 明确"永不句中切割" | **机制修复 ✅** |
| 固定窗口重叠重复占预算（R-02） | 坐标重叠去重（同文档版本、保留最高排名、无坐标者放行不误伤 PDF 页定位），四处接入，trace 加 `after_overlap_dedup` | **机制修复 ✅** |
| 多轮旧证据饿死新检索（R-06） | RAG 池与 TOOL_RESULT 池同样新者优先 | **机制修复 ✅** |
| O(n²) 重复序列化（R-17） | 增量字节记账（列表=2+Σ(条+分隔符)） | **机制修复 ✅** |
| reranker 隐式截断（R-14） | 显式 `max_length=8192` 常量+构造校验+可注入 | 阈值显式化——原问题就是"未显式固定"，**与问题形态匹配 ✅**（本质无"机制"可选） |
| **预览 1000 字符硬截断（R-03）** | 双层：①模型视图层机制化（投影整取整弃，上限不再造成"半个记录进窗口"）；②上限本身 1000→2000 常量+注释约束"须≥块长" | **部分机制化 ⚠️**：模型可见性层面已是机制修复；但 **2000 与 `knowledge_chunk_size_chars` 无运行时联动校验**——若部署把块长配到 >2000，工具返回/注册表/citation 摘录将重新出现静默尾部截断（见 G-01） |
| 双层预算钳制（R-05） | WARNING 日志（含两侧数值）后仍钳制 | 告警而非拦截——中间态，合理但非机制闭环（发布校验层未加） |
| 引用越界整单 502（R-19） | 仅越界类失败触发一次纠错重试，之后仍 fail-closed；schema 类失败不重试 | **机制性折中 ✅**（判定语义未变，只给一次自纠机会） |

结论：**七处真正的"强行截断/挤压"类缺陷全部以机制方式修复**；唯一保留阈值式缓解的是 R-03 的上限常量本身，且其危害面已被模型视图层的机制修复大幅压缩。

## 五、发现的问题与遗留（按重要性）

- **G-01【P1，遗留缺口】预览上限与块长无联动校验**：`MAX_EVIDENCE_EXCERPT_CHARS=2000` 与 `settings.knowledge_chunk_size_chars`（默认 1200，可配至 100_000）之间没有启动/发布时校验。注释写明约束但机器不执行——块长配 3000 时静默尾部截断在记录层回归（模型视图仍是"整条"，但那条记录本身缺尾部且无标记）。建议：settings 校验器加一条 `MAX_EVIDENCE_EXCERPT_CHARS >= knowledge_chunk_size_chars`（或直接 `max(2000, chunk_size)` 派生），一行修复，堵死回归路径。
- **G-02【P1，剩余空间知会】中文默认路径仍只送 1/5 条完整记录**：默认 rag_records_v1 投影每条仍携带 chunk_id 64hex、document_id/revision UUID 与 253B 引用对（R-04 只删了 source+scores ≈180B）。我复算：中文 5000 池送达 1 条（4330B）。实施报告"三档收敛为一档"**指召回率收敛**（0.783≈0.790），字节效率档差仍在——compact_v1 短 ID/私有注册表形态仍是 opt-in，是下一个明确的交付层收益点（配合池大小产品决策）。表述需精确：召回已收敛，**每字节信息效率未收敛**。
- **G-03【P2】R-24 双重投影确认未修**：`retrieval.py:655` 内部 `assemble_evidence_plan` 仍在运行（本次只在其前加了去重）；实施报告已如实标注"收敛属行为变更需独立重放验证"。保持开放。
- **G-04【P2】R-25 失败标记的 status 仍是 SUCCESS**：`{"status":"SUCCESS","truncated":true,"evidence_projection":"FAILED"}` ——可区分性达成，但语义上自相矛盾；后续可考虑独立状态值。
- **G-05【P2】R-06 新者优先的对侧代价**：两轮都超预算时旧轮变 18B marker（我复算确认）。方向正确（模型正行动的是新一轮），但意味着第一轮证据可能整轮不可见——多轮策略（R-08）设计时需把"按轮配额"作为备选。
- **G-06【P3，笔误】实施报告方法节写"100 题 A/B"、遗留节写"100 题为 development 子样本"**，但工件与结果表均为 200 题全量（README 索引也写 200）。以 200 为准；不影响结论，建议提交前更正。
- **G-07【流程】集成测试仍未跑**（本机无 PostgreSQL）。涉及集成面的改动（retrieval metadata 新键、citation_qa 整取语义、search_knowledge 防御）已同步单测，但合入前应按实施报告建议在有库环境跑一次 `pytest -m integration`。
