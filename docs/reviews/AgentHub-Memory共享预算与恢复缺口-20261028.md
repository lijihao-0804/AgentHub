# Memory M4：共享预算与恢复缺口

日期：2026-10-28。本文是对当前代码的静态复核和后续设计边界，不是全链路预算或生产摘要验收。

## 已确认的实现事实

1. 摘要 job 保存的单次预估价格、dispatch 记录和 `budget_reserved` 标志，并没有直接扣留主 Run 或 Workspace 的共享余额。现在 `SummaryBudgetReserver` 默认拒绝，无真实预算实现就不能派发。测试中的允许实现只是测试桩。
2. 主 Run 的 `_cost_guard_failure` 在下一次模型轮开始前检查已记录费用；最终轮返回结果后不再次经过这一检查。因此最后一轮费用超限或费用不可测时，现有守卫本身不能证明该 Run 没有超过上限。价格是估算或响应报告，不能把它称作供应商账单。
3. 网关可以在主模型调用内重试或切换 fallback，而 Run 的 usage 聚合主要记录最终响应；失败尝试是否产生供应商费用可能未知。并行辅助模型调用也没有一个和主模型共同扣留余额的持久账户。
4. 摘要未知结果目前只持久化到摘要 job 和 dispatch，尚未与触发 Run 的状态、共享预留对账及生产恢复任务连通。后续需结合异步摘要的生命周期设计 `NEEDS_ATTENTION` 传播，不能擅自把已经终结的 Run 改成另一状态。
5. 已对同一 Workspace、Run 和模型轮次建立摘要 job 唯一约束；缺少轮次的历史 job 会阻止该 Run 创建新摘要。轮次仍由调用方提供，尚未从真实 checkpoint 可信绑定、恢复和调度。执行单要求每个派发边界至多一个 job，并不等于整个 Run 永远只能有一个摘要 job。

第 2、3 项涉及既有主运行时；它们不因新增摘要代码自动得到解决。当前没有把研究账本与业务预算混为一体，也没有改变已有 Agent 默认或业务数据库。

## 统一设计方向

- 为一个 Run 冻结明确的预算币种、额度及价格来源；构建覆盖主模型、fallback、摘要和辅助模型的同一持久账户。若可用价格、币种或换算依据不足，不能用估算冒充可证明的硬限。其他币种只有在显式提供并冻结可核对的换算依据时才可纳入，不自动假设汇率。
- 每个供应商 attempt 在实际调用之前，在同一事务内按稳定身份登记并预留最坏费用；并发调用锁定同一账户。失败、超时、取消和未确认结果保留可能已发生的费用，不能按零结算，也不能自动释放。普通主模型的重试/fallback 语义和用户配置需保留，但每一次 attempt 都必须受账户约束。
- 摘要 job 绑定真实、持久的派发边界身份，数据库按 Workspace、Run、边界及用途约束唯一性；重复队列投递、多个不同内容身份或多 worker 均不能产生第二次调用。同一个 Run 在不同边界的独立任务不应被错误合并。
- 供应商返回后的 usage、估算费用、供应商报告费用、预留和最终对账金额分别保存；只有有可信凭据时才改变相应账户状态。应对已知响应先持久化再验证，并按原状态恢复，不重新选择来源或重发。
- 数据库和远端供应商之间没有分布式原子事务。即使引入 dispatch permit，在“本地记录已提交”和“远端确已接收”之间仍有不可消除的崩溃窗口；无法证明未发送时必须保留 `UNKNOWN_OUTCOME`，除非供应商提供可核验的幂等或查询契约。不要把本地 permit 宣称为 exactly-once。
- 按固定顺序获取 Run/账户、摘要 job、dispatch 与预留锁，处理超时、延迟响应、权限撤销和恢复；在与真实生命周期兼容的前提下，让需人工对账的未确认结果可追踪地影响 Run 状态。

## 验收范围

在命名的隔离 PostgreSQL 和受控假供应商中验证主模型与摘要并发、并行辅助调用、fallback、重复投递及跨进程崩溃。分别注入预留提交前、提交后但网络边界不明、供应商已进入但响应未保存、响应已保存未结算、结算后恢复等窗口；核对真实 adapter 调用次数、账户余额、未知费用保留、权限和 Run 状态。计价缺失、币种不一致、实际费用超过预留时必须有明确结果。没有真实供应商账单查询时，只报告预留与响应估算，不宣称实际账单已结算。

生产接入还依赖可信来源验证、受保护事实审阅、固定 revision 恢复、真实 worker/调度和质量门槛。必须先完成这些依赖及质量评测，不能仅凭局部数据库测试解除当前发布门槛。

## 开源实现对照（2026-10-28）

[LangMem 的短期摘要实现](https://github.com/langchain-ai/langmem/blob/main/src/langmem/short_term/summarization.py)记录已经摘要的消息 ID 和最后一条消息，并在摘要边界补齐相应工具结果；其默认 token 计数是近似的，`max_summary_tokens` 本身也不等于供应商输出限制。AgentHub 已有冻结来源和完整交换的思路；这里应借鉴的是明确来源水位与消息组边界，而不是把近似计数器当成模型窗口上界，或把模型写出的摘要当成权威动作记录。

[LiteLLM 的预算预留实现](https://github.com/BerriAI/litellm/blob/main/litellm/proxy/spend_tracking/budget_reservation.py)在供应商请求之前估算上限并占用额度，随后进行对账；其代码对不能估算的请求存在不建立预留、退回已记录费用检查的路径。AgentHub 的严格模式不能直接沿用该退路：价格、币种、完整输入或 attempt 身份不可确认时应停止新增有预算调用；同时每个 fallback 和辅助调用都必须进入同一账户。项目对预算落地和异常恢复的独立验证仍是必要条件，上述源码不是 AgentHub 验收证据。

落地时，预留入口应位于实际网关的每一次供应商 attempt 之前：`_generate_chain` 和 `_stream` 各自含有重试及 fallback；仅在 Run 的模型轮次外层预留一次，会漏掉失败的尝试。流式输出可能在最终 usage 返回前已经对用户可见，事后检查不能撤销已发出的 token；执行状态与账务对账仍要分别处理。当前辅助调用的 task-local 记录能阻止一部分不可计价请求，但它不是跨进程持久预算账户，也不替代网关级预留。

## Run 账本原语（未接入生产）

新增的数据库原语按 Workspace 和 Run 固定一个币种、额度，预留时锁定账户并拒绝并发超额；同一 attempt 重复创建只返回已有记录，绝不是重新调用供应商的许可。未知或超时结果保留预留。新预留要求上游声明保守最大值，但该类型本身不能证明价格、请求输入及供应商费用确实都有可验证上界。

账本将模型响应估算与最终供应商账单区分：目前仅接收可信调用方已核实并另行保存的账单引用作为最终结算，估算不能释放预留；账单引用字符串本身不证明账单真实性。实际账单超过额度时仍保存可表示范围内的实际金额，显示超额并阻止后续新增预留；金额超出数据库精度时不能假装已经入账，原始账单必须由将来的证据存储保留。该原语目前没有账单采集或验证实现，也没有处理供应商账单修正或汇率。

隔离 PostgreSQL 的 13 项定向测试覆盖并发预留、同身份冲突、跨事务缓存刷新、未知结果、估算拒绝释放、超额账单、跨币种、回滚和留存约束；另一隔离库升级到 0045 后，摘要迁移、服务、来源审阅与 worker 定向回归共 94 项通过。`alembic check` 未发现新增元数据差异。**当前摘要服务仍使用默认拒绝的预算接口，主模型、重试、fallback、辅助调用及流式网关都未连接此账本；不能由这些局部测试声称 Run 硬成本上限已接入或真实供应商账单已核验。**
