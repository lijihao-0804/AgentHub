0026	# Overview
0027	
0028	At a high level, every Spark application consists of a *driver program* that runs the user's `main` function and executes various *parallel operations* on a cluster. The main abstraction Spark provides is a *resilient distributed dataset* (RDD), which is a collection of elements partitioned across the nodes of the cluster that can be operated on in parallel. RDDs are created by starting with a file in the Hadoop file system (or any other Hadoop-supported file system), or an existing Scala collection in the driver program, and transforming it. Users may also ask Spark to *persist* an RDD in memory, allowing it to be reused efficiently across parallel operations. Finally, RDDs automatically recover from node failures.
0029	
0030	A second abstraction in Spark is *shared variables* that can be used in parallel operations. By default, when Spark runs a function in parallel as a set of tasks on different nodes, it ships a copy of each variable used in the function to each task. Sometimes, a variable needs to be shared across tasks, or between tasks and the driver program. Spark supports two types of shared variables: *broadcast variables*, which can be used to cache a value in memory on all nodes, and *accumulators*, which are variables that are only "added" to, such as counters and sums.
0031	
0032	This guide shows each of these features in each of Spark's supported languages. It is easiest to follow
0033	along with if you launch Spark's interactive shell -- either `bin/spark-shell` for the Scala shell or
0034	`bin/pyspark` for the Python one.

0285	# Resilient Distributed Datasets (RDDs)
0286	
0287	Spark revolves around the concept of a _resilient distributed dataset_ (RDD), which is a fault-tolerant collection of elements that can be operated on in parallel. There are two ways to create RDDs: *parallelizing*
0288	an existing collection in your driver program, or referencing a dataset in an external storage system, such as a
0289	shared filesystem, HDFS, HBase, or any data source offering a Hadoop InputFormat.
0290	
0291	## Parallelized Collections
0292	
0293	<div class="codetabs">
0294	
0295	<div data-lang="python"  markdown="1">
0296	
0297	Parallelized collections are created by calling `SparkContext`'s `parallelize` method on an existing iterable or collection in your driver program. The elements of the collection are copied to form a distributed dataset that can be operated on in parallel. For example, here is how to create a parallelized collection holding the numbers 1 to 5:
0298	
0299	{% highlight python %}
0300	data = [1, 2, 3, 4, 5]
0301	distData = sc.parallelize(data)
0302	{% endhighlight %}
0303	
0304	Once created, the distributed dataset (`distData`) can be operated on in parallel. For example, we can call `distData.reduce(lambda a, b: a + b)` to add up the elements of the list.
0305	We describe operations on distributed datasets later on.
0306	
0307	</div>
0308	
0309	<div data-lang="scala"  markdown="1">
0310	
0311	Parallelized collections are created by calling `SparkContext`'s `parallelize` method on an existing collection in your driver program (a Scala `Seq`). The elements of the collection are copied to form a distributed dataset that can be operated on in parallel. For example, here is how to create a parallelized collection holding the numbers 1 to 5:
0312	
0313	{% highlight scala %}

0337	
0338	One important parameter for parallel collections is the number of *partitions* to cut the dataset into. Spark will run one task for each partition of the cluster. Typically you want 2-4 partitions for each CPU in your cluster. Normally, Spark tries to set the number of partitions automatically based on your cluster. However, you can also set it manually by passing it as a second parameter to `parallelize` (e.g. `sc.parallelize(data, 10)`). Note: some places in the code use the term slices (a synonym for partitions) to maintain backward compatibility.

0340	## External Datasets
0341	
0342	<div class="codetabs">
0343	
0344	<div data-lang="python"  markdown="1">
0345	
0346	PySpark can create distributed datasets from any storage source supported by Hadoop, including your local file system, HDFS, Cassandra, HBase, [Amazon S3](http://wiki.apache.org/hadoop/AmazonS3), etc. Spark supports text files, [SequenceFiles](https://hadoop.apache.org/docs/stable/api/org/apache/hadoop/mapred/SequenceFileInputFormat.html), and any other Hadoop [InputFormat](http://hadoop.apache.org/docs/stable/api/org/apache/hadoop/mapred/InputFormat.html).
0347	
0348	Text file RDDs can be created using `SparkContext`'s `textFile` method. This method takes a URI for the file (either a local path on the machine, or a `hdfs://`, `s3a://`, etc URI) and reads it as a collection of lines. Here is an example invocation:
0349	
0350	{% highlight python %}
0351	>>> distFile = sc.textFile("data.txt")
0352	{% endhighlight %}
0353	
0354	Once created, `distFile` can be acted on by dataset operations. For example, we can add up the sizes of all the lines using the `map` and `reduce` operations as follows: `distFile.map(lambda s: len(s)).reduce(lambda a, b: a + b)`.
0355	
0356	Some notes on reading files with Spark:
0357	
0358	* If using a path on the local filesystem, the file must also be accessible at the same path on worker nodes. Either copy the file to all workers or use a network-mounted shared file system.
0359	
0360	* All of Spark's file-based input methods, including `textFile`, support running on directories, compressed files, and wildcards as well. For example, you can use `textFile("/my/directory")`, `textFile("/my/directory/*.txt")`, and `textFile("/my/directory/*.gz")`.
0361	
0362	* The `textFile` method also takes an optional second argument for controlling the number of partitions of the file. By default, Spark creates one partition for each block of the file (blocks being 128MB by default in HDFS), but you can also ask for a higher number of partitions by passing a larger value. Note that you cannot have fewer partitions than blocks.
0363	
0364	Apart from text files, Spark's Python API also supports several other data formats:
0365	
0366	* `SparkContext.wholeTextFiles` lets you read a directory containing multiple small text files, and returns each of them as (filename, content) pairs. This is in contrast with `textFile`, which would return one record per line in each file.
0367	
0368	* `RDD.saveAsPickleFile` and `SparkContext.pickleFile` support saving an RDD in a simple format consisting of pickled Python objects. Batching is used on pickle serialization, with default batch size 10.
0369	
0370	* SequenceFile and Hadoop Input/Output Formats
0371	
0372	**Note** this feature is currently marked ```Experimental``` and is intended for advanced users. It may be replaced in future with read/write support based on Spark SQL, in which case Spark SQL is the preferred approach.
0373	
0374	**Writable Support**
0375	
0376	PySpark SequenceFile support loads an RDD of key-value pairs within Java, converts Writables to base Java types, and pickles the
0377	resulting Java objects using [pickle](https://github.com/irmen/pickle/). When saving an RDD of key-value pairs to SequenceFile,
0378	PySpark does the reverse. It unpickles Python objects into Java objects and then converts them to Writables. The following
0379	Writables are automatically converted:
0380	
0381	<table>
0382	<thead><tr><th>Writable Type</th><th>Python Type</th></tr></thead>
0383	<tr><td>Text</td><td>str</td></tr>
0384	<tr><td>IntWritable</td><td>int</td></tr>
0385	<tr><td>FloatWritable</td><td>float</td></tr>
0386	<tr><td>DoubleWritable</td><td>float</td></tr>
0387	<tr><td>BooleanWritable</td><td>bool</td></tr>
0388	<tr><td>BytesWritable</td><td>bytearray</td></tr>
0389	<tr><td>NullWritable</td><td>None</td></tr>
0390	<tr><td>MapWritable</td><td>dict</td></tr>
0391	</table>
0392	
0393	Arrays are not handled out-of-the-box. Users need to specify custom `ArrayWritable` subtypes when reading or writing. When writing,
0394	users also need to specify custom converters that convert arrays to custom `ArrayWritable` subtypes. When reading, the default
0395	converter will convert custom `ArrayWritable` subtypes to Java `Object[]`, which then get pickled to Python tuples. To get
0396	Python `array.array` for arrays of primitive types, users need to specify custom converters.
0397	
0398	**Saving and Loading SequenceFiles**
0399	
0400	Similarly to text files, SequenceFiles can be saved and loaded by specifying the path. The key and value
0401	classes can be specified, but for standard Writables this is not required.
0402	
0403	{% highlight python %}
0404	>>> rdd = sc.parallelize(range(1, 4)).map(lambda x: (x, "a" * x))
0405	>>> rdd.saveAsSequenceFile("path/to/file")
0406	>>> sorted(sc.sequenceFile("path/to/file").collect())
0407	[(1, u'a'), (2, u'aa'), (3, u'aaa')]
0408	{% endhighlight %}
0409	
0410	**Saving and Loading Other Hadoop Input/Output Formats**
0411	
0412	PySpark can also read any Hadoop InputFormat or write any Hadoop OutputFormat, for both 'new' and 'old' Hadoop MapReduce APIs.
0413	If required, a Hadoop configuration can be passed in as a Python dict. Here is an example using the
0414	Elasticsearch ESInputFormat:
0415	
0416	{% highlight python %}
0417	$ ./bin/pyspark --jars /path/to/elasticsearch-hadoop.jar
0418	>>> conf = {"es.resource" : "index/type"}  # assume Elasticsearch is running on localhost defaults
0419	>>> rdd = sc.newAPIHadoopRDD("org.elasticsearch.hadoop.mr.EsInputFormat",
0420	                             "org.apache.hadoop.io.NullWritable",
0421	                             "org.elasticsearch.hadoop.mr.LinkedMapWritable",
0422	                             conf=conf)
0423	>>> rdd.first()  # the result is a MapWritable that is converted to a Python dict
0424	(u'Elasticsearch ID',
0425	 {u'field1': True,
0426	  u'field2': u'Some Text',
0427	  u'field3': 12345})
0428	{% endhighlight %}
0429	
0430	Note that, if the InputFormat simply depends on a Hadoop configuration and/or input path, and
0431	the key and value classes can easily be converted according to the above table,
0432	then this approach should work well for such cases.
0433	
0434	If you have custom serialized binary data (such as loading data from Cassandra / HBase), then you will first need to
0435	transform that data on the Scala/Java side to something which can be handled by pickle's pickler.
0436	A [Converter](api/scala/org/apache/spark/api/python/Converter.html) trait is provided
0437	for this. Simply extend this trait and implement your transformation code in the ```convert```
0438	method. Remember to ensure that this class, along with any dependencies required to access your ```InputFormat```, are packaged into your Spark job jar and included on the PySpark
0439	classpath.
0440	
0441	See the [Python examples]({{site.SPARK_GITHUB_URL}}/tree/master/examples/src/main/python) and
0442	the [Converter examples]({{site.SPARK_GITHUB_URL}}/tree/master/examples/src/main/scala/org/apache/spark/examples/pythonconverters)
0443	for examples of using Cassandra / HBase ```InputFormat``` and ```OutputFormat``` with custom converters.

0514	## RDD Operations
0515	
0516	RDDs support two types of operations: *transformations*, which create a new dataset from an existing one, and *actions*, which return a value to the driver program after running a computation on the dataset. For example, `map` is a transformation that passes each dataset element through a function and returns a new RDD representing the results. On the other hand, `reduce` is an action that aggregates all the elements of the RDD using some function and returns the final result to the driver program (although there is also a parallel `reduceByKey` that returns a distributed dataset).
0517	
0518	All transformations in Spark are <i>lazy</i>, in that they do not compute their results right away. Instead, they just remember the transformations applied to some base dataset (e.g. a file). The transformations are only computed when an action requires a result to be returned to the driver program. This design enables Spark to run more efficiently. For example, we can realize that a dataset created through `map` will be used in a `reduce` and return only the result of the `reduce` to the driver, rather than the larger mapped dataset.
0519	
0520	By default, each transformed RDD may be recomputed each time you run an action on it. However, you may also *persist* an RDD in memory using the `persist` (or `cache`) method, in which case Spark will keep the elements around on the cluster for much faster access the next time you query it. There is also support for persisting RDDs on disk, or replicated across multiple nodes.
0521

0614	<div class="codetabs">

0618	Spark's API relies heavily on passing functions in the driver program to run on the cluster.
0619	There are three recommended ways to do this:
0620	
0621	* [Lambda expressions](https://docs.python.org/2/tutorial/controlflow.html#lambda-expressions),
0622	  for simple functions that can be written as an expression. (Lambdas do not support multi-statement
0623	  functions or statements that do not return a value.)
0624	* Local `def`s inside the function calling into Spark, for longer code.
0625	* Top-level functions in a module.
0626	
0627	For example, to pass a longer function than can be supported using a `lambda`, consider
0628	the code below:
0629	
0630	{% highlight python %}
0631	"""MyScript.py"""
0632	if __name__ == "__main__":
0633	    def myFunc(s):
0634	        words = s.split(" ")
0635	        return len(words)
0636	
0637	    sc = SparkContext(...)
0638	    sc.textFile("file.txt").map(myFunc)

0641	Note that while it is also possible to pass a reference to a method in a class instance (as opposed to
0642	a singleton object), this requires sending the object that contains that class along with the method.
0643	For example, consider:
0644	
0645	{% highlight python %}
0646	class MyClass(object):
0647	    def func(self, s):
0648	        return s
0649	    def doStuff(self, rdd):
0650	        return rdd.map(self.func)
0651	{% endhighlight %}

0654	`func` method *of that `MyClass` instance*, so the whole object needs to be sent to the cluster.
0655	
0656	In a similar way, accessing fields of the outer object will reference the whole object:
0657	
0658	{% highlight python %}
0659	class MyClass(object):
0660	    def __init__(self):
0661	        self.field = "Hello"
0662	    def doStuff(self, rdd):
0663	        return rdd.map(lambda s: self.field + s)
0664	{% endhighlight %}

0667	of accessing it externally:
0668	
0669	{% highlight python %}
0670	def doStuff(self, rdd):
0671	    field = self.field
0672	    return rdd.map(lambda s: field + s)
0673	{% endhighlight %}

0779	### Understanding closures <a name="ClosuresLink"></a>
0780	One of the harder things about Spark is understanding the scope and life cycle of variables and methods when executing code across a cluster. RDD operations that modify variables outside of their scope can be a frequent source of confusion. In the example below we'll look at code that uses `foreach()` to increment a counter, but similar issues can occur for other operations as well.
0781	
0782	#### Example
0783	
0784	Consider the naive RDD element sum below, which may behave differently depending on whether execution is happening within the same JVM. A common example of this is when running Spark in `local` mode (`--master = local[n]`) versus deploying a Spark application to a cluster (e.g. via spark-submit to YARN):
0785	
0786	<div class="codetabs">
0787	
0788	<div data-lang="python"  markdown="1">
0789	{% highlight python %}
0790	counter = 0
0791	rdd = sc.parallelize(data)
0792	
0793	# Wrong: Don't do this!!
0794	def increment_counter(x):
0795	    global counter
0796	    counter += x
0797	rdd.foreach(increment_counter)
0798	
0799	print("Counter value: ", counter)
0800	{% endhighlight %}
0801	</div>
0802	
0803	<div data-lang="scala"  markdown="1">
0804	{% highlight scala %}
0805	var counter = 0
0806	var rdd = sc.parallelize(data)
0807	
0808	// Wrong: Don't do this!!
0809	rdd.foreach(x => counter += x)
0810	
0811	println("Counter value: " + counter)
0812	{% endhighlight %}
0813	</div>
0814	
0815	<div data-lang="java"  markdown="1">
0816	{% highlight java %}
0817	int counter = 0;
0818	JavaRDD<Integer> rdd = sc.parallelize(data);
0819	
0820	// Wrong: Don't do this!!
0821	rdd.foreach(x -> counter += x);
0822	
0823	println("Counter value: " + counter);
0824	{% endhighlight %}
0825	</div>
0826	
0827	</div>
0828	
0829	#### Local vs. cluster modes
0830	
0831	The behavior of the above code is undefined, and may not work as intended. To execute jobs, Spark breaks up the processing of RDD operations into tasks, each of which is executed by an executor. Prior to execution, Spark computes the task's **closure**. The closure is those variables and methods which must be visible for the executor to perform its computations on the RDD (in this case `foreach()`). This closure is serialized and sent to each executor.
0832	
0833	The variables within the closure sent to each executor are now copies and thus, when **counter** is referenced within the `foreach` function, it's no longer the **counter** on the driver node. There is still a **counter** in the memory of the driver node but this is no longer visible to the executors! The executors only see the copy from the serialized closure. Thus, the final value of **counter** will still be zero since all operations on **counter** were referencing the value within the serialized closure.
0834	
0835	In local mode, in some circumstances, the `foreach` function will actually execute within the same JVM as the driver and will reference the same original **counter**, and may actually update it.
0836	
0837	To ensure well-defined behavior in these sorts of scenarios one should use an [`Accumulator`](#accumulators). Accumulators in Spark are used specifically to provide a mechanism for safely updating a variable when execution is split up across worker nodes in a cluster. The Accumulators section of this guide discusses these in more detail.
0838	
0839	In general, closures - constructs like loops or locally defined methods, should not be used to mutate some global state. Spark does not define or guarantee the behavior of mutations to objects referenced from outside of closures. Some code that does this may work in local mode, but that's just by accident and such code will not behave as expected in distributed mode. Use an Accumulator instead if some global aggregation is needed.
0840	
0841	#### Printing elements of an RDD
0842	Another common idiom is attempting to print out the elements of an RDD using `rdd.foreach(println)` or `rdd.map(println)`. On a single machine, this will generate the expected output and print all the RDD's elements. However, in `cluster` mode, the output to `stdout` being called by the executors is now writing to the executor's `stdout` instead, not the one on the driver, so `stdout` on the driver won't show these! To print all elements on the driver, one can use the `collect()` method to first bring the RDD to the driver node thus: `rdd.collect().foreach(println)`. This can cause the driver to run out of memory, though, because `collect()` fetches the entire RDD to a single machine; if you only need to print a few elements of the RDD, a safer approach is to use the `take()`: `rdd.take(100).foreach(println)`.

0895	`counts.collect()` to bring them back to the driver program as an array of objects.

0898	custom `equals()` method is accompanied with a matching `hashCode()` method.  For full details, see
0899	the contract outlined in the [Object.hashCode()

1130	### Shuffle operations
1131	
1132	Certain operations within Spark trigger an event known as the shuffle. The shuffle is Spark's
1133	mechanism for re-distributing data so that it's grouped differently across partitions. This typically
1134	involves copying data across executors and machines, making the shuffle a complex and
1135	costly operation.
1136	
1137	#### Background
1138	
1139	To understand what happens during the shuffle, we can consider the example of the
1140	[`reduceByKey`](#ReduceByLink) operation. The `reduceByKey` operation generates a new RDD where all
1141	values for a single key are combined into a tuple - the key and the result of executing a reduce
1142	function against all values associated with that key. The challenge is that not all values for a
1143	single key necessarily reside on the same partition, or even the same machine, but they must be
1144	co-located to compute the result.
1145	
1146	In Spark, data is generally not distributed across partitions to be in the necessary place for a
1147	specific operation. During computations, a single task will operate on a single partition - thus, to
1148	organize all the data for a single `reduceByKey` reduce task to execute, Spark needs to perform an
1149	all-to-all operation. It must read from all partitions to find all the values for all keys,
1150	and then bring together values across partitions to compute the final result for each key -
1151	this is called the **shuffle**.
1152	
1153	Although the set of elements in each partition of newly shuffled data will be deterministic, and so
1154	is the ordering of partitions themselves, the ordering of these elements is not. If one desires predictably
1155	ordered data following shuffle then it's possible to use:
1156	
1157	* `mapPartitions` to sort each partition using, for example, `.sorted`
1158	* `repartitionAndSortWithinPartitions` to efficiently sort partitions while simultaneously repartitioning
1159	* `sortBy` to make a globally ordered RDD
1160	
1161	Operations which can cause a shuffle include **repartition** operations like
1162	[`repartition`](#RepartitionLink) and [`coalesce`](#CoalesceLink), **'ByKey** operations
1163	(except for counting) like [`groupByKey`](#GroupByLink) and [`reduceByKey`](#ReduceByLink), and
1164	**join** operations like [`cogroup`](#CogroupLink) and [`join`](#JoinLink).
1165	
1166	#### Performance Impact
1167	The **Shuffle** is an expensive operation since it involves disk I/O, data serialization, and
1168	network I/O. To organize data for the shuffle, Spark generates sets of tasks - *map* tasks to
1169	organize the data, and a set of *reduce* tasks to aggregate it. This nomenclature comes from
1170	MapReduce and does not directly relate to Spark's `map` and `reduce` operations.
1171	
1172	Internally, results from individual map tasks are kept in memory until they can't fit. Then, these
1173	are sorted based on the target partition and written to a single file. On the reduce side, tasks
1174	read the relevant sorted blocks.
1175	
1176	Certain shuffle operations can consume significant amounts of heap memory since they employ
1177	in-memory data structures to organize records before or after transferring them. Specifically,
1178	`reduceByKey` and `aggregateByKey` create these structures on the map side, and `'ByKey` operations
1179	generate these on the reduce side. When data does not fit in memory Spark will spill these tables
1180	to disk, incurring the additional overhead of disk I/O and increased garbage collection.
1181	
1182	Shuffle also generates a large number of intermediate files on disk. As of Spark 1.3, these files
1183	are preserved until the corresponding RDDs are no longer used and are garbage collected.
1184	This is done so the shuffle files don't need to be re-created if the lineage is re-computed.
1185	Garbage collection may happen only after a long period of time, if the application retains references
1186	to these RDDs or if GC does not kick in frequently. This means that long-running Spark jobs may
1187	consume a large amount of disk space. The temporary storage directory is specified by the
1188	`spark.local.dir` configuration parameter when configuring the Spark context.
1189	
1190	Shuffle behavior can be tuned by adjusting a variety of configuration parameters. See the
1191	'Shuffle Behavior' section within the [Spark Configuration Guide](configuration.html).
1192	
1193	## RDD Persistence
1194	
1195	One of the most important capabilities in Spark is *persisting* (or *caching*) a dataset in memory
1196	across operations. When you persist an RDD, each node stores any partitions of it that it computes in
1197	memory and reuses them in other actions on that dataset (or datasets derived from it). This allows
1198	future actions to be much faster (often by more than 10x). Caching is a key tool for
1199	iterative algorithms and fast interactive use.
1200	
1201	You can mark an RDD to be persisted using the `persist()` or `cache()` methods on it. The first time
1202	it is computed in an action, it will be kept in memory on the nodes. Spark's cache is fault-tolerant --
1203	if any partition of an RDD is lost, it will automatically be recomputed using the transformations
1204	that originally created it.
1205	
1206	In addition, each persisted RDD can be stored using a different *storage level*, allowing you, for example,
1207	to persist the dataset on disk, persist it in memory but as serialized Java objects (to save space),
1208	replicate it across nodes.
1209	These levels are set by passing a
1210	`StorageLevel` object ([Scala](api/scala/org/apache/spark/storage/StorageLevel.html),
1211	[Java](api/java/index.html?org/apache/spark/storage/StorageLevel.html),
1212	[Python](api/python/reference/api/pyspark.StorageLevel.html#pyspark.StorageLevel))
1213	to `persist()`. The `cache()` method is a shorthand for using the default storage level,
1214	which is `StorageLevel.MEMORY_ONLY` (store deserialized objects in memory). The full set of
1215	storage levels is:
1216	
1217	<table>
1218	<thead><tr><th style="width:23%">Storage Level</th><th>Meaning</th></tr></thead>
1219	<tr>
1220	  <td> MEMORY_ONLY </td>
1221	  <td> Store RDD as deserialized Java objects in the JVM. If the RDD does not fit in memory, some partitions will
1222	    not be cached and will be recomputed on the fly each time they're needed. This is the default level. </td>
1223	</tr>
1224	<tr>
1225	  <td> MEMORY_AND_DISK </td>
1226	  <td> Store RDD as deserialized Java objects in the JVM. If the RDD does not fit in memory, store the
1227	    partitions that don't fit on disk, and read them from there when they're needed. </td>
1228	</tr>
1229	<tr>
1230	  <td> MEMORY_ONLY_SER <br /> (Java and Scala) </td>
1231	  <td> Store RDD as <i>serialized</i> Java objects (one byte array per partition).
1232	    This is generally more space-efficient than deserialized objects, especially when using a
1233	    <a href="tuning.html">fast serializer</a>, but more CPU-intensive to read.
1234	  </td>
1235	</tr>
1236	<tr>
1237	  <td> MEMORY_AND_DISK_SER <br /> (Java and Scala) </td>
1238	  <td> Similar to MEMORY_ONLY_SER, but spill partitions that don't fit in memory to disk instead of
1239	    recomputing them on the fly each time they're needed. </td>
1240	</tr>
1241	<tr>
1242	  <td> DISK_ONLY </td>
1243	  <td> Store the RDD partitions only on disk. </td>
1244	</tr>
1245	<tr>
1246	  <td> MEMORY_ONLY_2, MEMORY_AND_DISK_2, etc.  </td>
1247	  <td> Same as the levels above, but replicate each partition on two cluster nodes. </td>
1248	</tr>
1249	<tr>
1250	  <td> OFF_HEAP (experimental) </td>
1251	  <td> Similar to MEMORY_ONLY_SER, but store the data in
1252	    <a href="configuration.html#memory-management">off-heap memory</a>. This requires off-heap memory to be enabled. </td>
1253	</tr>
1254	</table>
1255	
1256	**Note:** *In Python, stored objects will always be serialized with the [Pickle](https://docs.python.org/3/library/pickle.html) library,
1257	so it does not matter whether you choose a serialized level. The available storage levels in Python include `MEMORY_ONLY`, `MEMORY_ONLY_2`,
1258	`MEMORY_AND_DISK`, `MEMORY_AND_DISK_2`, `DISK_ONLY`, `DISK_ONLY_2`, and `DISK_ONLY_3`.*
1259	
1260	Spark also automatically persists some intermediate data in shuffle operations (e.g. `reduceByKey`), even without users calling `persist`. This is done to avoid recomputing the entire input if a node fails during the shuffle. We still recommend users call `persist` on the resulting RDD if they plan to reuse it.
1261	
1262	### Which Storage Level to Choose?
1263	
1264	Spark's storage levels are meant to provide different trade-offs between memory usage and CPU
1265	efficiency. We recommend going through the following process to select one:
1266	
1267	* If your RDDs fit comfortably with the default storage level (`MEMORY_ONLY`), leave them that way.
1268	  This is the most CPU-efficient option, allowing operations on the RDDs to run as fast as possible.
1269	
1270	* If not, try using `MEMORY_ONLY_SER` and [selecting a fast serialization library](tuning.html) to
1271	make the objects much more space-efficient, but still reasonably fast to access. (Java and Scala)
1272	
1273	* Don't spill to disk unless the functions that computed your datasets are expensive, or they filter
1274	a large amount of the data. Otherwise, recomputing a partition may be as fast as reading it from
1275	disk.
1276	
1277	* Use the replicated storage levels if you want fast fault recovery (e.g. if using Spark to serve
1278	requests from a web application). *All* the storage levels provide full fault tolerance by
1279	recomputing lost data, but the replicated ones let you continue running tasks on the RDD without
1280	waiting to recompute a lost partition.
1281	
1282	
1283	### Removing Data
1284	
1285	Spark automatically monitors cache usage on each node and drops out old data partitions in a
1286	least-recently-used (LRU) fashion. If you would like to manually remove an RDD instead of waiting for
1287	it to fall out of the cache, use the `RDD.unpersist()` method. Note that this method does not
1288	block by default. To block until resources are freed, specify `blocking=true` when calling this method.
1289	
1290	# Shared Variables
1291	
1292	Normally, when a function passed to a Spark operation (such as `map` or `reduce`) is executed on a
1293	remote cluster node, it works on separate copies of all the variables used in the function. These
1294	variables are copied to each machine, and no updates to the variables on the remote machine are
1295	propagated back to the driver program. Supporting general, read-write shared variables across tasks
1296	would be inefficient. However, Spark does provide two limited types of *shared variables* for two
1297	common usage patterns: broadcast variables and accumulators.
1298	
1299	## Broadcast Variables
1300	
1301	Broadcast variables allow the programmer to keep a read-only variable cached on each machine rather
1302	than shipping a copy of it with tasks. They can be used, for example, to give every node a copy of a
1303	large input dataset in an efficient manner. Spark also attempts to distribute broadcast variables
1304	using efficient broadcast algorithms to reduce communication cost.
1305	
1306	Spark actions are executed through a set of stages, separated by distributed "shuffle" operations.
1307	Spark automatically broadcasts the common data needed by tasks within each stage. The data
1308	broadcasted this way is cached in serialized form and deserialized before running each task. This
1309	means that explicitly creating broadcast variables is only useful when tasks across multiple stages
1310	need the same data or when caching the data in deserialized form is important.
1311	
1312	Broadcast variables are created from a variable `v` by calling `SparkContext.broadcast(v)`. The
1313	broadcast variable is a wrapper around `v`, and its value can be accessed by calling the `value`
1314	method. The code below shows this:
1315	
1316	<div class="codetabs">
1317	
1318	<div data-lang="python"  markdown="1">
1319	
1320	{% highlight python %}
1321	>>> broadcastVar = sc.broadcast([1, 2, 3])
1322	<pyspark.broadcast.Broadcast object at 0x102789f10>
1323	
1324	>>> broadcastVar.value
1325	[1, 2, 3]
1326	{% endhighlight %}
1327	
1328	</div>
1329	
1330	<div data-lang="scala"  markdown="1">
1331	
1332	{% highlight scala %}
1333	scala> val broadcastVar = sc.broadcast(Array(1, 2, 3))
1334	broadcastVar: org.apache.spark.broadcast.Broadcast[Array[Int]] = Broadcast(0)
1335	
1336	scala> broadcastVar.value
1337	res0: Array[Int] = Array(1, 2, 3)
1338	{% endhighlight %}
1339	
1340	</div>
1341	
1342	<div data-lang="java"  markdown="1">
1343	
1344	{% highlight java %}
1345	Broadcast<int[]> broadcastVar = sc.broadcast(new int[] {1, 2, 3});
1346	
1347	broadcastVar.value();
1348	// returns [1, 2, 3]
1349	{% endhighlight %}
1350	
1351	</div>
1352	
1353	</div>
1354	
1355	After the broadcast variable is created, it should be used instead of the value `v` in any functions
1356	run on the cluster so that `v` is not shipped to the nodes more than once. In addition, the object
1357	`v` should not be modified after it is broadcast in order to ensure that all nodes get the same
1358	value of the broadcast variable (e.g. if the variable is shipped to a new node later).
1359	
1360	To release the resources that the broadcast variable copied onto executors, call `.unpersist()`.
1361	If the broadcast is used again afterwards, it will be re-broadcast. To permanently release all
1362	resources used by the broadcast variable, call `.destroy()`. The broadcast variable can't be used
1363	after that. Note that these methods do not block by default. To block until resources are freed,
1364	specify `blocking=true` when calling them.
1365	
1366	## Accumulators
1367	
1368	Accumulators are variables that are only "added" to through an associative and commutative operation and can
1369	therefore be efficiently supported in parallel. They can be used to implement counters (as in
1370	MapReduce) or sums. Spark natively supports accumulators of numeric types, and programmers
1371	can add support for new types.
1372	
1373	As a user, you can create named or unnamed accumulators. As seen in the image below, a named accumulator (in this instance `counter`) will display in the web UI for the stage that modifies that accumulator. Spark displays the value for each accumulator modified by a task in the "Tasks" table.
1374	
1375	<p style="text-align: center;">
1376	  <img src="img/spark-webui-accumulators.png" title="Accumulators in the Spark UI" alt="Accumulators in the Spark UI" />
1377	</p>
1378	
1379	Tracking accumulators in the UI can be useful for understanding the progress of
1380	running stages (NOTE: this is not yet supported in Python).
1381	
1382	<div class="codetabs">
1383	
1384	<div data-lang="python"  markdown="1">
1385	
1386	An accumulator is created from an initial value `v` by calling `SparkContext.accumulator(v)`. Tasks
1387	running on a cluster can then add to it using the `add` method or the `+=` operator. However, they cannot read its value.
1388	Only the driver program can read the accumulator's value, using its `value` method.
1389	
1390	The code below shows an accumulator being used to add up the elements of an array:
1391	
1392	{% highlight python %}
1393	>>> accum = sc.accumulator(0)
1394	>>> accum
1395	Accumulator<id=0, value=0>
1396	
1397	>>> sc.parallelize([1, 2, 3, 4]).foreach(lambda x: accum.add(x))
1398	...
1399	10/09/29 18:41:08 INFO SparkContext: Tasks finished in 0.317106 s
1400	
1401	>>> accum.value
1402	10
1403	{% endhighlight %}
1404	
1405	While this code used the built-in support for accumulators of type Int, programmers can also
1406	create their own types by subclassing [AccumulatorParam](api/python/reference/api/pyspark.AccumulatorParam.html#pyspark.AccumulatorParam).
1407	The AccumulatorParam interface has two methods: `zero` for providing a "zero value" for your data
1408	type, and `addInPlace` for adding two values together. For example, supposing we had a `Vector` class
1409	representing mathematical vectors, we could write:
1410	
1411	{% highlight python %}
1412	class VectorAccumulatorParam(AccumulatorParam):
1413	    def zero(self, initialValue):
1414	        return Vector.zeros(initialValue.size)
1415	
1416	    def addInPlace(self, v1, v2):
1417	        v1 += v2
1418	        return v1
1419	
1420	# Then, create an Accumulator of this type:
1421	vecAccum = sc.accumulator(Vector(...), VectorAccumulatorParam())
1422	{% endhighlight %}
1423	
1424	</div>
1425	
1426	<div data-lang="scala"  markdown="1">
1427	
1428	A numeric accumulator can be created by calling `SparkContext.longAccumulator()` or `SparkContext.doubleAccumulator()`
1429	to accumulate values of type Long or Double, respectively. Tasks running on a cluster can then add to it using
1430	the `add` method.  However, they cannot read its value. Only the driver program can read the accumulator's value,
1431	using its `value` method.
1432	
1433	The code below shows an accumulator being used to add up the elements of an array:
1434	
1435	{% highlight scala %}
1436	scala> val accum = sc.longAccumulator("My Accumulator")
1437	accum: org.apache.spark.util.LongAccumulator = LongAccumulator(id: 0, name: Some(My Accumulator), value: 0)
1438	
1439	scala> sc.parallelize(Array(1, 2, 3, 4)).foreach(x => accum.add(x))
1440	...
1441	10/09/29 18:41:08 INFO SparkContext: Tasks finished in 0.317106 s
1442	
1443	scala> accum.value
1444	res2: Long = 10
1445	{% endhighlight %}
1446	
1447	While this code used the built-in support for accumulators of type Long, programmers can also
1448	create their own types by subclassing [AccumulatorV2](api/scala/org/apache/spark/util/AccumulatorV2.html).
1449	The AccumulatorV2 abstract class has several methods which one has to override: `reset` for resetting
1450	the accumulator to zero, `add` for adding another value into the accumulator,
1451	`merge` for merging another same-type accumulator into this one. Other methods that must be overridden
1452	are contained in the [API documentation](api/scala/org/apache/spark/util/AccumulatorV2.html). For example, supposing we had a `MyVector` class
1453	representing mathematical vectors, we could write:
1454	
1455	{% highlight scala %}
1456	class VectorAccumulatorV2 extends AccumulatorV2[MyVector, MyVector] {
1457	
1458	  private val myVector: MyVector = MyVector.createZeroVector
1459	
1460	  def reset(): Unit = {
1461	    myVector.reset()
1462	  }
1463	
1464	  def add(v: MyVector): Unit = {
1465	    myVector.add(v)
1466	  }
1467	  ...
1468	}
1469	
1470	// Then, create an Accumulator of this type:
1471	val myVectorAcc = new VectorAccumulatorV2
1472	// Then, register it into spark context:
1473	sc.register(myVectorAcc, "MyVectorAcc1")
1474	{% endhighlight %}
1475	
1476	Note that, when programmers define their own type of AccumulatorV2, the resulting type can be different than that of the elements added.
1477	
1478	</div>

1531	*Warning*: When a Spark task finishes, Spark will try to merge the accumulated updates in this task to an accumulator.
1532	If it fails, Spark will ignore the failure and still mark the task successful and continue to run other tasks. Hence,
1533	a buggy accumulator will not impact a Spark job, but it may not get updated correctly although a Spark job is successful.

1539	For accumulator updates performed inside <b>actions only</b>, Spark guarantees that each task's update to the accumulator
1540	will only be applied once, i.e. restarted tasks will not update the value. In transformations, users should be aware
1541	of that each task's update may be applied more than once if tasks or job stages are re-executed.
1542	
1543	Accumulators do not change the lazy evaluation model of Spark. If they are being updated within an operation on an RDD, their value is only updated once that RDD is computed as part of an action. Consequently, accumulator updates are not guaranteed to be executed when made within a lazy transformation like `map()`. The below code fragment demonstrates this property:
1544	
1545	<div class="codetabs">
1546	
1547	<div data-lang="python"  markdown="1">
1548	{% highlight python %}

1550	def g(x):
1551	    accum.add(x)
1552	    return f(x)
1553	data.map(g)
1554	# Here, accum is still 0 because no actions have caused the `map` to be computed.
1555	{% endhighlight %}
1556	</div>

1587	# Unit Testing
1588	
1589	Spark is friendly to unit testing with any popular unit test framework.
1590	Simply create a `SparkContext` in your test with the master URL set to `local`, run your operations,
1591	and then call `SparkContext.stop()` to tear it down.
1592	Make sure you stop the context within a `finally` block or the test framework's `tearDown` method,
1593	as Spark does not support two contexts running concurrently in the same program.
