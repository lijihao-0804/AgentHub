### F00｜观测契约与指标基础（P0）

**现状：** 公式较完整，但真实 driver 的观测不足；检索分支只保存最终 `chunk_ids`，不能据此声称采集了完整候选层。synthetic driver 只能验证流程。

**主要文件：** [knowledge/contracts.py](../../packages/knowledge/contracts.py)、[retrieval.py](../../packages/knowledge/retrieval.py)、[evaluation/runner.py](../../packages/evaluation/runner.py)、[metrics.py](../../packages/evaluation/metrics.py)、[metrics_service.py](../../packages/evaluation/metrics_service.py)、[reproducibility.py](../../packages/evaluation/reproducibility.py)。新增观测契约模块及单测文件。

**步骤：**

1. 定义 `observation_schema_version`、driver 类型、字段来源、采集完成/缺失原因、业务验收结果与 evaluator 版本；声明哪些字段为敏感内容。
2. 从真实 RetrievalTrace 取候选融合排名和最终 evidence，分别保存 candidate/final IDs、实际 k、快照与策略身份；不从 expected 构造真实观测。
3. 新契约缺候选字段时，候选指标返回 NOT_AVAILABLE；历史 observation 按原 evaluator 版本解读，不悄悄重算旧报告。
4. 业务验收、安全结果和费用需提供真实来源；未采集不能填 false/0。冻结契约变更后的 evaluator manifest。
5. 报告统一导出 JSON 原始记录与 Markdown 汇总，显示真实/受控/synthetic 分组、分母、缺失和失败。

**测试：** 最终召回与候选召回不同；缺字段；不同 k；empty truth 与不适用；旧契约兼容；manifest 不匹配；跨工作区；真实与 synthetic 分组。

**i18n 建议：** `evaluation.observationSource`、`evaluation.observationMissing`、`evaluation.sampleCoverage`。

**验收：** 10 条受控样本可逐条还原观测来源；缺失不被算成通过；历史报告不改变；候选/最终指标明确区分。

### F01｜反馈、人工纠正与回归导入（P1）

**主要文件：** [共享会话](../../apps/web/components/apps/app-conversation-pane.tsx)、[运行转数据集面板](../../apps/web/components/evaluation/add-run-to-dataset-panel.tsx)、[evaluation/service.py](../../packages/evaluation/service.py)、[evaluation 路由](../../apps/api/routes/evaluation.py)、[threads/service.py](../../packages/threads/service.py)。建议新增 `packages/feedback/`、对应 API schema/route、前端 API client 与迁移。

**步骤：**

1. 新增 workspace+Run/Turn 关联反馈，存评分、分类、备注、创建者、版本/修订信息；纠正文本按业务内容权限处理，不写默认 trace。
2. 分类包括事实错误、检索遗漏、工具错误、时延、表达和其他；评分与纠正分开，点赞不自动等于事实正确。
3. 定义提交、审核、导入权限及审计；用户仅能反馈自己有权读取的输出，管理员不自动获得跨 workspace 内容。
4. 审核后的纠正通过现有 dataset 服务创建/追加草稿版本，人工发布；绑定反馈及 Run 来源。导入幂等键和事务避免重复生成。
5. 默认仅导入 DEV；HOLDOUT 需要独立治理流程。已发布版本不修改，差评原输出不能自动作为 expected。

**测试：** 越权读取/纠正；重复提交/导入；并发审核；Run 与 Turn 关联不匹配；已发布不可变；跨会话响应；HOLDOUT 拦截；纠正缺失时不能当参考答案。

**i18n 建议：** `feedback.rating`、`feedback.category`、`feedback.correction`、`feedback.review`、`feedback.importToDev`、`feedback.imported`。

**验收：** 演示一次失败→分类→纠正→审核→DEV 新版本→回归；每步可追溯，重复导入不产生重复条目。

**主要文件：** [运行事件](../../packages/agent_runtime/events.py)、[事件存储](../../packages/agent_runtime/event_store.py)、[工具 runtime](../../packages/tools/runtime.py)、[runs API](../../apps/api/routes/runs.py)、[knowledge API](../../apps/api/routes/knowledge.py)、[运行详情](../../apps/web/app/runs/[runId]/page.tsx)、[知识详情](../../apps/web/app/knowledge/[knowledgeBaseId]/knowledge-detail-client.tsx)、[快照服务](../../packages/knowledge/snapshots.py)。

**步骤：** 定义安全参数摘要（字段白名单、长度限制、secret 与 PII 策略）→添加耗时/身份/结果状态→有权限时读固定 snapshot/revision/chunk→引用链接与分片预览→兼容历史无摘要事件。

业务正文只经授权内容接口按需取；事件继续默认安全投影。权限不足显示元数据与说明。历史证据缺失应明确报错，不用 LATEST 替换。事件重放有界/降级边界继续声明，不承诺全量 token 持久化。

**测试：** 密钥/保留身份字段/嵌套敏感内容脱敏；超长参数；无内容权限；退役文档的历史引用；错误快照归属；历史事件；加载失败与换 workspace。

**i18n 建议：** `run.toolArgumentsSummary`、`run.stageDuration`、`knowledge.snapshotEvidence`、`knowledge.historicalEvidenceMissing`、`run.summaryUnavailable`。

**验收：** 一次运行可从答案追到固定证据与工具结果，越权和敏感信息测试通过；没有摘要的历史数据正常展示。

### F03｜多轮业务验收器（P0/P1）

**主要文件：** [threads/service.py](../../packages/threads/service.py)、[evaluation/runner.py](../../packages/evaluation/runner.py)、[validation.py](../../packages/evaluation/validation.py)、[metrics.py](../../packages/evaluation/metrics.py)、[tools/actions.py](../../packages/tools/actions.py)、[evaluation benchmark](../../benchmarks/evaluation/runner.py)。建议新增场景 schema、隔离 fixture、业务验收器与多轮 driver。

**步骤：**

1. 用 Support 定义初始业务状态、预设用户轮次/澄清回复、合法工具约束、审批决策与业务后置条件；用户模拟先用脚本，避免引入第二个随机模型。
2. 每个 task/repetition 使用独立测试 fixture；Run 链聚合至同一场景，保留各轮冻结身份。多轮预算不绕过单 Run 限制。
3. 区分回答结束、运行成功和任务完成；根据工单数量/客户归属/最终状态等持久事实验收。
4. 用必要步骤、先后约束、禁止动作和可选步骤描述轨迹；允许多种合法调用顺序，不强制一个字符串序列。
5. 覆盖澄清、审批同意/拒绝、重复输入、取消、未知结果；未知结果的正确业务终态可以是 NEEDS_ATTENTION，不要求所有任务 SUCCEEDED。

**测试：** 文本说已开工单但数据库没有；错误客户；重复工单；合法替代顺序；跨轮身份；重复 token；两次审批；fixture 污染；UNKNOWN_OUTCOME 被当成功。

**i18n 建议：** `evaluation.businessOutcome`、`evaluation.scenarioTurns`、`evaluation.postconditionFailed`。

**验收：** 首批 10 条受控任务覆盖正确、失败与未知，均能根据持久事实解释评分；多轮 driver 不修改冻结版本和审批记录来伪造结果。

### F04｜真实对照、标注与质量回归（P1）

**主要文件：** [实验服务](../../packages/evaluation/experiments.py)、[runner](../../packages/evaluation/runner.py)、[judge](../../packages/evaluation/judge.py)、[release_gate](../../packages/evaluation/release_gate.py)、[benchmarks](../../benchmarks/evaluation)、[CI](../../.github/workflows/ci.yml)。新增真实运行入口与版本化任务/结果目录；不复用 synthetic 成绩做质量报告。

**步骤：** 10 条试跑→检查费用与采集→整理 60–100 条分层任务→按来源/模板分割 DEV/HOLDOUT→冻结数据与版本→只改变一个变量→每任务独立执行三次→成对比较→人工复核失败和 judge 分歧。

引用支持度先人工标注事实断言与支持证据；自动 judge 只作为辅助，冻结 rubric/model 配置并检查解析失败。真实模型质量检查单列 CI/manual dispatch，不替换已有 conformance gate。供应商不可用为阻塞/未知，不算通过。

**测试：** 相同任务配对；不完整重复采样；数据集变更；HOLDOUT 暴露；judge 不可用/解析失败；费用未知；报告来源；质量退化触发 gate；基础设施失败与质量失败分开。

**i18n 建议：** `evaluation.realModel`、`evaluation.conformanceOnly`、`evaluation.stabilityAllRuns`、`evaluation.judgeAgreement`。

**验收：** 有可复核的原始与汇总报告、明确数据/模型身份、至少三类失败分析；性能改善或质量提高不是必需，真实结果可以显示无收益或退化。

### F05｜故障恢复、安全攻击与隔离验证（P1）

**主要文件：** [审批对账](../../packages/approvals/reconciliation.py)、[审批服务](../../packages/approvals/service.py)、[入库任务](../../packages/knowledge/ingestion.py)、[MCP 安全](../../packages/mcp/security.py)、[checkpoint 集成测试](../../tests/integration/test_m5a_checkpoint_runtime.py)、[审批集成测试](../../tests/integration/test_m5a_approval_runtime.py)、[approval benchmark](../../benchmarks/approval_runtime)。新增恢复/安全场景及报告 runner。

**步骤：** 枚举已决定未恢复、checkpoint/业务表不同步、执行后响应丢失、租约过期/重复投递、客户端断流等窗口→注入故障→重启/对账→查 Run/审批/业务结果→测恢复时延。攻击集涵盖用户、恶意文档、工具返回和长期记忆入口；同时跑正常控制任务。

外部写使用隔离模拟服务，可明确构造已执行却超时；不向真实业务反复发副作用。UNKNOWN_OUTCOME 正确保留人工关注，不要求自动恢复为成功。独立两 workspace 验证资源读取、工具身份与写入。

**测试：** 重复副作用；拒绝后执行；并发 claim；恢复脚本重入；确定失败误判 unknown；秘密泄漏；跨租户访问；攻击引发非法写；正常请求被全部拒绝。

**i18n 建议：** 报告优先离线；如接入 UI，使用 `evaluation.recoveryLatency`、`evaluation.attackSuccessRate`、`evaluation.benignTaskSuccess`。

**验收：** 故障矩阵每行有注入点、持久证据、预期与实际状态；安全结果给 0/N 或 x/N 与正常完成率，不能宣称现实风险为零。

### F06｜时延、成本与负载对照（P1/P2）

**主要文件：** [runtime](../../packages/agent_runtime/runtime.py)、[gateway](../../packages/model_gateway/gateway.py)、[观测契约](../../packages/observability/contracts.py)、[观测指标](../../packages/observability/metrics.py)、[评测聚合](../../packages/evaluation/metrics_service.py)、[前端 SSE](../../apps/web/lib/api/agent-runtime.ts)。新增受控负载脚本。

**步骤：**

1. 分开记录服务端首个可见 delta、客户端收到首个文本 delta与总完成时延；各自声明起点、时钟与重连规则，不混为一列。
2. 使用单进程单调时钟测阶段耗时；检索已有 trace 复用，模型/工具阶段补采集，不能用跨进程 wall clock 相减制造精度。
3. 新增全部尝试成本/业务成功任务数；按币种和采集覆盖率报告，保留现有成功执行平均成本指标。
4. 固定 CPU/GPU/内存、数据量、模型、冷热条件与负载，逐步增加并发；分别测受控 provider 系统容量和真实 provider 端到端表现。
5. 记录失败率、队列积压、限流、连接池、资源使用与 p95，找到瓶颈后只优化一个变量并复测。

**测试：** 首帧仅 run.started；无文本输出；断线重连；多次尝试计费；未知用量/多币种；零业务成功；阶段缺失；负载数据隔离与资源收尾。

**i18n 建议：** `metrics.ttft`、`metrics.effectiveTaskCost`、`metrics.usageCoverage`、`metrics.stageLatency`。

**验收：** 公式单测及采集完整；有冷/热、至少三档并发报告，声明测试持续时间和 provider 条件；不以 mock 吞吐宣传真实模型 QPS。

### 共同计算规则

- 版本、样本数、原始来源与缺失原因随指标一起保存；新 metric 使用 evaluator version，不改写历史结果。
- 零分母返回 NOT_APPLICABLE/NOT_AVAILABLE 并说明原因；未知不填 0，也不默认安全。
- 成对比较固定数据、版本和一项变量；多次执行重置工单/会话/记忆条件，保留每次有效快照。
- 第一轮建立真实基线，随后冻结质量/成本门槛；不用未经测量的 99% 或 1 秒做验收。
- 隔离测试里的拒绝后执行、越权执行和重复副作用预期为 0；出现非零必须分析修复，不能为让 gate 通过调宽阈值。
- 小样本报告原始比例及样本量；不使用极少请求的 p95 宣称生产 SLA，不将不同模型/硬件结果直接混合。

## 5. 数据集与报告规范

先准备 10 条受控任务验证采集；完整真实评测建议 60–100 条，具体比例由标注审阅决定。按单跳、多跳、无答案、歧义、审批、故障、攻击分类；攻击与正常质量集分开。DEV/HOLDOUT 按源文档和业务模板分组分割，不只随机分改写题。

每个任务记录：case ID、业务目标、初始状态、用户轮次、允许/禁止动作、后置条件、相关证据、答案可得性、split、标签及标注者/审阅记录。费用和敏感信息使用单独受控内容策略。

报告分为 JSON 原始记录与 Markdown 摘要；必须包含：build SHA、数据版本/hash、AgentVersion/spec hash、知识/记忆身份、模型配置、价格/evaluator、硬件/冷热/并发、各指标分母与未知、失败样本、运行命令及真实退出码。
