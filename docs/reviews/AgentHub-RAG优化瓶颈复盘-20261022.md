# AgentHub RAG 优化瓶颈复盘

## 核心判断

此前多数分支改善了局部指标，却没有改善最终前排证据。当前还有两个独立损失：召回候选不全、融合截断丢失；在剩余候选内，排序仍有余量。
Onyx 已在两数据集得到排序收益，但仍是benchmark适配器，尚未兑现为生产使用收益。生产已实现的快照SQL JOIN改善时延，不能与质量改进混称。

这次补充是用户要求反思后的**事后解释**，不是新方法选型。FiQA test已暴露，不用这些诊断重选该测试集上的融合权重、路由或预算。
无新增API、模型推理或参数搜索。原确认评分和六项门槛保持不变。

## FiQA全648题的阶段损失

全57,638文档，原baseline真实trace；覆盖率是每题标注相关来源覆盖率的宏平均，不是回答准确率。

| 阶段 | 候选中全部标注相关来源覆盖率 | 文档nDCG@10 |
|---|---:|---:|
| dense原始30块 | 0.574303003 | 0.397266092 |
| sparse原始30块 | 0.265860670 | 0.150761999 |
| 两路并集，最多60块 | 0.598908015 | 无定义的融合顺序，不作比较 |
| RRF截断20块 | 0.486299589 | 0.318534019 |
| 同20块BGE重排 | 0.486299589 | 0.413369313 |
| 同20块Onyx来源选择 | 0.486299589 | 0.453196126 |

并集以外缺753个标注相关问题—文档对，候选内到融合20又丢203对；标注正例对共1706。
这些是微观对数，不与宏平均覆盖率混成同一百分比。203对中176仅dense找到、23仅sparse找到、4两路均找到。
dense前5个文档内的gold没有被这个融合截断丢失；损失主要不是dense头部，而是其后续独有相关来源。

由此能确认损失发生的位置，尚不能直接确定最初漏召回的原因。文本表示、查询表达、切块上下文与ANN误差尚需分别检验，不能一概归因于embedding能力。
未标注文档也不能一律断言不相关，公开qrels不完整仍是限制。

## 为什么换融合/扩池/去重未转化为收益

现有RRF在两路各30、k=60时，对两个列表共同命中的块有结构性偏好：
最低双路分数2/(60+30)=0.022222，仍高于单路第一名1/(60+1)=0.016393。
因此双路命中块必排在任何单路命中块之前。相关性分数的绝对差距和来源通道质量不进入这个比较。
这是一项由[当前实现](../../packages/knowledge/retrieval.py)直接确定的性质，不能由此推断所有共同命中块均不相关，或所有单路块均应保留。
FiQA sparse单路较弱，结合大量dense独有gold被截断，支持把“候选合并是否过度依赖一致命中”作为下一独立DEV假设，而不是立刻在FiQA上改权重。

SciFact另有直接证据：learned sparse单路nDCG@10从0.63308升至0.65865，但融合后增益仅0.00035，最终BGE排序反而未通过选型。
DBSF融合nDCG提高0.01185，最终只提高0.000077。上游排序改善没有传到末端。

扩池并不能解决重排器的误排：SciFact40块补回36个相关对，首个相关文档仅23题前移、78题后移；加入更多难负例后净前排收益未过门槛。
来源配额减少重复块，却只补回1个相关对；重复块没有被证实是主要缺失原因。父文档重排没有扩大候选，输入更长导致padding成本增加，但质量未过门槛。
这些结论仅针对已运行的固定移植，不等于否定原项目的完整设计。尤其来源软配额不等于Haystack embedding MMR，父文档前置重排不等于检索后父上下文扩展。

## 当前候选的排序上限

把已召回的20块按现有qrels理想排序，FiQA文档nDCG@10上限约0.536175；当前BGE0.413369、Onyx0.453196。
这只是**固定候选、固定标注内的oracle**，不是实测模型成绩或全局RAG上限。两路并集的相同oracle约0.645430。
因此继续只改20块的顺序有有限空间；要越过固定候选上限，必须改变被保留的候选集合或最初召回。

Onyx带来的增益与此一致：不改变来源集合，明显提高前排质量，Recall@20保持相同；它不能补回被前面丢掉的来源。
跨来源比较和判断关系的能力为何更强，是与观察一致的解释，尚非对模型内部机制的因果验证。

## 对工作方法的修正

试验顺序应更早把“召回上限、融合损失、条件排序能力、最终消费者准入”作为主线，而非逐个替换流行组件。
只比较每个新组件自身的分数，很容易把局部提升误当作RAG提升；只看最终分数，则看不见收益在哪一环被抵消。
后续每个假设应明确它试图补回哪类丢失、改变哪个集合、成本来自哪里，并设置停止规则。

已经验证的方向，应先完成版本级opt-in生产接入、usage/预算记账、工具层保序和真实端到端对照，再继续增加新机制。
新的召回研究需用独立DEV检验候选保留与通道质量感知的机制，保留新的确认集，不再用FiQA test调出配置。
真实回答质量还需另设有参考答案和证据的任务，测回答正确性、证据忠实性及引用；当前检索分数不能替代这些结果。
