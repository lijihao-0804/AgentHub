# AgentHub 证据池机制审查：为什么要限量、能不能全送、别人怎么做

- 问题（用户）："找到 5 条证据只送 1 条明显不合理——这 5 条已经是我们 RAG 筛出来的，再丢掉质量肯定不行。这个机制为什么设置？能不能取消、全部送过去？其他项目怎么做？只审查不改代码。"
- 方法：修复后代码实测各场景送达率；追溯机制设立动机（M4-D 引入提交 `c76116b`、AGENTS.md 规则 20、ADR-011）；其他项目对照用本仓已有源码级调研（[完整问答架构与瓶颈诊断](AgentHub-RAG完整问答架构与瓶颈诊断-20261024.md)，核查过 PaperQA/Onyx/RAGFlow 源码）+ 通用框架行为（LangChain/LlamaIndex 为公知默认行为，标注【识】）。
- 一句话结论：**机制本身有正当职责（多轮窗口守门），但当前"5000 字节当 token"的记账方式对中英文都有 3~4.5 倍的系统性高估——池子实际只用了模型窗口的不到 10%。你说的"检索到就该全送"在正确校准下基本能实现，不需要取消机制，需要把"配给制"改成"护栏制"。**

---

## 一、先校准事实：到底丢了几条（修复后代码实测）

| 场景（k=5） | 默认池 5000 | @8000 |
| --- | --- | --- |
| 英文短段落（MuSiQue 型，~300 字符） | **5/5 全送**（4644B） | — |
| 英文 1200 字符块 | 2/5 | — |
| 中文 1200 字符块 | **1/5**（4039B） | 2/5（7950B） |

三个推论：
1. "5 条只送 1 条"不是普遍现状，是**"中文/长块 × 默认池"**的特定组合；英文短段已经全送。
2. 但你的方向感是对的：k=5 是我们自己检索+重排+去重后筛出来的精选，**默认形态下中文确实只剩 1 条**——这正是 F1 低的直接原因之一。
3. 真正的元凶不是"池子小"，是**记账膨胀**：`Utf8ByteTokenEstimator` 把每个 UTF-8 字节记 1 个"token"。英文 1 真实 token ≈ 4 字节（≈4 倍高估）；中文一条 1200 字符记录 = 3320 字节但真实 token 约 744（**4.5 倍高估**）。若按真实 token 记账，5000 的池能装约 6 条中文记录——"全送"根本不用改池子，改记账就行。

## 二、这个机制为什么存在（设立动机核查）

引入于 M4-D（`c76116b`，2026-09-18），AGENTS.md 规则 20"所有进入模型的上下文必须过 ContextBudgetPolicy"。从代码内注释与 ADR-011 还原的**真实职责**：

1. **保底不被挤掉**：系统提示、工具定义、当前问题是"强制类别"，必须永远装进窗口——预算先扣它们，剩余才给证据/工具结果/记忆。没有这个保证，一个巨大的工具结果可以把"用户正在问的问题"挤出窗口。
2. **多轮积累控制**：Agent 可以多轮检索（R-06 修复后每轮 5 条），证据池跨轮共享；对话历史也逐轮增长。无上限时 N 轮 × k 条无限累积。
3. **不可信内容限额**：工具输出和记忆被强制标 UNTRUSTED 且有独立上限（防注入面）。
4. **备忘（ADR-011）**：记忆是证据不是指令——"三个月前记录的偏好绝不能把当前问题挤出窗口"。

**判定：职责正当，不是为省证据设计的**。问题出在参数校准（5000 字节 ≈ 英文 1250 真实 token ≈ 16k 窗口的 8%——守门员身高设成了门板的 8%）。

## 三、其他项目怎么做（对照）

| 项目 | 做法 | 证据级别 |
| --- | --- | --- |
| **Onyx** | 检索 top-k 块整体进消息历史；不做单条预算，**在整条历史层面对照模型真实上下文窗口做裁剪**（新消息保留、旧消息丢弃） | 源码级（本仓调研：chat/llm_loop.py） |
| **PaperQA** | 检索后有**证据过滤**（失败/无关/重复剔除，session 累积），上下文按 **tiktoken 真实 token 计数**控制预算 | 源码级（本仓调研：docs.py get_evidence） |
| **RAGFlow** | top_n/相似度阈值配置；"检索到"与"交付阅读"**分别记账**（EvidenceRegistry 在材料实际交给模型时才发引用 ID）——与我们的注册表思路同源 | 源码级（本仓调研） |
| LangChain / LlamaIndex | retriever 返回 top-k，**全部拼进 prompt，无逐条预算**；靠用户自己调 chunk 大小和 k 控制体量 | 【识】公知默认行为 |

共同点：**没有人用"保守字节估计"当 token 记账**；要么按真实 token 计（PaperQA），要么以模型窗口为界做历史级裁剪（Onyx），要么干脆不设单条预算（LangChain 系）。我们的字节估计器是为"离线确定性、无 tokenizer 依赖"付出的代价（设计注释写明了这一点），代价就是 3~4.5 倍膨胀。

## 四、"能不能取消、全送过去"的判定

**直接取消（无上限）：不建议**，会失去 §二 的全部四项保证，具体会在三处翻车：多轮累积（50 条证据挤掉当前问题）、恶意/畸形超大块（上游 bug 时一条 100k 字符的记录直接撑爆）、fallback 链里小窗口模型（预算按链上最小窗口算，规则已内建）。

**等效达到"全送"的正确做法——把配给改成护栏**（三选一或组合，按性价比排序）：

1. **改记账（最根本）**：估计器对 ASCII 按 ~4 字节/token、CJK 按 ~1 字符/0.6-1 token 折算，或接入 provider tokenizer。改完后现有 5000 池即可装 5-6 条中文记录——**不用动池子就实现"检索到全送"**。
2. **池子挂靠模型窗口**：`max_retrieval_tokens` 默认改为 `min(链上窗口) 的某个比例`（如 25%），而非写死 5000——16k 窗口 → 4000 真实 token（≈16k 字节证据），比现在大 3 倍且随模型自动伸缩。
3. **只调默认值**：5000→8000（已有量化：中文 1/5→2/5）。改动最小但治标。

任何一条都属默认行为变更，按纪律需先过一次 ~400 调用的非劣效 A/B（方案 1/2 影响所有语料，方案 3 已有部分数据）。

## 五、建议（待批准后执行，本轮未改任何代码）

推荐**方案 1+2 组合**（一次 A/B 覆盖）：估计器折算 + 池子按窗口比例派生——语义从"省着给"变成"窗口装得下就全给、装不下才裁"。预期：中文 1/5→5/5、英文长块 2/5→5/5，与所有对照项目的实践对齐，同时保留多轮/强制类别/防注入守门。
