# 客服退款政策 RAG：施工前问题诊断

日期：2026-10-26。检查时 HEAD：`3a9490343b1b5e7828316e3c1db7411cf6291451`。

依据：[执行报告](AgentHub-客服退款政策RAG执行报告-20261026.md)、原始 A 请求/响应、S1 检索 trace 与三层交付记录、政策正文、金标及执行器代码。本轮只有本地只读分析与本文档写入，无新增模型调用、数据库操作、产品代码或提示词修改。

## 判断

不是一个单独的“RAG 不好”问题。目前能定位到三条独立故障链，以及一项增加误读机会的数据因素：

| 方面 | 直接证据 | 判断强度 |
| --- | --- | --- |
| 回答忠实度 | 首题允许替代凭据的原句已经出现在实际最终模型请求，回答仍遗漏一种凭据；又把空退款记录推断成不存在申请 | 已确认发生；模型内部成因尚不能确定 |
| 检索结果的证据充分性 | S1 的 S0-031 召回了现行 7 日规则，但最终选择没有保留；观察和准入未再丢失这条规则，因为它在此前已经缺失 | 已定位缺失阶段；不能外推实际 A 查询或全部题 |
| 评测契约与执行状态 | 引用格式误报；金标遗漏等价材料、也未覆盖首题关键替代条件；B 未执行被写成不可构造 | 已确认，影响归因可信度 |
| 合成政策的表达一致性 | 同页允许签收单，又反复强调安装验收单，未清楚定义两种凭据及时间字段的关系 | 已确认文本存在；是否导致本次回答错误仍是假设 |

因此先修复测量和材料契约，再分别验证回答忠实度与证据筛选。暂不凭一个回答换模型、扩大上下文、堆 top-k 或增加复杂检索框架。

## 1. 首题：证据送达之后，回答发生语义收窄

原始证据：[S0-003-A.json](../../benchmarks/evaluation/experiments/support_refund_rag/private/requests/S0-003-A.json)。第 3 次请求为实际最终回答请求。

- `search_knowledge` 交付 6 块，其中 4 块来自大件政策、2 块来自版本说明。
- 第一块 `16e91c36ad…` 的 1200 字 snippet 完整包含：“只有安装验收单或客户签收单可以启动本政策窗口”。该工具观察标记 `truncated=false`。
- 最终回答却写：“只有安装验收单能启动这个窗口（第 5 条）”。这将允许集合 `{安装验收单, 客户签收单}` 收窄为 `{安装验收单}`，不是一般措辞简化。
- 本订单确有安装验收时间，30 日窗口、第 1 日与截止日算对。因此这是回答中的政策概括错误，尚不能说本单已经发生错误拒绝，更不能据此估计其他案例误判率。
- 最终响应 `finish_reason=stop`，输出 1736 tokens，低于 2048 输出上限；实际输入 7668 tokens，配置上下文 32768。结合关键原句确实可见，没有证据把此次遗漏归因于硬截断、上下文溢出或输出被切断。

现有模板已要求每项事实来自本轮工具、不补缺失字段、不编造条款，所以不是“完全没写 grounding 规则”。但这些是自然语言约束，没有强制输出规则的 AND/OR、例外和适用范围，也没有在这条完成路径上阻止不受原文支持的绝对化陈述。`runtime_graph.py` 将无工具调用的非空响应作为 `final_output`，运行成功不提供政策语义正确保证。

可疑诱因包括长上下文中的条件整合、反复强调安装凭据、回答先长篇分析再二次转述时丢失限定。但单次响应、没有 B 或控制实验，不能断言是注意力、模型能力上限、英语系统提示或某一位置效应。也不能证明单加一句提示就能稳定修复。

## 2. 空记录：事实边界与工具输出语义不够明确

实际 `get_order` 和 `get_refund_status` 都给出 `refund:null`，没有申请历史、查询覆盖范围或明确的“全部历史中无申请”字段。回答却写“没有生成任何退款申请或退款单”。

这是从“本次没有返回对象”跳到了“业务事件从未存在”。即使末尾又建议核实此前申请，也不能消除前面的绝对断言。两处相同空值不等于两份完整申请历史证明。

实验 fixture 的输出实现仅使用 `row.get("refund")`，工具描述也只有读取退款状态，没有区分未找到、未提供、历史未查询等含义。因此：

1. 回答越界已确认；现有 grounding 约束没有被可靠遵守。
2. 实验工具契约的歧义是可修复的输入因素；需要先定义 `null` 的实际语义。
3. 本次用的是隔离 fixture，不能据此认定生产退款适配器也有同样输出缺陷。若未来改公共契约，应另行核对生产适配器和消费者。

合理表述应限定为“本次查询未返回退款记录；是否曾提交申请还需核对申请历史”。该例只用于诊断预期语义，不写回历史回答。

## 3. 独立检索问题：相关性排序未保证决定性事实一起送达

证据：[S0-031 检索记录](../../benchmarks/evaluation/experiments/support_refund_rag/private/s1/retrieval-results/S0-031.json)、[交付重放](../../benchmarks/evaluation/experiments/support_refund_rag/private/admission/S0-031.json)。这是原问题直接检索的 S1，不是模型实际构造的 A 查询。

该题需要说明历史 15 日页面与现行官网 7 日规则的关系：

- 现行 `POL-REFUND-WINDOW-01` 被 dense 排第 2、融合候选排第 5，正文含明确 7 日数字，说明索引与初始召回在此例已找到目标。
- 最终 6 块为：版本说明、历史 15 日、版本说明、版本说明、新版合约设备、大件政策。
- 其中 3/6 块来自同一版本说明文档；现行 7 日原页和其他含等价七日规则的候选均未保留。
- 原始工具、观察、最终模型视图这 6 个 chunk ID 和 snippet 长度一致。因此决定性缺失已经发生在重排/最终结果筛选阶段，不能归因于后续准入。
- 准入汇总有 `truncated=true`，但本例 6 块 snippet 均未改变。不能只看总截断标志就认定政策正文被裁掉。

代码路径用 query 与 chunk 的重排分数排序，再经重叠去重、最终数量限制。冻结配置没有启用文档候选上限或联合证据选择，替代文档惩罚为 0。它优先回答“哪些段落与问题相关”，不保证“解决此问题所需的当前规则与历史关系全部齐备”。问题中出现“15 日历史页面”，可能使解释版本、复述历史的长文取得高分；分数表现支持这种相关性偏向，但模型内在机制仍未验证。

这是证据集合充分性不足，不是这个例子的向量库漏入库，也不能笼统写成 reranker 实现算错。已有 trace 只保存最终数量内的 rerank 排名，不能宣称知道现行页在完整重排池的精确名次。

不宜直接过滤所有 superseded 文档：历史合约仍可能合法使用旧版；本题解释历史页面也需要保留旧规则。不宜直接给最终结果强制每文档一块：跨段组合题可能需要同文多块。候选限制与最终选择也不是同一开关。

## 4. 材料与评测同时有“误报”和“漏检”风险

### 4.1 合成政策不是完全清楚的独立真值

[大件政策](../../benchmarks/evaluation/experiments/support_refund_rag/data/docs/05_marketplace_long_refund_active.md)第 5 条明确允许客户签收单；第 2 条从安装验收单起算，后文又说母订单集中签收不能代替单件验收，版本说明还写没有安装验收时间则不能起算大件窗口。

这些话可能通过“单件凭据 vs 母订单物流签收”得到一致解释，但目前没有明确定义客户签收单证明的是物流交付还是单件验收、替代时取哪个时间字段。模型仍不应引用第 5 条却删掉“或客户签收单”；同时，测试材料也不适合用未定义的业务关系来测一个唯一答案。

下一版需清楚定义凭据类型、证明对象、时间字段与优先关系。若保留矛盾作为压力题，应标成冲突题，预期保留争议，而不是暗中按唯一口径评分。旧快照保持不动。

### 4.2 金标既会误判缺证，也可能放过条件丢失

- 部分题强制指定 source+逐字 quote，未列等价原文，造成有据却判缺失。既有七题复核应逐条重新定案，不能直接把 34/41 改成通过。
- S0-003 的 evidence group 只要求 30 日起算原句；`key_facts` 也只有安装验收次日起算和第 30 日。这份金标本身没有覆盖两种凭据与 null 边界，依靠它的“证据完整”不能检出本次所有语义错误。
- 引用身份合法只证明来源可见，不证明该来源支持整句话。source_id 解析修正解决了格式误报，没有解决事实支持性评分。

因此 82.9% 冻结值不能直接解释为真实语义召回率；与此同时，金标修正也不能掩盖 S0-031 已确认的缺证。

### 4.3 原始停止原因与后续语义发现必须分开

实际首次停止由旧解析器的 `A_POLICY_CITATIONS_MISSING` 触发；“允许替代条件遗漏”是离线后续发现，不是当时自动语义门槛拦住的。当前执行器在发 B 前主要检查运行/工具链、证据与引用身份，并未自动裁决这一政策表达错误。

异常处理把尚未执行的 B 统一改为 `UNCONSTRUCTABLE`，但引用失败不代表没有合法 A 前请求。这是诊断状态分类问题。平台 ExperimentRun 的 `SUCCEEDED` 又是 driver 处理完成，不能替代阶段是否完成、实际派发数和质量结果。应保持执行完成、场景运行状态、质量裁决三者分开，不把运行枚举全局改成业务验收枚举。

## 5. 建议施工顺序与验证方式

### 第一步：先把测量做准，不动生产参数

范围只在本实验：

1. 统一正文、提示和评分支持的引用形式；离线检查合法、未知来源、缺失引用与语义不支持分别呈现。
2. 复核全部金标，按业务原子事实组织 AND/OR、时间/范围/例外；允许等价来源，仍保留必要证据要求。补上禁止从空记录推断历史不存在等边界。
3. 下一版合成政策消除非刻意歧义，或者显式作为冲突案例；发布新版本、新快照，保留旧分数和旧错误。
4. 修正 B 的停止状态分类，并分别汇总实际完成、未执行、质量失败。确认实际 A trace 采集启用；如要精确归因全池排序，需明确收集完整重排结果，而非假定现有 trace 已有。

验收：不调用模型，也能让已存原始 A 得到“引用身份合法、语义部分错误”的正确分类；S0-031 仍被识别为决定性证据缺失；B 显示因停止未派发。旧账和原始结果不覆盖。

### 第二步：用最小对照区分两个产品方向

**检索方向先做零生成调用重放：**以冻结基线和审定后的证据事实为依据，比较“只调整查询表达”“只调整证据选择”各自的效果，不同时更换 embedding/reranker。聚焦新旧版本、跨段 AND、同文多块三类，记录现行规则保留、历史依据保留、最终证据覆盖和 token 开销。把本诊断暴露过的题标为 DEV，不作为独立泛化证明。选择仅在多个相关案例上有效且无明显回退的最小改动。

**回答方向先设计、后小规模调用：**在固定模型和相同来源条件下比较原模板与候选的“事实—原文—条件/例外—结论”回答约束；测试 OR、AND、否定、未知/不存在和正文冲突。工具 null 的定义若要改变，应作为单独变量或单独实验，不与提示改动混合。优先限制无依据的“只有、任何、已经、从未”等断言，不以塞入本题标准答案代替通用能力。

B 只能帮助诊断证据选择；同一来源本身有歧义、或充分材料仍很长时，B 也可能失败。因此不能把 B 当作模型质量的绝对上限。

### 第三步：证据支持后才做最小产品改动

如果基线重放明确是最终证据组合失败，推进有评测依据的检索选择改进；如果受控输入下仍反复出现语义收窄，再考虑应用层结构化政策判断或可解释的事实支持校验。是否需要公共工具契约变更，则依据真实适配器的 null/历史覆盖语义决定。

不先上一个可自行生成错误的 LLM judge 来掩盖问题，不直接换模型，不扩大正式实验。新的小规模请求应另存运行版本，使用既有授权范围内的剩余预算与明确调用台账；本轮诊断没有消耗新的模型额度。

## 结论边界

当前最优先的工程工作是修复实验测量契约；已确认的产品方向是“回答忠实度”和“最终证据充分性”两项。不能把二者互相替代，也不能根据一题回答宣布整套 RAG 已失效。此次没有修改产品或继续付费评测，下一步应先完成第一步的离线修复，再凭对照结果选择最小实现。
