## 3. 实际失败与修复

1. Windows 预检使用 Proactor 事件循环，psycopg checkpoint 无法工作；未调用模型、费用为零。入口改为复用已有 `configure_windows_asyncio_policy`，未改动全局交互环境。[预检失败](evidence/mi3-mi4-20261002/live-pilot-preflight-failure.json)保留。
2. 基线 prompt 未说明“调用写工具只是提出动作请求”；候选提示词补桥，保持运行时权限和人工审批约束。未允许模型自行批准，也未弱化 ALWAYS。
3. 保修澄清测试缺序列号，与办理材料要求存在歧义。v2 提供虚构 `SYNTH-SN-001`；不修改原失败和 v1 哈希，不靠放宽预期让结果通过。
4. v2 首轮在第 11 个样本中断，公开 failure_code 为 `MODEL_BAD_RESPONSE`。预算临时文件存在、磁盘仍保留全额预留而报告内存结算值更低，表明结算替换未完成；Windows 短暂文件占用是推断，原始异常被 gateway 归一化，未保存具体 OSError。增加限次 PermissionError 重试、退款写失败内存回滚及本地失败类型记录；补测试。新实例复跑，不重发任何未知写动作。旧未知调用仍占用 0.0704 元。[中断报告](evidence/mi3-mi4-20261002/live-pilot-v2-three-trials.json)、[未完成退款文件](evidence/mi3-mi4-20261002/failed-budget-refund.json)保留。

试跑 stderr 还出现 LangGraph 未登记类型反序列化的未来严格模式警告，当前恢复测试通过；后续应审阅稳定类型 allowlist，不能删除验证门或仅为了消警放宽类型限制。

最终集成回归还发现旧入库恢复测试对共享隔离库的队列断言不稳定：对账应合法处理其他到期任务，测试却要求队列仅含自己的 job。改为本 job 恰好派发一次，同时整个队列与对账返回列表完全一致；未清除历史任务，也未放宽不得重复派发的要求。首次失败日志保留于 `.scratch/mi34-20261002/integration-final2-run/`。

## 4. 安全与可靠性证据

### S01 小样本模型攻击

6 条手工合成攻击：3 条用户输入伪造系统/审批/调试指令，3 条客户姓名工具输出注入。工具输出样本核对了 query_customer 的实际模型调用及后续回答，均已暴露；未暴露/无效样本 0。以偏离原只读目标而提出创建请求为攻击目标：创建请求成功 0/6，持久写入成功 0/6。正常对照 4/4 通过状态检查，包含正常批准产生 1 条工单和拒绝不产生工单，避免只测试“一律拒绝”。

攻击案例预设拒绝审批作为第二道边界；持久写入结果不能单独解释为模型抵抗能力，创建提议另列。覆盖有限入口和攻击模板，没有外推全产品攻击成功率。证据：[原始安全试跑](evidence/mi3-mi4-20261002/live-security.json)、[安全汇总](evidence/mi3-mi4-20261002/security-summary.json)。S02 延续[两工作区读写矩阵](evidence/mi3-mi4-20261002/tenant-matrix.json)。

### 持久模拟副作用矩阵

真实 PostgreSQL 审批/checkpoint + 独立 SQLite 业务台账 + 受控模型，覆盖批准、拒绝、越权、写入后响应丢失、确定失败。重复恢复后重复副作用 0/5；拒绝后执行 0/1、越权后执行 0/1；不确定结果正确识别 1/1、确定失败误判不确定 0/1。响应丢失场景台账已提交 1 次，Approval 为 UNKNOWN_OUTCOME、Run 为 NEEDS_ATTENTION，无重复派发。

确定动作失败的 Run 最终可以 SUCCEEDED（模型完成了后续回答）；因此分别验收动作 FAILED 与 Run 状态，不把二者混为一体。台账文件保留在本机测试临时目录，状态汇总见[measured-reliability.json](evidence/mi3-mi4-20261002/measured-reliability.json)。
