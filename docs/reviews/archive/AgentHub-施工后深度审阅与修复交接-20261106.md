## 3. M01：Memory 提取异常分类不完整

**证据与影响。** [memories.py:364](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/apps/worker/tasks/memories.py:364) 调用 `prepared.generate_resolved`，随后解析候选、持久化 `candidate_payload`，再执行确定性 Memory 写入。`_extract_owned_memories` 的异常处理在 [memories.py:422](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/apps/worker/tasks/memories.py:422) 只看候选是否已落库：有候选则保留 RUNNING/RECORDING_PENDING，无候选则 FAILED/MEMORY_EXTRACTION_FAILED。

因此，provider 可能已收到请求但超时/响应丢失，与明确派发前错误落到同一普通错误码；同文件 `_claim_extraction` / `_reconcile_memory_jobs` 对 owner 丢失却使用 `MEMORY_EXTRACTION_OUTCOME_UNKNOWN`。这是两条恢复路径的分类不一致。当前普通 FAILED 也不会被该 job 自动重发，**未证明存在重复收费事故**。

**不能用 candidate_payload 为空推导“结果未知”。** 为空还可能是 ContextBudgetPolicy 拒绝、凭据/冻结路由校验失败、授权撤销、已返回响应的处理失败或候选落库失败。`parse_candidates` 对一般无效 JSON 会返回空候选，现有合同允许无记忆完成；不要顺手改成未知网络结果。

### 最小修复要求

1. 把派发准备、可能进入网络、收到完整响应、候选已持久化、Memory 记录完成区分为明确阶段。阶段应来自真实调用边界；若 gateway 内部准备仍会零派发拒绝，仅把“进入 generate_resolved”当作“已经发送”只能说明可能派发，不可伪造精确发送证明。

3. 复用现有 job 表达：`FAILED + MEMORY_EXTRACTION_OUTCOME_UNKNOWN` 已存在。表的 status 约束只允许 PENDING/RUNNING/COMPLETED/SKIPPED/FAILED，**本问题不要求直接增加 UNKNOWN_OUTCOME 枚举或迁移**。

**持久阶段与成本的边界：** 正常异常处理可先用明确本地阶段和安全 gateway code 完成分类；若要在进程崩溃后也区分“派发意图已提交/响应已到达”，需新增安全的持久阶段证据，另行设计 additive migration。派发意图标记不是已发送证明：intent 后、网络前崩溃仍须保守 unknown。当前仅靠 owner 丢失和无 payload 判断为 unknown 是有意的保守恢复，不能把它单列为 P0“误报收费”缺陷。主线 0052 与预算 Draft 0053 不同，禁止机械地指定下一迁移为 0054，必须按实际合入图选择父 revision。

## 5. B02：未知状态落库失败未保守映射为待对账

**源码链路。** [model_budget_adapter.py:214](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/packages/agent_runtime/model_budget_adapter.py:214) 在 `mark_unknown_outcome` 写库失败时抛出 `RUN_BUDGET_UNKNOWN_OUTCOME_FAILED`。该码未进入 [runtime_graph.py:164](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/packages/agent_runtime/runtime_graph.py:164) 的 attention 集合；model 节点捕获 `ModelAttemptBudgetError` 后仅返回 failure_code。收尾 [runtime_service.py:2125](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/packages/agent_runtime/runtime_service.py:2125) 又只查询已落库 `UNKNOWN_OUTCOME`，因此写库失败而留在 RESERVED 的 attempt 不能靠这次查询补救。

**触发条件：** 预留成功且 provider 已进入调用 → provider 超时/异常 → UNKNOWN 写入的独立事务失败 → 后续 Run 收尾连接恢复。结果可能是普通失败，而应该显式等待费用对账。hold 保留不等于状态展示已经正确。

**取消路径是同一问题的另一个分支。** [gateway.py:658](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/packages/model_gateway/gateway.py:658) `_mark_cancelled_unknown_outcome` 使用 shield 尝试持久化，但一般持久化失败只 warning；外层继续抛原 CancelledError。service 的取消收尾可能因此只写 AGENT_STREAM_CANCELLED/普通失败，而 RESERVED attempt 又无法触发 UNKNOWN 查询。这里不能简单“去掉取消、改抛业务异常”而不检查 worker/API 的取消合同：需要同时保留停止请求的语义和不可丢失的财务待对账信号。

### 最小修复要求

1. 不依赖 UNKNOWN 落库成功，仍将这一明确错误映射到 `NEEDS_ATTENTION`，保留准确 failure_code 和原 reservation。原错误码别改成正常额度不足。
2. 不能笼统把所有 `RUN_BUDGET_*` 拒绝都映为未知：派发前余额不足/配置不支持仍是可确定拒绝。对 ledger 自身业务错误与数据库异常逐项定义分类。
3. 保证 UNKNOWN 写入失败不会使 gateway 回到 retry/fallback；不得新建 attempt 换身份再发。普通无预算模型重试的既有合同另行保留，不能为此全局删除 fallback。
4. 若数据库持续不可用，不能承诺终态一定已持久化；要求系统恢复后由既有恢复/对账路径保守接管。只加内存 run_status 而没有恢复证明不等于完整 durable 闭环。

证据为 [.github/workflows/ci.yml:3](E:/JAVA/AI+agent/AgentHub/.worktrees/ae1/.agents/worktrees/codex/local-development/.github/workflows/ci.yml:3)：push/pull_request 均无分支过滤；未见 concurrency。第 137 行全量 integration 后又执行多个 M7 integration 文件；第 191 行全量 non-integration 后再执行相应 unit 文件。相关 integration 文件已声明 integration marker，unit 文件也在 tests 收集范围中。**这与前端统一八组入口不同；后者已经集中调用，不要再次重写。**

### 先做低风险去重，路径分流另选切片

1. 建议保留 main push 的主线集成和 PR 的候选验证；分支 push 与同一 PR 不再各跑一套完整 CI。没有 PR 的草稿分支是否需手动检查，在项目合同中明确；不要无授权调整仓库 branch protection。
2. 增加按 PR/分支区分的 concurrency，取消同一 PR 已过时运行，保留不同 PR/main 的独立结果。不要把主线结果错误复用到不同 merge candidate；PR 的合并候选与分支 head 也并非天然同一个执行树。
3. 用 collect-only node id/marker 与配置检查逐项证明专项已被全量收集，再删除重复执行；注意原 M7-C 两项还在全量前执行，可能隐含次序/fixture 隔离用途，先查因果。不得仅看文件名相似就删除。
4. 保留迁移升级/check、checkpoint bootstrap、必需 integration、前端 production build/类型检查、数据 validate-only、conformance 工件生成/上传。工件生成与测试断言不是同一种交付，不因全量 pytest 通过就删除。
5. 若继续做文档/前后端路径分流，采用未知路径回退完整检查；特别处理 `.github`、migrations、shared contracts、pyproject/lockfile 和构建脚本。需要的 check 名称必须稳定产出结论，避免 workflow-level paths 跳过后 required checks 永久 pending。
6. 开发阶段只跑受影响文件；最终候选一次完整 CI，合并后保留主线验证。不能把已跳过的 backend 写成“已执行通过”，也不能在未核实身份/环境时复用旧提交绿灯。

**验收场景：** 同仓 PR 更新只启动预期的一套；快速连续两次 push 后旧 PR run 被取消；main push 仍完整；陌生路径不漏检；专项 node id 不丢；故意失败能正确传播；必要工件仍生成。实际远端触发验证必须有对应推送授权，未授权时交付本地 YAML/事件矩阵和待验证项，不冒充已远端验收。
