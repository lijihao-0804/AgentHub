## 3. 必须写入主报告的收窄结论

以下六条应作为后续汇总结论，避免原笔记被原样采纳：

1. **主案例**：保留“`start` 声称贯穿全书，但后续使用了多个局部案例”的编辑问题；不得要求 Customer Support Agent 成为全书唯一案例。可推荐一条默认主线，同时保留局部变体。
2. **先修与目标**：保留“全局入口没有目标读者与 Python/SQL 门槛”；不得说章节缺学习目标或全书缺先修。章节 `summary` 可见，9 章有先决概念。
3. **输入输出账本**：保留“`business` 章末函数长箭头与已有阶段表的对应不够直接”；不得说全书缺账本。全书写入追踪已有较完整的表格式基础。
4. **练习标准**：`practice` 已有三道“参考解法与通过标准”、合格账本示例和最终掌握说明。可以谈答案揭示体验，不可把“没有正式评分表”写成“没有掌握门槛”。
5. **章节长度**：字符数差异是事实，严重失衡是需要阅读证据的判断。不能仅据长度拆分 `exceptions`、`rag`、`wiki`。
6. **案例闭环**：`business` 已解释质量闭环与运营闭环，`evaluation` 已提 `create_version_from_run`。当前问题收窄为跨章示例 ID 和开场转场不够清楚，不构成“闭环缺失”。

## 5. 复核限制

- 本次没有运行读者测试，因此没有证明任何具体章节“必然让新人卡住”；长度、术语密度和叙事跳跃均为静态文本证据。
- 没有复核动画场景、键盘焦点、响应式布局或 2K 宽屏几何。
- 没有核对业务实现；`plan/plan.md` 只用于确认主 Demo 的产品语义，没有把它解释成教材唯一案例约束。
- 既有内容笔记中的代码规模、表格数量和重复句统计大多可复现；本复核反对的是从这些事实直接推出强整改要求。
